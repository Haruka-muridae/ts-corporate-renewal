New Risks

AI Agentが「実行」を始めると、
新しいリスクが生まれる。

AIがチャットに答えるだけなら、できることは限られています。しかしAI Agentが業務を実行するようになると、AIの誤判断がそのまま実際の業務操作につながります。

  • メールを読む・送る
  • カレンダーを操作する
  • Driveのファイルへアクセスする
  • GitHubを操作する
  • APIを実行する
  • ファイルを作成・削除する

そのとき、こんな不安が現実の問題になります。

  • 「AIにメールやGoogle Driveを操作させて、本当に大丈夫なのか？」
  • 「AIにAPIキーやOAuth Tokenを見せても問題ないのか？」
  • 「AIが間違えてメールを送信したら？」
  • 「外部文書に悪意のある指示が含まれていたら？」
  • 「AIが顧客Aの情報を顧客Bへ出してしまったら？」
  • 「AI Agentにどこまで権限を与えるべきなのか？」

「便利さ」と「権限」は別の問題です。AIの性能がどれだけ上がっても、この問題はAI自身には解決できません。

Core Idea

「AIに、安全に行動するようお願いする」のではなく、

AIが間違えることを前提に、
システム側で制御する。

AIに仕事を任せるなら、権限までAI任せにしない。本サービスが提供するのは、AI Agentを実業務へ接続するための安全な実行基盤です。

AIと実行のあいだに、
制御の層を置く。

  2. ↓

実行の可否は、AIとは独立した制御層が決める。

「AIが安全だと判断したから実行する」のではなく、
AIとは独立したシステム側の制御によって実行可否を決めます。

Agent Roles

処理の重さではなく、
責任で分ける。

複数のAIモデルを使うこと自体が目的ではありません。判断・実装・検証・秘密情報の取り扱いを別々のAgentに分け、1つのAIにすべての権限と責任が集中しない構成にします。

通常の業務

  1. User
  2. ↓
  3. Executive Agent
  4. ↓
  5. Lead Agent
  6. ↓
  7. Worker Agent

統括役が計画し、実務役が実行する。

重要な判断

  1. Lead Agent
  2. ↓
  3. Critic Agent による検証
  4. ↓
  5. Executive Agent の最終判断

独立した検証役を挟み、1つのAIの結論だけで進めない。

秘密情報の処理

  1. 通常 Agent
  2. ↓
  3. Secret Boundary
  4. ↓
  5. Secure Agent / Credential Broker

通常AgentはSecretの生値に触れず、境界の先に委譲する。

Fable
Executive — 要件の裁定・最終判断
Opus
Lead / Critic — 計画・難所の実装・検証
Sonnet
Worker — 通常の実装・調査
Codex
Secure — 秘密情報境界内の処理

※ 現在の想定構成です。特定のモデルに恒久的に依存せず、技術の進化に応じて構成を変更できるように設計します。

Security by Design

抽象的な安心ではなく、
具体的な設計で。

本サービスのセキュリティは、強さの主張ではなく、リスクを抑えるための具体的な設計思想の組み合わせです。

Least Privilege

最小権限

必要以上の権限をAIへ与えません。業務に要る範囲だけを、対象を絞って許可します。

Read-only First

閲覧から始める

初期導入では可能な限り閲覧権限から開始し、書き込みは必要になってから検討します。

Human Approval

人間による承認

送信・削除・共有・権限変更などの高リスク操作は、人間による承認を前提とします。

Secret Separation

Secretの分離

API Key・Token・Passwordなどを、通常のAIコンテキストから分離して管理します。

Sandbox

隔離された実行環境

秘密情報を扱う処理や検証中の操作は、隔離された実行環境の中で行います。

Prompt Injection 対策

外部情報は命令にしない

メール・文書・Webページなどの外部情報を「命令」ではなくUntrusted Dataとして扱います。

Auditability

監査可能性

誰が、どのAI・ツールを通じて、何を実行したかを追跡できる構成を目指します。

Maximum Restriction

最初から何でも許可しない。
必要になったものだけ解禁する。

新規導入は、次の初期状態から始めます。業務上必要になった機能について、目的とリスクを確認しながら段階的に許可していきます。

Initial State

Filesystem
原則拒否
Network
原則拒否
Secret
直接取得を原則拒否
Command
許可されたもののみ
External Write
原則拒否
Tenant Access
対象顧客のみ
Sandbox
タスク終了後破棄

拒否から始まる設計（deny-by-default）だからこそ、「なぜこの権限を許可したのか」を1つずつ説明できる状態を保てます。

Steps

導入までの流れ。

  1. ヒアリング

    業務内容、AIへ任せたい作業、利用サービス、セキュリティ要件を確認します。

  2. 権限・アーキテクチャ設計

    Agent構成、MCP / API、OAuth Scope、Human Approvalなどを設計します。

  3. 初期環境構築

    Claude Codeを中心とした開発・実行環境を構築します。

  4. 外部サービス連携

    必要なGoogle Workspaceなどとの接続を設定します。

  5. セキュリティ設定・試験

    Secret分離、権限制御、Sandbox、Prompt Injection対策などについて確認します。

  6. 運用開始

    Maximum Restrictionを基本状態として運用を開始します。

  7. 段階的改善

    実際の利用状況を確認しながら、必要な機能・権限のみを追加します。

FAQ

よくある質問。

AIにAPIキーを渡すのですか？

通常Agentが平文のSecretへ恒常的にアクセスする構成を避け、Credential StoreやCredential Broker等を利用して分離する設計を基本とします。

AIが勝手にメールを送ることはありませんか？

初期構成では外部への書き込みを制限し、送信・削除・共有等の高リスク操作についてHuman Approvalを要求する設計を基本とします。

Google Workspace以外にも対応できますか？

MCPまたは公式API等が利用できるサービスについて個別に検討します。追加連携は別途費用が発生する場合があります。

Claude以外のAIも利用できますか？

用途・セキュリティ要件・モデル特性に応じて複数モデルを役割分担させることを想定しています。

導入後に権限を増やせますか？

可能です。ただし初期状態では権限を限定し、業務上必要になった権限をリスク確認後に段階的に追加する方式を基本とします。

100万円ですべてのシステム開発が含まれますか？

含まれません。100万円は標準的な初期設計・導入を基準とした価格です。独自システム開発、新規サービス連携、大規模なカスタマイズ等は別途見積となります。
