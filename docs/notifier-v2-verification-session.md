## 0. 先に読むこと（実測で分かった3件）

事前に実環境を確かめたところ、**チェックリストのままでは通らない項目が3つ**あった。
段取りに織り込んであるが、理由を知らずに進めると誤判定する。

### 0-1. E節は `NOTIFIER_ENTITLEMENT` では失効しない（**手順の差し替えが要る**）

ご自身のアカウントは `payment_exempt = TRUE` である
（KV のライセンス記録が `plan:"exempt"` になっていた）。
[gas-auth/Notifier.gs](../gas-auth/Notifier.gs) の `evaluateNotifierEntitlement_` は

```
1. account_status → 2. 契約 → 3. payment_exempt ← ここで通る → 4. NOTIFIER_ENTITLEMENT
```

の順で、**免除は 4 に到達する前に valid を返す。**
`NOTIFIER_ENTITLEMENT` を何に変えても、この account では失効しない。

**`payment_exempt` を FALSE にする案は採れない。**
[gas-auth/Sessions.gs](../gas-auth/Sessions.gs) がセッション検証のたびに
`isSubscriptionUsable_` を通すため、**その瞬間に録音アプリから締め出され、
ログインし直すこともできなくなる**（`subscription_status` が `exempt` のため）。
失効の画面を見に行けなくなり、E節そのものが実行不能になる。

> **採る手順**: テンプレート側の Script Property `LICENSE_KEY` を、
> **形は正しいが登録されていない値**へ一時的に差し替える。
>
> - gas-auth にも `users` にも触らないので、**ログインに影響しない**
> - ゲートは `valid:false / status:not_found` を返す（本日 curl で実測済み）
> - tick の evaluate が `LICENSE_STATE=expired` を記録 → 画面が赤くなる（E-3・E-4）
> - `notify_queue` が増えない（E-6）
>
> 差し替え値の例: `ZZexpiredProbeZZZZZZZZZZZZZZZZZZZZZZZZZZZZZ`（43文字）
> **本物の値は事前にご自身で控えてください。私には見せないでください。**

**この差し替えで確かめられないこと**（正直に記録する）:
`NOTIFIER_ENTITLEMENT` の判定そのもの（`all_active` / `plan:` の分岐）は、
免除でない利用者が現れるまで実機で確認できない。宿題 B-10 として残す。

### 0-2. ［接続テスト］はライセンスの状態を取り直さない（**最大5分待つ**）

画面の「ご契約」は `getSettings` が返す `LICENSE_STATE` で、これを書くのは
**同期（`syncCalendar_`）だけ**である（[CalendarSync.gs](../gas-notifier/CalendarSync.gs)）。
同期は5分間隔なので、KV を消してもキーを差し替えても、
**［接続テスト］を押した瞬間には変わらない。**

E-3 / E-8 は「変更 → **次の同期を待つ（最大5分）** → ［接続テスト］」の順で行う。
押しても変わらないことを不合格と読まないこと。宿題 B-09 として残す。

### 0-3. 認証系 GAS はコールドスタートで8秒を超えることがある

本日の実測で、しばらく叩いていない状態から呼ぶと
`license verify: reachable=false ... status=unreachable` になった（`wallTime` 9.07秒 /
`AUTH_GAS_TIMEOUT_MS` は8秒）。**直後に温めてから呼ぶと `reachable=true` に戻る。**

初回だけ失効側へ倒れる（fail closed）ので、**E節の直前に私が1回温める。**
段取りに入れてある。

## 4. G節の残りについて（代行可否の検討結果）

### `pending` の 200 は、私からは確かめられない

`pending` は接続キー（秘密）と、**実在する購読の `endpoint`** の両方を要求する。
どちらも私が持つべきでない値なので、外形からは `UNAUTHORIZED` までしか到達しない。
購読を偽造して 200 を作ると、`sent_log` の `fetchedBy` に架空の `subId` が入り、
C-5 の判定が壊れる。**健全性を壊さずに代行する方法は無い。**

### 代わりに、DevTools 1回で見ていただく観点（1行）

> 通知が届いた直後の Network で `action=pending` の要求を1つ開き、
> **Status が 200 で、Response の `data.notifications` が空配列でない**ことを見る
> （空配列なら、その端末は既に取得済みか `endpoint` が一致していない）。

これは 08:28 の「初弾ログ」のときに1回見るだけで済みます。

### 私が代行できる部分（要 `/exec` URL のみ・秘密ではありません）

`?action=pending`（キー無し）が `{"ok":false,"error":{"code":"UNAUTHORIZED"}}` を返すことは、
外形から確かめられます。**これは「貼り替えたスナップショットが公開に反映されているか」の
確認になります**（古いデプロイなら `INVALID_ACTION` が返る）。
`/exec` URL を貼っていただければ、P-1 の直後に実行します。
