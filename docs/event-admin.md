# 交流会 管理画面

実装仕様書9章の管理画面。URL は `/event/admin/`。

| 画面 | URL |
| --- | --- |
| ログイン | `/event/admin/login/` |
| 申込者一覧 | `/event/admin/`（`?eventId=<events.id>` で開催回を選べる。後述） |
| 申込者詳細 | `/event/admin/<申込ID>/` |
| 申込者CSV（全件／回指定） | `/event/admin/csv/applications/`（`?eventId=` を付けるとその回だけ） |
| 名札印刷用CSV（支払済みのみ／回指定） | `/event/admin/csv/nametags/`（同上） |

未ログインでページを開くとログイン画面へ送られ、CSV は 401 で拒否される（受入条件10）。

## 1. 管理者ユーザーの作成

管理者は Supabase Auth に登録する。**このプロジェクトの Supabase に登録された
利用者＝管理者**という設計にしてある。一般の申込者は認証を一切通らない
（申込はサーバー側が service role キーで書き込む）。

そのため、**管理者以外を登録してはいけない**。あわせて新規登録も止めておく。

### 1-1. 新規登録を無効にする（最初に1回だけ）

<https://supabase.com/dashboard/project/ixxxlmfhrtommsfiumlz/auth/providers>

* **Email** を開き、**Allow new users to sign up** を **オフ**にする

これを切らないと、誰でも自分でアカウントを作って管理画面に入れてしまう。

### 1-2. 管理者を追加する

<https://supabase.com/dashboard/project/ixxxlmfhrtommsfiumlz/auth/users>

1. 右上の **Add user** → **Create new user**
2. **Email** に管理者のメールアドレスを入れる
3. **Password** を設定する（自動生成でもよい）
4. **Auto Confirm User** を**オン**にする
   （オフだと確認メールを踏むまでログインできない）
5. **Create user**

この手順を管理者2名分（齋藤貴之・齋藤悠貴）行う。パスワードは本人へ直接渡し、
最初のログイン後に各自で変更してもらうこと。

### 1-3. パスワードを変える・忘れたとき

同じ画面で対象の利用者の行の「…」から **Reset password** を選ぶと、
パスワード再設定のメールが送られる。または **Update user** から直接設定する。

### 1-4. 管理者を外すとき

同じ画面から **Delete user** で削除する。削除すると、その利用者が持っていた
セッションでは次のページ表示から入れなくなる。管理画面はページを開くたびに
Supabase へ利用者の有効性を問い合わせているため、期限切れを待つ必要はない。

## 2. できること

### 申込者一覧

受付番号 / 氏名 / メール / 会社名 / 業界 / 職種 / 立場 / 年齢区分 / 出禁申告 /
割引内訳 / 支払金額 / ステータス / 申込日時 / 決済日時 を表示する。
上部に全件数・支払済み件数・支払済みの合計金額を出す。

### 開催回の選択（2026-08〜、複数開催日対応）

開催日はGoogleカレンダーの予約から自動で複数回登録されるようになったため
（[docs/event-app-database.md](event-app-database.md) 4-1）、一覧の上部に開催回の
切り替えリンクが並ぶ。`?eventId=<events.id>` を付けたURLで直接開くこともできる。

- 既定（`?eventId=` なし）は「直近の公開回」（開催日が最も近い未来の公開回）。
  該当が無ければ最新の行（開催日が最も新しい行）を表示する。
- 定員（支払済み件数 / capacity）・CSVの絞り込みは、選択中の回に対して行う。
  回をまたいで合算すると「支払済み / 定員」の対応が崩れるため。
- イベントが1件も無い（初回導入直後など）場合だけ、全申込を混ぜて表示する。

### sync_warning（カレンダー同期の警告）

選択中の回に `events.sync_warning` が入っていると、一覧の上部に警告として表示する。
支払済みの申込がある回で、カレンダー側の予定が**日時変更・削除・改題**されたときに
自動で記録される（自動では参加者へ連絡しない。詳しくは
[docs/event-app-database.md](event-app-database.md) 4-1 の状態遷移表）。

警告が出たら、Google カレンダー側の現状を確認したうえで、参加者への連絡が必要かどうかを
人手で判断すること。改題を元に戻す・予定を復元すれば、次回の同期で自動的に再公開される。

一覧にはカレンダー同期の最終実行時刻・結果（`calendar_sync_state`）も表示する。
一度も同期していない場合（初期状態）は「未実行」と出る。長時間更新されていない
場合は、Google 側の障害かリフレッシュトークンの失効を疑う。

結果の文言に次が含まれる場合は、**カレンダー側の異常を疑う状態**として扱う。

* `予定の痕跡が無く対象も0件のため N件の受付停止を見送りました（取得異常の可能性。要確認）`
  公開中で未来の回が残っているのに、その予定のIDがカレンダーの応答に
  **削除済みとしてすら現れず**、取り込み対象も1件も無かった状態。カレンダーの障害・
  権限の変更・トークンやカレンダーIDの取り違えでも同じ応答（空の一覧）になるため、
  公開中の回を一斉に止めてしまわないよう受付を残している。
  Google カレンダー側で当該の予定が実際にどうなっているかを確認すること。
  **予定を削除・改題した場合はこの状態にならず、通常どおり受付が止まる**（後述）。
* `失敗: カレンダーの予定が上限（2500件）を超えました`
  取得期間（3ヶ月）のカレンダー予定が上限を超え、一覧が途中で切れている。
  切れた分を「予定が無い」と誤判定しないよう、同期そのものを中止している
  （DBの内容は変わらない）。対象期間の予定を整理するか、上限の見直しが必要。

### 申込者詳細

全入力情報、割引計算の内訳、Stripe の ID 類、譲渡履歴、管理者メモを表示する。

割引の内訳は `payments` に保存した**申込時点のスナップショット**を正とする。
参考として現在の割引ルールで計算し直した金額も併記し、食い違う場合は
その旨を示す（ルール変更の前後で申し込まれた記録を見分けるため）。

### 申込者情報の編集（譲渡対応）

氏名・フリガナ・メール・電話・会社名・部署名・役職名・管理者メモを書き換えられる。

「譲渡として記録する」にチェックすると、譲渡元の氏名とメール、譲渡日時を
履歴に残す。2回目以降の書き換えでは譲渡元を上書きしない（最初の申込者が
分からなくなるため）。

**受付番号と支払金額は変わらない**（仕様書7.2）。譲渡先の属性が違っても
差額の徴収・返金はしない。

### 参加確定メールの再送

現在登録されているメールアドレス宛に送り直す。譲渡で宛先を変えたあとに使う。
受付番号が未発行（＝支払済みでない）の場合は送れない。

### CSV出力

* **申込者CSV**：一覧と同じ項目。`?eventId=` を付けるとその回だけに絞れる（無指定は全回）
* **名札印刷用CSV**：**支払済みのみ**、氏名・会社名・業界・職種・立場の5項目だけ。
  **年齢は含めない**（仕様書7.3。当日の名札に年齢を記載しないため）。こちらも
  `?eventId=` で回を絞れる

どちらも Excel で開けるよう BOM 付き・CRLF で出力する。氏名や会社名が
`=` などで始まる場合に Excel が数式として実行しないよう無害化している。
ファイル名は回を指定した場合その回の開催日、無指定の場合は出力日の日付になる。

### 返金

管理画面からは行わない。Stripeダッシュボードから手動で返金すると、
Webhook を通じてステータスが「返金済み（例外対応）」になる（仕様書7.1）。

## 3. 実装しないもの

* **受付状態の手動切替**（受付中 / 満席 / 受付終了）
  仕様書9章には管理画面から変更する要件があったが、事業者判断により要件から外した
  （2026-08-01）。2026-08〜は `GET /event/api/schedule/` を LP（`script.js`）が見て
  自動で切り替えるため、そもそも手動切替の必要性自体が薄い。受付を止めたいときは
  「カレンダーの予定を消す／改題する」（下記「カレンダー運用ルール」）が正規の操作。
  `public/event/index.html` の `data-event-status` は、API が取得できないときだけ
  効く静的フォールバックとして残っている（[docs/event-app-database.md](event-app-database.md) 参照）。
* ダッシュボード / イベント編集画面 / 割引ルール管理 / 返金機能（フェーズ2）

## 3-1. カレンダー運用ルール（開催日の追加・停止）

開催日はGoogleカレンダー（`architect@potenitas.com` の primary）が真実源。
**このルールを外れると同期対象から漏れる、または意図せず重複公開される**ため、
予定を作る・消す・変更するときは必ず守ること。

* **タイトルは「【SV顧客用】渋谷CAFEご予約」に完全一致させる。** 前後にスペースが
  入る、絵文字が付く、部分一致になるなどは同期対象外になり、開催日として取り込まれない。
* **主催者自身が作成した予定だけが対象。招待で届いた予定は対象外。** 他人が作って
  このカレンダーへ招待した予定は、タイトルが完全一致していても取り込まない
  （`organizer.self`／`creator.self` を見ている）。これが無いと、第三者が同じ題名の
  予定を作って招待するだけで開催回を1つ増やせてしまうため。**予定は必ず
  `architect@potenitas.com` 自身で作成すること。**別のアカウントで作って共有した予定は、
  何度同期しても開催日として現れない。誕生日・不在・集中時間などの自動生成される
  予定（`eventType` が `default` 以外）も対象外。
* **予定の長さは60分を超えるようにする。** 表示・保存する開催時間は「開始+30分〜
  終了-30分」（設営・撤収バッファ）のため、60分以下の予定はバッファ適用後に
  開始≥終了となり、取り込まれない（`applyBuffer` が `null` を返す）。
* **同じ時間帯に重複する予定を作らない。** 同期は重複を検出・統合しない。同時間帯に
  2件あると2回とも公開され、参加者が別々の回として申し込める状態になる。
* **募集を止める手段はカレンダー予定の削除または改題だけ。** `is_published=false` に
  なり、対象外になった時点で新規の申込ページ・APIから見えなくなる。**支払済みの
  申込がある回を消す・改題する場合は、削除前に管理画面の sync_warning を確認し、
  必要なら参加者へ手動で連絡すること**（自動送信はない）。
  **開催予定が1件しか無い状態でその1件を消す・改題する場合も同じように止まる**
  （削除・改題はカレンダーの応答に痕跡が残り、取得できている証拠になるため）。
  なお **DB の `events.is_published` を直接 `false` にしても受付は止まらない**。
  カレンダーに対象の予定が残っていれば、次の同期（最大10分後）で「戻ってきた回」と
  判定され、`is_published=true` に戻る。カレンダーが真実源であることの帰結であり、
  DB を直接いじる運用は取らない。
* **受付停止が見送られるのは「取得異常が疑われるとき」だけ。** 具体的には
  「その予定のIDがカレンダーの応答に削除済みとしてすら現れない」かつ
  「取り込み対象の予定が1件も無い」が同時に成り立つ場合に限る。上記
  「sync_warning」節の状態文言を参照。
* **予定の説明欄には、支払済み人数と予約者名簿が自動で書き込まれる（2026-08〜）。**
  支払が確定したとき・返金が反映されたとき・管理画面で申込者情報を更新したときに、
  次の形のブロックが説明欄へ追加・更新される。

  ```
  ―― 申込状況（自動更新・編集しないでください） ――
  支払済み: 5名 / 定員30名
  1. TSAM-0001 山田太郎
  2. TSAM-0002 鈴木花子
  更新: 2026-08-19 11:30
  ――――――――――――――――――――
  ```

  名簿に載るのは**支払済みの申込だけ**（受付番号の昇順）。返金するとその人は名簿から
  自動的に消える。載るのは**受付番号と氏名だけ**で、メール・電話・会社名・年齢区分は
  載らない（カレンダーはアプリの外に出る情報なので、当日の受付に要る最小限に絞っている。
  他の項目は管理画面かCSVで見る）。譲渡で氏名を書き換えると、その場で名簿も更新される。
  ブロックの**外側**に書いた連絡事項（会場へのメモ等）は書き換えられない。逆にブロックの
  中身を手で直しても、次の更新で上書きされる。**ブロックの区切り線を消さないこと。**
  消すと自動更新の範囲を特定できなくなり、次回は同じブロックがもう1つ追加される
  （手書きのメモは消えない）。**タイトルには何も書き込まない**（タイトルは同期の
  完全一致キーで、変わると受付が止まるため）。
  人数や名簿が更新されない場合は書き込み用トークン（`GOOGLE_CALENDAR_WRITE_REFRESH_TOKEN`）の
  未設定・失効を疑う。書き戻しが失敗しても申込・決済・確定メール・申込者情報の編集には
  影響しない。参加者が非常に多い回では、説明欄の文字数上限を避けるため名簿を省略して
  人数だけを書く（その旨がブロックに出る）。
* 開催日を追加したいときは、対象の時間帯にタイトル完全一致の予定を作るだけでよい。
  次回の同期（最大10分後、または `/event/apply/`・`/event/api/schedule/` への
  アクセスで即時）で `events` に1行増える（定員は既定30名、受付開始は即時、
  受付終了は開催開始時刻）。定員や受付期間を変えたい場合は、行が作られたあとに
  管理画面から確認し、必要ならマイグレーションで `events` を更新する
  （管理画面に編集UIは無い。[docs/event-app-database.md](event-app-database.md) 参照）。

## 4. 設計上の要点

### セッション

アクセストークンは httpOnly の Cookie に置く（ブラウザのJavaScriptからは読めない）。
Cookie のパスは `/event/admin` に限定し、公開画面へは送らない。

ページを開くたびに Supabase へ問い合わせて有効性を確かめる。期限の見た目だけで
通すと、管理者を削除した直後にも入れてしまうため。期限が近い場合は
リフレッシュトークンで取り直す。

### ログインの失敗メッセージ

「メールアドレスが存在しない」と「パスワードが違う」を区別せず、
同じ文言を返す。区別すると、登録済みのアドレスを探る手掛かりになる。
