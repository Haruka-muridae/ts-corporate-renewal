## §2 未検証項目の検証方法

KeyStore と OAuth には**オリジンの制約**がある。これが検証場所を決める。

- KeyStore は `localStorage`。**オリジンが違えば別の保管庫**になる
  （[keystore-spec-v1.md](./keystore-spec-v1.md) §3）
- OAuth は「承認済みJavaScript生成元」に登録したオリジンでしか動かない

### 2-1. ローカルで検証できるもの

`npm run dev`（`http://localhost:3000`）で確認できる。KeyStore は
**同じローカルオリジンの Portal でキーを保存すれば参照できる**。
本番に保存したキーは見えないが、参照の仕組み自体は確かめられる。

| 項目 | 方法 | 合否 |
| --- | --- | --- |
| `guardPage()` が未ログインを弾く | セッションを消して検証ページを開く | `/login/` へ遷移する |
| KeyStore からキーを取得できる | ローカル Portal でキーを保存 → 検証ページで `KeyStore.get('gemini')` | 取得できる。未保存時は Portal へ誘導 |
| KeyStore を直接触っていない | コード検査＋自動テスト | `localStorage` の直接参照が無い |
| **Gemini API の呼び出し** | 利用者キーを `x-goog-api-key` に載せて `generativelanguage.googleapis.com` を叩く | JSON が返る。キーが URL に出ない |
| 構造化出力（JSON Schema） | 同上。名刺テキストのサンプルを投げる | §FR-12 の必須項目が揃う |
| 行順崩れ対策プロンプト | OCR結果を模した「行が入れ替わったテキスト」を投げる | 会社名・氏名が正しい項目に入る |
| 無料枠のレート上限挙動 | 上限まで連続で投げる | 429 が返り、AI-002 の案内に落ちる |
| 数式サニタイズ | `=1+1` を含む値を `escapeCellText` に通す | 先頭にアポストロフィが付く |
| 外部通信先が3系統のみ | `fetch` をスタブして呼び出し先を記録 | §12 の3ホスト以外へ出ない |

> **Gemini はローカルで検証できる。** Gemini API はブラウザから直接叩くだけで、
> オリジンの登録を必要としない（キーはヘッダーで送る）。
> これがローカル検証の範囲を大きく広げている。

### 2-2. OAuth の生成元登録を必要とするもの

**「本番でしかできない」ものではない。** 承認済みJavaScript生成元にその
オリジンを登録してあれば、ローカルでもプレビューでも動く。

| 項目 | 必要な前提 |
| --- | --- |
| **Google OAuth の同意フロー** | 検証に使うオリジンが生成元に登録済みであること |
| Drive OCR の実データ精度 | OAuth が通ること（上に従属） |
| 保存構造の作成・再発見 | 同上 |
| OAuth同意画面の「未確認アプリ」警告の有無 | 同上。警告の有無は同意画面の設定で決まり、オリジンでは変わらない |

### 2-2-1. どのオリジンでも検証できないもの

| 項目 | 扱い |
| --- | --- |
| **本番のキーでの通し確認** | 検証しない。KeyStore は同一オリジンなら読めるという構造上の性質であり、Portal も検証ページも同じオリジンに配信される以上、成立はあたりまえに保証される。プレビューでは「そのオリジンの Portal でキーを保存し直す」ことで同じ経路を確かめられる |
| Cloud クォータの上限値 | 検証ではなくダッシュボードでの確認事項。場所に依存しない |

### 2-3. 採用する方式 — Vercel のプレビューURL

プレビューは `*.vercel.app` で**別オリジン**だが、ブランチごとに安定した
エイリアスが割り当てられる。これを承認済みJavaScript生成元へ登録すれば、
**本番を触らずに OAuth まで含めた検証ができる**。

| | 本番URL | プレビューURL | ローカル |
| --- | --- | --- | --- |
| KeyStore | 本番のキーが使える | そのオリジンで保存し直す | 同左 |
| OAuth | 生成元登録済み（card-scanner 実績） | **生成元の追加登録が必要** | 生成元の追加登録が必要 |
| 到達性 | 誰でも（URLを知れば） | Vercel SSO で保護 | 自分だけ |
| main への影響 | **あり** | 無し | 無し |

**プレビューURL方式に決定した（§6-3）。** `main` を触らずに済み、かつ
Vercel SSO で第三者から見えない。生成元を1つ追加するだけで足りる。

ただし、この方式には**確かめていない前提が2つある**。どちらも §5 の
検証順序で最初に潰す（項目 0-1、0-2）。

1. **プレビューのエイリアスURLの実体**。ブランチ名 `docs/card-ocr-phase0-plan`
   はスラッシュを含み、Vercel 側で変換・切り詰めが起きる。生成元に登録する
   値が確定しないと、この方式は始められない
2. **Vercel SSO と Google のポップアップの相性**。GIS のトークンモデルは
   ポップアップで `accounts.google.com` を開き `postMessage` で親へ返すため、
   理屈のうえでは SSO と干渉しないはずだが、確かめていない

## §3 本番ドメインでの検証の進め方（採らない。将来のために残す）

**§6-3 の決定によりこの方式は採らない。** §5 の項目 0-1・0-2 が通らず
プレビュー方式が成立しなかった場合の退避先として、手順を残しておく。

**本番の利用者に見える場所へ検証ページを置く行為**なので、慎重に扱う。

### 3-1. 「Portal未掲載＋`guardPage()` のみ」方式の可否

**技術的には可能。ただし「隠れている」とは考えないこと。**

- `APP_REGISTRY` に載せなければ Portal のグリッドには出ない
- `guardPage()` を入れれば、未ログインでは中身が描画されない
- **しかし HTML と JS の取得自体は防げない。** 静的ホスティングの限界であり、
  [app-registry.js](../../public/portal/app-registry.js) の注意書きと
  SECURITY_NOTES.md が明記しているとおり

したがって、置いてよいのは次を全て満たす場合に限る。

1. 検証ページに秘密情報を書かない（キーもIDもコードに埋めない）
2. 利用者のデータを読み書きしない（自分のアカウントでのみ操作する）
3. 撤去期限を決めてから置く

### 3-2. 手順

```text
1. docs/card-ocr-phase0-plan ブランチから feat/card-ocr-poc を切る
2. public/production-app/card-ocr/poc/ に検証ページを置く
   - guardPage() を必ず入れる
   - APP_REGISTRY には登録しない
3. PR を作り、プレビューURLで動く範囲を先に確認する
4. main へマージ（＝本番公開）。ここは人の判断で行う
5. 本番URL https://tsam-ai.com/production-app/card-ocr/poc/ で検証する
6. 検証が終わったら撤去する（下記）
```

### 3-3. 撤去手順

```text
1. public/production-app/card-ocr/poc/ を削除する PR を作る
2. テストスイート（tests/unit/card-ocr-poc.mjs）も一緒に削除し、
   tests/run.mjs の SUITES から外す
3. main へマージ。1〜2分で URL が404になることを確認する
4. Google Cloud の承認済みJavaScript生成元から、検証用に足したオリジンを外す
```

**撤去を忘れないための仕掛け**: 検証ページの `<h1>` と画面上部に
「検証用。◯月◯日に撤去予定」と日付を書いておく。

これは MVP の利用者案内（要件定義書 §5.3、§FR-24）を書くときに、
改めて同意画面を見て記録すればよい。取り直す方法は3つある。

1. 検証ページで「連携を解除する」→ 再連携（`prompt: 'consent'` が付く経路ではないため、
   同意画面が再表示されない場合がある）
2. Google アカウントの「サードパーティ アプリとサービス」で付与済みの権限を見る
3. Cloud Console の OAuth同意画面で、設定されているスコープの説明文を見る

> 「未確認アプリ」警告が**出なかった**ことは、MVP 公開前に公開ステータスを
> 「本番」へ切り替える際の判断材料になる（§6-1）。現状「テスト」かつ
> テストユーザー登録済みのため警告が出ていない可能性が高く、
> **「本番」へ切り替えたときに同じとは限らない。**

### 4-1. Google Cloud の既存設定は流用できるか

**コードから判定できた範囲では、大部分が流用できる。**

| 項目 | 判定 | 根拠 |
| --- | --- | --- |
| Google Drive API の有効化 | **流用可**（有効化済み） | card-scanner と voice-recorder が使用中 |
| Google Sheets API の有効化 | **流用可**（有効化済み） | card-scanner が使用中。README が「このアプリで初めて使う」として有効化を指示済み |

> 「OAuthクライアントは開発用・本番用を分離する」としている。既存IDは
> テスト環境 `/apps/` が使っており、共用すると片方の設定変更がもう片方に及ぶ。
>

> 決まる**。したがって card-scanner が作ったファイルは新しいクライアントからは
> 見えない。本アプリは独自の保存構造を作るため実害は無く、むしろ
> テスト環境のデータと混ざらないという点で望ましい分離になる。

### 4-3. クォータの実測値と評価（2026年8月3日）

| API | プロジェクト単位 | 利用者単位 |
| --- | --- | --- |
| Drive | 12,000 / 分 | 12,000 / 分（同値） |
| Sheets 読み取り | 300 / 分 | 60 / 分 |
| Sheets 書き込み | 300 / 分 | 60 / 分 |

**結論: 想定する利用者数では制約にならない。** §5 の項目16 は合格とする。

根拠は、1件の登録で使う呼び出し回数から見た試算である。

| 処理 | API | 回数 |
| --- | --- | --- |
| 保存構造の確認・作成 | Drive | 初回のみ数回。2回目以降はキャッシュで0〜1回 |
| OCR（変換・取得・削除） | Drive | 3回 |
| 保存画像のアップロード | Drive | 1回 |
| 重複キー列の取得 | Sheets 読み取り | 1回 |
| 行の追加（＋変更履歴） | Sheets 書き込み | 1〜2回 |

**律速は Sheets の書き込み**（プロジェクト全体で 300/分）である。
1件あたり最大2回なので、**全利用者の合計で毎分150件**の登録に耐える。

利用者単位では 60/分、つまり1人あたり毎分30件。**1件の所要時間は
中央値45秒を見込んでいる**（要件定義書 §13.1）ため、人がこの上限に
届くことはない。**先に頭打ちになるのは OCR の処理時間であって、
クォータではない。**

> **引き上げ申請は現時点で不要。** 必要になるのは「同時に登録している
> 利用者が常時100人を超える」ような規模で、MVP の想定を大きく超える。
> 監視するなら Sheets の書き込みを見る。

## §6 決定事項

起案時に判断できなかった6件は、**2026年8月3日にすべて決定した。**
決定を覆す場合は、ここの理由を読んだうえで行うこと。

### 6-1. OAuth同意画面の公開ステータス → **「テスト」のままフェーズ0を進める**

**決定**: 公開ステータスは切り替えない。テストユーザーに検証用アカウントを
入れて進める。「本番」への切り替えは MVP 公開前に行う。

**理由**: 「本番」への切り替えに Google 側の確認手続きが要るかどうかが、
まだ分かっていない。そこを検証の前提条件にすると、手続き待ちで検証全体が
止まる。テストユーザー枠は100名あり、フェーズ0には十分足りる。

必要な手続きの洗い出しは、要件定義書 §18 でもフェーズ0の作業項目である。
**§4-2 A で分かった内容は、この文書へ追記すること。**

### 6-2. OAuthクライアント → **`card-ocr` 用に新規作成する**

**決定**: 既存クライアントID（`public/apps/auth-config.js`）を流用しない。
`TSAM AI card-ocr` を新規に作る。

**理由**: 要件定義書 §13.4 の「開発用・本番用を分離する」に従う。既存IDは
テスト環境 `/apps/` が使っており、共用すると片方の設定変更がもう片方に及ぶ。

加えて `drive.file` はクライアントIDごとに見えるファイルの範囲が決まるため、
分離すると card-scanner が作ったファイルは本番アプリから見えなくなる。
**これは欠点ではなく、テスト環境のデータと混ざらないという利点である。**

代償は、生成元の登録先が2箇所になること。この程度の手間は受け入れる。

### 6-3. 検証場所 → **Vercel のプレビューURL**

**決定**: プレビューURLに生成元を1つ追加して検証する。本番へ検証ページを
置く方式（§3）は採らない。§3 の手順は、将来必要になったときのために残す。

**理由**: `main` を触らずに済み、Vercel SSO で第三者から見えない。
本番方式は `main` へのマージ（＝本番公開）が必要で、撤去も同じ手間がかかる。

**この決定には確かめていない前提が2つある**（§2-3 に記載）。
§5 の項目 0-1・0-2 で最初に潰す。**そこが崩れたらこの決定をやり直す。**

### 6-4. 保存フォルダ名 → **`TSAM AI/名刺データ/` のまま**

**決定**: 要件定義書 §FR-07 のとおりとする。card-scanner の
`TSAM AI/名刺スキャナ/` とは統合しない。

**理由**: 統合すると、本番アプリがテスト環境のデータ構造に依存する。
これは「本番からテスト環境へ線を伸ばさない」という方針（§1-3、
[repository-structure.md](../repository-structure.md) §2-1）と同じ理由で避ける。

なお `/apps/` はテスト環境であり一般利用者には案内していないため、
**2つのフォルダが並ぶのは事業者自身のドライブだけ**である。
一般利用者のドライブには `名刺データ` しか作られない。

### 6-5. 評価用サンプル名刺 → **既存の受領済み名刺を使い、測定後に破棄**

**決定**: 精度測定のために名刺を新たに集めない。既に交換済みの自社宛の
名刺から §16.1 の内訳に合うものを選ぶ。測定が終わったら、検証で作られた
保存先ごと削除する。

**理由**: 測定のためだけに第三者の個人情報を新たに集めると、利用目的の
説明が難しくなる（要件定義書 §14.5）。再測定が必要になれば測り直せばよい。

### 6-6. `card-parser.js` の複製 → **フェーズ0では複製しない**

**決定**: 884行の正規表現抽出は本番側へ複製しない。Gemini 単独の精度を先に測る。

**理由**: 正規表現抽出を先に入れると、**Gemini がどれだけ効いているかを
測れなくなる**。単独で測ってから、足りない項目にだけ足すほうが、複製する量を
根拠を持って決められる。フェーズ0の目的は方式の検証であって、精度の作り込み
ではない。

## §7 項目12・13（精度と所要時間）の測定手順

フェーズ0で残っている最後の2項目。**要件定義書 §16.2 の定量受入基準を
実測で確定させる**のが目的であり、精度を作り込む工程ではない。

> **これは「表面のみ」の測定である（要件定義書 v3.1）。**
>
> 50枚は表面1枚ずつを測る。**両面の精度検証はここで行わない。**
> 裏面付きサンプル15枚での検証は、フェーズ2の完了条件に置かれている
> （v3.1 §16.1、§18）。
>
> **この50枚を両面対応のあとで測り直す必要はない。** 表面のOCRと分類の
> 経路は両面対応を入れても変わらないため、測り直す費用に見合う情報が
> 得られない（v3.1 §16.1）。
>
> 測定結果を記録するときは「表面のみの測定である」ことを併記すること。
> あとから両面の数字と並べたときに、取り違えないようにするため。

### 7-1. 先に実装が要る — いまの検証ページでは測れない

現在の検証ページは、**OCR と Gemini が別々の節に分かれている。**

- 「3. Gemini API の疎通と分類」は**固定の架空サンプル**を送っている
- 「4. 保存構造と Drive OCR」は**テキストを表示するだけ**で、分類しない

項目12 が測るのは「**画像 → OCR → Gemini → 項目**」の通しの正解率である。
したがって、次の3つを足す必要がある。

| 追加するもの | 理由 |
| --- | --- |
| **OCR の結果を Gemini へ流す経路** | 通しで測るため。いまは繋がっていない |
| **1件あたりの所要時間の計測** | 項目13。要件定義書 §13.1 の「読み取り開始〜確認画面表示」を測る |
| **結果の書き出し（CSV）** | 50枚ぶんを手で転記すると誤りが混じる。集計もできない |

> **正解データの入力欄は作らない。** 画面で1枚ずつ正解を打ち込むのは
> 手間がかかるうえ、打ち間違いが精度の数字に化ける。
> **書き出したCSVへ、あとから正解列を追記して突き合わせる**ほうが確実で、
> 測り直しもできる。

### 7-2. 評価用サンプルの用意

要件定義書 §16.1 の内訳で50枚。**既に交換済みの自社宛の名刺から選ぶ**
（§6-5 の決定。測定のために新たに集めない）。

| 種別 | 枚数 |
| --- | --- |
| 日本語横書き | 20 |
| 縦書き | 8 |
| 日英併記 | 8 |
| 英語のみ | 5 |
| ロゴ表記のみ | 4 |
| 低品質（かすれ・傾き・影） | 5 |

撮影は要件定義書 §8.2 に合わせる（長辺1,600〜2,000px、1.5MB以下、
名刺全体が写っていること、正しい向き）。

**ファイル名に通し番号を付ける**（`01.jpg`〜`50.jpg`）。CSVの行と
突き合わせるときの手がかりになる。

### 7-3. 測定の進め方

```
1. 50枚を順に検証ページへ入れる
2. 1枚ごとに CSV へ1行が積まれる（自動）
3. 50枚終わったら CSV を書き出す
4. CSV に正解列を追記する（表計算ソフトで手入力）
5. 正解率と所要時間を集計する
```

**連続で流さず、間を空けること。** 無料枠キーはレート上限が低く、
続けて投げると 429 になる（項目14 はこの過程で確かめられる）。
**429 が出たら、それは不具合ではなく項目14 の観測データである。**
待ってから再開し、何枚目で当たったかを記録する。

Drive 側は1件あたり3回の呼び出しで、50枚でも150回。12,000/分の上限
（§4-3）には遠く及ばない。

### 7-4. 判定基準（要件定義書 §16.2）

| 指標 | 基準 |
| --- | --- |
| 主要5項目の正解率 | **85%以上**（会社名・氏名・役職・メール・電話） |
| メール正規化の一致率 | **95%以上** |
| 処理完了率 | **95%以上**（エラーで止まらず確認画面まで到達） |
| 登録所要時間 | **手入力より短いこと** |
| 推測による追加 | **0件**（入力に無い情報を Gemini が作っていないこと） |

| 項目13 の指標 | 基準（要件定義書 §13.1） |
| --- | --- |
| 1件全体（読み取り開始〜確認画面表示） | 中央値 **45秒以内** / 95パーセンタイル **90秒以内** / 最大許容180秒 |

**「推測による追加0件」は自動では測れない。** CSV を目で見て、
名刺に書かれていない値が入っていないかを確かめる。1件でもあれば
プロンプト（§FR-13）の見直しに戻る。

### 7-5. 測定後の後始末

- 検証で作られた `TSAM AI/名刺データ` を**フォルダごと削除する**（§6-5 の決定）
- 名刺画像もローカルから消す
- 結果の数値だけをこの文書へ追記する。**CSV の中身（第三者の個人情報）は
  リポジトリへ入れない**
