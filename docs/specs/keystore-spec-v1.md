# KeyStore 仕様書 v1

対象範囲: `public/auth/keystore.js` ＋ これを使うすべての画面・アプリ

制定: 2026年7月31日

---

## §1 位置づけ

KeyStore は、**利用者本人が発行した外部AIサービスのAPIキー**を、
その端末のなかだけで預かるための共通資産である。

Portal（`/portal/`）が最初の利用者だが、Portal 専用ではない。
今後 `public/apps/` 配下のアプリがキーを使うときも、ここを経由する。

認証（当社が発行するセッショントークン）は扱わない。
そちらは [login-page-detailed-spec-v3.md](./login-page-detailed-spec-v3.md) §7 に従う。

---

## §2 いちばん重要な原則 — サーバーへ送らない

**KeyStore が預かるキーを、当社のサーバー（GAS）へ送らない。**

理由は3つある。

1. **当社のものではない。** キーは利用者が Google AI Studio で発行し、
   利用者に課金される資格情報である。当社が預かる筋合いがない。
2. **預かると守る義務が生じる。** 保管すれば、漏洩したときの責任も、
   退会時に確実に消す責任も当社に生じる。預からなければ、その義務は生じない。
3. **預かる必要がない。** キーを使うのはブラウザ上のアプリであり、
   ブラウザから直接 Gemini API を呼べば足りる。サーバーを経由する理由がない。

したがって、次のコードを書いてはならない。

- キーを `public/auth/api.js` のリクエストへ載せる
- キーを `console.log` / `console.error` へ出す
- キーを URL のクエリ文字列へ載せる（ヘッダーを使う。§5）
- キーを画面へ平文で表示する（伏せ字にする。§5）

この原則は**テストで固定している**（§7）。

### §2-1 KeyStore の外で localStorage を触らない

キーに触る口を KeyStore の4つの関数だけに閉じる。

画面やアプリが `localStorage.getItem('tsam-api-keys')` を直接書くと、
「どこかで GAS へ送っていないか」を確かめる範囲がファイル全体へ広がる。
入口が1つなら、この仕様書と `public/auth/keystore.js` を読むだけで確かめられる。

## §3 保存の形

`localStorage` に **JSON を1件だけ**置く。
プロバイダー名をキーにしたオブジェクトとする。

| 保存キー | 値 |
| --- | --- |
| `tsam-api-keys` | `{"gemini":"AIza..."}` |

保存キーの名前は `KEYSTORE_STORAGE_KEY` として定数化する。
**この値を変えない。** 変えると既存端末のキーが読めなくなる。

### §3-1 プロバイダーごとに保存キーを分けない

`tsam-api-key-gemini` `tsam-api-key-openai` のように分けない。

分けると、増えるたびに消し忘れの対象が増える。
1件の JSON なら、消すときも移すときも（§6-1）対象が1つで済む。

### §3-2 中身が空になったら保存キーごと消す

最後の1件を `remove()` したら、`localStorage` から `tsam-api-keys` を削除する。
`{}` を残さない。「何も入っていない入れ物」が残っていると、
端末を調べたときに「何か保存されている」と誤解させる。

### §3-3 壊れた値でも画面を止めない

`tsam-api-keys` に壊れた JSON・配列・文字列・空文字が入っていても、
例外を投げず「何も保存されていない」として扱う。

開発者ツールから手で書き換えられる場所なので、
そこにある値のせいで画面が開かなくなるほうが困る。

## §4 公開API

```js
import { KeyStore, PROVIDERS } from '../auth/keystore.js';

KeyStore.get(provider)          // string | null
KeyStore.set(provider, value)   // boolean（保存できたか）
KeyStore.remove(provider)       // boolean
KeyStore.has(provider)          // boolean
```

| 関数 | 決めごと |
| --- | --- |
| `get` | 未保存・空文字・保存先なしはすべて `null` |
| `set` | 空文字と空白のみは**拒否**して `false`。前後の空白は落として保存 |
| `remove` | 元から無くても `true`（結果として無い状態になるため） |
| `has` | `get(provider) !== null` と同義 |

補助として次を公開する。

| 名前 | 用途 |
| --- | --- |
| `KEYSTORE_STORAGE_KEY` | 保存キー名（`'tsam-api-keys'`） |
| `PROVIDERS` | プロバイダー名の定数（`{ gemini: 'gemini' }`） |
| `isKeyStoreAvailable()` | 保存先が使えるか（プライベートモード対策） |

### §4-1 空文字での削除を許さない

`set(provider, '')` は削除ではなく**拒否**とする。

「空文字で上書き＝削除」を許すと、入力欄の初期化ミスや
未入力のままの送信で、気づかないうちにキーが消える。
消す意思は `remove()` という別の名前で示させる。

### §4-2 プロバイダー固有の処理を KeyStore へ入れない

キーの形式チェック（`AIza` で始まるか）や疎通テストは、
**KeyStore の仕事ではない。** これらは Gemini という個別サービスの都合である。

KeyStore は「名前をつけて文字列を預かる」ことだけを行う。
現在それらは `public/portal/portal.js` にある
（`looksLikeGeminiApiKey()` / `testGeminiApiKey()`）。
2つ目の利用者が同じ判定を必要としたときに、共通の置き場所へ移す（§6-2）。

## §5 保存済みの値の見せ方

画面へ平文を出さない。**先頭4文字と末尾4文字だけ**を残し、あいだを伏せる。

```
AIza•••••••••••••••••••••••••••••••MNOP
```

12文字以下の値は全部伏せる。
「先頭4＋末尾4」を機械的に当てると、8文字なら全部見えてしまう。

入力欄は `type="password"` とし、表示切替（`public/auth/ui.js` の
`attachPasswordToggle`）を添える。ログイン画面のパスワード欄と同じ部品を使う。

**保存済みの値を入力欄へ書き戻さない。**
「変更」を押したときの入力欄は空から始める。
画面のどこにも平文を置かないため。

疎通テストでキーを送るときは、URL のクエリ文字列ではなく
**HTTPヘッダー（`x-goog-api-key`）** へ載せる。
クエリに置くと、開発者ツールの履歴や拡張機能から拾える場所が1つ増える。

## §6 将来拡張の発動条件

**いま実装しない。** 下の条件が実際に起きたときに、この節を読んで着手する。
起きていないうちに作らない。使われない分岐は壊れたことにも気づけない。

### §6-1 複数端末で同じキーを使いたいという要望が出たら

→ **エクスポート／インポートを検討する。**

キーは端末ごとに保存されるため、別の端末では入力し直しになる。
これは §2 の帰結であって不具合ではない。

要望が出たときも、**サーバーへ預ける形は採らない。**
JSON をファイルとして書き出し、別の端末で読み込ませる形を先に検討する。
`tsam-api-keys` の値がそのまま書き出す単位になる（§3 の形にしてある理由の1つ）。

書き出したファイルは平文である。
実装するなら、その旨を画面に明記することまでを1組とする。

### §6-2 2社目のプロバイダーを扱うことになったら

→ **画面にキーの入力欄を1つ増やす。** それだけで足りるようにしてある。

- `PROVIDERS` に名前を1つ足す
- 保存の形は変えない（同じ JSON に2件目が入る。§3-1）
- `public/auth/keystore.js` は変更不要

このとき、形式チェックと疎通テストが2社ぶん必要になる。
そこで初めて、プロバイダー固有の処理の共通の置き場所を作る（§4-2）。
1社しかないうちに抽象化しない。

## §7 テスト

| 場所 | 確認 |
| --- | --- |
| `tests/unit/frontend.mjs`「KeyStore」 | 保存キー名／保存の形が JSON 1件／2件目も同じキーへ入る／空文字と空白の拒否／前後の空白を落とす／最後の1件で保存キーごと消える／壊れた値5種で例外を投げない／保存先が無い環境 |
| `tests/browser/auth-screens.mjs`「Gemini APIキーの設定」 | `localStorage` の中身が `{"gemini":"..."}` そのもの／`api`・`key` を含む保存キーが `tsam-api-keys` 1つだけ／伏せ字の形／画面にキーの中身が出ない／**キーがヘッダーで送られURLに出ない**／**GAS への通信にキーが含まれない**／`signOut()` 後もキーが残る |

疎通テストは `window.fetch` をスタブして確かめる。
**テストから実際の Gemini API へ通信しない。**
利用者のキーも当社のキーも使わずに済ませる。

「GAS への通信にキーが含まれない」は、スタブがすべての `fetch` を記録し、
`script.google.com` 宛の URL・ヘッダー・本文のどこにもキー文字列が
現れないことを確かめる形で見ている。§2 を実装が破ったときに落ちる。

## §8 設計判断の記録

### §8-1 ログアウトで消さない

`public/auth/session.js` の `signOut()` / `clearSessionToken()` は、
`tsam-api-keys` を掃除の対象に**含めない**。

セッショントークンは当社が発行した認証情報なので、ログアウトで捨てる。
APIキーは端末の持ち主の資産であり、当社が預かっているものではない。
ログアウトのたびに消すと、再ログインのたびに Google AI Studio で
取得し直すことになる。

消えるのは、利用者が `/portal/` の削除ボタンを押して確認したときだけとする。

共有端末を気にする利用者のために、削除の導線は常に見える場所へ置く
（API設定パネルを開けば「削除」がある）。

「ログアウトで消えたほうが安全ではないか」という考え方はあり得る。
だが、消えて困るのは本人であり、消えずに困るのは
**同じ端末の同じブラウザプロファイルを他人と共有している場合**に限られる。
その状況ではセッショントークン以外にも共有されるものが多く、
APIキーだけを消しても解決しない。

### §8-2 疎通テストは参照系だけを使う

モデル一覧の取得（`GET /v1beta/models`）を使う。
生成系（`generateContent`）は使わない。

保存ボタンを押しただけで利用者に課金が発生してはならない。
参照系なら、押し間違いでも利用者のデータにも請求にも影響しない。

### §8-3 疎通テストの失敗で保存を巻き戻さない

保存と疎通テストは独立させる。テストが失敗しても保存は残す。

「テストが通らないと保存されない」形にすると、
一時的な通信不良や利用上限のたびに、39文字のキーを入力し直すことになる。
保存しておけば、あとから「変更」で直せる。

### §8-4 形式チェックで保存を拒まない

`AIza` ＋ 35文字という形は、いまの Google の採番に過ぎない。

一致しなくても保存し、「一般的なGemini APIキーの形式と異なります。」と
添えるだけにする。Google が採番を変えたときに、
こちらの正規表現のせいで正しいキーを保存できなくなるほうが困る。

拒否ではなく警告なので、利用者は自分で判断して続けられる。
