## 0. 本書の前提と未確定事項

### 0.1 v2.0の設計原則（名刺OCR v3.0に準拠）

**利用者の資格情報（Geminiキー・OAuthトークン）も、利用者のデータ（領収書画像・領収書データ）も、当社サーバーへ一切送信しない。** 当社が提供するのは「道具（静的アプリ）」であり、データの器はすべて利用者自身のGoogleアカウントである。

| 区分 | v1.3からの変更 |
| --- | --- |
| データ保存先 | 会社ドライブ・会社スプレッドシートを**廃止**。領収書データ・原本画像は**利用者本人のマイドライブ**に保存する |
| バックエンド | GAS APIを**全廃**。OCR・重複照会・保存を含む全処理を、利用者のOAuthトークンによりブラウザからのGoogle API直接呼び出しへ変更（サーバーコードゼロ） |
| データの帰属 | 領収書データは利用者本人のGoogleアカウント内にのみ存在し、**当社はデータを保持・閲覧しない** |
| 保存先の準備 | 利用者のドライブに指定のフォルダ・スプレッドシートが存在しない場合、**アプリが自動作成する**（9章） |
| 社内経理の運用 | 会社シートへの集約は行わない。社内利用者が各自のドライブに保存し、経理が必要とする場合は利用者が自らのスプレッドシートを共有する |
| 権限分離 | 各利用者は自分のデータのみを扱う（構造上、他者のデータへ到達できない） |

### 0.2 OCR方式（フェーズ0で決定・選択肢を更新）

サーバーが消えたため、比較対象を以下の2案に更新する。Cloud Vision APIはKeyStoreが扱わないGCPキーを要するため除外する。

| 案 | 方式 | 特徴 |
| --- | --- | --- |
| A | Drive OCR（利用者トークンでDrive APIを直接呼び、Googleドキュメント変換）＋ルール抽出 | 追加コストなし、座標情報なし、一時ドキュメントは即時削除 |
| C | Gemini（利用者キー）への画像直接投入＋Structured Output | 実装が最も単純、キー未設定者は利用不可となる、無料枠では画像がGoogleに利用され得ることの明示が必須 |

折衷（A＋テキストのみGemini補完）はv1.3の構成を踏襲したもので、これもブラウザ内で完結する。

### 0.3 電子帳簿保存法への対応方針

v1.3の0.3項と同一とする。**本アプリは電帳法スキャナ保存要件を満たさない。紙原本は廃棄しない。** この案内は初回利用時画面に表示する。

### 0.4 Gemini APIキーの取り扱い（BYOK）

v1.3の0.4項と同一とする（無料枠許容・データ取り扱いの明示・有料化の推奨・出力と責任は利用者に帰属・当社は出力を検証しない・API制限推奨）。

### 0.5 データの帰属と責任分界（v2.0新設）

* 領収書データは利用者本人のGoogleアカウント内にのみ存在し、当社従業員を含む第三者は、利用者が自ら共有しない限りアクセスできない
* 領収書には取引先の情報・自社の経理情報が含まれるが、**当社はこれを取得・保管・閲覧しない**。データの管理・保管・削除の責任は利用者に帰属することを、利用規約に明記する
* ドライブの状態（容量・整理・利用者自身による削除）は当社は関知しない。**利用者がシート・フォルダを削除した場合、当社はデータを復元できない**（バックアップを保持しないため）。この点を初回利用時に案内する
* 上記の責任分界の整理は法務確認を経て確定する（名刺OCR v3.0 §14.5と同種の枠組みで確認する）

### 0.6 経理・税理士による確認事項

1. 電帳法の位置づけ（0.3項）
2. 勘定科目候補の初期マスタ（各利用者のシート内マスタとして配布する初期値）
3. 「要確認」データの確認手順（利用者自身が行う前提でよいか）
4. 責任分界・キー費用の規約明記（0.4・0.5項、法務確認）
5. 社内経理運用（各自ドライブ＋共有ベース）の承認

## 1. 背景・目的

v1.3の1〜2章の目的（領収書画像から必須項目を自動抽出し、誤った値の自動確定を最大のリスクとして防ぐ）は変わらない。変わるのは実現形態である。本アプリはTSAM AI Portalの一アプリとして、利用者自身のGoogleアカウントを器に動作する。

## 2. アプリ名称・配置

* 名称（仮）：領収書スキャナ
* アプリID：`receipt-ocr`
* 配置：`public/production-app/receipt-ocr/`（Portalと同一オリジン＝KeyStore参照の必須条件）
* PORTAL_APPSの登録パスに`apps/`を含めない（自動テストが禁止している）
* テスト環境`/apps/`のコードをimportしない。流用するロジックは本番側へ複製する

## 3. 対象範囲

### 3.1 MVPスコープ

* 領収書画像の取得（ファイル選択・カメラ撮影、JPEG/PNG、HEICはブラウザ内でJPEGへ変換できる場合のみ受付）
* 保存先（フォルダ・スプレッドシート）の自動プロビジョニング（9章）
* 原本画像の利用者ドライブへの保存
* OCR（方式はフェーズ0で決定）
* ルール抽出（v1.3の10章の全項目：必須3項目＋消費税内訳・支払方法・レシートNo.・電話番号・登録番号・勘定科目候補・宛名・但し書き）
* 金額正規化・妥当性検証・信頼度算出（v1.3の10.1・13・14章と同一）
* 必要時のみGemini補完（利用者キー・ブラウザから直接）
* SHA-256重複確認（自分のシートとの照合）
* 「要確認」の管理（利用者自身のシート上）
* 抽出結果の確認・修正UI（保存前に人が確認できる画面。v1.3で対象外だった修正UIは、保存前確認として最小限実装する）

### 3.2 対象外

* GAS等のサーバーコード、会社側でのデータ保管・閲覧
* 会社シートへの集約・管理者によるデータ修正運用
* 電帳法スキャナ保存対応（紙原本は廃棄しない）
* PDF・複数枚一括・商品明細・会計ソフト連携（将来拡張）
* 会社キーによるGemini呼び出し・フォールバック

## 4. 利用前提（3層ガード）

名刺OCR v3.0のFR-02と同一の3層判定を行う。

1. **TSAM AI認証**：共通実装`guardPage()`を使用（独自実装禁止）。未ログインは`/login/`へ誘導。Portalの一覧掲載の有無にかかわらず、アプリ自身にガードを入れる
2. **Google OAuth**：スコープは`drive.file`のみ。ドライブ全体を読むスコープを要求してはならない。トークンはメモリ上でのみ保持する
3. **Geminiキー**：`KeyStore.get('gemini')`。未設定時は抽出を開始せず、Portalのキー設定画面へ誘導する（導線が循環しないよう戻り先を明示）

キー未設定時の挙動はOCR方式による（案A採用時はルール抽出のみで動作し、補完をスキップして要確認とする。案C採用時はキーが必須となる）。

## 5. システム構成

```text
ブラウザ（静的アプリ・Portalと同一オリジン）
  ├─ TSAM AI認証（guardPage）
  ├─ OAuthトークン（drive.file・メモリのみ）
  ├─ KeyStore.get('gemini')
  │
  ├─ ① 保存先の検出・自動作成（9章）
  ├─ ② 画像取得 → SHA-256計算
  ├─ ③ 重複照合（Sheets APIで自シートのハッシュ列を取得し、ブラウザ内で照合）
  ├─ ④ 原本をDrive API v3で利用者ドライブへ保存
  ├─ ⑤ OCR（利用者トークンでDrive OCR、または利用者キーでGemini）
  ├─ ⑥ ルール抽出・正規化・検証・信頼度算出（v1.3と同一ロジック）
  ├─ ⑦ 必要時のみGemini補完（独立抽出→ブラウザ内で突合・evidence照合）
  ├─ ⑧ 確認・修正画面（保存前に利用者が確認）
  └─ ⑨ Sheets APIで自シートへ行追加

当社側に存在するもの：静的ファイル、Portalアイコン、KeyStore、TSAM AI認証系のみ。
サーバーコード・データベース・利用者データの保管場所は存在しない。
```

v1.3の2段階ワーカー・idempotencyKey・LockService・処理台帳・APIアクセストークンは、防御対象（会社シート）の消滅に伴い**全廃**する。二重登録防止は⑧の保存前確認・保存ボタンの多重押下ガード・③のハッシュ照合で担保する。

## 7. 抽出・検証仕様（v1.3を継承）

以下はv1.3と同一とする。実装はすべてブラウザ内で行う。

* **10章**：ルール抽出の全項目と採用条件（金額正規化・日付ラベル近接必須・合計金額の除外語・レシートNo.・登録番号のT文字必須と状態3値・電話番号・税率別内訳の表記区分・支払方法・勘定科目は候補のみ）
* **11章**：Gemini補完条件（要否判定ロジック。判定を実行するのがブラウザ内になる点のみ変更）
* **12.2〜12.5項**：独立抽出（ルール候補をプロンプトに含めない）、Structured Output、サニタイズ、リトライ1回、confidence不使用・evidence必須
* **13章**：金額・日付検証、evidence照合（改竄対策の意図は消滅するが、**Geminiの幻覚検出という品質チェックとして継続**する）、必須項目検証
* **14章**：信頼度のコード側スコアリング

## 8. 保存前確認（v2.0新設・最小限の修正UI）

自動確定のリスクを人の目で止める最後の関門として、シート保存前に確認画面を表示する。

* 抽出結果（必須3項目＋取得できた項目）と原本画像を並べて表示し、利用者が修正できる
* 信頼度が低い、または要確認判定の項目は強調表示する
* 利用者が修正した値は抽出値より優先し、extractionMethodに手修正の事実を記録する（v1.3の15章の4軸は原則として維持）
* 「要確認のまま保存」も選択できる（後からシート上で修正する運用を許容）

## 9. 保存先の自動プロビジョニング（v2.0新設・本改訂の中核）

### 9.1 作成する構造

```text
マイドライブ/TSAM AI/領収書データ/
├─ 原本/
│   └─ YYYY/MM/          ← 原本画像。月別フォルダは保存時に随時作成
└─ 領収書データ（スプレッドシート）
    ├─ タブ「領収書データ」   ← v1.3の16.1と同一の列構成（サーバー専用列を除く）
    ├─ タブ「OCR原文」       ← 管理IDと紐付け
    ├─ タブ「店舗マスタ」     ← 初期マスタ（0.6項で確定した値）を書き込む
    └─ タブ「設定」          ← 閾値等の利用者別設定＋スキーマバージョン
```

v1.3の16.1からの列変更：idempotencyKey・processingStatus・処理台帳関連を削除、登録者（申告値）を削除（本人のシートのため不要）。それ以外の列（レシートNo.・電話番号・税率別内訳・表記区分・支払方法・登録番号状態を含む）は維持する。

### 9.2 検出→作成フロー

アプリ起動のたびに以下を実行する。

```text
1. localStorageに保存済みのフォルダID・スプレッドシートIDを確認
2. IDあり → Drive APIで存在・アクセス可を確認 → OKなら利用
3. IDなし・無効 → drive.fileスコープで自アプリ作成ファイルを名前検索
   （drive.fileは本アプリが作成したファイルのみ参照できるため、
     利用者のドライブ全体を見ることなく自分の作成物を再発見できる）
4. 見つからない → フォルダ階層とスプレッドシートを新規作成し、
   ヘッダー行・初期店舗マスタ・スキーマバージョンを書き込む
5. 取得・作成したIDをlocalStorageへ保存する
```

初回作成時、「データはあなたのドライブに保存されます。当社は閲覧できません。削除すると復元できません」の案内（0.5項）と、無料枠キーの明示（0.4項）を表示する。

### 9.3 壊れた状態への対応（本章の実質的な本体）

| 状態 | 検出方法 | 挙動 |
| --- | --- | --- |
| シート削除済み | ID参照が404 | 名前検索→なければ再作成し、「空の状態から開始する。過去データは復元されません」を表示 |
| 列の改変（並べ替え・削除） | 起動時にヘッダー行をスキーマ定義と照合 | **書き込みを停止**して警告。修復方法（新シート作成 or 手動復旧）を案内。列位置を推測して書き込む処理は行わない |
| ファイルの移動・リネーム | 影響なし | IDで追跡するため通常動作 |
| タブ削除 | タブ名の存在確認 | 欠損タブのみ再作成（データタブが消えた場合は上記「シート削除」に準じる案内） |
| 2タブ同時初回起動 | 作成後の名前検索で複数構造を検出 | 作成日時が古い方へ寄せ、新しい方は利用しない旨を表示（自動削除はしない） |
| ドライブ容量不足 | API 403/insufficientStorage | DRV-003を表示し保存を中断（データ消失なし・原本未保存の旨を明示） |

### 9.4 スキーマの進化ルール

* 列は右端への追加のみ。既存列の削除・並べ替え・改名を行わない
* 設定タブにスキーマバージョンを記録し、アプリは旧バージョンのシートを検出したら不足列を右端に追加して更新する
* ヘッダー検証は名前の完全一致で行う

### 9.5 共有・権限

* 作成したフォルダ・ファイル・スプレッドシートに**共有設定を一切付与しない**
* OCR一時ドキュメント（案A採用時）は共有設定を行わず、テキスト取得後に即時削除する

## 10. 重複判定（v1.3の9.3項を簡約化）

* 画像のSHA-256をブラウザ内（Web Crypto API）で計算する
* Sheets APIで自シートの**ハッシュ列のみ**を取得し、ブラウザ内で照合する（全列の全件取得を行わない。名刺OCR v3.0 FR-21と同方式）
* 完全一致：登録済みである旨と既存の管理ID・行を表示し、保存しない
* 類似（同日・同店舗・同金額）：警告のみ表示し、保存は利用者の判断に委ねる。両者のレシートNo.が取得でき番号が異なる場合は警告しない
* 保存ボタンは処理中に無効化し、多重押下による二重登録を防ぐ

サーバーの排他制御は存在しないため、複数タブでの同時保存は完全には防げない。単一利用者・自己データという前提で許容し、発生時は類似警告と手動削除で回復する。

## 11. 「要確認」の運用（v1.3の18章を利用者完結に変更）

* 確認・修正の主体は利用者本人。自分のスプレッドシートを直接編集する
* プロビジョニング時に「要確認一覧」フィルタビューを作成しておく
* reviewStatus・科目確定フラグの更新も利用者が行う。編集可能列・保護列の区別（v1.3の18.2項）は、本人のシートのため強制しない。ただしヘッダー行のみ保護を設定する
* 訂正削除履歴は残さない（電帳法非対応の前提。0.3項）

## 12. エラーコード（表示用）

名刺OCR v3.0と共通の体系を用いる。サーバーが存在しないため、すべてブラウザ内での表示コードである。

| コード | 内容 |
| --- | --- |
| AUTH-001 | TSAM AI未ログイン（/login/へ誘導） |
| OAUTH-001 | Google未連携・トークン期限切れ（再連携を案内） |
| KEY-001 | Geminiキー未設定（Portalへ誘導） |
| KEY-002 | Geminiキー無効・権限不足（Portalへ誘導） |
| AI-002 | Geminiクォータ超過（利用者自身のクォータ・無料枠の場合の案内を含む） |
| DRV-001 | 保存先が見つからない（再作成の案内、9.3項） |
| DRV-002 | シート構造の改変検出（書き込み停止、9.3項） |
| DRV-003 | ドライブ容量不足 |
| OCR-001 | OCR失敗・文字数不足（要確認として保存するか選択） |
| SHEET-001 | シート書き込み失敗（原本保存済み・データ未保存の状態を明示し、再試行を案内） |
| DUP-001 | 同一画像が登録済み |

エラー時は「どこまで完了しているか」（原本保存済み／シート未保存）を必ず表示する。

## 13. セキュリティ要件

* **APIキー**：v1.3の12.1項 KeyStore要約・21.2項と同一（KeyStore.getのみ、localStorage直接操作禁止、通信先はGemini APIのみ、メモリ外保存禁止、会社キーフォールバック禁止、キーローテーションはPortal）
* **XSS対策を最重要要件とする**：v1.3の21.5項と同一（innerHTML不使用・第三者CDN不使用・CSP検証）。キーとOAuthトークンの窃取に直結するため
* **OAuth**：`drive.file`スコープのみ。トークンをメモリ外へ保存しない
* **数式インジェクション対策**：v1.3と同一（守る対象は利用者自身のシート）
* **通信の限定**：当社ドメインとの通信は静的資産の取得とTSAM AI認証系のみ。領収書画像・OCR文字列・抽出データ・キー・トークンを当社側へ送る通信は存在しないことを、**通信内容の検証**で確認する（個別基準）

## 14. 非機能要件

* 全処理がブラウザ内のため、1件の処理時間は「OCR（Gemini）API往復」に依存する。目標60秒以内
* 対応件数の上限は利用者ごとのGoogle APIクォータ・Geminiクォータに依存し、当社側の上限は存在しない
* **運用KPI（v1.3の22.5項）は当社がデータを閲覧しないため、集計できない。** 代替として、アプリ内に利用者向けの簡易統計（自シートから算出する要確認率・補完使用率）を表示し、改善判断は利用者のフィードバックと個別テストで行う
* 端末・回線が弱い環境では画像アップロードがボトルネックになるため、アップロード前にブラウザ内で長辺2,000px程度へ縮小するオプションを設ける（電帳法要件とは無関係である。0.3項）

## 15. 個別基準

### 15.1 精度（v1.3の24.1〜24.2と同一）

検証データ50枚以上・困難条件込み・開発/個別分離、合計金額98％・利用日95％・支払先90％・3項目完全一致90％、**誤った値を信頼度が高いとして提示した件数0件**、要確認への振り分け95％以上。

### 15.2 プロビジョニング

* 保存先が存在しない利用者の初回利用で、フォルダ・シート・初期マスタ・フィルタビューが自動作成される

* 作成物に共有設定が付与されていない

### 15.3 分離・安全性

* キー未設定・無効・クォータ超過時に、対応するKEY/AI系コードと誘導が表示される
* 保存前確認画面で修正した値が優先して保存され、手修正の事実が記録される

## 17. 完成定義

利用者がPortalから本アプリを開き、画像を選ぶだけで、①保存先が自動的に整い、②原本が自分のドライブに保存され、③抽出・検証された結果を保存前に自分の目で確認でき、④自分のスプレッドシートに記録される。この間、当社サーバーには利用者のいかなるデータも送信されない。

自動確定できない場合は「要確認」として保存され、原本画像・OCR原文・抽出候補を自分のシートで確認できる。紙原本を廃棄しない運用（0.3項）と、無料枠キーのデータ取り扱い（0.4項）・データ帰属（0.5項）が利用者に案内されている。
