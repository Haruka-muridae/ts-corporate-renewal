## 2. システムの目的

TSAM AI の利用者が、名刺OCRアプリ（`card-ocr`）が保存した名刺台帳「名刺管理」を、
台帳をスプレッドシートで直接開かずに**検索・閲覧・編集**できるようにする。

重点は次の順とする。

1. **台帳を壊さない。** 台帳の新規作成・列構成の変更は行わない（それは
   card-ocr の役割）。列構成が想定と食い違う場合は、閲覧のみに留めるか、
   読み込み自体を止める。
2. 名刺データは、**利用者の管理下から出さない**（当社サーバーへの送信
   ゼロ。card-ocr / card-mail の設計原則を引き継ぐ）。
3. 編集した内容は台帳の「変更履歴」タブに残し、**何を・いつ・どう変えたか**
   を追跡できるようにする（card-ocr 自身の登録・重複統合フローと同じ記録
   の形に揃える）。

---

## 3. 背景と課題

- 名刺OCRアプリにより、名刺の情報は利用者ごとのスプレッドシート
  「名刺管理」に貯まる。台帳を直接スプレッドシートで開いて修正すること
  はできるが、列位置を誤って書き換える・数式（画像リンク）を壊す・
  見出し行を崩すといった事故が起きやすい。
- テスト環境 `public/apps/card-manager/` は、名刺スキャナ（`card-scanner`。
  card-ocr とは別系統の実験アプリ）が作る台帳「名刺台帳（表裏対応 v3）」
  を対象にしており、**本番の台帳（card-ocr が作る「名刺管理」）とは列構成
  がまったく別物**である。本番公開にあたり、対象を card-ocr の台帳へ
  作り直す必要があった（§4.2）。

## 4. システム概要

### 4.1 全体構成

```
利用者のブラウザ（card-manager アプリ。静的配信）
  │ ① Google連携（drive.file のみ。トークンはメモリ上のみ）
  │
  ├─② 台帳の解決（Drive API・検索のみ）
  │     マイドライブ / TSAM AI / 名刺データ / 名刺管理
  │
  ├─③ 見出し行の検証（Sheets API）
  │     現在の列構成（card-ocr/schema.js の複製）と一致するかを確認
  │
  ├─④ 全行の読み込み・一覧表示・検索（会社名・キーワード）
  │
  └─⑤ 1件の編集・保存
        保存直前に record_id を再確認 → 行を更新 → 変更履歴タブへ追記
```

当社サーバーはどこにも登場しない。通信先は Google の2系統（Drive・
Sheets）と TSAM AI 認証系のみ（CSPで固定）。

### 4.2 なぜ card-ocr の台帳を読み書きできるのか

`drive.file` 権限は「**そのクライアントIDで作成したファイルだけ**」を
見せる。名刺台帳「名刺管理」は card-ocr のクライアントIDで作られている
ため、**本アプリは card-ocr（および同じ理由で共用している card-mail）と
同じクライアントIDを使う**ことで、利用者ごとの台帳をそのまま読み書き
できる。アプリごとにIDを分けて見える範囲を切るのが本来の方針（card-ocr
config.js）だが、本アプリは「card-ocr の台帳を編集する」のが目的そのもの
なので、例外として共用する（`docs/repository-structure.md` §4-1 の
「複製する」判断とは別の、クライアントID共用という既存の判断を踏襲した
もの）。

台帳の列定義（`schema.js`）・値のサニタイズ（`sanitize.js`）は
card-ocr のものを**そのまま複製**している。列を1つでも違えると、位置で
意味が決まる表へ誤った列の値を書き込む事故になるため、値ではなく
構造そのものを合わせる必要があった。

### 4.3 使用サービス

| サービス | 用途 | 備考 |
| --- | --- | --- |
| Google Identity Services | OAuth 認可（トークンモデル） | 承認済みの読み込み先のみ |
| Drive API | 台帳の場所の検索・検証（読むだけ） | フォルダもファイルも**作らない** |
| Sheets API | 台帳の見出し・全行の読み込み、1行の更新、変更履歴タブへの追記 | 台帳の作成・列の追加（スキーマ更新）は行わない |

## 5. 対象ユーザーとアクセス制御

- TSAM AI のログインユーザー（`guardPage()` を通る。card-ocr / card-mail
  と同じ）。
- Google連携は利用者本人の同意による。要求するスコープは `drive.file`
  のみ。
- 静的配信のためHTML/JSの取得自体は防げない（SECURITY_NOTES.md）。
  データを守るのは OAuth であって画面ガードではない（card-ocr と同じ整理）。

## 6. 前提条件

1. 利用者が名刺OCRアプリで名刺を登録済みで、台帳
   「マイドライブ / TSAM AI / 名刺データ / 名刺管理」が存在すること。
   **無い場合、本アプリは台帳を作らず**「先に名刺OCRアプリで登録」と案内
   する。
2. 台帳の見出し行が、本アプリが複製している列定義（`schema.js`。
   card-ocr/schema.js の SCHEMA_VERSION 3.5 相当）と一致していること。
   一致しない場合の扱いは §9 FR-05 のとおり。
3. デプロイは手動（`npm run deploy`）。`main` へのマージでは公開されない。
4. Portal のアプリ一覧（`public/portal/app-registry.js`）へ登録すること
   （本書の実装に含めている）。

## 7. スコープ

### 7.1 含める機能

- Google連携（`drive.file` のみ、トークンはメモリ上のみ）
- 台帳の解決（検索のみ）と見出し行の版の検証
- 全行の読み込み・一覧表示
- キーワード検索（全項目の全文検索・スペース区切りAND）・会社名での絞り込み
- 1件の詳細表示（自動項目・入力項目の両方）
- 入力項目（氏名・会社名・連絡先など）の編集・保存
- 保存直前の record_id 再確認（他端末・他タブでの競合検出）
- 保存時の重複判定キー（`duplicate_key`）の再計算
- 変更履歴タブへの記録（変更前後の値・日時。記録に失敗しても台帳の更新
  自体は成功として扱う）
- 台帳をスプレッドシートで直接開くための補助リンク
- Google連携の解除

### 7.2 含めない機能（現時点の判断）

| 機能 | 含めない理由 |
| --- | --- |
| 台帳の新規作成 | card-ocr の役割。空の台帳を作ると正本が競合する（card-mail と同じ判断） |
| 台帳の列構成の修復・アップグレード（`upgrade` 判定時に列を右へ足す） | card-ocr（`drive-storage.js`）の役割。このアプリは「読む・編集する」に責務を絞る。§11 |
| 名刺の新規登録（1件追加） | 画像からの読み取り・重複判定を伴うため card-ocr の役割。本アプリは既存行の編集のみ |
| 行の削除 | 誤操作で第三者の個人情報を含む行を消す事故を避ける。削除はスプレッドシート側で行う |
| メールアドレスの複数件管理 | 台帳の `メールアドレス` 列は1件のみ（card-ocr の schema.js）。テスト環境版にあった複数メール・主メール選択の仕組みは対象の台帳に存在しないため持たない |
| タグ・名刺交換日・場所・担当者での絞り込み | 台帳に該当する列が無い（card-ocr の要件定義書 §FR-16 でも未実装。§11） |
| OCR生テキストの表示 | card-ocr は抽出後の項目のみを台帳に保存し、OCRの生テキストは保存しない |
| 一括編集・CSVエクスポート | 単体編集で足りる。台帳をスプレッドシートで直接開く導線で代替できる |

## 8. 業務フロー（利用者の操作）

1. Portal からアプリを開く（ログイン必須）。
2. 「Googleドライブへ接続する」を押し、ドライブへの接続を許可する。
3. アプリが台帳の場所を解決し、見出し行の版を確認したうえで全行を
   読み込み、一覧を表示する。
   - 台帳が見つからない場合は、名刺OCRアプリでの登録を案内する。
   - 見出しが古い版（右端の列が足りないだけ）の場合、閲覧はできるが
     編集はできない旨を案内する。
   - 見出しが改変されている（並び替え・削除など）場合は、読み込み自体を
     止める。
4. キーワード・会社名で一覧を絞り込み、氏名を押して詳細を開く。
5. 「編集する」を押し、入力項目（自動項目は変わらず読み取り専用）を
   直して「保存する」を押す。
6. 保存の直前に、その行がまだ同じ名刺（同じ `record_id`）であることを
   確かめてから書き込む。他の場所で行がずれていた場合は保存を止め、
   一覧の読み込み直しを案内する。
7. 保存が成功すると、変更のあった項目を台帳の「変更履歴」タブへ追記する
   （失敗しても保存自体は成功として扱い、その旨を案内する）。

## 9. 機能要件

### FR-01 画面ガード

`guardPage()` を通るまで内容を描画しない（card-ocr / card-mail と同じ）。

### FR-02 Google連携

- スコープは `drive.file` のみ。**増やさない。**
- トークンはメモリ上のみ。Storage・URL・console・当社サーバーへ出さない。

### FR-03 台帳の解決（読むだけ・作らない）

- キャッシュ検証 → 名前・親・種別・未削除での検索、の順で解決する。
  **見つからなくても作らない**（空の台帳を作ると card-ocr の正本と
  競合する。card-mail と同じ判断）。「先に名刺OCRアプリで登録」と案内
  する。
- localStorage に入れるのは台帳の場所（ファイルID）だけ。

### FR-04 見出し行の検証と編集可否

台帳の見出し行を、本アプリが持つ列定義（現在の版）と比較し、次のいずれか
に分類する。

| 判定 | 状態 | 閲覧 | 編集 |
| --- | --- | --- | --- |
| 一致 | 最新版 | 可 | 可 |
| 右端の列が不足 | 旧版（card-ocr が列を追加する前に作られた台帳） | 可 | **不可** |
| 並び・削除・改名 | 改変された台帳 | **不可**（読み込み自体を停止） | 不可 |
| 空 | 台帳のタブに見出しが無い | 0件として表示 | 不可 |

「右端の列が不足」を編集不可にするのは、現在の列幅で行を書き込むと
Sheets のグリッド幅（既定26列）を超えて失敗しうるためであり、列を
広げて追従するのは card-ocr（`drive-storage.js` の役割）に委ねる
（§11）。「並び・削除・改名」で読み込み自体を止めるのは、列の位置が
信用できない状態で表示すると、電話番号の欄をメールアドレスとして
見せるような事故になるため。

**この検証は読み込み時だけでなく、保存の直前にも行う。** 読み込み後に
別の場所（card-ocr のスキーマ更新・利用者の手編集）で見出しが変わって
いても、`record_id` の一致だけでは検出できないため、保存直前に見出しを
取り直し、`'ok'` でなければ書き込まずに止める（FR-07）。

### FR-05 全行の読み込みと一覧・検索

- 台帳の全行を読み込み、`record_id` が空の行（誤って残った空行など）は
  一覧に出さない。
- キーワード検索は入力項目（会社名・部署名・役職・氏名・氏名カナ・
  郵便番号・住所・電話番号・携帯番号・FAX・メールアドレス・URL・その他）
  の全文検索。スペース区切りはAND検索。全角/半角・大文字/小文字・
  カタカナ/ひらがなの表記ゆれを吸収する。
- 会社名は完全一致（正規化後）での絞り込みのみ。台帳にタグ列が無いため、
  タグでの絞り込みは持たない（§7.2）。

### FR-06 詳細表示

- 自動項目（`record_id`・登録日時・重複判定キー・裏面の有無・裏面から
  補完した項目・表裏の画像ハッシュ/ファイルID/画像リンク・登録アプリの
  版・抽出プロンプトの版・要確認項目）は読み取り専用で表示する。
- 表面/裏面の画像は、Driveへのリンクを新規タブで開くだけで、埋め込み
  表示はしない（画像そのものを扱わないため、CSPの `img-src` に外部
  ドメインを含める必要が無い）。
- 閲覧モードでは、電話番号・携帯番号にはリンク（`tel:`）、メール
  アドレスにはリンク（`mailto:`）、URL（複数行可）には安全な
  `http`/`https` のものだけリンクを添える。

### FR-07 編集・保存

- 編集できるのは入力項目のみ。自動項目は編集できない。
- 保存の直前に、**見出し行と対象行を1回の通信（`values:batchGet`）で
  まとめて再取得する。** 見出しが `'ok'` でなくなっていた場合（読み込み
  後の列変更）は書き込まず、`'upgrade'` なら HEADER_OUTDATED、それ以外
  （`'altered'`・`'empty'`）なら HEADER_MISMATCH として台帳の読み込み
  直しを案内する。`writable`（FR-04・読み込み時点のスナップショット）は
  通信を発生させない早期リターンにのみ使い、実際の書き込み可否は
  この再取得結果で判定する。往復回数は行だけを取得していた従来と同じ
  1回である。
- 見出しが `'ok'` であることを確認したうえで、対象行の `record_id` が
  編集開始時と一致するかを確かめる。一致しなければ書き込まず、台帳の
  読み込み直しを案内する（行ずれの検出。テスト環境版の `ROW_CONFLICT`
  と同じ考え方）。
- 保存で書き換えるのは入力項目の列と、そこから再計算した重複判定キー
  （`duplicate_key`）の列のみ。自動項目（画像リンクの数式を含む）は
  読み取った生セルをそのまま書き戻す。**画像リンクの数式を組み立て直さ
  ない**（§11）。
- 重複判定キーは、メール → 携帯 → 会社名＋氏名 の優先順位で再計算する
  （card-ocr/schema.js の `buildDuplicateKey` と同じ規則）。連絡先を
  修正したのに古いキーが残ると、以後の名刺OCR側の重複検出が誤って働く
  ため。

### FR-08 変更履歴の記録

- 保存に成功した後、変更のあった項目（自動再計算された重複判定キーを
  含む）を、台帳の「変更履歴」タブへ、変更前値・変更後値・日時とともに
  追記する。
- **台帳の更新を先に行い、変更履歴の追記は後で行う。** 追記に失敗しても
  台帳の更新そのものは失敗として扱わない（更新はできたが記録は残せな
  かった旨を利用者に伝える）。card-ocr の重複統合フロー（`register.js`）
  と同じ順序・同じ考え方。
- **追記の前に「変更履歴」タブ自身の見出し行も検証する。** 検証せずに
  追記すると、そのタブが改変されていた場合に列がずれた壊れた記録を
  残してしまう。見出しが最新版と一致しないときは追記そのものを見送り、
  台帳の更新は成功のまま「記録は残せなかった」として利用者に伝える
  （通信・書き込みの失敗と同じ扱い）。
- 変更が無い場合（自動項目の閲覧のみで保存した等）は、変更履歴タブへの
  追記を行わない。

## 10. セキュリティ要件

| 脅威 | 対策 |
| --- | --- |
| 台帳の列位置を誤って書き換える | 見出し行が最新版と一致するときだけ書き込みを許可する（FR-04） |
| 数式インジェクション | 台帳は `USER_ENTERED` で書かれているため、書き込む値の先頭に数式文字が来る場合はアポストロフィを付けて無害化する（`sanitize.js`。card-ocr と同じ規則） |
| 画像リンクの破損 | 画像リンクの数式（`=HYPERLINK(...)`）を再構築せず、読み取った生セルのまま書き戻す |
| トークンの漏えい | メモリ上のみ保持。Storage・URL・console・例外メッセージに出さない |
| 台帳の新規作成による正本の競合 | 台帳・親フォルダとも一切作成しない（読み書き専用） |
| 他端末・他タブでの上書き競合 | 保存直前に `record_id` を再確認し、一致しない場合は書き込まない（FR-07） |
| 当社サーバーへの漏えい | 通信先をCSPで Google 2系統＋認証系に固定。当社サーバーは登場しない |

## 11. 採用しなかった案とその理由

- **テスト環境（card-scanner）の台帳をそのまま対象にする**: card-ocr と
  クライアントIDを共用する理由が「card-ocr の台帳を読み書きするため」
  である以上、対象を card-scanner の台帳のままにする意味が無い。本番では
  card-ocr の台帳「名刺管理」へ対象を作り直した（§4.2）。
- **見出しが `upgrade`（旧版）のときに、このアプリ自身が列を右へ広げて
  追従する**: card-ocr（`drive-storage.js`）の役割と重複する。同じ処理を
  2か所に持つと、片方だけ直して食い違う事故につながる（このアプリを
  card-ocr と別々に開発する理由そのもの。`docs/repository-structure.md`
  §4-1）。閲覧のみ許可し、編集は card-ocr 側で台帳を開いた際の自動更新に
  委ねることにした。
- **画像リンクの数式（`=HYPERLINK(...)`）を、保存のたびに URL から
  再構築する**: 読み取った数式全体を URL 検証にかけると、常に
  「Googleドライブの URL ではない」と判定されて数式が消える実装上の罠が
  ある（読み取った値は `=HYPERLINK("url","label")` という文字列全体で
  あり、URL 部分だけを指しているわけではない）。生セルをそのまま
  書き戻す設計にすることで、この罠を構造的に避けている。
- **変更履歴を記録しない（card-mail のように読むだけに徹する）**:
  card-mail は台帳を読むだけなので変更履歴が不要だが、本アプリは
  台帳を編集する。card-ocr 自身がすでに変更履歴タブ（`変更履歴`）を
  持っているため、そこに記録しないと「card-ocr からの変更は残るが
  card-manager からの変更は残らない」という不完全な履歴になる。
  schema.js の `HISTORY_COLUMNS`・`diffValues`・`buildHistoryRow` を
  複製し、同じ形式で追記することにした。
- **タグ・名刺交換日・場所・担当者での絞り込み**: card-ocr の要件定義書
  （`docs/specs/meishi-ocr-requirements-v3.md` FR-16）でも未実装であり、
  台帳に該当する列が無い。無い列を前提にしたUIは作らない。
- **名刺の新規登録・行の削除**: 新規登録は画像からの読み取り・重複判定を
  伴い、card-ocr の責務と重複する。削除は誤操作の被害が大きい（第三者の
  個人情報を含む行を取り消せない形で失う）。どちらも本アプリのスコープ
  外とし、必要な場合はスプレッドシート側の操作に委ねる。

## 12. 用語集

| 用語 | 意味 |
| --- | --- |
| drive.file | 「そのクライアントIDのアプリが作ったファイルだけ」に絞ったドライブ権限。台帳を読み書きできる根拠（§4.2） |
| 名刺管理 | card-ocr アプリが利用者のドライブに作るスプレッドシート。本アプリが読み書きする台帳そのもの |
| record_id | 台帳の1行（1件の名刺）を一意に識別するID。card-ocr がブラウザで生成する。本アプリはこれを使って保存直前に行の同一性を確認する |
| duplicate_key | 重複判定キー。メール→携帯→会社名＋氏名の優先順位で決まる。card-ocr の重複検出が使う |
| 見出し行の版（'ok'/'upgrade'/'altered'/'empty'） | 台帳の見出しが現在の列定義とどう食い違うかの分類。編集の可否を左右する（FR-04） |
| 変更履歴タブ | 台帳内の別タブ（`変更履歴`）。変更前後の値・日時を1項目1行で記録する |
