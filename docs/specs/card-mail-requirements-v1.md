## 2. システムの目的

名刺OCRアプリ（card-ocr）で保存した名刺のメールアドレス宛に、
**宛先どうしを互いに見せずに（BCCで）**、挨拶・案内などの同報メールを
一括送信できるようにする。

重点は次の順とする。

1. **誤送信・宛先漏えいを起こさないこと。** 宛先がTo/Ccに載る事故、
   壊れたアドレスへの送信、意図しない二重送信を仕組みで防ぐ。
2. 手作業（メールソフトでBCC欄に貼り付け）より確実で、件数が増えても
   同じ手順で送れること。
3. 送信の途中で失敗しても「どこまで送れたか」が必ず分かること。

---

## 3. 背景と課題

- 名刺OCRアプリにより、名刺のメールアドレスはスプレッドシート
  「名刺管理」に貯まるようになった。次の課題は「集めた宛先への連絡」である。
- メールソフトで手動BCC送信すると、(1) To/CcとBCCの取り違えで全宛先が
  互いに見える事故が起きうる、(2) Gmailの1通あたり宛先数の制限を超えると
  手で分割する必要がある、(3) OCR由来の壊れたアドレスが混ざっていても
  気づきにくい。
- そこで、宛先の検査・分割・送信を機械にやらせるAPIを用意する。

---

## 4. システム概要

### 4.1 全体構成

```
【既存】名刺の保存（本APIの範囲外）
  利用者のブラウザ（card-ocrアプリ）
    └─ 利用者自身のGoogleドライブ
         └─ スプレッドシート「名刺管理」 ← 宛先の正本はここ

【今回】メールの一斉送信
  運用者（あなた）
    │ ① 台帳の「メール」列から宛先をコピーする（人の作業）
    │ ② APIを呼ぶ（curl等。合言葉=APIトークンを添える）
    ▼
  tsam-ai.com のサーバー（Cloudflare Workers 上の Next.js）
    │ ③ 宛先を検査し、重複を除き、90件ずつの束に分ける
    ▼
  Gmail API（送信元: MAIL_FROM のアカウント）
    │ ④ 1束＝1通として送信。宛先は全員BCC
    ▼
  各宛先（受信者からは他の宛先が見えない）
```

### 4.2 なぜ「宛先を人がコピーして渡す」のか（最重要の前提）

**サーバーは名刺台帳を読めない。これは不具合ではなく、名刺OCRアプリの
設計方針の帰結である。**

- 名刺OCRアプリは「利用者のデータを当社サーバーへ一切送らない」方針で
  作られている（[meishi-ocr-requirements-v3.md](./meishi-ocr-requirements-v3.md) v3.0 の設計原則）。
- 台帳にアクセスできる鍵（Google OAuth トークン）は、利用者のブラウザの
  メモリ上にしか存在せず、権限も「このアプリが作ったファイルだけ」
  （drive.file）に絞ってある。
- したがって tsam-ai.com のサーバーには台帳を開く鍵がなく、
  **宛先一覧はAPIを呼ぶ人がリクエストに載せて渡す**しかない。
  これを「不便」ではなく「当社がデータを持たない設計の証拠」と位置づける。

サーバーに台帳を読ませる案を採らなかった理由は仕様書 §12 に記録してある。

### 4.3 使用サービス

| サービス | 用途 | 備考 |
| --- | --- | --- |
| Cloudflare Workers | APIの実行環境 | 交流会申込アプリと同じ配信基盤 |
| Gmail API | メール送信 | 交流会の参加確定メールと同じ送信元アカウント・同じ資格情報を使う |

新しい外部サービス・外部ライブラリは追加していない。

## 5. 利用者とアクセス制御

- 利用できるのは **APIトークン（環境変数 `CARD_MAIL_API_TOKEN` の値）を
  知っている者だけ**。当面は事業者本人のみを想定する。
- トークンは「合言葉」である。リクエストのヘッダーに添え、サーバー側の
  値と一致したときだけ送信できる。**一致しなければ一律401**（何が違うかは
  教えない）。
- **トークンが未設定の間、APIは全リクエストを拒否する。** 設定を忘れた
  状態で「誰でも当社名義でメールを送れる口」が開く事故を防ぐため。
- card-ocr アプリの画面からは呼べない（呼ばせない）。静的サイトに
  トークンを置くと公開と同じになるため。画面からの送信が必要になったら
  利用者認証の設計とあわせて別途検討する（仕様書 §12）。

## 6. 前提条件

1. ブランチが `main` へマージされ、**手動デプロイ（`npm run deploy`）**が
   実行されていること（このリポジトリは push しても自動デプロイされない）。
2. Cloudflare Workers の環境変数に `CARD_MAIL_API_TOKEN` が登録されて
   いること（32バイト以上のランダム値。リポジトリ・ドキュメントには書かない）。
3. Gmail送信の資格情報（`GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` /
   `GMAIL_REFRESH_TOKEN` / `MAIL_FROM`）が本番に設定済みであること
   （交流会の参加確定メールが動いていれば設定済み）。

## 7. スコープ

### 7.1 含める機能

- 宛先一覧＋件名＋本文を受け取り、BCCで一斉送信する
- 宛先の形式検査・重複排除・分割送信
- 送らずに送信計画だけ確認する dryRun
- 途中失敗時の「送信済み件数」の報告

### 7.2 含めない機能（現時点の判断）

| 機能 | 含めない理由 |
| --- | --- |
| 台帳からの宛先の自動取得 | §4.2 のとおりサーバーは台帳を読めない。読める設計にしない |
| 送信画面（UI） | 利用者が運用者本人のみのため、curl等で足りる。必要になったら要件を起こす |
| 宛名の差し込み（「〇〇様」の個別化） | 宛先ごとに1通ずつ送る方式になり、送信上限に触れやすい。必要になったら版を上げる |
| 送信履歴のサーバー保存 | 送信元Gmailの「送信済み」フォルダが記録を兼ねる |
| 受信拒否（オプトアウト）の自動管理 | 拒否の申出を受けた宛先を台帳側で外すのは運用者の作業（§10） |

## 8. 業務フロー（運用手順）

1. **宛先を集める**: スプレッドシート「名刺管理」の「メール」列から
   送りたい相手のアドレスをコピーする。
2. **まず dryRun**: `dryRun: true` を付けてAPIを呼ぶ。1通も送信されず、
   「何件に・何通に分けて送ることになるか」だけが返る。
   壊れたアドレスが混ざっていれば、ここで**どれが不正か一覧で**返る。
3. **不正な宛先を直す**: 台帳側の元データも直しておく（次回も使うため）。
4. **本送信**: `dryRun` を外して同じリクエストを送る。
5. **失敗したら**: 応答の「送信済み件数」を見る。送信済みの宛先を
   リストの先頭から除いた**残りだけ**で再度呼ぶ（先頭から順に送るため、
   送信済み＝リストの先頭N件である）。
6. **受信拒否の申出が来たら**: 台帳側にその旨を記録し、以後の宛先に
   含めない（§10）。

### 呼び出し例

```bash
curl -X POST https://tsam-ai.com/api/card-mail/send/ \
  -H "Authorization: Bearer ＜APIトークン＞" \
  -H "Content-Type: application/json" \
  -d '{
    "subject": "ご挨拶",
    "text": "本文…",
    "recipients": ["taro@example.com", "hanako@example.jp"],
    "dryRun": true
  }'
```

URLの**末尾スラッシュは必須**（無いとリダイレクトされ本文が落ちる。
Stripe Webhook と同じ罠）。

## 9. 機能要件

### FR-01 認証

APIトークンの一致を確認してから処理する。未設定は全拒否（§5）。

### FR-02 宛先の検査

メールアドレスの形式でないもの（OCRの読み取りミス等）を検出する。
**1件でも不正があれば、1通も送らずに全体を失敗にし、どれが不正かを返す。**
「送れる分だけ送る」と、送られなかった宛先の存在に運用者が気づけないため。

### FR-03 重複排除

同じアドレス（大文字小文字の違いを含む）は1件にまとめ、同じ人に
同じメールを2通送らない。まとめた件数は応答で報告する。

### FR-04 dryRun

送信せずに送信計画（宛先数・重複数・分割数）だけを返すモードを持つ。

### FR-05 BCC送信と分割

宛先は全員BCCに入れ、To は送信元自身にする（受信者から他の宛先が
見えない）。Gmailの1通あたり宛先数制限を踏まえ、90件ずつに分割して
1通ずつ順番に送る。

### FR-06 途中失敗の報告

送信が途中で失敗したら残りを打ち切り、**送信済み件数を必ず返す**。
送ってしまったメールは取り消せないため、「どこまで送れたか」の情報を
落とさないことを最優先とする。

### FR-07 記録

サーバーのログには件数のみを書き、**宛先アドレスは書かない**。

## 10. 法令・運用上の要件（運用者の責務）

- **特定電子メール法**: 名刺交換をした相手への広告宣伝メールは事前同意
  なしで送れる区分だが、**本文に送信者の氏名・名称と、受信拒否の申出先
  （メールアドレス等）を表示する義務がある**。本文の中身はAPIは検査しない
  ので、この表示は運用者が本文に含めること。
- 受信拒否の申出があった相手は台帳側で管理し、以後の宛先に含めない。
- Gmailには1日あたりの送信上限がある（アカウント種別により500〜2000宛先）。
  上限に達するとアカウントが一時送信停止になり、**交流会の参加確定メールも
  同じアカウントから出ている**ことに注意する。1リクエスト500件の上限は
  この保護のためでもある。

## 11. セキュリティ要件

| 脅威 | 対策 |
| --- | --- |
| 第三者がAPIを叩いて当社名義でメールを送る | APIトークン必須。未設定なら全拒否。照合は比較時間から値を推測されない方式 |
| 宛先に改行等を仕込み、メールのヘッダーを乗っ取る（ヘッダーインジェクション） | 宛先・件名・返信先に改行・空白を含む値は送信前に例外で停止 |
| 資格情報の漏えい | トークン・Gmail資格情報は例外メッセージ・ログに載せない。リポジトリにも書かない |
| 宛先アドレスの漏えい | 全宛先をBCCにし、Toは送信元自身。ログにアドレスを書かない |

---

## 12. 用語集

| 用語 | 意味 |
| --- | --- |
| BCC | 受信者に他の宛先を見せずに同じメールを届ける宛先欄。本APIは全宛先をここに入れる |
| APIトークン（Bearer トークン） | APIを呼ぶ資格を示す合言葉。リクエストのヘッダーに添える |
| dryRun | 「実際には実行せず、実行したらどうなるかだけ確認する」モード |
| drive.file | 「そのアプリが作ったファイルだけ」に絞ったGoogleドライブの権限。名刺OCRアプリが使っており、サーバーが台帳を読めない根拠（§4.2） |
| リフレッシュトークン | Gmail送信元アカウントの長期の鍵。サーバーがメールを送るときに使う（交流会アプリと共用） |
