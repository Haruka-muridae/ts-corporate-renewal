### 1.1 v1.0 からの変更点（v1.1・全面改訂）

**v1.0 の「会社サーバーAPI方式」を廃し、ブラウザ完結方式へ全面変更した。**

| 区分 | v1.0（廃案） | v1.1（本書） |
| --- | --- | --- |
| 宛先の取得 | 運用者が台帳から手でコピーしてAPIに渡す | **アプリが利用者の台帳「名刺管理」から自動で読み込む**（名刺OCRと同じ drive.file 連携） |
| 送信元 | 会社のGmail（サーバーのリフレッシュトークン） | **利用者自身のGmail**（ブラウザで gmail.send を認可） |
| 利用者 | 事業者本人のみ | **お客様全員** |
| サーバー | Next.js のAPI＋APIトークン認証 | **サーバーコードなし。** 当社サーバーは宛先も本文も受け取らない |
| 1通の宛先数 | 90件 | **100件**（To を付けないことで無償Gmailの上限にちょうど収まる） |

v1.0 を廃した理由: 名刺台帳は利用者ごとのGoogleドライブにあり、サーバーからは
読めない。v1.0 はそれを「宛先の手渡し」で回避したが、台帳がこちらのシステム
（名刺OCR）の作成物である以上、**名刺OCRと同じ連携をアプリ側で行えば
自動取得できる**。手渡しは運用の手間と転記ミスを生むだけだった。
また会社名義での代理送信は、お客様全員に開放する要件と両立しない
（誰でも会社名義で送れる口になる）。詳細は §12。

## 2. システムの目的

TSAM AI の利用者が、名刺OCRアプリで保存した名刺の宛先へ、
**自分自身のGmailから、宛先を相互に見せずに（BCCで）**宣伝・案内メールを
一括送信できるようにする。

重点は次の順とする。

1. **宛先漏えい・誤送信を仕組みで防ぐ。** 全宛先をBCCに入れ、To/Ccを
   使わない。壊れたアドレスは送信対象から外して利用者に見せる。
2. 名刺データも宛先も本文も、**利用者の管理下から出さない**
   （当社サーバーへの送信ゼロ。名刺OCRの設計原則を引き継ぐ）。
3. 送信の途中で失敗しても「どこまで送れたか」が分かり、
   **同じ相手への二重送信なしに**残りから再開できる。

---

## 3. 背景と課題

- 名刺OCRアプリにより、名刺のメールアドレスは利用者ごとのスプレッドシート
  「名刺管理」に貯まる。次の課題は「集めた宛先への一斉連絡」である。
- メールソフトで手動BCC送信すると、(1) To/CcとBCCの取り違えで全宛先が
  互いに見える事故が起きうる、(2) 1通あたりの宛先数制限（無償Gmailは
  100件）を超えると手で分割する必要がある、(3) OCR由来の壊れたアドレスに
  気づきにくい。
- 台帳からのコピー＆ペースト自体も転記ミスの温床になる。台帳は
  こちらのシステムが作っているのだから、読み取りまで自動化する。

## 4. システム概要

### 4.1 全体構成

```
利用者のブラウザ（card-mail アプリ。静的配信）
  │ ① Google連携（drive.file + gmail.send。トークンはメモリ上のみ）
  │
  ├─② 台帳の解決（Drive API・検索のみ）
  │     マイドライブ / TSAM AI / 名刺データ / 名刺管理
  │
  ├─③ 宛先の読み取り（Sheets API）
  │     「名刺データ」タブの「メールアドレス」列**だけ**を読む
  │
  │ ④ ブラウザ内で検証・重複排除・100件ずつに分割
  │
  └─⑤ Gmail API（利用者自身のアカウントから送信。宛先は全員BCC）
        1束＝1通として、上から順に直列送信
```

当社サーバーはどこにも登場しない。通信先は Google の3系統
（Drive・Sheets・Gmail）と TSAM AI 認証系のみ（CSPで固定）。

### 4.2 なぜ台帳を読めるのか（v1.0 の誤りの訂正）

drive.file 権限は「**そのクライアントIDで作成したファイルだけ**」を
見せる。名刺台帳は名刺OCR（card-ocr）のクライアントIDで作られているため、
**本アプリは card-ocr と同じクライアントIDを使う**ことで、利用者ごとの
台帳をそのまま読める。アプリごとにIDを分けて見える範囲を切るのが
本来の方針（card-ocr config.js）だが、本アプリは「card-ocr の台帳を読む」
のが目的そのものなので、例外として共用する。

### 4.3 使用サービス

| サービス | 用途 | 備考 |
| --- | --- | --- |
| Google Identity Services | OAuth 認可（トークンモデル） | 承認済みの読み込み先のみ |
| Drive API | 台帳の検索・検証（読むだけ） | フォルダもファイルも**作らない** |
| Sheets API | メールアドレス列の読み取り | 他の列（氏名・住所等）は取得しない |
| Gmail API | 利用者自身のアカウントからの送信 | `gmail.send`（送信のみ。受信箱は読めない） |

## 5. 対象ユーザーとアクセス制御

- TSAM AI のログインユーザー（`guardPage()` を通る。名刺OCRと同じ）。
- Google連携は利用者本人の同意による。**drive.file と gmail.send の
  両方が付与されたことを検証し、片方だけなら進まない**（読めるのに
  送れない、という分かりにくい失敗を防ぐ）。
- 静的配信のためHTML/JSの取得自体は防げない（SECURITY_NOTES.md）。
  データを守るのは OAuth であって画面ガードではない（card-ocr と同じ整理）。

## 6. 前提条件

1. 利用者が名刺OCRアプリで名刺を登録済みで、台帳
   「マイドライブ / TSAM AI / 名刺データ / 名刺管理」が存在すること。
   **無い場合、本アプリは台帳を作らず**「先に名刺OCRで登録」と案内する。
2. **Google Cloud 側の作業（公開前・コードには現れない）:**
   card-ocr のクライアントの OAuth 同意画面に `gmail.send` スコープを
   追加すること。gmail.send は**制限付きスコープ**のため、一般公開には
   Google の審査（セキュリティ評価を含みうる）が必要。審査完了までは
   「確認されていないアプリ」警告が出る（テストユーザー登録で回避可能）。
3. 公開時に Portal のアプリ一覧（`public/portal/app-registry.js`）へ
   登録すること（§7.2 のとおり本書の実装には含めていない）。
4. デプロイは手動（`npm run deploy`）。`main` へのマージでは公開されない。

## 7. スコープ

### 7.1 含める機能

- Google連携（drive.file + gmail.send、トークンはメモリ上のみ）
- 台帳の解決（検索のみ）とメールアドレス列の読み取り
- 宛先の検証・重複排除・不正宛先の一覧表示
- 件名・本文（テキストメール）の入力
- 特定電子メール法の表示義務の確認（チェックボックス）
- 100件ずつのBCC分割・直列送信、進捗表示
- 途中失敗時の送信済み件数表示と、残りからの再開

### 7.2 含めない機能（現時点の判断）

| 機能 | 含めない理由 |
| --- | --- |
| Portal への掲載 | Google審査（§6-2）完了が先。掲載はレジストリへの1行追加で足りる |
| 宛先の選別（会社・タグ等での絞り込み） | まず全件送信で成立させる。絞り込みは台帳の列設計とセットで次版 |
| 宛名の差し込み（「〇〇様」） | 宛先ごとに1通ずつになり送信上限に触れやすい。必要になったら版を上げる |
| HTMLメール | テキストで足りる。HTML化は迷惑メール判定率とセットで検討 |
| 送信履歴のアプリ内保存 | 利用者のGmail「送信済み」が記録を兼ねる |
| 受信拒否（オプトアウト）の自動管理 | 台帳側の運用（§10）。自動化は台帳の列追加が要るため次版で検討 |

## 8. 業務フロー（利用者の操作）

1. Portal からアプリを開く（ログイン必須）。
2. 「Googleと連携する」を押し、**ドライブの読み取りとメール送信の両方**を許可する。
3. アプリが台帳から宛先を読み込み、次を表示する:
   送信できる宛先数／送信通数（100件ずつ）／重複としてまとめた件数／
   形式が正しくない宛先の一覧（**これらには送信されない**）。
4. 形式が正しくない宛先があれば、名刺管理シート側で直して
   「宛先を読み込み直す」を押す（直さず残りだけに送ることもできる）。
5. 件名・本文を入力する。**送信者の氏名・名称と受信拒否の連絡先を
   本文に記載し**、記載した旨のチェックを入れる（入れないと送信できない）。
6. 「送信する」→ 確認ダイアログ（件数・通数・取り消せない旨）→ 送信。
   進捗が「n / m 通」で表示される。
7. 途中で失敗したら、「どこまで送れたか」が表示される。原因を解消して
   もう一度「送信する」を押すと、**残りの束だけ**に送信する
   （送信済みの相手には再送しない）。

## 9. 機能要件

### FR-01 画面ガード

`guardPage()` を通るまで内容を描画しない（card-ocr と同じ）。

### FR-02 Google連携

- スコープは `drive.file` と `gmail.send` の2つのみ。**増やさない。**
- 両方の付与を検証し、欠けていれば案内して進まない。
- トークンはメモリ上のみ。Storage・URL・console・当社サーバーへ出さない。

### FR-03 台帳の解決（読むだけ・作らない）

- キャッシュ検証 → 名前・親・種別・未削除での検索、の順で解決する。
  **見つからなくても作らない**（空の台帳を作ると card-ocr の正本と
  競合する）。「先に名刺OCRで登録」と案内する。
- localStorage に入れるのは台帳の場所（ファイルID）だけ。

### FR-04 宛先の読み取り

- 「名刺データ」タブの見出し行から「メールアドレス」列を**位置ではなく
  見出しで**探す（card-ocr の列構成は版で増えるため）。
- **その列だけ**を読む。台帳の他の列（氏名・住所・電話等の個人情報）を
  取得しない。
- 見出しが見つからなければ、台帳の改変を疑う案内を出す。

### FR-05 宛先の検証・重複排除

- メールアドレスの形式でない値は送信対象から外し、**一覧で見せる**
  （黙って除かない。台帳の修正を促す）。
- 大文字小文字だけ違う宛先は1件にまとめ、同じ相手に2通送らない。

### FR-06 BCC送信と分割

- 宛先は**上から順に100件ずつ**の束にし、1束＝1通としてBCCで送る。
- **To・From ヘッダーを付けない。** To を付けないのは、他人のアドレスを
  晒せないことに加え、無償Gmailの「1通100宛先」上限にBCC100件が
  ちょうど収まるようにするため。From は Gmail が本人のアドレスを入れる。
- 1通ずつ直列に送る（失敗位置の確定と、レート制限への配慮）。

### FR-07 途中失敗と再開

- 失敗したら残りを打ち切り、**送信済みの件数・通数を表示する**
  （送ったメールは取り消せないため、この情報を最優先で残す）。
- 再開時は送信済みの束を飛ばし、残りの束だけを送る。

### FR-08 法令表示の確認

- 「本文に送信者の氏名・名称と受信拒否の連絡先を記載した」チェックを
  入れない限り送信ボタンを有効にしない（§10）。
- アプリは本文の中身を検査しない（できない）。確認は利用者の宣言による。

## 10. 法令・運用上の要件（利用者の責務。画面にも明示する）

- **特定電子メール法**: 名刺交換をした相手への広告宣伝メールは事前同意
  なしで送れる区分だが、本文に**送信者の氏名・名称と受信拒否の申出先**の
  表示義務がある。受信拒否の申出があった相手には以後送信しない
  （台帳側での管理を案内する）。
- **個人情報**: 宛先は第三者の個人情報である。取り扱いの責任は
  データを保有する利用者にある（名刺OCR §5.3 と同じ整理）。
- **Gmailの送信上限**: 1日あたりの上限（無償アカウントは500宛先程度）を
  超えると、Googleにより一時的に送信が止められる。アプリは上限を
  検知できないため、上限エラー時は日を改める案内を出すに留める。

## 11. セキュリティ要件

| 脅威 | 対策 |
| --- | --- |
| 宛先アドレスの相互漏えい | 全宛先をBCC。To/Ccを使わない |
| ヘッダーインジェクション（宛先・件名への改行差し込み） | 送信前に検査して例外で停止。宛先の形式検査でも改行・カンマを弾く |
| トークンの漏えい | メモリ上のみ保持。Storage・URL・console・例外メッセージに出さない |
| 台帳の破壊 | 本アプリは台帳へ**一切書かない**（読み取り専用） |
| 個人情報の過剰取得 | メールアドレス列だけを読む。他の列を取得しない |
| 当社サーバーへの漏えい | 通信先をCSPで Google 3系統＋認証系に固定。当社サーバーは登場しない |

## 12. 採用しなかった案とその理由

- **会社サーバーAPI方式（v1.0）**: 宛先を人が手渡しする必要があり、
  転記ミスと手間を生む。会社名義での代理送信になるため、お客様全員への
  開放と両立しない（認証を配れない）。台帳はこちらのシステムの作成物
  なので、名刺OCRと同じ連携で読み取りまで自動化できる。v1.1 で全面差し替え。
- **新規クライアントIDの発行**: drive.file はクライアントIDごとに見える
  範囲が分かれるため、新規IDでは card-ocr の台帳が見えない。共用が唯一の
  現実解（§4.2）。Picker で毎回ファイルを選ばせる案は、操作が増えるうえ
  取り違えの余地を作るため見送り。
- **card-ocr アプリへの機能追加**: card-ocr の要件定義書は通信先を
  3系統に限定しており（§12）、Gmail を足すには要件改訂と再審査が要る。
  独立アプリなら card-ocr の要件・実装・審査状態に触れずに済む。
- **サーバー経由の送信ログ保存**: 「当社サーバーへ送信ゼロ」の原則が
  崩れる。Gmailの「送信済み」で足りる。
- **gmail.readonly 等の追加**: 送信に不要。権限が広いほど審査と利用者の
  不安が重くなる。

## 13. 用語集

| 用語 | 意味 |
| --- | --- |
| BCC | 受信者に他の宛先を見せずに同じメールを届ける宛先欄。本アプリは全宛先をここに入れる |
| drive.file | 「そのクライアントIDのアプリが作ったファイルだけ」に絞ったドライブ権限。台帳を読める根拠（§4.2） |
| gmail.send | Gmailの**送信のみ**を許す権限。受信箱の閲覧はできない。Googleの制限付きスコープで、公開には審査が要る |
| トークンモデル | リフレッシュトークンを持たず、短命のアクセストークンだけで動くOAuthの形。静的サイト向け |
| 名刺管理 | 名刺OCRアプリが利用者のドライブに作るスプレッドシート。宛先の正本 |
