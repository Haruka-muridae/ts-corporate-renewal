### §1-1 Portal アプリとは

## §2 Portal アプリの統一設計原則

### §2-1 クライアント完結（サーバーコードゼロ）

**Portal アプリには、当社のサーバーコード（Apps Script・Node.js など）を含めない。**

- 全処理はブラウザ上で実行される（静的ホスティング）
- サーバーへのAPI通信を必要としない実装が前提
- 外部API（Google API など）への直接呼び出しは許可される

### §2-2 BYOK（Bring Your Own Key）型セキュリティモデル

**ユーザーの資格情報（APIキー・OAuthトークン）や個人データは、当社サーバーに送信しない。**

| 区分 | 扱い |
| --- | --- |
| APIキー（Gemini など） | ユーザーの端末にのみ保存（KeyStore） |
| OAuthトークン | メモリ上のみ。localStorage / sessionStorage / Cookie に書かない |
| ユーザーデータ | ユーザー自身のリソース（Google Drive、ローカルストレージ）に保存 |
| 分析ログ・監査ログ | 個人情報を含まない形でサーバーに送信してよい（実装例なし） |

当社が提供するのは「道具（静的アプリ）」。データの器はすべてユーザー自身のリソースである。

### §2-3 データ保存先

Portal アプリが生成したデータは、以下の場所に保存する。当社が管理するストレージは使わない。

| データ種別 | 保存先 | 例 |
| --- | --- | --- |
| 長期保存データ | ユーザーのマイドライブ | 領収書画像・音声ファイル・下書き |
| 端末ローカル | localStorage / IndexedDB | アプリの設定・ドラフト |
| 一時的なデータ | メモリ | セッション中の作業状態 |

### §2-4 秘密情報の取り扱い

**静的ホスティングではHTMLと JS の取得自体は防げない。** 秘密にすべき情報は必ずサーバー側に置く。

| 情報種別 | 置き場所 |
| --- | --- |
| APIキー・トークン | ユーザー端末のKeyStore、またはユーザー自身が管理する外部サービス |
| ビジネスロジック・ルール | 秘密にしたければサーバーAPI側。ブラウザへは配信しない |
| 利用者の個人情報・履歴 | ユーザー自身のリソース。当社が預からない |

詳細は [SECURITY_NOTES.md](../../SECURITY_NOTES.md) を参照。

## §3 共通機能要件

### §3-1 認証・認可

| 要件 | 定め |
| --- | --- |
| 認証方式 | TSAM AI の本認証系に準拠（[login-page-detailed-spec-v3.md](./login-page-detailed-spec-v3.md)） |
| アクセス制御 | `guardPage()` により、ログイン状態・有効性を確認。無効なら `/login/?next=portal` へリダイレクト |
| セッションキー | `tsam-auth-session`（本認証系と同一） |
| 部外者アクセス | URLを知っていても、認証なしでは該当アプリを開けない |

各アプリは以下を実装する：

```javascript
import { guardPage } from '../../auth/session.js';
import { setScreenDepth } from '../../auth/config.js';

setScreenDepth(2);                // 階層に合わせる
const user = await guardPage();
if (!user) return;                // ここで描画を止める
// 以下、ユーザーが有効な場合の処理
```

### §3-2 Gemini APIキー（BYOK）

**Portal の [keystore-spec-v1.md](./keystore-spec-v1.md) で定義される KeyStore を通じて管理。**

| 項目 | 定め |
| --- | --- |
| 保存場所 | ユーザーの端末の localStorage（`tsam-api-keys` という1つのキー） |
| 送信先 | Google AI API。当社サーバーには送信しない |
| 送信方法 | `x-goog-api-key` ヘッダー、または URL パラメータ |
| キー検証 | アプリが実行時に疎通テスト（1回だけ、参照系API）を行う |
| 失敗時 | KeyStore からは削除しない。ユーザーが「削除」を押すまで保持 |

### §3-3 認証確認と画面ガード

Portal のアプリグリッドに出すだけでは不十分。各アプリ自身に、以下のガードを実装する：

1. **ページロード時の認証確認** - `guardPage()` で有効性を確認
2. **無効時のリダイレクト** - `/login/?next=portal` へ送る
3. **トークン消去** - リダイレクト前にローカルのセッションキーを削除

理由: 静的ホスティングでは、URL を知っている人なら Portal 経由でなくても開ける。当社が守れるのはサーバー側のデータ（他ユーザーの情報など）であって、このアプリのソース公開は防げない。

## §4 ユーザーインターフェース要件

### §4-1 言語・表記

| 項目 | 定め |
| --- | --- |
| UI言語 | 日本語（一部英数） |
| 用語 | 統一用語集を参照。個別アプリで造語しない |
| 敬語 | です・ます調（カジュアルすぎない） |
| 日時表記 | YYYY年M月D日（漢数字） |
| 単位 | 円・分・秒など、記号ではなく字を使う |

### §4-2 レスポンシブ・アクセシビリティ

| 項目 | 定め |
| --- | --- |
| 対応幅 | 320px、375px、768px、1024px、1440px で確認。横スクロール不可 |
| ネイティブ要素 | `div` や `span` に `role` を付けるより、`button` `input` `select` など適切なネイティブ要素を使う |
| ARIA | ネイティブ要素の代替にしない。`aria-label` は最後の手段 |
| キーボード操作 | Tab キーで到達できる。Enter / Space で操作可能 |
| 読み上げ | 支援技術でも意図が伝わるテキストと見出し構造 |
| アニメーション | `prefers-reduced-motion: reduce` に対応 |

### §4-3 色・デザイン

| 項目 | 定め |
| --- | --- |
| 色 | `css/style.css` のカスタムプロパティ（`--c-*` / `--color-*`）のみ使用 |
| テーマ対応 | light / dark 両モードで正常に表示 |
| フォント | `public/css/` の共通スタイルに定義されたもの |
| 新規クラス定義 | 各アプリは専用の CSS ファイルを持つ。共通スタイルに新しいクラスを足さない |

### §4-4 エラーメッセージ

| 項目 | 定め |
| --- | --- |
| 形式 | 「◯◯◯ができませんでした。××××をご確認ください。」 |
| 情報量 | ユーザーが取りうるアクション（再度試す、設定を確認するなど）を示す |
| 技術情報 | HTTP ステータスコード・エラーコードは併記してもよいが、技術的説明だけで終わらせない |
| テンポラリーエラー | 時間をおいて再度試すよう案内 |

## §5 データ保存・プライバシー要件

### §5-1 個人データの非保存

当社が以下を保持しない：

- ユーザーが入力・生成した仕事上のデータ（下書き・スクリプト・文字起こし結果など）
- ユーザーが選択した設定・嗜好
- アクセス履歴・使用時間・生成内容の詳細

### §5-2 保存する場合の形式

アプリが記録してよいのは、以下の程度：

| 項目 | 例 |
| --- | --- |
| 集計値 | 「このアプリは月に1000人が使った」 |
| 匿名エラーログ | 「validation error が発生した」（何をバリデートしたかは記さない） |
| 機能の利用統計 | 「下書き機能は全体の30%が使っている」 |

### §5-3 ユーザーの端末外へ出さない情報

以下の情報は、ユーザーの端末を離れない：

- APIキー・トークン
- ファイルの中身（画像・音声・テキスト）
- 個人識別情報（メールアドレス・電話番号など）

## §6 テスト・品質要件

### §6-1 単体テスト

| 項目 | 定め |
| --- | --- |
| テストフレームワーク | Playwright（ブラウザテスト） |
| テスト場所 | `tests/unit/` 直下（アプリID が名前） |
| 実行コマンド | `npm run test:auth-system:unit`（全テスト） または `node tests/run.mjs audio-transcriber`（単一） |
| カバレッジ | 新機能・修正は関連ロジック全体をカバーする。既存機能に新しい警告を足さない |

### §6-2 ブラウザ確認

リリース前に以下を実機で確認する（テストでカバーできない部分）：

- Portal グリッドにカードが表示される
- アプリがロードできる
- 入力→出力の主要フロー（ゴールデンパス）が機能する
- エラー時のメッセージが正しく出ている
- レスポンシブ（320px、1440px）で問題ない

### §6-3 型チェック

```bash
npm run typecheck
```

を実行して型エラーが出ない状態を保つ。既存エラーを増やさない。

### §6-4 リント

```bash
npm run lint
```

実装範囲に新しい警告を足さない。既存の`public/` 配下のエラーは移行前からの既知状況であり、対象外。

## §7 Portal との連携要件

### §7-1 app-registry への登録

各アプリを Portal で公開する場合、`public/portal/app-registry.js` へ1件追加する。

```javascript
Object.freeze({
  id: 'アプリID',           // 一意・不変（配置データの識別子）
  name: '表示名',            // カードに出すユーザー向け名前
  icon: '文字または画像URL', // 1〜2文字 または `.svg/.png` 等
  href: 'production-app/app-name/', // サイト内相対パス（先頭 / なし）
}),
```

### §7-2 id の不変性

`id` は、ユーザーの端末に保存された配置データ（`tsam-app-layout` の `order`）が指す先である。

**後から変えると、利用者が並べ替えた位置が失われる。** 名前や置き場所は変えてよいが、id は変えない。

### §7-3 href の形式

| 形式 | 例 | 扱い |
| --- | --- | --- |
| 相対パス（先頭 / なし） | `production-app/voice-recorder/` | 同一サイト内。Portal と同じオリジン |
| 絶対URL | `https://example.com/app/` | 別サイト。新タブで開く（`target="_blank"`) |

**先頭に `/` を付けない。** Portal 側で `rootPath() + href` で相対リンク化するため、先頭スラッシュがあると `//production-app/...` になる。

### §7-4 Portal ロード時の処理

Portal のスクリプト（`portal.js`）は以下の順で実行される：

1. `guardPage({ next: 'portal' })` でサーバーへ問い合わせ
2. 有効と答えたときだけ `renderAppsGrid()` を呼ぶ
3. `APP_REGISTRY` から全アプリをロード
4. `app-layout.js` で配置データを読み込み、各カードを描画

各アプリは Portal からの参照を前提とするが、ダイレクトアクセス（URL直接入力）も考慮する。

## §8 セキュリティ要件

### §8-1 入力検証

| 項目 | 定め |
| --- | --- |
| クライアント検証 | UX のため、形式チェック等をする |
| サーバー検証 | サーバーAPI呼び出しがあれば、サーバー側でも検証 |
| 信頼できない入力 | ユーザー入力・ファイル・外部API応答は検証してから使用 |

### §8-2 XSS 対策

- HTML は生成しない。ユーザー入力を `textContent` へ。URL は`href` へ
- `dangerouslySetInnerHTML` 等の危険な API は使わない
- リンク先 URL は、ユーザー入力の場合は検証（`http://` または `https://` で始まる）

### §8-3 通信セキュリティ

| 項目 | 定め |
| --- | --- |
| 通信 | HTTPS のみ。HTTP での API 呼び出しなし |
| キー送信 | `x-goog-api-key` ヘッダー。URL パラメータは避ける |
| CORS | 明確に許可されたオリジンからのみ呼び出す |

### §8-4 CORS と PNA（Private Network Access）

ローカル補助サービス（VOICEVOX など）へアクセスする場合：

- CSP ヘッダーで許可されたオリジンのみアクセス可
- PNA の権限確認（`Permissions-Policy`）をサーバーで行う
- ブラウザ側で「プライベートネットワークへのアクセスを許可するか」確認が入る

実装例: `public/production-app/short-script/` の VOICEVOX 連携

### §8-5 localStorage / Cookie

| 項目 | 定め |
| --- | --- |
| localStorage | 設定・ドラフト・APIキーは保存してよい |
| SessionStorage | セッション中の一時データ |
| Cookie | 認証系（セッションキー）のみ。アプリが新規に作らない |
| 秘密情報 | localStorage でも、サーバーキーを扱わない |

## §9 パフォーマンス要件

### §9-1 読み込み時間

| 項目 | 目安 |
| --- | --- |
| HTMLロード | < 1秒 |
| JS解析・実行 | < 500ms |
| 初回描画 | < 2秒（画像ロード待ちを含まない） |

### §9-2 リソースの最適化

- 不要なライブラリを含めない
- 大きなファイル（画像・動画）は遅延ロード
- `dependencies` は `next` / `react` / `react-dom` のみ（外部SDK は fetch で直接呼び出し）

### §9-3 バンドルサイズ

- 新しいライブラリの追加は、事前に確認を取る（[AGENTS.md](../../AGENTS.md) §2）
- 既存の dependencies に追加する変更は、サイズ影響を評価する

## §10 運用・保守要件

### §10-1 バージョン管理

各アプリの仕様書ファイルには、以下のヘッダーを含める：

```markdown
# アプリ名 要件定義書

バージョン: v1.0
作成日: 2026年8月12日
最終改訂: 2026年8月12日
ステータス: 実装済み

## 改訂履歴

| 版 | 日付 | 内容 |
| --- | --- | --- |
| v1.0 | 2026-08-12 | 初版 |
```

### §10-2 変更管理

実装と仕様書のずれが見つかったときは、以下の対応をする：

1. **実装が正しい場合** - 仕様書を直す
2. **仕様書が正しい場合** - 実装を直す
3. **どちらが正しいか判断できない場合** - 実装前に報告（進めない）

「黙って放置」は禁止。コードと仕様書は常に揃った状態を保つ。

### §10-3 コメント・ドキュメント

| 項目 | 定め |
| --- | --- |
| コード内コメント | 「何をしているか」より「**なぜそうしたか**」を書く |
| 既知の制限 | コード内に記載。テスト対象外の機能は「理由を明記」 |
| 将来拡張 | TODO コメントは許可。ただし JIRA チケット等のID を付け、期限を示す |

本書と個別仕様書が矛盾する場合は、個別仕様書の記述を優先する。

## §12 設計判断の記録

### §12-1 なぜ「サーバーコードゼロ」なのか

当社が秘密にしたい情報（ビジネスロジック・キー）はサーバーに置き、
ブラウザ上の処理（UI・入力検証・外部API呼び出し）は静的に配信する。

こうすることで：
- 利用者がブラウザのコンソールで見られるのは UI ロジックだけ
- 利用者の個人データ・キーを当社が預からない
- スケーリングがシンプル（CDN での静的配信）

### §12-2 なぜ BYOK なのか

ユーザーが自分のキーを持つことで：
- 当社が責任を負う情報を最小限に限定
- 利用者が使用量・コストをコントロール可能
- 規制対応（個人データ保護）がシンプル

### §12-3 なぜ各アプリが認証を確認するのか

Portal に出ているだけでなく、URL を直接入力してアクセスするユーザーもいる。
静的ホスティングでは、サーバーが認証を強制できない。
だから各アプリ自身が `guardPage()` を実行し、無効な場合だけサーバーへ問い合わせる。
