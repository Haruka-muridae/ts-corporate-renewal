# セッション検証キャッシュ 仕様書 v1.0

対象: `workers/auth-verify/`
関連: [login-page-detailed-spec-v3.md](./login-page-detailed-spec-v3.md) §5・§8、[portal-spec-v1.md](./portal-spec-v1.md) §8、[SECURITY_NOTES.md](../../SECURITY_NOTES.md) §4

---

## §1 背景と目的

保護ページは `guardPage()` の結果を待ってから描画する。その検証は認証系 Apps Script への往復であり、実測値は次のとおりだった。

| 経路 | 実測 |
| --- | --- |
| 静的ファイル（Cloudflare） | 0.05〜0.10 秒 |
| `action=health`（シートを読まない） | 1.19〜1.63 秒 |
| `verifySession`（シート走査＋書き込み） | 1.85〜2.60 秒 |
| コールドスタート | 35.09 秒 |

`health` が 1.2 秒を切らないことから、**Apps Script 側をどれだけ最適化しても保護ページを開くたびに 1.2 秒超を下回れない**。これは規模の問題ではなく構造の問題である。

本仕様は、検証結果を Cloudflare 側で短時間キャッシュし、命中時 0.1〜0.2 秒にすることを目的とする。

## §2 適用範囲

**対象**: `verifySession` のみ。

**対象外**: ログイン・ログアウト・パスワード設定/再設定・Stripe・メール送信。これらはブラウザから Apps Script へ直接送る現行のままとする。**パスワードをこの Worker へ通さない**のは意図的な線引きである。

## §3 設計原則

**この Worker は判定しない。**

有効かどうかを決めるのは Apps Script（sessions シート）だけである。Worker がするのは「Apps Script が有効と答えた事実」を短時間覚えることに尽きる。

この原則から次が導かれる。

- **Apps Script 側の変更が不要**（第1段では 1 行も触らない）
- **新しい秘密鍵が不要**。Worker が Apps Script へ送るのは利用者のセッショントークンだけで、`verifySession` は元から公開エンドポイント
- **アカウント状態・契約状態の判定ロジックを複製しない。** 再検証のたびに Apps Script の既存判定がそのまま通るため、判定が二重管理にならない
- **ロールバックがフロントの宛先を戻すだけで済む**

## §4 失効反映の上限

現行は検証のたびにアカウント状態と契約状態を再評価している。本仕様はこれを明示的に緩和する。

| 事象 | 反映までの上限 |
| --- | --- |
| セッション自身の期限切れ | **0 秒**（キャッシュ値に期限を持ち、毎回比較する） |
| ログアウト | **最大 TTL** |
| パスワード変更に伴う全セッション失効 | **最大 TTL** |
| 契約状態の変化 | **最大 TTL** |
| 手動でシートを編集しての停止・失効 | **最大 TTL** |
| （Apps Script 不通時）上記すべて | **最大 grace（§6）** |

TTL は **30 分**とする。利用者の了承済み。

短くすると再検証が増え KV の書き込み（無料枠 1,000/日）を食う。15 分では 300 人規模で余裕が薄く、60 分では失効の遅れが目立つ。書き込みが枠に迫った場合の手当ては、まず TTL を延ばし、それでも足りなければ置き場を D1 へ移す（どちらも無料のまま）。

## §5 stale-while-revalidate を採らない

期限切れの記録を返しつつ裏で更新する形にすると、**失効反映の上限が TTL ではなく grace になる**。受け入れられたのは 30 分であって 12 時間ではない。

したがって期限が切れたら**必ず Apps Script へ問い合わせてから返す**。古い記録を使うのは Apps Script へ届かないときだけ。

体感は「30 分に一度だけ約 2 秒、あとは 0.1 秒」となる。

## §6 Apps Script 不通時の継続（grace）

Apps Script へ届かない間、キャッシュ済みの結果を **12 時間**まで使い続ける。セッションの既定寿命と同じ値にし、grace がセッション本来の寿命を超えないようにする。

grace 中は失効が一切伝播しない。これは可用性のための妥協であり、**上限を設けること自体が要件**である。

## §7 「無効」と「判定できない」を混ぜない

`public/auth/session.js` は `SESSION_INVALID` を受け取るとトークンを削除する。一方 HTTP が 2xx でなければ `NETWORK` として扱い、トークンを残す。

| 状況 | 返すもの |
| --- | --- |
| Apps Script が無効と答えた | **200** + `SESSION_INVALID` |
| Apps Script へ届かない / 応答が JSON でない / 設定漏れ / 想定外 | **5xx**（`SESSION_INVALID` を返さない） |

**これを取り違えると、Apps Script の障害のたびに全利用者のトークンが消える。**

Apps Script は実行時例外や権限エラーのとき JSON ではなく HTML のエラーページを返す。**これを「無効」と読み違えない。**

`SESSION_INVALID` 以外の失敗コード（サーバー側の一時エラー、ロック待ち）も「判定できない」に分類する。

## §8 応答の形

Apps Script の `verifySession` と**バイト互換**とする。フロントの改造点を「宛先の差し替え」に限るため。

```
成功: { success: true,  data: { user, expiresAt, remember } }
失敗: { success: false, error: { code, message } }
```

エラー文言も Apps Script 側と一字一句そろえる。

`X-Verify-Source` ヘッダーでどこから返したかを添える（`cache` / `origin` / `grace` / `expired` ほか）。秘密ではなく、切替後の効果測定に使う。フロントは読まない。

## §9 キャッシュに置くもの・置かないもの

**キー**: セッショントークンの SHA-256（16進）に接頭辞を付けたもの。

**値**: Apps Script が返した `data`（公開ユーザー情報・セッション期限・remember）と、鮮度・grace の期限。

**置かない**: 生のセッショントークン（キー名にも値にも）、パスワードのハッシュとソルト、シートの行番号。

「無効」の結果は 60 秒だけ覚える。覚えないと、無効なトークンを投げ続けるだけで Apps Script を叩き放題になり、この Worker が増幅器になる。

**KV には公開ユーザー情報（メールアドレス・ロール）が TTL の間だけ入る。**Cloudflare のダッシュボードを見られる運用者には可視である。

## §10 失敗時の振る舞い

- KV の読み書きが失敗しても処理を止めない。**キャッシュ無しとして Apps Script へ直行**する（遅くなるだけで判定は正しい）
- キャッシュと実体が食い違った場合、**シートが常に正**。キャッシュは「TTL 以内に肯定判定済み」の写しでしかなく、**否定判断には一切使わない**
- KV は予告なく消えることがある。単なるミスとして扱う

## §11 無料枠

想定を 300 人・1 日 20 回（悲観ケース 300 人・50 回）として試算した。

| 資源 | 無料枠/日 | 見込み | 判定 |
| --- | --- | --- | --- |
| Workers リクエスト | 100,000 | 3,600〜15,000 | ○ |
| KV 読み取り | 100,000 | 4,000〜30,000 | ○ |
| **KV 書き込み** | **1,000** | 400〜800（悲観時 1,800） | **要監視** |

静的ファイルは Workers Assets が直接返し Worker を起動しないため、リクエスト数を消費しない（`wrangler.jsonc` に `assets` があり `run_worker_first` 未設定）。

**課金が必要になり得るのは KV 書き込みのみ。**その場合の手当ては §4 のとおり、TTL 延長 → D1 への移行の順で、どちらも無料のまま対処できる。

副次的に Apps Script 側の負荷も減る（検証が TTL ごとに間引かれるため）。

## §12 段階的導入

| 段 | 内容 | 戻し方 |
| --- | --- | --- |
| 0 | Apps Script に keep-alive と掃除の定期トリガーを設定 | トリガー削除 |
| 1 | Worker を作成・デプロイ。**フロントは未接続** | 影響なし |
| 2 | `verifyApiUrl` を追加し、`verifySession` の宛先のみ切替 | 設定を戻して再デプロイ |
| 3 | （任意）即時失効の purge。**Apps Script の変更が初めて発生** | 未実施 |

第2段でも既存利用者のセッションは無変更で有効。トークンは不透明な文字列のままで、正本も Apps Script のままだからである。初回アクセスがキャッシュミスで一度だけ従来の速度になるだけ。

**第2段には CSP の追従が含まれる（v1.1 追記）。** `public/production-app/` 配下の保護ページは各自の `<meta>` CSP で `connect-src` を明示しており、宛先だけを切り替えると guardPage の fetch が**ページ自身の CSP に遮断される**。ログイン画面とポータルには CSP が無いため素通りし、「ログインもポータルも動くのに、アプリを開くとログインへ弾かれる」という気づきにくい形で現れる（2026-08-14 に実際に発生）。宛先を変えるときは、全保護ページの `connect-src` へ新しいオリジンを FQDN で足す（`*.workers.dev` にはしない。誰でも使える共有ドメインのため）。設定と許可リストの食い違いは `tests/unit/frontend.mjs` の「保護ページの CSP が verifySession の宛先を許可している」が全ページ横断で検査する。

## §13 テスト

`tests/unit/auth-verify-cache.mjs`。Workers ランタイムも Chrome も要らず、実時間も実通信も使わない。

固定している性質: キャッシュ命中で Apps Script を叩かないこと／期限切れで必ず問い合わせること／**判定できないときに「無効」と答えないこと**／応答の形が Apps Script と一致すること／生トークンが KV に現れないこと／grace の上限／KV 障害時の継続。

## §14 採用しなかった提案とその理由

**① 署名済みトークン（HMAC）でローカル検証する**

最も速いが、**鍵が漏れると管理者を含む任意の利用者になりすませる**。本方式の失敗コスト（キャッシュを消される＝遅くなるだけ）と比べて非対称が大きすぎる。アカウント状態を claim に焼き込むため鮮度確保の別機構も要る。数千人規模になり、かつ TTL の遅延が業務上許容できなくなった時点で再検討する。

**② KV や D1 にセッションを複製し、正本を二重化する**

Apps Script 側に「発行時に書き込む」経路が要る。二重書き込みの整合が難所で、失敗すると「ログインできたのに検証で落ちる」という最悪の症状になる。本方式は正本を一切増やさない。

**③ Apps Script 側で `CacheService` を使う**

シート I/O は減るが、**往復の下限 1.2 秒は残る**（§1）。効果が本方式に大きく劣る。

**④ クライアント側で検証結果を使い回す**

「保護対象の内容はサーバー確認が終わるまで描画しない」という規則を破る。この規則は `public/auth/session.js` 冒頭・SECURITY_NOTES §1・portal-spec §8・login-spec §7 の 4 か所で宣言されており、例外を作ると以後すべての保護ページで「どちらの規則か」を考え続けることになる。恒久に不採用とする。

**⑤ 検証結果の stale-while-revalidate**

§5 のとおり。失効反映の上限が TTL ではなく grace になるため。
