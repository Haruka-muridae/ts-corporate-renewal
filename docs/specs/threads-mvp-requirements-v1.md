## 2. システムの目的

TSAM AI の利用者が、Threads への投稿文を「書く/貼る/AIで作る」→ 下書きとして
残す → 本文入りの Threads 投稿画面を開いて投稿する、を1画面で行えるようにする。
**これ以外の機能は持たない**(予約投稿・複数媒体・分析・画像投稿は対象外)。

重点は次の順とする。

1. **最後の「投稿」は必ず人が押す**(intent リンク方式。誤投稿・二重投稿が
   構造的に起きない。Threads の API・トークンを使わない)。
2. 投稿文・下書き・履歴を**利用者の管理下から出さない**(端末内保存のみ。
   当社サーバーへの送信ゼロ。名刺OCR・領収書スキャナの設計原則を引き継ぐ)。
3. AI 生成は補助にとどめ、生成しただけでは何も起きない(保存・投稿は人の操作)。

## 3. 機能要件

### 3.1 認証・掲載

- Portal(`public/portal/app-registry.js`)にアプリID `threads-post` で掲載する。
  **`id` は後から変えない**(apps-grid-spec-v1.md §4-c)。
- ページ自身でも `setScreenDepth(2)` + `guardPage()` を行い、利用者が返るまで
  中身を描画しない(app-registry.js 冒頭の約束)。

### 3.2 投稿文の入力と検証

- テキストエリアで書く/貼り付ける。文字数カウント(コードポイント基準・
  上限500字)を常時表示し、超過は赤く示す。
- 検証(空・500字超)は intent リンクを開く前に行い、不合格なら開かない。

### 3.3 投稿(intent リンク)

- 「Threads で投稿」で、本文入りの投稿画面
  (`https://www.threads.net/intent/post?text=…`)を別タブ
  (`noopener,noreferrer`)で開く。**最後の「投稿」は人が押す。**
- 開いた事実を履歴に記録する(§3.5)。Threads へ fetch はしない
  (CSP の connect-src にも threads.net を入れない)。

### 3.4 下書き(端末内)

- 「下書き保存」で localStorage(`tsam-threads-post-v1`)へ追記。
  一覧から「呼び出す」「削除」(削除は確認あり)。
- localStorage が使えない環境では、保存が効かない旨を画面に出したうえで
  書く・生成する・投稿画面を開くだけは動かす。
- 壊れた保存データは読み捨て、次の保存で作り直す(アプリを止めない)。

### 3.5 履歴(端末内)

- 「投稿画面を開いた」を日時・本文つきで記録し、新しい順に表示する。
- intent 方式では「Threads 側で本当に投稿されたか」は観測できないため、
  記録は「こちらで起きたこと」まで。その旨を画面にも明記する。
- 保持は直近100件。超えた分は古い順に捨てる。

### 3.6 投稿文の生成(Gemini)

- 「テーマ・指示」(上限100字)から投稿文を1本生成し、**テキストエリアに
  入れるだけ**。下書き・履歴へは自動で書かない。入力中の本文がある場合は
  置き換え前に確認する。
- **実装の方針は台本メーカー(`../short-script/gemini.js`)と同一**:
  利用者自身のキーを KeyStore から都度読む(モジュールに保持しない)、
  キーは `x-goog-api-key` ヘッダー(URL に載せない)、外部SDKなし、
  主モデル 404 のときだけフォールバックへ1回切り替え(429/503 では
  再試行しない)、GeminiError のコード分類と画面向け文言・エラーコード
  (KEY-001 など)。エラー分類は複製であり import しない
  (repository-structure.md §4-1)。
- モデルは `gemini-2.5-flash-lite`(フォールバック `gemini-3.5-flash-lite`)。
  他の本番アプリと同じ選定。
- プロンプトで「500字以内・創作の禁止・誇張しない・投稿文そのものだけを出力」
  を課し、コードフェンスは剥がす。それでも超過したら §3.2 の検証が止める。
- キー未設定でも生成以外の機能は全部動く。未設定時は Portal での設定を促す
  案内を出す(キー入力欄をこのアプリに作らない。KeyStore の一元管理)。
- **書き方の調整プロンプト(v3.1)**: 生成セクションに常設のテキストエリアを置き、
  文体・トーンなどの指示(例:「です・ます調で」「絵文字は使わない」)を書ける。
  - 入力は**自動保存**(下書きと同じ端末内保存 `STORAGE_KEY` の `stylePrompt`。
    下書き・履歴の操作で消えない)。ページを開くと復元される。
  - 空でなければ、以後の生成のたびにプロンプトへ
    「# 書き方の調整(利用者設定)」としてテーマより前に差し込む
    (先頭2000字で頭打ち)。空にすれば使われない。
  - 本機能は X 版・note 版にも同形で載る(各差分仕様の基底)。

## 4. システム構成

```
public/production-app/threads-post/
  index.html   … 画面。CSP は meta で宣言(connect-src: self / Gemini / 認証GAS のみ)
  style.css    … auth.css の土台に乗せるアプリ固有の並び
  config.js    … 定数の集約(モデル・上限・保存キー)。秘密情報を置かない
  post.js      … 検証・intent リンク・端末内保存(下書き・履歴)
  gemini.js    … Gemini 呼び出し(台本メーカーと同方針・エラー分類は複製)
  app.js       … DOM の付け外しだけ。guardPage → 描画 → イベント接続
```

- 保存は localStorage のみ。Cookie・サーバー・Drive を使わない。
- OAuth(GIS)を使わないため、Google Cloud 側の作業は**無い**。

## 5. 画面要件(1ページ)

- 方式の説明(最後の投稿は自分で押す)を常時表示
- テーマ・指示+「AIで生成」/キー未設定時は Portal への案内
- テキストエリア+文字数カウント/「下書き保存」「Threads で投稿」
- 下書き一覧(呼び出す・削除)/履歴一覧(記録範囲の注記つき)
- 保存領域が使えない環境への注記
- セマンティックHTML・`prefers-reduced-motion` 対応(AGENTS.md)

### 5.1 表示条件(v3.2。X 版・note 版にも同形で適用する)

**機能は変えない。出す・出さないと、まとめ方だけを決める。**

- **下書き・履歴は0件のあいだセクションごと出さない。** 見出しと空の一覧、および「下書きはまだありません。」は、初めて開いた利用者に何も伝えないまま画面を2段ぶん占めていた。1件目が保存された時点で現れる(描画のたびに `hidden` を付け外しする)。
  - **履歴の「記録されるのは『投稿画面を開いた』ことまで」の注記もセクションの中に置く。** この注記は履歴という記録が存在して初めて意味を持つ(§3.5 の要件そのものは変えない。0件のときに読ませないだけである)。
- **「書き方の調整」は `<details>` に畳む。** 一度決めたら触らない設定に近く、常時開いていると「毎回書くもの」に見える。**畳んでも保存と反映は従来どおり**で、開かずに生成しても保存済みの指示は使われる(§3.6)。ラベルは summary と重複するため視覚的には隠し、読み上げには残す。
- **キー未設定の案内は「Gemini APIキーが未設定です。」で始め、導線のリンク文言を「ポータルで設定する」にそろえる**(本番アプリ共通)。
- **フッターに「ポータルへ戻る」を置く**(他の本番アプリと同じ、素のテキストリンク)。

## 6. テスト

`node tests/run.mjs threads-post`(Node のみ・Chrome 不要)。
画面(app.js)は DOM の付け外しだけなので、ロジック層を直接固定する。

| 対象 | 固定する挙動 |
| --- | --- |
| post.js | 500字検証(コードポイント基準)、intent URL のエンコード、下書きの保存/一覧/削除、履歴の記録と100件上限、壊れた保存データの読み捨て |
| gemini.js | キーはヘッダーで URL に載せない、テーマ・500字・創作の禁止がプロンプトに載る、404 のみフォールバック、429 は再試行しない、状態分類(400/401/429/503)、空応答、キー未設定は通信しない |

## 7. セキュリティ・運用方針

- 当社サーバーは投稿文・下書き・履歴を**受け取らない**(送信先は Gemini と
  認証確認のみ。CSP で固定)。
- Gemini キーは利用者自身のもので、KeyStore(端末内)だけが扱う。
- アクセス制御はクライアント側ガード(`guardPage()`)が主。静的配信のため
  HTML/JS の取得自体は防げない(SECURITY_NOTES.md)。守るべきデータが
  端末内にしか無いため、これで足りる。

## 8. 導入・運用

- 配信は本リポジトリの `main` へのコミット+手動デプロイ(`npm run deploy`)のみ。
  Meta・Google Cloud 側の作業は無い。
- 利用者側は、AI 生成を使う場合のみ Portal で Gemini キーを設定する。

## 9. 採用しなかった提案とその理由

| 提案 | 不採用の理由 |
| --- | --- |
| Threads Graph API + 長期トークン方式(v1.0) | トークン方式が必須なのは無人の予約投稿だけ。60日トークン・Meta 審査・実地確認のコストに見合わない(v2.0 での判断を継続) |
| 予約リマインダーを本アプリに含める(v2.x) | 静的配信にはサーバーもトリガーも無く、閉じたブラウザからは何も送れない。**全く別機能として実装する**(発注者の判断・2026-08-12)。旧実装 `gas-threads/` を下敷きに、gas-notifier のような基盤を検討 |
| 下書き・履歴の Drive/Sheets 保存 | OAuth(GIS)とスコープ管理が付いてくる。端末内保存なら当社サーバー送信ゼロのまま審査不要。端末をまたぐ必要が出た時点で再検討 |
| キー入力欄をこのアプリに置く | KeyStore の一元管理(ポータルで設定)に反する。他の本番アプリと同じ導線にする |
| エラー分類の共有モジュール化 | repository-structure.md §4-1 の「import はしない」方針。複製で運ぶ |
| 自動再試行(429/503) | 結果は変わらず無料枠のクォータを削るだけ(台本メーカーと同じ判断) |
