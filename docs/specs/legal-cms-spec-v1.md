# 法務文書のスプレッドシート管理（Legal CMS）仕様書 v1

対象範囲: `gas-auth/Legal.gs` / `gas-auth/LegalSeed.gs` / スプレッドシート「TSAM AI 法務文書」 / `legal/terms/` `legal/privacy/` `legal/tokusho/`

制定: 2026年7月31日

---

## §1 目的と役割分担

`/legal/` 配下の3文書（利用規約・プライバシーポリシー・特定商取引法に基づく表記）を、
専用スプレッドシートで編集し、公開操作で静的HTMLを再生成して GitHub（`main`）へコミットする。

| 担当 | 役割 |
| --- | --- |
| スプレッドシート「TSAM AI 法務文書」 | 編集画面。**条文の正本はここ** |
| `gas-auth/Legal.gs` | 静的HTMLの生成と公開 |
| GitHub（`main`） | 版管理。公開のたびにコミットが積まれる |
| GitHub Pages | 配信 |

**配信は従来どおり静的HTML**である。閲覧のたびに Apps Script を呼ばないため、
GAS が止まっても法務ページは表示できる。可用性を落とさないための構成であり、
「スプレッドシートを直接読んで描画する」方式は採らない。

### §1-1 生成物であること

`legal/terms/index.html` `legal/privacy/index.html` `legal/tokusho/index.html` は
**生成物**である。手で編集してはならない。次回の公開で上書きされる。

生成HTMLの冒頭（`<!doctype html>` の直後）に、次の印が必ず入る。

```html
<!doctype html>
<!-- GENERATED FILE: 編集はスプレッドシート「TSAM AI 法務文書」から。
     直接編集禁止(次回公開で上書きされます) -->
```

`<!doctype html>` より前に置かないのは、宣言前の内容を嫌う古い実装を避けるため。

`docs/legal-source/*.md` は**初期移行の原本（アーカイブ）**であり、現在の正ではない。

## §2 スプレッドシート構成

ファイル名: `TSAM AI 法務文書`（マイドライブ/TSAM AI/Auth/）
Script Property: `AUTH_LEGAL_SPREADSHEET_ID`

認証設定スプレッドシートとは別ファイルにする。開く目的が違うため、
条文の編集中に運用設定へ触れてしまう事故を防ぐ。

### §2-1 `meta` シート

文書共通のヘッダ情報。

| 列 | 内容 |
| --- | --- |
| `doc_id` | `terms` / `privacy` / `tokusho` |
| `title` | `<h1>` に出る文書名 |
| `subtitle` | 見出し下の小見出し。空なら出力しない |
| `established_date` | 制定日（例: `2026年7月30日`） |
| `revised_date` | 改定日。空なら「改定」を出力しない（§5-3 で自動更新） |
| `version` | 版（例: `1.0`） |

制定・改定・版は `2026年7月30日 制定 ／ 2026年8月20日 改定 ／ Version 1.0` の順で
1行に組み立てる。空の項目は詰めて出力する。

### §2-2 `terms` / `privacy` シート（条単位）

粒度は**条単位**。1行が1条にあたる。

| 列 | 内容 |
| --- | --- |
| `block_id` | 一意ID（`t01` `p01` …）。空行は無視される |
| `heading` | 条見出し（例: `第1条（適用）`）。**空なら前文**として見出し無しで出力 |
| `body` | 本文。書式は §3 |
| `sort_order` | 表示順（昇順） |
| `enabled` | `TRUE` 以外の行は出力されない |

### §2-3 `tokusho` シート（表の行単位）

| 列 | 内容 |
| --- | --- |
| `row_id` | 一意ID（`k01` …） |
| `item_label` | 項目名（例: `販売事業者`）。**空なら表の前に置く前文** |
| `item_value` | 内容。書式は §3 |
| `sort_order` | 表示順（昇順） |
| `enabled` | `TRUE` 以外の行は出力されない |

前文は `sort_order` を表の行より小さくして先頭へ置く。

## §3 `body` / `item_value` の書式規約

条文はスプレッドシートから来る。**HTMLタグは書けない**（§3-6）。
必要な構造は、次の最小限の記法だけで表す。

### §3-1 段落

空行で段落が分かれる。前後の空白だけの行も空行として扱う。空行が続いても空の段落は作らない。

```
一つ目の段落。

二つ目の段落。
```

### §3-2 段落内の改行

段落の中の単一改行は `<br>` になる。住所や連絡先のように、
行を積み上げて読ませたい箇所で使う。

```
事業者名：TSアセットマネジメント合同会社
住所：神奈川県逗子市久木8丁目8番26号
```

### §3-3 箇条書き（`ul`）

行頭の `- `（半角ハイフン＋空白）または `・` で箇条書きになる。
`・` のあとの空白は任意。

```
- 一つ目
・二つ目
```

### §3-4 番号付きリスト（`ol`）

行頭の `1. `（半角数字＋ピリオド＋空白）で番号付きリストになる。

**書いてある番号は使わない。** 出力される番号は `ol` の並び順で振り直される。
条を挿入したときに以降の番号を振り直す手間をなくすため。

数字が行頭にあっても、直後がピリオド＋空白でなければリストにならない。
`1年間継続した場合の目安` はそのまま段落になる。

### §3-5 入れ子（1段のみ）

行頭を**半角スペース2つ以上、または全角スペース1つ以上**で字下げすると、
直前の項目にぶら下がる。

```
1. 当社は、次の場合を除き、本人の同意なく個人データを第三者へ提供しない。
  1. 法令に基づく場合。
  2. 人の生命、身体又は財産の保護のために必要である場合。
2. 決済処理のため、当社は Stripe に…
```

入れ子は**1段まで**。2段目を字下げしても1段目と同じ並びに入る。
条文の階層がそれ以上深くなるなら、条を分けたほうが読みやすい。

直前に親となる項目が無い状態で字下げした行は、通常の項目として扱う。
半角スペース1つでは字下げと見なさない（誤入力と区別できないため）。

### §3-6 HTMLタグは書けない

`<` `>` `&` `"` `'` はエスケープして出力する。
`<script>` と書いても文字として表示されるだけで、タグにはならない。

**エスケープしてから §3-7 の差し込みを展開する。**
順序が逆だと、編集者の入力で差し込み結果のタグを壊せてしまう。

### §3-7 差し込み記法

| 記法 | 展開結果 |
| --- | --- |
| `{email}` | `<a href="mailto:architect@potenitas.com">architect@potenitas.com</a>` |
| `{terms}` | `<a href="../terms/">利用規約</a>` |
| `{privacy}` | `<a href="../privacy/">プライバシーポリシー</a>` |
| `{tokusho}` | `<a href="../tokusho/">特定商取引法に基づく表記</a>` |

同じ記法が1行に何度出ても、すべて展開される。
知らない記法（`{foo}`）はそのまま文字として残る。

リンクはすべて**相対パス**である。ドメインを書かないため、
独自ドメインでもプロジェクトページのサブパスでも同じHTMLが動く。

宛先を変えるときは `gas-auth/Config.gs` の `LEGAL_CONTACT_EMAIL` と `LEGAL_LINKS` を直す。
条文側を一括置換する必要はない。

## §4 生成されるHTML

テンプレートは既存の `/legal/` の見た目をそのまま踏襲する。
スタイルは `auth/auth.css` を共有し、`Legal.gs` はCSSを持たない。

- `<h1 class="auth-card__title">` … `meta.title`
- `<p class="auth-legal__meta">` … `subtitle` と制定・改定・版
- `<div class="auth-legal__body">` … 本文
  - `article` … `<h2>` ＋ 段落・リスト
  - `table` … 前文の `<p>` ＋ `<table class="auth-legal__table">`
- `<div class="auth-links">` … 他の2文書と `/pricing/` への導線（自分自身へは出さない）

### §4-1 表の罫線

`.auth-legal__table` は、行の境界が二重線にならないよう、
隣り合うセルで片側ずつ罫線を落としている。

768px 以上では **2行目以降の** `th` `td` から上罫線を落とす。
`tr + tr` を付けずに `td` 全体から落とすと1行目にも効き、
表の上辺が `th` の幅（34%）で途切れて**右上角が開く**。

この欠けは `tests/browser/auth-screens.mjs` の
「法務ページの表：四辺の罫線が閉じること」で、
320 / 375 / 768 / 1024 / 1440px の5幅について機械的に検査する。

## §5 公開フロー

### §5-1 `previewLegalDocs()` — 公開せずに見た目を確かめる

GAS エディタから実行する。GitHub には**一切触らない**。

3文書のHTMLを生成し、`マイドライブ/TSAM AI/Auth/preview/` へ
`legal-preview-<doc_id>.html` として書き出し、実行ログにURLを出す。
同名のファイルがあれば中身を差し替えるため、実行するたびに増えることはない。

### §5-2 `publishLegalDocs()` — 公開する

GAS エディタから**手動で**実行する。

**セル編集での自動公開（`onEdit` トリガー）は設けない。**
書きかけの条文がそのまま本番へ出るのを防ぐため、公開は明示実行だけとする。

1. `GITHUB_TOKEN` が未設定なら、作成手順を案内して中断する（§6）
2. 3文書のHTMLを生成する
3. GitHub Contents API で既存ファイルを取得し、内容が同じ文書はスキップする
4. 変更のあった文書だけをコミットする
5. 実行ログへ「変更された文書 / スキップされた文書 / コミットURL / Pages反映まで1〜2分」を出す

### §5-3 改定日の扱い

改定日は**コミットの前に**確定させ、確定後のHTMLを送る。

公開したあとに改定日を書くと、載っている日付と実際の公開日がずれるだけでなく、
次回の比較で必ず差分が出るため、条文を直していなくてもコミットが積み上がる。

- 既存ファイルの内容が変わったとき … `revised_date` を公開日（日本時間）に更新し、生成し直してから送る
- 新規作成のとき … 改定日は入れない（**制定であって改定ではない**）

版（`version`）は自動で上げない。実質的な改訂を行うときは、
運用者が `meta` の `version` を手で上げてから公開する。

### §5-4 コミット

コミットメッセージ:

```
docs(legal): publish from spreadsheet (<doc_id>, … / v<version> / <ISO日時>)
```

同じ公開回のコミットは、文書が複数でも同じメッセージにする。
版が文書ごとに違う回は `v1.0+1.1` のように連結する。

**Contents API は1ファイル＝1コミット**である。
2文書以上が同時に変わった回は、同じメッセージのコミットがその数だけ並ぶ。
Git Data API を使えば1コミットにまとめられるが、
差分の追跡しやすさより実装の単純さを優先した。

### §5-5 `TOS_VERSION` との連動

`meta.version` が前回公開時から変わっていると、実行ログに警告を出す。

```
【警告】terms の版が 1.0 → 1.1 に上がりました。
認証設定シートの TOS_VERSION も更新が必要です（現在: 1.0）。
```

`TOS_VERSION` は申込み時に取得した同意の版であり
（[pricing-consent-spec-v1.md](./pricing-consent-spec-v1.md)）、
規約を改訂したのに据え置くと、**古い版で同意した申込みを受け付け続けてしまう**。
逆に上げると、その時点で画面を開いていた利用者の同意は無効になり、再読込が必要になる。

前回公開時の版は Script Property `LEGAL_PUBLISHED_VERSION_<doc_id>` に記録する。

## §6 GitHub トークン

`Script Properties` の `GITHUB_TOKEN` を使う。
`SECRET_KEYS` に入れてあるため、**設定シート経由では読めない**。
実行ログにも返り値にもシートにも出さない。

未設定のときは `publishLegalDocs()` が手順を案内して中断する。
1バイトも送信しない。

作成手順は [../instructions/2026-07-31-github-token.md](../instructions/2026-07-31-github-token.md)。
要点は Fine-grained personal access token を **対象リポジトリのみ / Contents: Read and write のみ** で作ること。

公開先は設定シートの `GITHUB_REPO`（`owner/repo`）と `GITHUB_BRANCH`（既定 `main`）で決める。
こちらは秘密ではないため設定シートで変更できる。

## §7 初期データの移行

`importLegalDocsFromCurrent_()` が、制定時点の3文書（Version 1.0）をシートへ投入する。

**シートが空（ヘッダーのみ）のときだけ**投入する。
運用開始後に `setupAuthSystem()` を実行しても、編集済みの条文を上書きしない。

投入するデータは `gas-auth/LegalSeed.gs` にある。
これは公開中のHTMLから機械変換したものであり、手で書き写していない。
**投入後の正本はスプレッドシートであり、`LegalSeed.gs` を直しても公開物は変わらない。**

| シート | 行数 |
| --- | --- |
| `meta` | 3 |
| `terms` | 24（前文＋第1条〜第23条） |
| `privacy` | 17（前文＋1.〜16.） |
| `tokusho` | 26（前文＋25項目） |

移行結果は `tests/unit/legal.mjs` が検証する。
生成HTMLの読める内容が、移行前の公開HTML（`tests/fixtures/legal-published/`）と
**完全に一致**することを確かめている（タグ構造の違いは許容）。

## §8 設計判断の記録

### §8-1 スプレッドシートを直接読んで描画しない

法務ページの表示に Apps Script を挟むと、GAS の障害・実行上限・レイテンシが
そのまま法務文書の閲覧不能につながる。特定商取引法の表記は
「申込み前にいつでも確認できる」ことが求められるため、可用性を落とせない。

### §8-2 `onEdit` トリガーを置かない

セル編集での即時反映は、書きかけの条文をそのまま公開してしまう。
条文は「途中の状態」が外部に出てはならない種類の文書であるため、
公開は明示実行だけとした。プレビュー（§5-1）で確認の手段は用意している。

### §8-3 入れ子を1段に限る

現行の3文書で必要な階層は1段だけである（プライバシーポリシー §6）。
一般的なマークアップ言語をまるごと持ち込むと、
編集者が書ける構造と生成側が保証できる構造がずれていく。
必要な分だけを規約として定め、テストで固定した。

### §8-4 書式規約に §3-2（段落内改行）と §3-5（入れ子）を足した

当初の指示にあった規約は「空行・箇条書き・番号付きリスト・差し込み・エスケープ」の5つだった。
しかし現行のプライバシーポリシーには `<br>` で積み上げた事業者情報と、
1段の入れ子リストがある。この2つが無いと**移行前の内容を再現できない**ため、
規約として明文化したうえで追加した。

### §8-5 番号を振り直す

`3. ` と書いてあっても3番目として出さず、並び順で振り直す。
条を1つ挿入したときに以降すべてを書き直す運用は、必ず抜けが出る。

## §9 テスト

| スイート | 内容 |
| --- | --- |
| `tests/unit/legal.mjs` | 書式規約のパース、エスケープ、生成HTML、移行結果の一致、GitHub API（モック）、プレビュー |
| `tests/browser/auth-screens.mjs` | 法務ページの表示、罫線が四辺で閉じること（5幅×3ページ）、草案痕跡ゼロ、リンク、登録番号 |
| `tests/fixtures/legal-published/` | 移行前の公開HTML。一致検証の基準 |

`tests/fixtures/legal-published/` は移行が内容を落としていないことを示す唯一の証拠であり、
生成側に合わせて書き換えてはならない。
条文を正式に改訂したときは、改訂内容とともに更新する。
