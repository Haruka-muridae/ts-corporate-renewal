# カレンダーURL通知アプリ 要件定義書 v1

対象範囲: `public/production-app/calendar-url-notifier/` ／ `gas-notifier/`（配布テンプレートの拡張） ／ `workers/notifier-gate/src/constants.mjs`（`FEATURE_RULES`）

制定: 2026年8月13日／同日 実装・本番公開

Portal への並び方は [apps-grid-spec-v1.md](./apps-grid-spec-v1.md) が、
通知基盤の設計理由は [notifier-design-notes.md](../notifier-design-notes.md) が持つ。
本書は**このアプリが何をするか**だけを定める。

---

## §1 位置づけ

Google カレンダーの予定の開始前に通知を出し、**通知を操作した端末でだけ、
その予定に紐づく URL を開く**アプリ。

録音アプリ（`public/production-app/voice-recorder/`）のカレンダー通知と
**同じ Push 基盤を使うが、別のアプリとして Portal に並ぶ**。
録音アプリ側の通知の挙動は変更しない。

| | 録音アプリの通知 | 本アプリ |
| --- | --- | --- |
| 目的 | 予定の開始前に録音を促す | 予定に紐づくページを開く |
| 遷移先 | 録音画面（固定） | **予定ごとに変わる URL** |
| `feature` | `calendar` | `openurl` |

### §1-1 なぜ ntfy ではなく既存基盤なのか

先行検討では Google Apps Script から ntfy.sh へ publish する構成を作った。
セットアップは軽いが、**予定名と URL が公開の中継サーバーを経由する**。

通知基盤は「運営へ渡るのは予定の骨格だけ」という前提で作られている
（[notifier-design-notes.md](../notifier-design-notes.md) §3）。
Portal に並ぶ本番アプリが、その前提を満たさない経路で予定名を外へ出すと、
利用者から見て**同じ画面から入る2つのアプリで扱いが違う**ことになる。
ntfy 版は検証用として `~/calendar-notify-gas` に残し、本番へは持ち込まない。

## §2 開く URL の決め方

通知タップ時に開く URL は、利用者の Apps Script が予定から解決する。
**上から順に探し、最初に見つかったものを採る。**

| # | 出どころ | 検証 |
| --- | --- | --- |
| 1 | 説明欄の `OPEN_URL:` 行 | HTTPS ＋ 許可ホスト |
| 2 | 場所欄が URL の場合、その値 | 同上 |
| 3 | 説明欄の中で最初に見つかった URL | 同上 |
| 4 | Google Meet のリンク | Google 生成のため検証を免除 |
| 5 | その予定の Google カレンダー画面（`htmlLink`） | 同上 |

**5 があるので、URL を書いていない予定でもタップ先が必ずある。**
1〜3 が検証に落ちた場合、通知を取り消さずに 4→5 へ回す。
「通知が出ること」と「知らないサイトを開かされないこと」は別に扱う。

### §2-1 予定ごとの通知時刻

説明欄に `OPEN_BEFORE: <0以上の整数>` があれば、その予定だけ通知時刻を上書きする。
無ければ設定画面の既定値を使う。

上書きは骨格の `timingMin` に載せて判定へ渡す。
`timingMin` は既に `ALLOWED_EVENT_FIELDS` にあり、**新しい項目を運営へ増やさない。**

### §2-2 URL は運営へ渡らない

URL は `notify_queue` / `sent_log`（利用者のスプレッドシート）にだけ置き、
Service Worker が `pending` で取りに来るときに返す。

判定（`/v1/evaluate`）へ送る骨格には URL を含めない。
含めても Workers 側の `validateEvents` が要求ごと拒否する
（[constants.mjs](../../workers/notifier-gate/src/constants.mjs) `ALLOWED_EVENT_FIELDS`）。
**「送らないよう気をつける」ではなく「送れない」側で守る。**

## §3 機能要件

| ID | 要件 |
| --- | --- |
| FR-01 | 時刻付きの予定を通知対象とする。終日予定は対象外 |
| FR-02 | 通知時刻は「予定開始 − 通知分数」。分数は §2-1 の順で決まる |
| FR-03 | 通知タイトルに予定名、本文に開始までの時間を出す |
| FR-04 | 通知本体のタップで §2 の URL を開く |
| FR-05 | アクションボタンにも予定名を載せる（「〈予定名〉を開く」） |
| FR-06 | 登録済みの全端末へ通知が届く。URL を開くのは操作した端末だけ |
| FR-07 | 同じ予定・同じ通知分数で二重に送らない。開始時刻が5分以上動いたら送り直す |
| FR-08 | 予定に書かれた URL は HTTPS のみ採用する。許可ホストを設定できる |
| FR-09 | 設定画面で、通知分数・出欠フィルタ・許可ホストを変更できる |
| FR-10 | 設定画面から接続テストとテスト通知を実行できる |
| FR-11 | 直近の通知予定を設定画面で確認できる |

FR-07 の「5分」は既存の判定
（[evaluate.mjs](../../workers/notifier-gate/src/evaluate.mjs) `isAlreadyNotified`）を
そのまま使う。本アプリのために閾値を変えない。

## §4 判定ルール（ゲート側）

`FEATURE_RULES` へ1行足す。

```js
export const FEATURE_RULES = {
  calendar: { attendanceFilter: true,  allDayFilter: true },
  openurl:  { attendanceFilter: true,  allDayFilter: true },
};
```

未登録の `feature` は通らない作りになっているため、**この1行が無いと
テンプレートを配っても通知は1件も出ない**（`unknown-feature` で落ちる）。

### §4-1 出欠フィルタを引き継ぐ

先行検討の ntfy 版は「欠席と回答した予定も通知する」形だった。
本アプリでは `attendanceFilter: true` とし、既存と揃える。

理由は Portal に2つの通知アプリが並ぶことにある。
同じカレンダーの同じ予定について、片方は通知し片方はしない状態を
利用者に説明できない。フィルタの有無は設定画面で切り替えられる（FR-09）。

## §5 画面

`public/production-app/calendar-url-notifier/`。既存アプリと同じ構成にする。

| 要素 | 内容 |
| --- | --- |
| アクセス制御 | `guardPage()`。Portal に出さないだけでは URL を知る人が開ける |
| セットアップ | テンプレートのコピー → ウィザード → 引き継ぎリンクの受け取り |
| 設定 | 通知分数・出欠フィルタ・許可ホスト |
| 状態 | 接続状態、直近の通知予定、最後のエラー |
| 試す | 接続テスト、テスト通知 |
| Service Worker | Push 受信 → `pending` 取得 → 通知表示 → クリックで `data.url` を開く |

スタイルは `css/style.css` のカスタムプロパティだけを使い、
このアプリ専用の色を新しく定義しない。

### §5-1 Service Worker の遷移先

録音アプリの Service Worker は遷移先が固定（録音画面）だが、
本アプリは `pending` が返した `openUrl` を開く。

`openUrl` が空だったとき、および `pending` を取得できなかったときは、
**このアプリの画面を開く通知**にする（直近の通知予定を確認してもらう）。

通知を出さない選択は採らない。`userVisibleOnly: true` で購読している以上、
Push を受けて何も表示しないと、ブラウザが購読を打ち切ることがある。
代わりに、**行き先を持たない「開く」ボタンは出さない。**
押しても何も起きないボタンを作らないためである。

`purpose` が `openurl` でない通知（録音アプリ向け）は、この Service Worker では表示しない。
1つの通知シートで両方が動くため、`pending` には他方の通知も混ざる。

## §6 データ

配布テンプレートのシートへ列を**末尾に**足す
（[notifier-design-notes.md](../notifier-design-notes.md) §2-3）。

| シート | 追加する列 | 内容 |
| --- | --- | --- |
| `notify_queue` | `openUrl` | 通知タップ時に開く URL |
| `sent_log` | `openUrl` | 同上（`pending` が返す） |

`purpose` は既存の列をそのまま使い、本アプリの通知には `openurl` を入れる。

`upcoming`（GAS の API）の応答には `feature` を添える。
1つのシートで2機能が動くため、これが無いと設定画面（FR-11）が
録音アプリ側の予定まで「URL が開く通知」として並べてしまう。

---

## §7 Portal への登録

アプリ一覧はスプレッドシート（暫定DB）から取る（[apps-grid-spec-v1.md](./apps-grid-spec-v1.md) §15）。
**`public/portal/app-registry.js` には足さない。** あそこは取得失敗時の
フォールバックで、`localhost` を指す3件だけであることがテストで固定されている（同 §14-3）。

| 列 | 値 |
| --- | --- |
| A: アプリID | `calendar-url-notifier`（後から変えない。同 §5-1） |
| B: アプリ名 | カレンダーURL通知 |
| C: アプリURL | `production-app/calendar-url-notifier/` |
| D: アイコンURL | 未定（省略すると名前の1文字目になる） |

**この行の追加は運営者の操作である。** シートは Google Workspace 側にあり、
リポジトリの変更では反映されない。

---

## §8 やらないこと

- 録音アプリの通知の挙動を変えること
- 通知の判定ロジックを利用者側へ戻すこと
- 利用者の操作なしに URL を開くこと（モバイル OS で成立しない）
- 予定変更後に、すでに配信済みの通知を取り消すこと
- 秒単位の配信時刻の保証（TTL 5分の設計は [notifier-design-notes.md](../notifier-design-notes.md) §6-2）

## §9 テスト

| 場所 | 確認 |
| --- | --- |
| `tests/unit/notifier-gate.mjs` | `openurl` が判定を通る／未登録の feature は通らない／URL を含む要求は拒否される |
| `tests/unit/`（新規） | URL 解決の優先順位／HTTPS 以外と許可ホスト外を採らない／フォールバックで通知が消えない／`OPEN_BEFORE` の解釈 |
| `tests/browser/`（新規） | 未ログインのリダイレクト／配信HTMLの `hidden`／設定の保存と読み戻し／320〜1440px で横あふれ無し |
| `tests/unit/frontend.mjs` | Portal のアプリ一覧に `localhost` を足していない（既存の検査が落ちないこと） |

判定の検査は既存スイートへ足す。新しいランナーを増やさない。

## §10 着手前に決めたこと（2026-08-13 確定）

| ID | 事項 | 決定 |
| --- | --- | --- |
| **Q-01** | 配布テンプレートを既存と共用するか、分けるか | **共用（確定）。** 利用者のスプレッドシートと接続キーを2組に増やさないため。配布済みのコピーは、コードを貼り替えるまで URL通知だけが使えない（録音通知は動き続ける） |
| Q-02 | 許可ホストの既定値 | **空（制限なし）。** 許可外の URL は採用しないだけで通知は残るため（§2）、既定を絞ると「なぜ予定ページが開くのか」が分かりにくい |
| Q-03 | アイコン | **設定しない。** 名前の1文字目が出る（apps-grid §14-2） |

### §10-1 共用にしたことで発生した制約

キューの行キー（`gas-notifier/Store.gs` の `queueKey_`）は、
**`calendar` のときだけ従来の形（`eid|timing`）を保つ。**

全機能に `feature` を足すと、すでに配布済みのシートにある行と形が変わり、
更新直後の同期で同じ予定が「新しい行」として積み直される。
既存の形を保てば、増えるのは新機能ぶんの行だけで済む。

## §11 採用しなかった提案とその理由

| 提案 | 理由 |
| --- | --- |
| ntfy.sh を使う | 予定名と URL が公開の中継サーバーを通る（§1-1） |
| 録音アプリの通知に統合し、行き先の一種として扱う | 本番稼働中・受け入れ済みの機能の仕様変更になる。重複は残るが、影響範囲を切るほうを採った |
| URL をゲートへ渡し、判定と一緒に返す | 運営が予定の中身を持たない設計（§2-2）を崩す |
| URL の無い予定は通知しない | 「予定があるたびに必ずタップできる」という利用者の要件に反する。§2-5 のフォールバックで満たす |
| `public/portal/app-registry.js` へ直接足す | 取得失敗時のフォールバック定義であり、本番の登録先ではない（§7） |
