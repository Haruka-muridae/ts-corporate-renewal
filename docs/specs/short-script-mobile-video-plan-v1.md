## 1. 目的と方針

### 1.1 なぜスマホ完結か

現行の音声・動画生成(short-script-spec-v1 §13)は、利用者のPCで動くローカル補助サービス(ai-video-app)+VOICEVOX を前提とする。この構成は実証済みだが、**利用者に「PCを持っていて、アプリをセットアップできる」ことを要求する**。ショート動画の主な投稿者はスマホだけで完結したい層であり、PC前提は利用の入口で大半を落とす。さらに Windows 向けセットアップ配布のワークストリームは凍結した(§7)ため、PC前提を新規利用者へ広げる道も閉じた。

そこで第3段階は、**お客様のスマホ(ブラウザ/PWA)だけで「台本生成 → 音声合成 → 字幕付き縦型動画(1080×1920、30秒)の書き出し → 写真アプリへ保存」を完結させる**。

### 1.2 なぜ月額0円のままか

本ポータルの原則(short-script-spec-v1 §0.1、keystore-spec-v1)は「当社が提供するのは道具であり、利用者のデータも資格情報も当社サーバーへ送らない。サーバーコードはゼロ」である。動画生成をクラウド(当社サーバーまたは外部SaaS)へ出すと、

* 当社に従量課金の原価が生じ、月額0円が崩れる。
* 台本・音声・画像という利用者の生成物が当社(または第三者)のサーバーを通る。これは名刺OCR以来の「送信しない」原則の放棄である。

よって**すべての処理を利用者の端末内で行う**。当社の追加コストは静的ファイルの配信のみ(Cloudflare Workers の既存無料枠内)。台本生成の Gemini 呼び出しだけは従来どおり BYOK(利用者のキー・利用者の課金)で、これは第1段階から変わらない。

### 1.3 決定済みの前提(利用者承認済み)

* 音声は VOICEVOX/ずんだもんを**断念**し、ブラウザ内ローカル実行できる TTS として **piper-plus(話者:つくよみちゃん、モデル約38MB、MIT)** を第一候補に採用する。断念理由は §7 に記録する。
* クラウド生成は**不採用**(§7)。
* Windows 配布ワークストリーム(ai-video-app のセットアップ配布)は**凍結**(§7)。
* 動画合成は ffmpeg.wasm を**不採用**とし、「Canvas + JASSUB + WebCodecs + Mediabunny」構成を採用(§2・§7)。

## 2. アーキテクチャ

### 2.1 処理フロー

すべて端末内。どの段でもネットワーク送信は発生しない(台本生成の Gemini 呼び出しを除く。それも利用者キーで Google へ直接)。

```
台本 { title, scenes[] }            … 第1段階の生成物をそのまま食う(§8.3 の JSON と同形)
   │
   ▼ ① 音声合成(piper-plus + onnxruntime-web。完全オフライン)
シーンごとの PCM(WAV) ──► 実測音声長で各シーンの seconds を確定
   │                          (音ズレ防止。秒数の明示指定をしない方針は v1.5 §7.7 と同じ)
   ▼ ② 字幕(ASS)生成
buildAss(scenes)               … ai-video-app lib/subtitle.ts の複製(§2.4)
   │
   ▼ ③ フレーム合成(1080×1920・30fps・30秒 ≒ 900フレーム)
Canvas: 背景画像の Ken Burns 描画(ズーム/パンを自前計算)
  + JASSUB(libass の wasm)が ASS をラスタライズ → Canvas へ重ねる
   │
   ▼ ④ エンコード・多重化
WebCodecs VideoEncoder(H.264、ハードウェア)
WebCodecs AudioEncoder(AAC) ──► Mediabunny で MP4 へ多重化
   │
   ▼ ⑤ 保存
Web Share API(navigator.share({files}))で写真アプリへ
(不可なら <a download> フォールバック)
```

各部品の役割と選定理由:

| 部品 | 役割 | なぜこれか |
| --- | --- | --- |
| piper-plus + onnxruntime-web | 日本語TTS(端末内) | npm 配布・ブラウザ完全オフライン動作・RTF 0.078(30秒音声を約2.3秒で合成)。モデル38MB・MIT。品質は M1 で実機確認する(§5)。 |
| Canvas 2D | 背景の Ken Burns 描画 | 現行 ai-video-app は FFmpeg zoompan で実現している効果を、`drawImage` の矩形計算で再現する。GPU 支援があり 30fps 生成に足る。 |
| JASSUB | ASS 字幕のラスタライズ | libass の wasm 移植。現行の ASS 生成ロジック(§2.4)を**そのまま**活かせる。字幕を独自 Canvas 描画で作り直すと、縁取り・折り返し・タイミングの挙動が PC 版と乖離する。 |
| WebCodecs | H.264 + AAC エンコード | 端末のハードウェアエンコーダを使う唯一のブラウザAPI。ソフトエンコード(ffmpeg.wasm)の速度・メモリ問題(§7)を回避する。Clipchamp が同系構成の実運用例。 |
| Mediabunny | MP4 多重化(mux) | エンコード済みチャンクをコンテナへ詰めるだけの純JSライブラリ。wasm 不要・小さい。 |
| Web Share API | 写真アプリへの保存 | iOS で「ファイル」ではなく写真ライブラリへ直接渡せる標準経路。ユーザー操作起点が必須のため、完成後に「保存する」ボタンで発火する。 |
| Screen Wake Lock | 生成中の画面消灯防止 | 生成は最大でも数十秒〜数分かかる。画面が消えるとタブがサスペンドされ生成が死ぬため、生成中のみ取得し、完了・失敗・`visibilitychange` で解放する。 |

### 2.2 設計上の制約と判断

* **SharedArrayBuffer を要求しない。** onnxruntime-web・JASSUB はマルチスレッド(SAB)版と単スレッド版を持つ。SAB には COOP/COEP ヘッダ(cross-origin isolation)が要り、`next.config.ts` でサイト全体へ波及する(認証の Apps Script 疎通や他アプリを巻き込む)。RTF 0.078 なら単スレッドで足りる見込みのため、**単スレッド wasm を採用**し、ヘッダ変更をしない。M1 で実測し、足りない場合のみ COOP/COEP をこのアプリのパスに限定して足す案を再検討する。
* **CSP(meta)の変更は最小にする。** wasm 実行のため `script-src` へ `'wasm-unsafe-eval'` を追加し、Worker 起動のため `worker-src 'self' blob:` を追加する。`connect-src` は**変えない**(全アセットが同一オリジンだから。§4 の推奨案の帰結)。現行の `http://127.0.0.1:3000` 系の許可は companion 経路の扱い(§2.3)に従う。
* **UA 判定をしない。** 経路の選択(§3)は `VideoEncoder.isConfigSupported()` 等の機能検出だけで行う。UA 文字列は偽装・変動があり、iPadOS は Mac を名乗る。
* **解像度ネゴシエーション。** Android の一部端末は 1080p H.264 のハードウェアエンコードに失敗する(w3c/webcodecs #397)。`isConfigSupported` を 1080×1920 → 720×1280 → 540×960 の順に試し、最初に通った解像度で生成する。字幕・Ken Burns は PlayRes 基準の相似縮小なので見た目は保たれる。どの解像度になったかは画面に表示する(黙って劣化させない)。
* **メモリ設計。** 900フレームを貯めない。フレームは生成→エンコード投入→ `close()` を逐次行い、エンコーダの `encodeQueueSize` でバックプレッシャをかける。iOS Safari の wasm/タブのメモリ上限(旧機種 約1.5GB)を超えないことが ffmpeg.wasm 不採用の理由そのものであり、採用構成でも同じ規律を守る。

### 2.3 PC 利用(companion 連携)との共存方針

比較した2案:

| 案 | 利点 | 欠点 |
| --- | --- | --- |
| A: 自動判別で併存(スマホ=端末内、PC=従来の ai-video-app 連携) | PC の VOICEVOX 品質を使い続けられる | 生成経路が2系統になり、3状態判定(§13.3)・テスト・ヘルプ・エラー文言を**二重に**維持し続ける。Windows 配布凍結により、新規PC利用者へ補助サービスが広がる見込みもない |
| B: 端末内生成に一本化 | 経路が1本。WebCodecs はデスクトップ Chrome/Edge でも動くため、**PCでも同じ端末内生成が使える**。保守対象が減る | 既存のPC利用者の声(ずんだもん)が つくよみちゃん に変わる。VOICEVOX 品質を好む利用者には後退 |

**推奨は B(端末内生成への一本化)**。ただし段階を踏む:

1. M1 の実機品質確認に合格することを一本化の条件とする。
2. M2 では端末内生成を**既定**とし、companion 連携(`companion.js`・3状態判定・エンジン起動ボタン)はコードを残したまま UI を「PCアプリで作る(上級者向け)」の折りたたみへ退避する。**新機能は足さない(凍結)**。
3. M3 完了後、利用実態を見て companion 経路の削除を**別途判断**する(削除時は short-script-spec-v1 §13 の廃止改訂と CSP から `127.0.0.1` 許可の除去を同時に行う)。

なぜ即時削除しないか:v1.5 で作り込んだ 3状態判定は現に動いており、壊すだけの変更を品質確認前に行う理由がない。なぜ自動判別にしないか:判別条件(「PCらしさ」)が UA 判定になりがちで §2.2 の方針に反し、かつ2系統維持の固定費が残るため。

## 3. 対応環境マトリクス

経路は3本。すべて機能検出で選ぶ(§2.2)。

| 環境 | 判定 | 経路 |
| --- | --- | --- |
| iOS Safari 26+ | `VideoEncoder` あり かつ AAC の `AudioEncoder.isConfigSupported` が通る | **高速経路**:WebCodecs(H.264+AAC)+ Mediabunny。生成は実時間より速い |
| iOS Safari 16.4〜25 | `VideoEncoder` はあるが AAC エンコード不可 | **リアルタイム経路**:`canvas.captureStream()` + 音声は AudioContext の `MediaStreamDestination` → `MediaRecorder`(`video/mp4`)。**30秒の動画に実時間30秒かかる**。生成中は Wake Lock とプレビュー表示で「録画中」であることを示す |
| iOS 16.3 以前 | `VideoEncoder` なし | **非対応案内**:音声(WAV)の再生・保存と台本コピーまで提供し、動画化は「iOS を更新してください」と案内する |
| Android Chrome 94+ | `isConfigSupported` の結果による | 高速経路。ただし (a) 1080p 失敗端末は §2.2 の解像度ネゴで降格、(b) AAC 不可端末(ライセンス起因で存在)はリアルタイム経路へ降格 |
| デスクトップ Chrome/Edge | 同上 | 高速経路(§2.3 の一本化により PC も同じ経路) |
| デスクトップ Safari/Firefox | 検出結果による | 検出に従い高速→リアルタイム→非対応の順に落ちる |

補足:

* リアルタイム経路の `MediaRecorder` は `mimeType: 'video/mp4'` を第一候補にし、非対応なら `video/webm` は**採用しない**(写真アプリ・SNS 互換のため。webm しか吐けない環境は非対応案内へ)。
* いずれの経路でも生成中は Screen Wake Lock を取得する。取得失敗(旧ブラウザ)は続行し、「画面を消さないでください」を表示する。

## 4. アセット配信設計(25MiB 制約への対処)

### 4.1 制約

本番配信は Cloudflare Workers(OpenNext、`wrangler.jsonc`)で、静的アセットは **1ファイル 25MiB 上限**がある。piper のつくよみちゃんモデル(約38MB)はそのままでは置けない。onnxruntime-web の wasm も版によっては上限に迫る。

### 4.2 対処案の比較

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| a: 分割配置+結合ロード | 25MiB 超のファイルを `*.part1` / `*.part2` に割って同梱し、ブラウザで fetch → ArrayBuffer 結合 → SHA-256 検証してから使う | **同一オリジンのまま**。CSP 変更不要・外部可用性に依存しない・`check:vendor` の SHA-256 慣行に載る・オフライン(PWA)キャッシュも単純 | リポジトリにバイナリ約70MBが入る。結合ローダーを書く必要がある(数十行) |
| b: 外部CDN参照(Hugging Face 等)+CSP 追加 | モデル・wasm を外部から取得 | リポジトリが軽い | **利用の事実が第三者へ漏れる**(IP・タイミング)。「どこにも送信しない」と説明する画面から第三者への通信が出るのは説明を濁す。外部の可用性・改変リスク、`connect-src` 拡大、SRI をかけても運用が増える |
| c: モデルの量子化縮小(25MiB 未満へ) | int8 量子化等で 38MB → 約20MB を狙う | 分割不要・DL量減 | **音質劣化が未検証**。M1 の品質確認(ただでさえ合否判定)に変数を1つ足すことになる。量子化パイプラインの保守も増える |

**推奨は a(分割配置+結合ロード)**。なぜなら本ポータルの原則は「同一オリジン・送信しない・ベンダリング」であり、a だけがこの3つを全部満たす。c は a の**後続最適化**として有望(成功すれば分割が不要になり DL 量も減る)なので、M1 で余力があれば量子化版の聴き比べも行うが、設計は a を前提に組む。

実装規律:分割は機械的なバイト分割とし、マニフェスト(`vendor-manifest.json`:ファイル名・分割数・各パートと結合後の SHA-256・総バイト数)を同梱する。ローダーはマニフェストを読んで結合し、**SHA-256 が合わないアセットは使わない**(壊れた動画を黙って作らないため)。

### 4.3 同梱(ベンダリング)候補一覧

AGENTS.md の「外部ライブラリ追加は事前承認」に従い、承認後 external-dependency-approvals.md へ記録し、NOTICE と SHA-256 を `check:vendor` に載せる。サイズは概算であり **M1 で実測して確定する**。

| 依存 | 用途 | ライセンス | 概算サイズ | 置き場所(案) | 25MiB 分割 |
| --- | --- | --- | --- | --- | --- |
| piper-plus(JSランタイム) | TTS 呼び出し | MIT | 数百KB | `public/production-app/short-script/vendor/piper/` | 不要 |
| つくよみちゃん ONNX モデル+設定JSON | 音声モデル | MIT(モデル)。**話者利用条件としてクレジット表記「つくよみちゃん」が必要** → アプリ内とヘルプに表記 | 約38MB | 同上 `model/` | **要(2分割)** |
| onnxruntime-web(JS+wasm) | ONNX 推論 | MIT | JS 約0.5MB+wasm 約10〜25MB(版依存) | `vendor/ort/` | 実測して超過分のみ |
| JASSUB(JS+worker+wasm) | ASS ラスタライズ | JASSUB: MIT / libass: ISC | 約5〜8MB | `vendor/jassub/` | 不要見込み |
| Mediabunny | MP4 多重化 | MPL-2.0(要確認) | 約0.5MB | `vendor/mediabunny/` | 不要 |
| 日本語サブセットフォント(Noto Sans JP サブセット) | 字幕フォント | SIL OFL 1.1 | 約3〜8MB | `vendor/fonts/` | 不要 |

### 4.4 初回ダウンロード量とキャッシュ戦略

* 初回合計は**実測81.8MB**(§4.3の見積り約70MBより増えた分は、piperのG2P wasmがOpenJTalk+NAIST-JDICを含む多言語一体配布のため約58MBに達したこと。日本語のみに絞った軽量版は上流に無い)。Wi-Fi 推奨の旨と進捗バー(バイト数ベース)を必ず出し、**利用者の明示操作(「音声データを準備する」ボタン)で開始する**。画面を開いただけで 70MB を落とし始めない(GIS 承認記録 1-1 の「無条件に外部通信を発生させない」と同じ規律。同一オリジンでも通信量への配慮は同じ)。
* キャッシュは **Cache Storage** に versioned キー(`short-script-vendor-v1`)で保存し、2回目以降はネットワークへ行かない。Service Worker は M3 の PWA 化で導入し、それまでは fetch→Cache Storage 直書きのローダーで足りる(Service Worker なしでも Cache Storage API は使える)。
* iOS はサイト未訪問が続くと(目安7日)スクリプト書き込みのストレージを削除しうる。**消えても再ダウンロードで復旧するだけ**であり、整合性は SHA-256 検証(§4.2)が守る。ヘルプに「しばらく使わないと再ダウンロードが発生する」旨を書く。
* PWA 化(M3)では Service Worker はアプリシェル(HTML/CSS/JS)を precache し、巨大アセットは上記 Cache Storage 運用のまま(SW の precache に 70MB を入れると更新のたびに再取得の危険があるため分離する)。

#### 4.4.1 M1実装で判明した事項(独立レビュー指摘への対応。改訂履歴0.2)

M1の初回実装では、上記の「2回目以降はネットワークへ行かない」が実際には成立していなかった(独立レビューで確定)。原因と対応を以下に記録する。

* **キーの不一致(修正済み)**: `prepareAllAssets`(手順1「音声データを準備する」)は結合後の論理パス(`asset.path`)をキーに `cache.put` していたが、`loadPiperWasmModule`(piperの分割wasmを読む処理)は分割パート(`part.path`)をキーに `cache.match` していたため、キーが一致せず常にmissし、合成のたびに約58MBを再取得していた。`mobile-lab/vendor-loader.mjs` の `assetVirtualUrl()` にキー計算を一本化し、`getVerifiedAssetBytes()` / `getVerifiedAssetBlobUrl()` という単一の取得入口(初回: 分割fetch→結合→SHA-256検証→Cache Storage保存、2回目以降: `cache.match`)を経由させることで解消した。バイナリ資産(piper G2P wasm・onnxruntime-web wasm・JASSUB wasm・フォント)は例外なくこの入口を通り、**2回目以降は実測どおりネットワーク不要**になる。
  * onnxruntime-web(wasm本体)は `env.wasm.wasmBinary` に検証済みバイト列を直接渡す(URLを経由しないため取得漏れが起きない)。
  * JASSUBのwasm・フォントは検証済みバイト列から Blob URL を作り、`wasmUrl`/`modernWasmUrl`/`availableFonts` に渡す(JASSUBのWorkerは `fetch(受け取ったURL)` でこれらを取得する実装であることをソースで確認済み。Blob URLはfetch可能)。
  * piper G2P wasmは既存どおり `wasmLoader` DI(ArrayBuffer直渡し)を使う。
* **JSモジュールの残存ギャップ(検証は追加、実行経路は未解消)**: `ort.wasm.min.mjs`・`jassub.js`・JASSUBのWorker本体(`worker.js`)・`mediabunny.min.mjs`・piper-plus本体(`src/index.js`)は、いずれも `vendor-manifest.json` の検証対象に追加し、手順1の時点でバイト取得とSHA-256検証を行うようにした。ただし**実行そのもの(`import()`)は同一オリジンへの再取得のままであり、「検証したバイト列」と「実行したバイト列」が完全に一致する保証はまだ無い**。これはBlob URL化すると相対import(同ディレクトリ内の他ファイル参照)が壊れるためで、jassub.js・piper-plus本体・onnxruntime-web(グルーJS)のいずれも同様の理由でこの経路を採る。**完全なオフライン化と実行バイトの完全一致保証はM3のService Worker導入時に行う**(§5 M3)。
* **初回ダウンロード実測**: 81.8MB(バイナリ資産のみ。上記のJS検証対象追加により合計は約81.9MBへ微増したが、増分は数十KB程度でJSファイル自体は小さい)。

## 5. 実装マイルストーン

### M1: 音声+書き出しの体験試作(品質のゲート)

**目的:利用者がスマホで「声の品質」と「生成時間」を判断できる最小物を出す。** つくよみちゃんの品質が不合格なら以降は組まない(§2.3 の一本化条件)。

* 一時検証ページ `public/production-app/short-script/mobile-lab/`(guardPage 保護。M2 で本体へ統合後に削除)。ローカルでは KeyStore も HTTPS 制約も満たせないため、**実機確認はプレビュー/本番配信で行う**(short-script-spec-v1 §0.3 と同じ事情)。
* 内容:固定の短い台本 → piper 合成 → 再生。続けて背景1枚+字幕で 1080×1920/30秒 MP4 を書き出し、写真アプリへ保存。
* ベンダリング承認(§4.3)と分割ローダー(§4.2)はここで入れる。
* **完了条件**:(1) 利用者の実機(iPhone・可能なら Android 1台)で音声品質を合否判定できた、(2) 30秒動画の生成時間と成功可否を iOS 高速経路/リアルタイム経路の両方で実測した、(3) アセット実サイズと初回DL体験を実測した。

### M2: 台本メーカー統合

* 本体の「音声・動画を作る」パネルへ端末内生成を既定として統合。AI生成・貼り付け・セグメント編集(背景画像 `segmentImages` を含む)の3入力すべてから動画化できる。
* シーン秒数を実測音声長で確定し、ASS(複製した subtitle ロジック)と Ken Burns を全シーンへ適用。
* companion 連携を折りたたみへ退避(§2.3)。
* **完了条件**:(1) 3入力いずれからも実機で MP4 を書き出せる、(2) 字幕の見た目(13字×2行・白文字黒縁・下部中央)が PC 版と一致、(3) 既存の第1段階の完成定義(v1.5 §12)を壊していない、(4) 新規 lint 警告ゼロ。

### M3: 仕上げ

* 経路フォールバック(§3)の全実装:機能検出→高速/リアルタイム/非対応の出し分け、解像度ネゴ、AAC 不可時の降格。
* Wake Lock、生成進捗(`aria-live`)、保存導線(Web Share → a[download] フォールバック)、失敗時のエラーコード整備(§9 の流儀で `VID-xxx` 系を新設)。
* PWA 化:manifest+Service Worker(アプリシェルのみ precache。§4.4)。
* ヘルプ改訂:つくよみちゃんクレジット表記、初回DL・再DL、非対応環境の案内。仕様書(本書→仕様書への昇格 or short-script-spec の改訂)を揃える。
* **完了条件**:(1) §3 の各行を実機・実ブラウザで1回ずつ通した記録がある、(2) ヘルプ・クレジット表記・承認記録・NOTICE が揃っている、(3) companion 経路の扱い(温存/削除)の判断が記録されている。

## 6. テスト戦略

既存の流儀(tests/run.mjs:スイートを別プロセスで実行、`assert.mjs` の `check/section/finish`、実サービスへ通信しない、DOM 前提コードはソース静的検証。先例 `tests/unit/short-script-companion.mjs`)に載せる。

**Node で検証できるもの**(純関数に切り出すことが実装の設計条件):

| 対象 | 検証内容 |
| --- | --- |
| `subtitle.mjs`(複製) | `chunkText` の句読点優先分割・強制分割、`wrapChunk` の2行折り返し、`buildAss` の時刻書式・比例配分。**ai-video-app 側のテスト値と同じ入出力で回し、複製が乖離していないことを固定する** |
| タイムライン計算 | 実測音声長 → 各シーンの開始秒・Ken Burns パラメータ(ズーム率・パン)の算出 |
| 経路選択 | 機能検出結果(真偽値の組)を引数に取る純関数が、§3 のマトリクスどおりの経路・解像度を返すこと(WebCodecs 本体はスタブ) |
| 分割ローダー | マニフェスト解釈・パート結合・SHA-256 不一致時の拒否(`crypto.subtle` は Node にもある) |
| ベンダー整合 | `check:vendor` 方式で同梱物の SHA-256 と NOTICE の突き合わせ |
| ソース静的検証 | `index.html` の CSP に `'wasm-unsafe-eval'` / `worker-src` があること、`innerHTML` 不使用、Wake Lock の取得・解放呼び出しの存在 |

**実機頼みのもの**(自動化しない。M1/M3 の完了条件として手動確認の記録を残す):

* piper の音質・RTF、onnx/wasm の実メモリ。
* WebCodecs のエンコード成否(とくに Android 端末差)、MediaRecorder の `video/mp4` 出力。
* Web Share → 写真アプリ保存、Wake Lock の実効。
* Playwright での自動化は**しない**。承認範囲が録音アプリ E2E に限られており(approvals 1-2)、かつ headless 環境にハードウェアエンコーダが無く「実機で動く」ことの証明にならない。広げる場合は改めて承認を取る。

## 7. 採用しなかった案とその理由(short-script-spec-v1 §14 に相当)

| 案 | 却下の理由 |
| --- | --- |
| VOICEVOX/ずんだもんの継続(スマホでも) | VOICEVOX は**ローカルエンジン必須でブラウザ版が存在しない**。スマホにエンジンを立てる手段がなく、wasm 移植も配布物の規模・保守の点で現実的でない。声の同一性より「スマホ完結」を優先し、ブラウザ内ローカル実行できる piper-plus(つくよみちゃん)へ乗り換える。**利用者承認済み(2026-08)** |
| クラウド生成(当社サーバー/外部SaaSでの TTS・動画合成) | 月額0円が崩れる(従量原価が当社に発生)。利用者の台本・音声・画像がサーバーを通り、「どこにも送信しない」原則(§0.1 系)に反する。障害点と規約依存も増える |
| ffmpeg.wasm での動画合成 | iOS Safari のメモリ制約(旧機種 約1.5GB、wasm32 の上限 2GB)に 1080p×30秒の合成が収まらず、ソフトエンコードは実時間の数倍かかる。ハードウェアエンコーダ(WebCodecs)+Canvas/JASSUB 構成(Clipchamp と同系)で置き換える |
| ネイティブアプリ(iOS/Android) | 開発者登録の年会費・審査・配布の固定費が月額0円方針に反する。ブラウザ/PWA で全処理が端末内実行できる以上、ストアを介す理由がない。KeyStore(同一オリジン localStorage)との同居もできない |
| Windows 配布(ai-video-app セットアップ)の継続 | スマホ完結が成立すれば PC 前提の配布は主経路でなくなる。二正面の保守(インストーラ・エンジン起動系 v1.5 §13.3 と、本書の端末内生成)は割に合わない。**凍結**(廃止ではない。既存利用者の companion 経路は §2.3 の判断まで温存) |
| 外部CDN(Hugging Face 等)からのモデル配信 | §4.2 案b のとおり。第三者への通信が発生し「送信しない」の説明を濁す。同一オリジン分割配置で足りる |
| SAB(マルチスレッド wasm)前提の構成 | COOP/COEP がサイト全体へ波及する。単スレッドで性能が足りる見込みのため要求しない(§2.2。実測で覆れば限定適用を再検討) |
| 字幕の独自 Canvas 描画(JASSUB を使わない) | 折り返し・縁取り・タイミングの挙動が PC 版(libass/FFmpeg)と乖離し、ASS 資産(subtitle ロジック)を捨てることになる。wasm 1個分のサイズ増のほうが安い |

## 8. リスクと未解決事項

| リスク/未解決 | 影響 | 手当て |
| --- | --- | --- |
| piper(つくよみちゃん)の音質が利用者基準に届かない | 計画全体の前提が崩れる | **M1 をゲートにする**(§5)。不合格時の次候補(他の piper 話者・量子化版の比較試聴)を M1 で並べる |
| 実機での TTS 速度・メモリ(RTF 0.078 は測定環境値) | 低価格 Android で待ち時間・クラッシュ | M1 で実測。単スレッドで不足なら §2.2 の再検討 |
| Android の 1080p エンコード失敗(w3c/webcodecs #397) | 一部端末で生成不能 | 解像度ネゴ(§2.2)+リアルタイム経路への降格(§3)。実測記録を残す |
| iOS の AAC エンコードが Safari 26+ 限定。利用者側の Safari 版数分布が不明 | 高速経路に乗れる比率が読めない | リアルタイム経路(§3)で全 iOS 16.4+ を救う。版数分布の実態はリリース後の問い合わせ傾向で見る(計測を仕込まない方針のため) |
| サブセットフォントの欠字(固有名詞・記号) | 字幕が豆腐になる | M1 でセグメント編集の自由入力を想定した欠字確認。不足ならサブセット範囲を広げる(サイズと交換) |
| つくよみちゃんのクレジット表記漏れ | 利用条件違反 | アプリ画面とヘルプへの表記を M3 完了条件に含める(§5) |
| Cache Storage の追い出し(iOS 7日規則) | 再ダウンロード発生 | 挙動として受け入れ、ヘルプに明記(§4.4)。PWA ホーム画面追加で緩和されるかは M3 で確認 |
| Mediabunny のライセンス最終確認(MPL-2.0 想定) | 同梱可否 | ベンダリング承認時(§4.3)に原文確認し approvals へ記録 |
| リアルタイム経路の音ズレ(MediaRecorder の canvas+audio 同期) | 30秒で徐々にずれる可能性 | M3 で実機確認。許容外なら当該環境は音声WAV+動画(無音)+手動結合の案内など縮退を検討(未解決) |
| 生成中のタブ切り替え・着信(iOS はバックグラウンドで wasm 停止) | 生成失敗 | Wake Lock+「画面を切り替えないでください」表示+失敗時の明示リトライ。完全な防止は不可能(受容) |
