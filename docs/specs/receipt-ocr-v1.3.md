## 0. 本書の前提と未確定事項

### 0.1 OCR方式は未確定である（フェーズ0で決定）

本書の6章以降は「Google Drive OCR＋ルール抽出」を主経路とする前提で記述しているが、**この方式は未検証であり、フェーズ0の実測比較の結果によって差し替える**。

比較対象は以下の3案とする。

| 案 | 方式 | 特徴 |
| --- | --- | --- |
| A | Drive OCR＋ルール抽出 | 追加コストなし。レイアウト情報（座標）なし。行順序が崩れやすい |
| B | Cloud Vision API＋座標ベースルール | 座標付きテキストが高速に取得でき「ラベルの近く」を厳密に定義できる。従量課金 |
| C | Gemini（BYOKキー）への画像直接投入＋Structured Output | 実装が最も単純。BYOK方式ではブラウザから画像を直接送信する形になる。外部送信は画像全体 |

いずれの案でも、13章の検証ロジック・15章のステータス管理・16章のシート構成は共通で使用できるよう、OCR/抽出部分をモジュールとして分離する（22.4項）。

### 0.2 経理・税理士による確認が必要な事項

以下は開発側だけでは確定できないため、実装前に経理担当・顧問税理士の確認を得る。

1. 電子帳簿保存法に関する本システムの位置づけ（0.3項の方針で問題ないか）
2. 勘定科目の運用ルール（候補提示のみとし確定は人間が行う方針で問題ないか、店舗マスタの初期値）
3. インボイス（適格請求書）情報の取得粒度（免税事業者の扱いを含む）
4. 「要確認」データの確認担当者と確認手順
5. Gemini APIキーの区分ポリシー（無料枠許容・開示・責任帰属）の規約文言（0.4項。法務確認を含む）

### 0.3 電子帳簿保存法（スキャナ保存）への対応方針

**本MVPは電子帳簿保存法のスキャナ保存要件を満たさない。紙の領収書原本は、本システムへの登録後も従来どおり保管し、廃棄しない。**

本システムのデータは経理業務の効率化のための参考データであり、税務上の保存書類としては紙原本を正とする。この方針は利用者向け案内にも明記し、「撮影したので紙は捨ててよい」という誤解を防ぐ。

将来スキャナ保存に対応する場合、少なくとも以下が必要となり、アーキテクチャに影響するため、対応時は要件定義からやり直す。

* 解像度・階調要件の充足検証（A4相当で約388万画素以上等）と、要件未達画像の受付拒否
* 訂正・削除の履歴が残る保存方式（スプレッドシート直編集では満たせない）
* 検索要件（取引年月日・取引金額・取引先）の保証
* 事務処理規程の整備

### 0.4 Gemini APIキーの取り扱い方針（BYOK）

本システムはPortal既存のBYOK方式に従う。Gemini APIキーは利用者がPortalのAPIキーパネルに設定し、ブラウザのストレージにのみ保存される。**キーはGASへ送信せず、GASで預からない**（既存keystoreの設計原則に準拠）。このためGemini呼び出しはブラウザが直接行う2段階フロー（12章）となる。

キー区分（無料枠・有料）の扱いは、名刺OCRアプリ（v3.0 §14.6）とPortal全体で統一する。

* **無料枠キーでの利用を許容する。** 区分の選択は利用者の判断に委ねる
* ただし無料区分では、送信したOCR文字列（経理データを含む）がGoogleのプロダクト改善に利用され得る。このデータ取り扱いを、キー設定パネル付近および本アプリの初回利用時案内に開示する
* 実在の経理データを扱う業務利用であるため、**有料区分キーの使用を推奨する**（強制はしない）
* キー区分の選択と、それに伴うデータ取り扱いの責任は利用者に帰属することを利用規約に明記する（文言は法務確認を経て確定する。0.2項）
* システム（当社）はキー区分を検証・保証しない（検証手段が存在しない）
* キーにはAPI制限（Generative Language APIのみ）を設定することを利用者に推奨する

| 利用形態 | キー | システム側の対応 |
| --- | --- | --- |
| お試し・動作検証 | 無料枠キー可 | データ取り扱いの開示 |
| 業務利用（実在の経理データ） | **有料区分キーを推奨** | 推奨の明示。強制はしない |

## 1. 背景

領収書やレシートの画像を手作業で確認し、利用日、支払先、金額、消費税、勘定科目などをスプレッドシートへ入力する作業には、一定の時間と入力ミスが発生している。

本システムでは、Google Driveに保存された領収書画像をOCRで文字列化し、ルール処理によって必要な項目を抽出する。ルール処理だけでは判定できない場合に限りGemini APIを利用し、処理コストと外部送信量を抑えながら、領収書データ化を自動化する。

なお、本システムは会計証憑（金額・税額）を扱うため、**「間違った値を自信を持って自動確定すること」を最大のリスク**と位置づける。抽出できないことよりも、誤った値の自動確定を防ぐことを設計上優先する。

---

## 2. 目的

本MVPの目的は、領収書画像から以下の処理を自動で実行するAPIを構築することである。

1. 領収書原本をGoogle Driveに保存する
2. OCRで文字情報を取得する
3. 日付、支払先、合計金額などをルール処理で抽出する
4. 抽出できない場合のみGeminiで補完する
5. 抽出結果をGoogleスプレッドシートに保存する
6. 重複登録や不正な金額を検知する
7. 自動確定できないデータを「要確認」として管理し、人による確認・確定までの運用を成立させる

## 4. MVPの対象範囲

### 4.1 MVP第1段階（本書の必須スコープ）

* DriveファイルID指定による領収書画像の受付（JPEG・PNG）
* Google Drive上の原本画像の管理
* OCRによる文字抽出（方式はフェーズ0で決定）
* 利用日・支払先・合計金額の抽出（あわせて消費税内訳・支払方法・レシートNo.・電話番号・登録番号を取得できた場合に記録）
* 店舗マスタによる勘定科目「候補」の提示
* 抽出失敗時のGemini補完（BYOK・2段階フロー。12章）
* 金額および日付の妥当性検証
* SHA-256による重複確認（登録済みデータとの照合）
* 冪等性制御（idempotencyKey）と排他制御（LockService）
* スプレッドシートへのデータ保存
* 処理結果のJSON返却
* エラーおよび処理履歴の保存
* 「要確認」データの確認運用（フィルタビューとステータス更新）

### 4.2 MVP第2段階（第1段階の安定稼働後に着手）

* Base64画像送信の受付
* 類似データ（同日・同店舗・同金額）の重複候補判定
* 非同期処理化（受付即応答＋ポーリング）

### 4.3 MVP対象外

* PDF内の複数ページ一括処理
* 複数領収書が写った画像の分割

* 領収書画像の自動台形補正
* ユーザーによる修正専用画面（スプレッドシート直編集で代替。18章）
* freee、マネーフォワード等との連携
* 複数通貨・外貨換算
* 銀行明細との自動照合
* 会計仕訳の自動登録
* 大量ファイルの一括バッチ処理
* 一般ユーザー向けアカウント管理・課金機能
* 電子帳簿保存法スキャナ保存要件への対応（0.3項）

## 8. 入力仕様

### 8.1 APIエンドポイント

Apps Script Webアプリとして公開された単一のWebアプリURLに対してPOSTリクエストを送信する。Apps Scriptの仕様上、パスによるルーティング（`/receipt`等）は行えない。

### 8.2 入力方式（MVP第1段階はDriveファイルID指定のみ）

すでにGoogle Driveへ保存されている画像を処理する。

```json
{
  "accessToken": "API_ACCESS_TOKEN",
  "idempotencyKey": "client-generated-uuid",
  "fileId": "GOOGLE_DRIVE_FILE_ID",
  "requestedBy": "user@example.com"
}
```

* `idempotencyKey`は**クライアントが生成する一意キー（UUID推奨）で、必須**とする。リトライ時は必ず同一キーを再送する。
* `requestedBy`はクライアント申告値であり検証されないため、参考情報として扱う。監査上の利用者特定には使用しない。
* Base64送信（第2段階スコープ）を追加する際は、`fileId`との同時指定禁止、サイズ上限、事前圧縮要件を別途定義する

#### 補完結果の返送（2段階フローの第2段階）

第1段階で`geminiRequired: true`が返された場合、ブラウザはGemini呼び出し後に以下を送信する。

```json
{
  "accessToken": "API_ACCESS_TOKEN",
  "phase": "complete",
  "receiptId": "RCP-20260802-A7K3M9",
  "geminiResult": { "merchantName": "株式会社サンプル", "merchantEvidence": "..." }
}
```

Apps Scriptはパスルーティングができないため、`phase`フィールドで第1段階・第2段階を判別する。このリクエストに**Gemini APIキーを含めてはならない**。含まれていた場合、サーバーは処理を拒否する。。

### 8.3 入力制約

* 対応形式はJPEG、JPG、PNGとする
* 1リクエストにつき領収書1枚とする
* `fileId`は許可された受付フォルダ配下のファイルであること（配下でない場合は`FILE_ACCESS_DENIED`）
* 画像の長辺は2,000px前後を推奨する（電帳法要件とは無関係である。0.3項）
* APIアクセストークンが一致しない場合は処理しない

### 8.4 クライアント実装要件

* HTTPタイムアウトは**90秒以上**に設定する。同期処理は最大60秒程度かかり得るため、30秒等の短いタイムアウトは二重送信の原因となる
* 自動リトライを行う場合、必ず**同一のidempotencyKey**を送信する
* Apps ScriptへのPOSTは302リダイレクトを返すため、**リダイレクト追従を有効にし、リダイレクト時にPOSTをGETへ変換しないクライアント**を使用する
* HEIC画像はクライアント側でJPEGへ変換してから送信する

### 8.5 Apps ScriptのHTTP制約

* HTTPステータスコードは制御できず、正常・エラーとも**常に200**で返る。クライアントはレスポンスJSONの`ok`と`errorCode`で成否を判定する
* 1実行あたりの上限は6分である。超過が見込まれる処理は受け付けない

## 9. 処理フロー

### 9.1 受付処理

APIはリクエスト受信後、以下の順で確認する。

1. APIアクセストークン
2. 必須項目（idempotencyKeyを含む）
3. idempotencyKeyの既存判定（9.2項）
4. ファイル形式・ファイルIDへのアクセス可否・許可フォルダ配下であること
5. 画像ファイルであること

入力値に問題がある場合、OCR処理は実行せずエラーを返す。

### 9.2 冪等性制御

処理台帳（16.4項）でidempotencyKeyを管理し、以下のとおり動作する。

```text
同一idempotencyKeyのリクエストを受信した場合：
・処理中　　→ 現在の処理状態を返す（新規処理は開始しない）
・完了済み　→ 保存済みの処理結果をそのまま返す
・失敗済み　→ 既存の管理IDを引き継いで処理を再開する
```

これにより、クライアントのタイムアウト起因のリトライや、シート保存失敗後の再送で二重登録・処理不能（デッドロック）が発生しないことを保証する。

第2段階（補完結果の返送）については、同一receiptIdへの格上げは1回のみ有効とする。2回目以降は`PHASE_CONFLICT`を返し、最初の結果を維持する。reviewStatusが「REVIEWED」（人が確認済み）の行への格上げも拒否する（人の判断を機械が上書きしない）。

### 9.3 排他制御と重複判定

重複判定の開始からスプレッドシート登録の完了までを、`LockService.getScriptLock()`による排他区間とする。ロック取得待ちのタイムアウト時は`RATE_LIMITED`を返す。

SHA-256ハッシュの照合先は、**スプレッドシートに登録済みのデータ（SHA-256列）のみ**とする。Drive上のファイル走査による照合は行わない。これにより、「前回処理で原本だけ保存されシート保存に失敗した」ケースの再実行が、自分自身の残存ファイルと衝突して`DUPLICATE_RECEIPT`になる事故を防ぐ。

#### 完全一致判定

登録済みデータとSHA-256が一致した場合、同一画像として登録を停止し、既存の管理IDを返す。

なお、SHA-256は同一ファイルの再送のみ検知でき、撮り直し・再圧縮した画像は検知できない。重複防止の完全な保証ではなく、明白な二重送信の防御と障害調査を目的とする。

#### 類似データ判定（第2段階）

利用日・支払先・合計金額の一致による重複候補判定は第2段階とする。実装時は以下に留意する。

* 支払先は店舗マスタで正規化した後の名称で比較する（OCR揺れ対策）
* 同一店舗での同日複数回利用（昼夜、往復交通費等）は正当な取引として普通に発生するため、**登録は停止せず警告のみ**とする
* 両方のデータでレシートNo.（10.5項）が取得でき、かつ番号が異なる場合は、正当な別取引として重複候補から除外する
* 運用開始後に誤検知率を実測し、判定の有効・無効と条件を調整する

### 9.4 OCR処理

OCR方式はフェーズ0で決定する（0.1項）。Drive OCRを採用する場合の要件は以下とする。

* Drive API v3の`ocrLanguage`パラメータに`ja`を指定する（v3に本パラメータは存在するが、Apps Scriptの高度なサービス経由での動作はフェーズ0で実機確認する）
* OCR用の一時Googleドキュメントは、テキスト取得後に**完全削除**する（ゴミ箱への移動では30日間残存するため不可）
* 原本画像は削除しない

## 10. ルールによる項目抽出

OCR文字列から、正規表現およびキーワード判定で項目を抽出する。

**前提となる制約：** プレーンテキスト化されたOCR結果では行順序・左右の対応関係が崩れることがあり、「近くの金額」という判定の信頼性には限界がある。このため、ルール抽出の結果は13章の検証に合格して初めて採用し、**検証に不合格の場合はルールで値が取れていても確定しない**（安全側に倒す）。

### 10.1 金額の正規化（全金額フィールド共通の前処理）

抽出したすべての金額文字列は、単一の正規化関数を通してから使用する。

```text
処理内容：
1. 全角数字・全角記号を半角化する
2. 「¥」「円」「,」等の記号・単位を除去する
3. 整数へ変換する
4. 変換に失敗した場合はnullとする（0にしない）

対策対象の誤読例：
「1,000」→ 1000
「1.000」→ カンマのドット誤認。1と解釈しないこと
「¥1000」→ 1000
```

変換失敗（null）の金額は「抽出できなかった」として扱い、13章の必須項目検証で要確認に落とす。

### 10.2 利用日

以下の形式を対象とする。

```text
2026年8月2日 / 2026/08/02 / 2026-08-02 / 2026.08.02
令和8年8月2日 / R8.8.2 / 26/08/02（2桁年）
```

**判定方針：** レシートにはポイント失効日・クーポン有効期限・キャンペーン期間・カード有効期限など、取引日以外の日付（未来日を含む）が多数印字される。このため「現在日以前の日付を選ぶ」という消去法は誤取得の危険が高い。

* 「取引日」「利用日」「発行日」「領収日」等のラベルに近接する日付のみをルール抽出の対象とする
* ラベル近接で特定できない場合は、ルールでの確定を行わず、Gemini補完または要確認とする

### 10.3 支払先・店舗名

以下の優先順位で判定する。

1. 店舗マスタに登録された名称（正規化に使用）
2. OCR文中の先頭付近にある法人名・店舗名
3. 「株式会社」「合同会社」「店」「支店」等を含む文字列
4. Geminiによる補完

電話番号、住所、担当者名のみの行は店舗名として採用しない。

### 10.4 合計金額

以下のキーワードに近接する金額を候補とする。

* 合計 / 総合計 / 合計(税込) / 税込合計
* ご請求額 / お支払額 / 領収金額 / お買上金額 / お買上計
* 現計

以下は合計として採用しない、または優先しない。

* 「お預り」「お釣り」は採用しない（合計より大きい金額が混在する典型原因）
* 「小計」は最終合計より優先しない
* 「クレジット支払」額は現金併用時に合計と一致しないため、合計の根拠としない

**候補が複数残った場合はルールで確定せず**、Gemini補完または要確認とする。

### 10.5 レシートNo.（伝票番号）

「伝票番号」「レシートNo」「取引No」「No.」等のラベルに近接する番号を抽出する。取得できた場合のみ記録する（必須項目ではない）。

* ラベル近接を必須とし、番号単独では採用しない（電話番号・会員番号・適格請求書登録番号との混同防止）
* 用途：類似重複判定の補助キー。同日・同店舗・同金額でもレシートNo.が異なれば正当な別取引と判定でき、誤検知を減らせる

### 10.6 適格請求書登録番号（第1段階）

```text
T＋13桁の数字（例：T1234567890123）
```

* 「T」の文字が明示的に認識できた場合のみ、続く13桁を登録番号候補とする。**数字13桁のみの検出にTを補って採用することは禁止する**（電話番号・伝票番号との混同防止）
* 「登録番号の記載がない（免税事業者の可能性）」と「記載はあるがOCRで読めなかった」を別フラグで区別する。両者は仕入税額控除の処理が異なる
* チェックデジット検算は、法人番号形式の番号に対する信頼度加点としてのみ使用する（個人事業主の登録番号には適用できないため、不一致を即エラーとしない）
* 形式に一致しない場合は空欄＋「読取失敗」とし、値を補正しない

### 10.7 電話番号（TEL）

「TEL」「電話」「☎」等のラベルに近接する、0始まり10〜11桁の番号を抽出する。取得できた場合のみ記録する（必須項目ではない）。

* ラベルまたは市外局番形式（ハイフン・括弧区切り）の確認を必須とし、数字列単独では採用しない（レシートNo.・会員番号・登録番号との混同防止）
* 用途：店舗マスタ照合の補助キー。店名はOCR揺れで照合が外れやすいが、電話番号は揺れが少ないため、マスタに電話番号が登録されている場合は**電話番号一致を最優先の照合キー**とする

### 10.8 勘定科目（候補のみ）

**勘定科目は本システムでは確定しない。常に「候補」として提示し、確定は人間が行う。**

同一の支払先でも利用目的によって科目は変わる（例：Amazonでの購入は消耗品費・新聞図書費・備品等に分かれ、カフェの利用は会議費・交際費・個人利用に分かれる）ため、支払先のみからの自動確定は原理的に不可能である。

* 店舗マスタに一致した場合、登録済みの科目を**候補**として設定し、科目候補の出所を「店舗マスタ」と記録する
* マスタに該当しない場合、Geminiによる候補判定を行い、出所を「Gemini」と記録する
* いずれの場合も、科目確定フラグの初期値は「未確定」とする
* 店舗マスタの初期値は経理担当が定義する。本書には具体的な対応表を記載しない（旧版10.7の対応表は削除した）

### 10.9 消費税内訳（税率別）

「8％対象」「10％対象」「内税」「外税」等のラベルに近接する金額から、8％・10％それぞれの対象額・税額を抽出する。取得できた場合のみ記録する（必須項目ではない）。

* レシート上の対象額には税込表記・税抜表記の両方が存在するため、**印字された値をそのまま記録**し、表記区分（税込／税抜／不明）を併記する
* 軽減税率の「※」「＊」マークによる商品単位の判別は行わない（商品明細の解析はMVP対象外）
* 検算の扱いは13.1項に従う（表記区分が特定できた場合のみ参考検証）

### 10.10 支払方法

以下のキーワードから判定し、取得できた場合のみ記録する。

* 現金
* クレジットカード（VISA / Mastercard / JCB / AMEX）
* コード決済（PayPay / 楽天ペイ 等）
* 交通系IC（Suica / PASMO / ICOCA 等の実表記を含む）
* 電子マネー
* 振込

「クレジット支払」等の金額行は支払方法の判定に使用するが、合計金額の根拠には使用しない（10.4項。現金併用時のズレ防止）。

## 11. Gemini補完条件

Gemini補完の**要否判定はサーバー側**で行い、**実行はブラウザ**が行う（12章）。以下のいずれかに該当した場合のみ、第1段階レスポンスで`geminiRequired: true`を返す。

1. 利用日をルールで確定できない
2. 支払先をルールで確定できない
3. 合計金額をルールで確定できない（候補複数を含む）
4. 金額検証（13章）に不合格
5. 正規表現による抽出結果に矛盾がある

**geminiRequiredとしない条件（重要）：**

* OCR文字列が空、または30文字未満（設定変更可）の場合は、**補完を要求せず「OCR失敗・要確認」とする**。OCRが情報を失っている場合、テキストのみを受け取るGeminiは誤補完（推測）しかできないためである
* Gemini利用が設定で停止されている場合（この場合、第2段階の受付も拒否する）

また、ブラウザ側にキーが未設定の場合、Portalは第2段階をスキップし、データは要確認のまま残る。画面には図のキー未設定バナーから設定を促す。

Gemini停止時は抽出できない領収書がすべて要確認となり、要確認処理の運用負荷が増大する。停止は障害時・規約変更時等の緊急措置と位置づける。

## 12. Gemini連携仕様（BYOK・2段階フロー）

### 12.1 キーの取り扱いとフロー構成

* キーはBYOK方式（0.4項）。Portalのブラウザストレージにのみ保存され、GASへ送信しない・GASで預からない
* Gemini呼び出しは**ブラウザが直接**行う。認証は`x-goog-api-key`ヘッダー（Portal既存実装と同方式）
* キー区分（無料枠・有料）は利用者の判断に委ねる（0.4項）。業務経理データを送信するため有料区分を推奨し、無料枠のデータ取り扱いを開示する
* 原則として画像は送信せず、OCR文字列のみを送信する（フェーズ0で案C採用時は本項を改訂する）

Portal側の実装は、名刺OCRアプリと同一のKeyStore規約（名刺OCR v3.0 FR-23）に従う。

* `KeyStore.get('gemini')`のみを入口とし、localStorageを直接操作しない
* キー管理UIを本アプリ内に持たず、未設定（KEY-001）・無効（KEY-002）時はPortalのキー設定画面へ誘導する。誘導の導線が循環しないよう戻り先を明示する
* キーの送信先はGemini APIエンドポイントのみとし、メモリ外へ保存しない
* **会社キーへのフォールバックは行わない**
* アプリのフロントエンドは`public/production-app/`配下に配置し、Portalと同一オリジンで配信する（KeyStore参照の必須条件）。PORTAL_APPSの登録パスに`apps/`を含めない（自動テストが禁止している）
* 使用モデルは静的設定ファイルで変更可能とし、主モデル404時はフォールバックモデルで1回再試行する

処理は2段階に分かれる。

```text
第1段階（サーバー）：
OCR・ルール抽出・検証まで実施し、結果を必ず保存する。
補完が必要な場合はreviewStatus=REQUIREDで保存を完了した上で、
geminiRequired: trueとOCR文字列をレスポンスに含めて返す。

第2段階（ブラウザ→サーバー）：
ブラウザがOCR文字列をGeminiへ送信し、結果JSONをサーバーへ返送する。
サーバーはevidence検証・突合・再検証に合格した場合のみ行を更新する。
```

**第2段階が実行されなくてもデータは失われない。** タブを閉じる、キー未設定、Gemini障害のいずれの場合も、第1段階で要確認として保存済みのデータがそのまま残るだけであり、宙吊りの未完了状態は発生しない。

### 12.2 独立抽出と突合（アンカリング対策）

第1段階レスポンスにはルール抽出結果（data）とOCR文字列の両方が含まれるが、Portal側は**ルール抽出の候補値をGeminiのプロンプトに含めてはならない**。ルールが誤った候補を出した場合にGeminiがそれを追認するアンカリングを防ぐため、GeminiにはOCR文字列のみから独立に抽出させ、突合は第2段階の受付時にサーバー側で行う。

```text
突合結果の扱い：
・一致　　→ 信頼度加点
・不一致　→ 要確認（どちらかを自動採用しない）
・ルール側が未取得 → Gemini値を候補として採用し、13章の検証にかける
```

### 12.3 出力形式

以下はPortal側（クライアント）の実装要件とする。

* Gemini APIの**Structured Output（responseSchema）とresponse_mime_type: "application/json"**を使用し、プロンプト指示のみに依存しない
* Markdownコードフェンス等が付与される場合に備え、`JSON.parse`前にサニタイズ処理を行う
* 呼び出し失敗・パース失敗時は1回までリトライし、それでも失敗した場合は第2段階を送信せず、利用者に失敗を表示する（データは第1段階で要確認として保存済みのため、サーバー側の追加処理は不要）
* Geminiのタイムアウトは30秒、リトライは1回とする

### 12.4 プロンプト要件

```text
以下は日本の領収書をOCRした文字列です。

事実として読み取れる情報のみを抽出してください。
不明な項目はnullを返してください。
金額を推測で補完しないでください。
各項目について、根拠となったOCR文字列の該当箇所をevidenceとして返してください。

抽出項目：
・支払先
・利用日
・合計金額
・消費税合計と税率別内訳（8％・10％の対象額・税額）
・支払方法
・適格請求書登録番号
・レシートNo.
・電話番号
・勘定科目候補
・摘要
```

### 12.5 出力スキーマ

```json
{
  "merchantName": "株式会社サンプル",
  "merchantEvidence": "株式会社サンプル 東京都...",
  "transactionDate": "2026-08-02",
  "dateEvidence": "領収日 2026年8月2日",
  "totalAmount": 11000,
  "amountEvidence": "合計 ¥11,000",
  "expenseCategoryCandidate": "会議費",
  "description": "会場利用料",
  "warnings": []
}
```

**Geminiにconfidence（信頼度の自己申告値）を返させない。返された場合も使用しない。** LLMの自己申告確率は校正されておらず、自動確定の判定根拠にできない（14章）。代わりにevidence（根拠文字列）を返させ、OCR原文に実在するかをコード側で照合する。

## 13. 抽出結果の妥当性検証

抽出値（ルール・Geminiとも）は、そのまま確定データとして使用せず、必ずコード側で以下を検証する。

### 13.1 金額検証

**旧版の「許容誤差1円」は撤回する。** 端数処理方法（切捨て・切上げ・四捨五入）は事業者裁量であり、値引き・クーポン・ポイント充当・非課税品の混在により、正当なレシートの相当数が1円基準では不整合となるためである。

検証は以下の条件付きロジックとする。

```text
基本検証（常時）：
・合計金額が0円より大きい
・合計金額の桁数が妥当（1円以上1,000万円未満。閾値は設定変更可）
・金額正規化（10.1）に成功している

検算（税額が取得できた場合のみ）：
・合計金額 × 税率からの逆算で税額と±数円以内に整合するか
　→ 整合すれば信頼度加点（OCRの桁誤読の検知に有効）
　→ 不整合でも即エラーとせず、値引き行等の有無を確認

検算スキップ条件：
・「値引」「割引」「クーポン」「ポイント」等の行を検出した場合、
　検算をスキップし、警告内容に「値引きあり・検算省略」を記録する
```

「8％対象額＋10％対象額 ≒ 合計」の検算は、表記区分（10.9項）が「税込」と特定でき、かつ値引き等が検出されていない場合のみ参考検証として行う。一致すれば信頼度加点、不一致でも警告の記録にとどめ、要確認判定の単独根拠とはしない（表記の多様性による正当な不一致が多いため）。

### 13.2 日付検証

* 日付として解釈でき、和暦・2桁年の西暦変換が正常であること
* 未来日でないこと（未来日はポイント失効日等の誤取得を示唆するため要確認）
* 1年超過去の日付は要確認とする（閾値は設定変更可）

### 13.3 evidence検証（第2段階の必須検証）

Geminiが返した各evidenceが、**サーバーが保存しているOCR原文**の中に実在することを照合する。実在しないevidenceを伴う値は採用せず、要確認のままとする。

BYOK・2段階フローではGemini結果がブラウザ経由で返送されるため、クライアント側での改ざん・偽装が理論上可能である。evidence検証はその防御を兼ねる。サーバー保存のOCR原文に存在しない値は、経路を問わず採用されない。

### 13.4 必須項目検証

以下を必須項目とする。不足する場合、reviewStatusを「REQUIRED」とする。

* 支払先
* 利用日
* 合計金額
* 原本画像URL

## 14. 信頼度判定

**信頼度はコード側で算出する。Geminiの自己申告値は使用しない。** また、信頼度は「どの経路で処理したか」ではなく「値がどれだけ確からしいか」の推定として設計する（旧版の「Gemini未使用なら高」という条件は、正しさの根拠にならないため廃止する）。

加点方式のスコアリング例（初期値。運用実測に基づき調整する）：

```text
日付：
・ラベル（利用日等）に近接して取得：+30
・日付候補が1件のみ：+20
・ルールとGeminiが一致：+20

金額：
・合計ラベルに近接して取得：+30
・金額候補が1件のみ：+20
・税額逆算と整合：+30
・ルールとGeminiが一致：+20

支払先：
・店舗マスタ完全一致：+20
・ルールとGeminiが一致：+10

減点：
・値引き検出により検算省略：-10
・evidence照合不可：採用しない（スコア対象外）
```

スコアの閾値により高・中・低へ分類する。閾値は設定シートで管理し、フェーズ0・受入テストの結果で校正する。

## 15. ステータス体系

旧版の単一ステータス（8種）は「処理方法・処理結果・確認状態・重複状態」が混在していたため、以下の4軸に分離する。「AI補完で処理成功かつ要確認」「重複候補かつ処理成功」等の状態を正しく表現するためである。

```text
processingStatus（処理結果）：
  RECEIVED / PROCESSING / SUCCEEDED / FAILED

reviewStatus（確認状態）：
  NOT_REQUIRED / REQUIRED / REVIEWED

duplicateStatus（重複状態）：
  NONE / CANDIDATE / EXACT

extractionMethod（抽出方式）：
  RULE / GEMINI / HYBRID / MANUAL
```

APIレスポンスおよびスプレッドシートは、この4軸で状態を表現する。

**書き込み時の共通要件：**

* OCR・Gemini・リクエスト由来のすべての文字列は外部入力として扱い、先頭が `=` `+` `-` `@` の場合はシングルクォートを前置してから書き込む（数式インジェクション対策）

* 行の更新は行番号ではなく管理IDで検索して行う（並べ替え・削除への耐性）

## 18. 「要確認」データの確認運用

要確認データの解消フローをMVPの必須要件とする（修正専用画面は対象外のため、スプレッドシート直編集で運用する）。

### 18.1 確認手順

1. メインシートに「要確認一覧」フィルタビュー（reviewStatus = REQUIRED）をあらかじめ作成しておく
2. 確認担当者（0.2項で決定）は、原本画像URL・OCR原文・警告内容を参照して値を修正する
3. 修正完了後、reviewStatusを「REVIEWED」に、必要に応じて科目確定フラグを更新する
4. extractionMethodを「MANUAL」に変更する（人手修正の識別）

### 18.2 直編集時のシート保全

* 編集可能列（利用日・支払先・摘要・科目・金額・reviewStatus・科目確定フラグ）と保護列（管理ID・SHA-256・idempotencyKey・原本情報・OCR関連・受付日時）を分け、保護列にはシート保護を設定する
* 更新日時列は編集をトリガーに自動更新する

### 18.3 運用上の注意

本運用では訂正・削除の履歴は残らない。これは0.3項のとおり電帳法要件を満たさない前提の運用であり、紙原本の保管によって担保する。

## 20. エラー時の動作

### OCR失敗・文字数不足時

* 原本画像はDriveに残す
* **Geminiを呼び出さない**（11章）
* processingStatus=FAILED、reviewStatus=REQUIREDとして記録し、エラーJSONを返す
* 処理台帳を「失敗済み」とし、同一キー再送で再開可能とする

### Gemini失敗時（ブラウザ側で発生）

* 第1段階の時点でOCR・ルール抽出結果は要確認として保存済みであり、サーバー側の追加処理は不要
* Portal側は1回のリトライ後、失敗を利用者に表示する
* 第2段階の検証不合格時は、サーバーは行を更新せず、warningsを返して要確認のまま維持し、検証結果を処理ログに記録する

### スプレッドシート保存失敗時

* 原本画像はDriveに残す
* 処理台帳を「失敗済み」として記録を試行する
* `SHEET_WRITE_FAILED`を返す
* 同一idempotencyKeyの再送は9.2項により処理を再開する（9.3項のとおり、残存原本との自己ハッシュ衝突は発生しない設計とする）

## 21. セキュリティ要件

### 21.1 API認証・公開設定

* Webアプリの公開範囲・実行主体（デプロイ者として実行か、アクセスユーザーとして実行か）を導入時に明示的に決定し、本書に追記する。「全員（匿名を含む）」公開が必要な場合、防御は実質URLとトークンのみとなることを認識する
* APIアクセストークンを必須とし、Apps Script Propertiesに保存する。ソースコードへ直接記述しない
* トークンは環境（本番・検証）で分離し、**ローテーション手順を定める**（漏えい時・担当者交代時）
* 簡易レート制限（単位時間あたりの受付件数上限）を設け、超過時は`RATE_LIMITED`を返す。クォータ枯渇とGemini課金の暴走を防ぐ
* `fileId`は許可フォルダ配下であることを検証する（8.3項）
* `requestedBy`は申告値であり監査情報として信用しない（8.2項）

### 21.2 Gemini APIキー（BYOK）

* キーはPortalのブラウザストレージにのみ保存し、**GASへ送信しない・GASで預からない**（0.4項。既存keystoreの原則に準拠）
* 本APIのリクエスト・レスポンス・ログ・シートのいずれにもキーを含めない。第2段階リクエストにキーが含まれていた場合、サーバーは処理を拒否する
* キー区分は利用者の判断に委ね、無料枠のデータ取り扱いをキー設定パネルと初回利用時案内に開示する。業務経理データには有料区分を推奨する（0.4項）。システムはキー区分を検証・保証しない
* キーにはAPI制限（Generative Language APIのみ）を設定することを利用者に推奨する
* 設定シートからGemini利用を停止できる（geminiRequiredを返さず、第2段階の受付も拒否する。緊急措置。11章）

### 21.3 データ送信制御

* Geminiへの送信はブラウザが行い、原則としてOCR文字列のみを送信する（フェーズ0で案Cを採用した場合は画像直接送信となり、本項を改訂する）
* OCR文字列にも社名・住所・電話番号等が含まれるため、外部送信であることに変わりはなく、0.4項の開示・有料区分推奨・責任帰属の明記を必須の前提とする

### 21.4 Drive・シート権限

* 原本フォルダは限定公開とする。「リンクを知っている全員」への公開は行わない
* OCR原文シートの閲覧権限は、メインシートより狭く設定できる構成とする（16.2項）
* シート保護（18.2項）を設定する

### 21.5 クライアント側XSS対策（最重要要件）

キーはブラウザのlocalStorageに平文で保存されるため、**XSSはGeminiキーの窃取に直結する**。名刺OCR v3.0 §14.3と同様に、Portal側実装では以下を最重要要件とする。

* OCR結果・Gemini出力・ユーザー入力を信頼できない入力として扱い、画面表示に`innerHTML`を使用しない
* 外部スクリプトは必要最小限とし、第三者CDNを使用しない
* CSPの適用可否を実装時に検証する

## 22. 非機能要件

### 22.1 処理性能

* 1件ずつ同期処理する
* サーバー側処理（第1段階・第2段階とも）は各30秒以内を目標とする。Gemini呼び出しはブラウザ側に分離されたため、サーバーの1リクエストはGemini待ちを含まない。補完込みの全体所要時間は60秒以内を目標とする（クライアントのタイムアウトは90秒以上。8.4項）
* Apps Scriptの6分制限を超える見込みの処理は受け付けない
* 同時大量処理は保証しない。処理の各ステージ（受付／OCR／抽出／保存）はモジュール分離し、将来の非同期化（第2段階）で受付即応答＋ポーリング方式へ移行できる構造とする

### 22.2 対応件数

* 1日100件以内、1リクエスト1件、同時実行は少数を想定する
* 上限に近づいた場合は、非同期化またはCloud Runへの移行を検討する

### 22.3 可用性

社内MVPのため、厳密な稼働率保証は行わない。Google各サービスおよびGemini APIの障害時には処理できない可能性がある。

### 22.4 保守性

以下をモジュールとして分離する。**特にOCR・抽出部分は、フェーズ0の結果による方式差し替え（Drive OCR / Cloud Vision / Gemini画像入力)に対応できるインターフェースとする。**

* API受付・冪等性・排他制御
* Drive操作
* OCR処理（差し替え可能）
* ルール抽出（差し替え可能）
* 金額正規化
* Gemini処理
* 妥当性検証・信頼度算出
* スプレッドシート保存
* ログ処理

設定値はPropertiesまたは設定シートから読み込む。

### 22.5 運用KPI（稼働後の継続計測）

以下を週次で集計し、閾値超過時にルール追加・店舗マスタ強化・閾値調整の改善サイクルを回す。

| 指標 | 目標（初期値） | 意味 |
| --- | --- | --- |
| 要確認率 | 20％以下 | 人手処理の残存量。高止まりは自動化が機能していないことを示す |
| Gemini発動率 | 40％以下 | コスト抑制方針（本システムの存在意義）の実測。高止まりの場合は方式C（画像直接）への転換を検討する |
| 誤自動確定の報告件数 | 0件 | 発覚時は即時に原因分析と閾値見直しを行う |

## 24. 受入基準

### 24.1 検証データ

* **最低50枚、推奨100枚**の実物領収書を使用する
* 実運用の構成比に合わせ、かつ以下の困難条件を**意図的に含める**：感熱紙の劣化・低コントラスト、8％/10％混在、値引き・ポイント利用、レイアウトが崩れやすい縦長レシート、飲食店の手書き様式、A4型請求書兼領収書
* **開発・ルール調整に使用したデータと、受入テスト用データを分離する**（受入用データでのルール調整は禁止）

### 24.2 精度基準

「正答」は項目単位で判定し、以下をすべて満たすこと。

| 項目 | 基準 |
| --- | --- |
| 合計金額の正答率 | 98％以上（誤りは会計事故に直結するため最重要） |
| 利用日の正答率 | 95％以上 |
| 支払先の正答率 | 90％以上 |
| 必須3項目すべて正しい領収書の割合 | 90％以上 |
| **誤った値を信頼度「高」として自動確定した件数（見逃し）** | **0件** |
| 抽出不能・不整合を要確認へ正しく振り分けた割合 | 95％以上 |

見逃し0件は他のすべての基準に優先する。抽出率が基準に届かない場合はスコープ・閾値の調整で対応できるが、見逃しは対応できないためである。

### 24.3 基本処理・制御

* JPEGまたはPNG画像を処理でき、原本がDriveに保存され、結果がシートへ記録され、原本URLから元画像を確認できる
* ルールのみで処理できる場合はgeminiRequiredを返さない
* OCR文字列が基準未満の場合、補完を要求せず要確認となる
* Gemini停止設定でもシステム全体が動作する（第2段階は拒否される）
* 補完実施有無・抽出方式がシートへ記録される

### 24.4 冪等性・重複・排他

* 同一画像（同一ファイル）の再送を重複として検知し、新しい行を作成しない
* シート保存失敗後、同一idempotencyKeyの再送で処理が再開され、二重登録も自己ハッシュ衝突も発生しない
* 同一idempotencyKeyの同時送信で二重登録が発生しない
* 完了済みキーの再送で前回結果が返る

### 24.5 安全性

* APIトークンなしでは処理できない
* Gemini APIキーが当社ドメイン（GASを含む）へのいかなるリクエストにも含まれないことを、**通信内容の検証**で確認する。ログ・シートにも残らない
* OCR原文に存在しないevidenceを伴う第2段階結果が拒否される（偽装耐性）
* 第2段階を実行しなくてもデータが要確認として保存されている
* REVIEWED（確認済み）の行が第2段階で上書きされない
* 原本画像・OCR原文が一般公開されない
* 先頭が`=`等の店舗名がシート上で数式として解釈されない
* エラー時にも原本画像と処理ログが確認できる

| 12 | 同一キーを同時に2件送信 | 排他制御により1件のみ処理 |
| 13 | 完了済みキーを再送 | 前回結果をリプレイ |
| 14 | APIトークンなし | AUTH_FAILED |
| 15 | 許可フォルダ外のfileId | FILE_ACCESS_DENIED |
| 16 | Gemini APIエラー | ルール結果を要確認で保存 |
| 17 | GeminiがJSON以外を返却 | サニタイズ→リトライ→失敗時は要確認 |
| 18 | 店舗名が「=」で始まる | 数式として解釈されず文字列で保存 |
| 19 | 他社宛の領収書 | 宛名が取得できれば記録（検知は人の確認による） |
| 20 | シート書込みエラー | SHEET_WRITE_FAILED |
| 21 | 補完必要案件で第2段階を正常実行 | 検証合格で格上げ、抽出方式HYBRIDを記録 |
| 22 | OCR原文に存在しないevidenceを返送 | 採用されず要確認のまま |
| 23 | 同一receiptIdへ第2段階を2回送信 | 2回目はPHASE_CONFLICT |
| 24 | 第2段階を実行せずタブを閉じる | 要確認として保存済み、データ欠損なし |
| 25 | 確認済み（REVIEWED）行への第2段階送信 | PHASE_CONFLICTで拒否 |
| 26 | 第2段階リクエストにAPIキーが混入 | サーバーが処理を拒否 |
| 27 | キー未設定の利用者が補完必要案件を送信 | 第1段階のみ実行、要確認として保存 |

## 26. 開発フェーズ

### フェーズ0：OCR方式検証（実装前・最優先）

## 28. MVPの完成定義

本MVPは、利用者がDriveファイルIDをAPIへ送信することで、以下が自動実行される状態を完成とする。

```text
【第1段階（サーバー）】
冪等性・重複確認
↓
OCR（フェーズ0で決定した方式）
↓
ルール抽出・金額正規化・検証・信頼度算出
↓
スプレッドシート登録（補完が必要な場合は要確認として保存）
↓
処理結果返却（必要時はgeminiRequired + OCR文字列）

【第2段階（補完が必要な場合のみ・ブラウザ）】
BYOKキーでGeminiを直接呼び出し（独立抽出）
↓
結果JSONをサーバーへ返送
↓
evidence検証・突合に合格した場合のみ行を格上げ
```

あわせて、以下が成立していることを完成条件に含める。

1. 自動確定できない場合、誤った内容を確定登録するのではなく「要確認」として原本画像・OCR原文・抽出候補を確認でき、**人が確認・修正して確認済みへ遷移させる運用（18章）が回っている**こと
2. 受入基準（24章）、特に**見逃し0件**を満たしていること
3. 紙原本を廃棄しない運用ルール（0.3項）が利用者に周知されていること
4. 無料枠キーのデータ取り扱いの開示（0.4項）がキー設定パネルと初回利用時案内に表示され、キー区分の責任帰属が利用規約に明記されていること
