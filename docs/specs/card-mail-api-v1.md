# 名刺メール配信API 仕様書 v1

- 版: v1.0（2026-08-10 初版）
- 対象: `app/api/card-mail/send/route.ts` ＋ `lib/card-mail/`
- 関連: [meishi-ocr-requirements-v3.md](./meishi-ocr-requirements-v3.md)（名刺データの保存側）

---

## §1 目的とスコープ

名刺OCRアプリ（`card-ocr`）で保存した名刺データのメールアドレス宛に、
**BCCで一斉送信**するためのサーバーAPI。挨拶・案内などの同報連絡を、
宛先を相互に見せずに送ることを目的とする。

スコープ外:

- 台帳（スプレッドシート「名刺管理」）からのアドレス抽出（§2の理由で呼び出し側の責務）
- 宛先ごとの差し込み（宛名の個別化）。必要になったら版を上げて検討する（§12）
- 送信履歴の保存。当面は送信元Gmailの「送信済み」が記録を兼ねる

## §2 全体像

```
呼び出し側（運用者の手元のスクリプト等）
  │  POST /api/card-mail/send/（Bearer トークン + 宛先一覧 + 件名 + 本文）
  ▼
Next.js ルートハンドラ（Cloudflare Workers 上）
  │  検証・重複排除・90件ずつに分割
  ▼
Gmail API（送信元アカウントのリフレッシュトークンで送信、宛先はBCC）
```

**宛先はリクエストで受け取る。** 名刺データの正本は利用者自身の
スプレッドシートにあり、アクセスできるのは利用者のブラウザが持つ
drive.file トークンだけである（要件定義書 §FR-02。トークンはメモリ上のみで
サーバーへ送らない）。サーバーは台帳を読めないし、読めるようにもしない。
台帳からのアドレス抽出は呼び出し側で行う（台帳の「メール」列をコピーする、
CSVに書き出す等）。

## §3 エンドポイント

```
POST https://tsam-ai.com/api/card-mail/send/
Content-Type: application/json
Authorization: Bearer <CARD_MAIL_API_TOKEN の値>
```

**末尾スラッシュ必須。** `trailingSlash: true` のため、スラッシュなしへの
POSTは308リダイレクトになり、多くのHTTPクライアントは本文を落とす
（Stripe Webhook と同じ罠。CLAUDE.md「配信構成」）。

## §4 認証

- `Authorization: Bearer` ヘッダーのトークンを、環境変数
  `CARD_MAIL_API_TOKEN` と照合する。
- **トークン未設定は全拒否**（500 "not configured"）。設定を忘れた状態で
  無認証APIとして公開される事故を防ぐ。
- 照合は両値のSHA-256を `timingSafeEqual` で比べる（比較時間から値を
  探らせない）。
- 認証失敗は一律 401。「形式が違う」「値が違う」を区別して返さない。

トークンは十分に長いランダム値（32バイト以上）を運用者が生成して
Cloudflare Workers の環境変数に登録する。**リポジトリ・ドキュメント・
静的サイトのどこにも書かない。**

## §5 リクエスト

| フィールド | 型 | 必須 | 内容 |
| --- | --- | --- | --- |
| `subject` | string | ○ | 件名。250文字まで |
| `text` | string | ○ | 本文（テキストメール）。100,000文字まで |
| `recipients` | string[] | ○ | 宛先。1〜500件 |
| `replyTo` | string | – | 返信先。メールアドレス形式 |
| `dryRun` | boolean | – | `true` なら1通も送らず送信計画だけ返す |

宛先の扱い:

- 前後の空白を落としたうえで形式を検査する。
- 大文字小文字だけが違う宛先は1件にまとめる（送信には最初に現れた表記を使う）。
- **形式が不正な宛先が1件でもあれば、全体を400にして送らない。**
  OCR由来のデータには読み取りミスが混ざりうるため、「送れる分だけ送る」と
  送られなかった宛先の存在に気づけない。どの宛先が不正かは応答の
  `invalidRecipients` に載る。事前確認には `dryRun` を使う。

## §6 応答

成功（200）:

```json
{ "sentCount": 200, "duplicateCount": 3, "batches": [
    { "recipientCount": 90, "messageId": "..." },
    { "recipientCount": 90, "messageId": "..." },
    { "recipientCount": 20, "messageId": "..." } ] }
```

dryRun（200）:

```json
{ "dryRun": true, "recipientCount": 200, "duplicateCount": 3, "batchCount": 3 }
```

エラー:

| 状態 | 意味 |
| --- | --- |
| 400 | 検証エラー。`error` に利用者向けメッセージ。不正な宛先があれば `invalidRecipients` |
| 401 | 認証失敗 |
| 500 | サーバー側の設定不備（トークンまたはGmail資格情報の未設定） |
| 502 | 送信が途中で失敗。**`sentCount` に送信済み件数が載る** |

**送ってしまったメールは取り消せない。** 502のときは残りの送信を打ち切って
あるので、呼び出し側は `sentCount` を見て、送信済みの宛先を除いた残りだけを
送り直す。

## §7 送信の仕様

- 宛先は **90件ずつのBCC** に分割し、1通ずつ**直列に**送る。90件なのは、
  無償Gmailの「1通あたり100宛先まで」に余裕を持たせるため。直列なのは、
  失敗時に「どこまで送れたか」を確定させるためと、レート制限を無用に
  突かないため。
- **To は送信元自身**（`MAIL_FROM`）。BCCだけのメールは迷惑メール判定を
  受けやすく、To に他人のアドレスを晒すこともできないため。
- Bcc ヘッダーはアドレスごとに折り返す（RFC 5322 の1行998文字制限）。
- 宛先・件名・返信先に改行を含む値は送信前に例外で止める
  （メールヘッダーインジェクション対策）。
- 送信は Gmail API を fetch で直接叩く（外部SDKなし）。認証は送信元
  アカウントのOAuthリフレッシュトークン。

## §8 制限値と理由

| 値 | 制限 | 理由 |
| --- | --- | --- |
| 宛先/リクエスト | 500 | Gmailの1日あたり送信上限（アカウント種別により500〜2000宛先）を1回の操作で使い切らない |
| 宛先/通（BCC） | 90 | 無償Gmailの1通100宛先制限に余裕を持たせる |
| 件名 | 250文字 | 誤入力の早期検出 |
| 本文 | 100,000文字 | 同上 |

## §9 運用上の注意（送信者の責務）

- **特定電子メール法**: 名刺交換の相手への広告宣伝メールは事前同意なしに
  送信できる区分だが、**送信者の氏名・名称、受信拒否の申出先（メール
  アドレス等）を本文に表示する義務がある。** 受信拒否の申出があった相手は
  台帳側で管理し、以後の宛先に含めないこと。本文の内容はAPIでは検査しない。
- Gmailの送信上限に注意する。上限を超えるとアカウントが一時的に送信停止に
  なる。大量に送る日は他の自動送信（交流会の参加確定メール）と送信元を
  共有していることを考慮する。
- 短時間に大量送信すると受信側で迷惑メール判定を受けやすい。数百件規模を
  超える運用が常態化するなら配信SaaSへの移行を検討する（§12）。

## §10 環境変数

| 名前 | 内容 |
| --- | --- |
| `CARD_MAIL_API_TOKEN` | このAPIの呼び出しを許可するトークン（新設） |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `GMAIL_REFRESH_TOKEN` / `MAIL_FROM` | Gmail送信の資格情報と送信元。交流会アプリと同じ値を読む |

Gmail系を交流会アプリと同じ名前で読むのは、送信元が同じアカウントで
デプロイ先も同じ Workers 環境のため。同じ秘密を二重登録すると
ローテーション時に片方だけ更新されて壊れる。コードの独立は読み口
（`lib/card-mail/config.mjs`）を分けることで保つ。

## §11 テスト

`tests/unit/card-mail.mjs`（`node tests/run.mjs card-mail`）。
Gmail API は偽の fetch で置き換え、実送信はしない。

## §12 採用しなかった提案とその理由

- **サーバーが台帳を直接読む**: drive.file トークンはブラウザのメモリ上に
  しかなく、サーバーへ送らないのが要件（§FR-02）。サーバー用に別の資格情報
  （サービスアカウント等）を持つと、利用者のドライブへの常時アクセス権を
  当社が持つことになり、「当社サーバーを通さない」という
  card-ocr / receipt-ocr の設計方針と矛盾する。
- **card-ocr アプリの画面からこのAPIを直接呼ぶ**: 要件定義書 §12 が許す
  通信先3系統に自社APIを足す要件変更が必要になるうえ、APIトークンを
  静的サイトに置くことになり認証が成立しない。画面からの送信が必要に
  なったら、利用者認証の設計とあわせて版を上げて検討する。
- **交流会アプリの管理者セッション（`tsam-event-admin`）で守る**: 系を
  またぐ（CLAUDE.md「共存している3つの系」）。Cookie の path も
  `/event/admin` に限定されている。
- **宛先ごとに1通ずつ送る（To 個別）**: 宛先数だけAPI呼び出しが増え、
  送信上限とレート制限に触れやすい。宛名の差し込みが必要になったら再検討。
- **メール配信SaaS・外部SDKの導入**: dependencies を増やさない方針
  （AGENTS.md、CLAUDE.md「外部SDKを使わない」）。開封率計測や数千件規模の
  配信が必要になった時点で、事前確認のうえ再検討する。
