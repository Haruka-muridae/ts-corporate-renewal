# Portal 画面仕様書 v1.5.1

対象範囲: `public/portal/index.html` / `public/portal/portal.js` / `public/auth/auth.css`（`.auth-portal-*` `.auth-apps*` `.auth-app-card*` `.auth-account*` `.auth-api-panel*`）

アプリの並び方と配置データは [apps-grid-spec-v1.md](./apps-grid-spec-v1.md) が定める。

改訂履歴は[末尾](#改訂履歴)にある。

## §1 位置づけ

Portal はログイン後の最初の画面であり、**アプリを選ぶための画面**である。

読み物ではないため、名乗り直し・導入文・説明文を置かない。
画面を開いた人がまず見るべきものはアプリの一覧であり、
それより上に置くものは少ないほどよい。

認証の扱いは [login-page-detailed-spec-v3.md](./login-page-detailed-spec-v3.md) に従う。
本仕様書はレイアウトと表示条件だけを定める。

`portal.js` がサーバーへ問い合わせ、**有効と答えたときだけ**外す（§8）。

### §2-1 上端から詰める

`<main>` に `.auth-main--top` を付け、**縦センタリングを外す**。

`public/auth/auth.css` の既定（`.auth-main`）は `justify-content: center` である。
入力欄が数個しかないログイン系の画面には合うが、
一覧が縦に伸びる Portal に当てると、内容が画面の高さに満たないあいだ
上に大きな空白ができ、ヘッダーバーが宙に浮く。

上余白は 0 にして、**帯そのものをビューポート上端へ接させる**。
文字の逃げは `.auth-portal-bar` の内側の余白（`padding-top: 14px`）で作る。

`.auth-main--top` は 768px 以上のメディアクエリでも上余白を 0 に戻す。
`.auth-main` 側が一括指定（`padding: 48px 24px 56px`）で上書きしてしまうため。

**この扱いは `/portal/` だけに適用する。** 他の画面の縦センタリングは変えない。

## §3 ヘッダーバー

`.auth-portal-bar`。1本の細い帯に、画面名・肩書き・ログアウトをまとめる。

| 位置 | 内容 | 要素 |
| --- | --- | --- |
| 左 | 「Portal」＋逆三角（アカウント情報の開閉トグル） | `h1.auth-portal-bar__title > button#portal-account-toggle` |
| 左 | ロールバッジ（管理者のみ） | `#portal-user-badge` |
| 右 | 「API設定」＋逆三角（API設定の開閉トグル） | `button#portal-api-toggle` |
| 右端 | ログアウト | `#portal-logout` |

- 見出しは `h1` のまま。見た目を小さくしても文書構造は変えない
- **メールアドレスは帯に出さない。** アカウント情報パネル（§7）へ移した
- 帯に押せる要素はこの**3つだけ**。順序も左からこのとおりに固定する
- 折り返しは `flex-wrap` に任せ、幅ごとの分岐を持たない

API設定トグルはアカウント側と同じ作り（`button` ／ `aria-expanded` ／
`aria-controls` ／ 押下領域 44px ／ 逆三角が180度回る）にする。
見出しを包む必要がないぶん、こちらは `button` 単体で置ける。

### §3-3 開閉トグルは見出しの内側に置く

```html
<h1 class="auth-portal-bar__title">
  <button id="portal-account-toggle" type="button"
          aria-expanded="false" aria-controls="portal-account-panel">
    Portal
    <svg class="auth-portal-bar__chevron" aria-hidden="true">…</svg>
  </button>
</h1>
<span id="portal-user-badge" hidden></span>
```

**`h1` を `button` の内側へ入れてはならない。** 順序はこの向きに固定する。

`button` の子孫は読み上げ上ひとかたまりに潰れる（presentational children）。
`h1` を内側に置くと見出しとして拾えなくなり、見出しジャンプで移動する利用者が
この画面の主題を掴めなくなる。§10-1 で `h1` を維持した判断がそこで無効になる。
包む向きなら「Portal（見出し）」と「Portal（ボタン・折りたたみ）」の両方が残る。

`button` の内容物は「Portal」と逆三角だけにする。
逆三角は `aria-hidden="true"` の装飾であり、読み上げでは状態を `aria-expanded` が伝える。
**ロールバッジをトグルの内側へ入れない。** ボタン名が「Portal 管理者」になり、
同時に `h1` の読み上げ名も濁る。バッジは押せる範囲の外に置く。

逆三角の回転は CSS が `aria-expanded` を見て決める
（`.auth-portal-bar__toggle[aria-expanded='true'] .auth-portal-bar__chevron`）。
JS が付け外しする専用クラスを持たないため、見た目と支援技術の状態がずれない。

### §3-1 ブランドブロックを置かない

`.auth-brand`（TSAM AI ／ TSアセットマネジメント合同会社）は **Portal には置かない**。

ログイン前の画面では「どこのサイトか」を示す必要があるが、
ログイン後は既に分かっている。社名はフッターに残す。

**この変更は `/portal/` だけに適用する。** `/login/` `/pricing/` `/password/*`
`/payment/*` `/legal/*` のブランドブロックはそのまま残す。

### §3-2 ロールバッジ

サーバーが返した `user.isAdmin === true` のときだけ出す。
**メールアドレスで判定しない。**

これは表示だけであり、権限そのものはサーバー側が持つ。
バッジを消しても管理者機能は使えるし、出しても権限は増えない。

## §4 削除した要素

| 要素 | 理由 |
| --- | --- |
| `.auth-brand` ブロック | §3-1 |
| 「ご利用になるアプリを選択してください。」 | グリッドを見れば分かる。1行ぶんアプリを下げる価値がない |
| カード内の「◯◯を開く」リンク | カード全体をリンクにしたため不要（§6-2） |
| ヘッダーバーのメールアドレス（`#portal-user-email`） | アカウント情報パネルへ移した（§7）。同じ値を2か所に出さない |
| 画面下部のアカウント情報カード | 同上。パネルへ移設した（§7-2） |
| **0件のときの「準備中」16枠とページ送り（v1.5）** | 節ごと隠す（§6・§6-1）。押せないものを16個数えさせない |
| **AI Studio の URL の再掲（v1.5）** | 同じURLを2度読ませていた（§7-5） |
| **「新しいタブで開きます。」（v1.5）** | `target="_blank"` が示す。文で断るほどの話ではない（§7-5） |

メールアドレスは `#portal-account-email` の1か所だけに出る。
`portal.js` の `render()` も1か所へ書くだけになった。

## §5 APIキー未設定バナー

`.auth-portal-banner` / `#portal-api-key-banner`。
鍵の図・本文「Gemini APIキーが未設定です。」・設定画面への導線を並べる。

### §5-1 表示条件

`portal.js` の `shouldShowApiKeyBanner()` が判定する。

```js
export function shouldShowApiKeyBanner() {
  return !KeyStore.has(PROVIDERS.gemini);
}
```

| 状態 | 表示 |
| --- | --- |
| KeyStore に `gemini` が無い | **出す** |
| KeyStore に `gemini` がある | 出さない |

**サーバーへ問い合わせない。** 引数も取らない。

キーは当社が預かっていない（[keystore-spec-v1.md](./keystore-spec-v1.md) §2）ため、
サーバーは設定済みかどうかを知らないし、知る必要もない。
判断の材料はこの端末の KeyStore だけとする。

保存が済んだら即時に消し、削除したら即時に戻す。
`renderApiKeyState()` が保存状態を見て、パネルとバナーを同時に描き直す。
2か所で別々に判断すると、片方だけ古い表示が残る。

### §5-2 導線はページを移動しない

`#portal-api-key-action`。**`a` ではなく `button`** とする。

押すとAPI設定パネル（§7-3）を開き、入力欄へ焦点を移す。
画面は移動しない。設定先が同じ画面の中にあるのだから、
移動する理由がない。

`a` のままだと押した瞬間に画面が切り替わり、
「どこへ行ったのか」を利用者が追う必要が出る。

## §6 アプリグリッド

**定義は [apps-grid-spec-v1.md](./apps-grid-spec-v1.md) が持つ。**

並び方・配置データ・ページ送り・アプリ定義（`public/portal/app-registry.js`）は
すべてそちらで定める。ここには Portal 側から見た接点だけを書く。

| 接点 | 内容 |
| --- | --- |
| 位置 | APIキーバナー（§5）より**下**。バナーとの上下関係は変えない |
| 要素 | `section#portal-apps-section.auth-apps` > `#portal-apps`（ページ群）＋ `#portal-apps-pager` |
| 幅 | `min(360px, 100%)` で中央寄せ。**PCでも広げない**（apps-grid §3） |
| 描画 | `portal.js` の `renderAppsGrid()`。`guardPage` が利用者を返したあとに呼ぶ |
| **表示（v1.5）** | **お気に入りが0件のあいだは節ごと `hidden`**（apps-grid §2-3）。下の「全アプリ一覧」は常に出る |

### §6-1 空状態のメッセージを置かない

「ご利用可能なアプリは順次追加されます。」（旧 `#portal-apps-empty`）は**廃止した。**

0件のときはお気に入りの節そのものが消える（v1.5）。
無いものについて文で断る必要はない。

v1.4 までは0件でも「準備中」の枠が16個並んでいた。
Portal は「アプリを選ぶための画面」（§1）であり、
押せない枠を16個数えさせる画面ではない。

### §6-2 カード

`.auth-app-card` > `a.auth-app-card__link` > アイコン・名前。

- **カード全体が1つのリンク**。名前・アイコンのどちらを押しても同じ場所へ行く
- 中央寄せ、角丸 12px
- アイコンは `aria-hidden="true"`。名前の1文字目を絵にしただけなので読み上げでは繰り返さない

角丸 12px はフォームのカード（`--radius-card: 6px`）より大きい。
押せる面であることを形でも示すため、意図的に変えている。

一言説明（`description`）は**置かない**。2列の枠に収まらず、
アプリを選ぶのに名前とアイコンで足りる。

## §7 アカウント情報

`.auth-account` / `#portal-account-panel`。**ヘッダーバー直下の開閉パネル。**
枠線1px・角丸 `--radius-card`（6px）。

項目名と値を**縦に積む**（`dl`）。

| 項目名 | 値 |
| --- | --- |
| メールアドレス | `#portal-account-email` |
| ご契約の状態 | `#portal-account-subscription` |
| パスワード | 「パスワードを変更する」→ `../password/reset/` |

1行に繋ぐ形は採らない。長いメールアドレスと契約状態が地続きになり、
どこまでがアドレスなのか読み取れなくなる（§10-4）。

契約状態は内部値をそのまま出さず、日本語へ置き換える
（`active` → 「ご利用中」、`exempt` → 「決済不要（管理者）」など）。
`paymentExempt === true` の利用者は契約状態より優先して「決済不要（管理者）」を出す。

### §7-1 開閉

| 項目 | 定め |
| --- | --- |
| 初期状態 | **閉**。配信されるHTMLの時点で `hidden`、`aria-expanded="false"` |
| 開く操作 | §3-3 のトグル。クリック／Enter／Space |
| 開いた印 | `aria-expanded="true"`／`hidden` を外す／逆三角が180度回る |
| 状態の保存 | **しない。** 再読み込みで閉に戻る |
| 位置 | ヘッダーバーと APIキーバナー（§5）のあいだ |

状態を持つのは `aria-expanded` と `hidden` の2つだけとする。
見た目のための第3の状態（クラスなど）を増やさない。

`portal.js` は `click` だけを見る。`button` 要素なので Enter と Space は
既定動作で `click` になる。`keydown` を自前で拾うと二重に発火する。

**開閉状態を `localStorage` へ書かない。** アカウント情報は普段見るものではなく、
開いたままにしておく理由がない。保存する値が増えれば、
その値を消す責任（ログアウト時・失効時）も増える。

### §7-2 画面下部には置かない

v1 では一覧より下の小型カードだった。ヘッダーバー直下へ移した。

閉じているあいだは高さを持たないため、アプリの一覧を押し下げない。
下部に置いていたときは、アプリが増えるほどアカウント情報が遠ざかっていた。

### §7-3 API設定パネル

`.auth-account.auth-api-panel` / `#portal-api-panel`。
アカウント情報と**同じ枠**（`.auth-account`）を土台にする。
2枚のパネルの見た目を揃えるため、枠を別に定義しない。

中身は上から次の順に置く。

| 位置 | 内容 |
| --- | --- |
| 見出し | 「Gemini APIキー」 |
| 説明 | 保管の説明とキーの取得手順（§7-5） |
| 未保存のとき | 入力欄（`type="password"` ＋ 表示切替）と「保存する」 |
| 保存済みのとき | 伏せ字表示（前後4文字）と「変更」「削除」 |
| 削除を押したとき | 確認（「削除する」「やめる」） |
| 末尾 | 結果表示（`#portal-api-message`。保存・疎通・エラー） |
| 末尾 | Google Workspace の紹介（§7-6）。**本文は `details` で畳む**（v1.5） |

伏せ字の作り方と、入力欄へ保存済みの値を書き戻さない決めごとは
[keystore-spec-v1.md](./keystore-spec-v1.md) §5 に従う。

#### 保存を押したときの順序

1. 空なら「APIキーを入力してください。」で止める
2. KeyStore へ保存する。保存できなければそこで止める
   （プライベートモード等。ログイン時と同じ言い回しで案内する）
3. **保存はここで確定**。入力欄を空にし、表示を保存済みへ切り替え、バナーを消す
4. 続けて疎通テストを1回だけ実行する
5. 結果を文章にして出す

| 状況 | 文言 | 種別 |
| --- | --- | --- |
| 疎通成功・形式も一致 | 保存しました。接続を確認しました。 | 完了 |
| 疎通成功・形式が違う | 保存しました。一般的なGemini APIキーの形式と異なります。接続を確認しました。 | お知らせ |
| 400 / 401 / 403 | …このAPIキーでは接続できませんでした。Google AI Studio で発行したキーをご確認ください。 | エラー |
| 429 | …利用上限に達している可能性があります。時間をおいて再度お試しください。 | エラー |
| 応答なし | …接続を確認できませんでした。通信環境をご確認ください。 | エラー |
| その他 | …接続を確認できませんでした（HTTP nnn）。 | エラー |

**疎通成功でも形式が違うときは「完了」と言い切らない。**
「完了」とだけ読み上げると、添えた警告が流される。

保存とテストが独立である理由、形式チェックで拒否しない理由、
参照系のAPIだけを使う理由は
[keystore-spec-v1.md](./keystore-spec-v1.md) §8-2〜§8-4 にある。

#### 削除

「削除」を押しただけでは消さない。確認を1枚挟む。
取り消せない操作であり、押し間違いで39文字の再取得になるため。

確認はパネルを閉じたり開き直したりすると消える（次に押すときは最初から）。

### §7-4 2枚のパネルは排他

**アカウント情報とAPI設定は同時に開かない。** 開いたほうが勝ち、もう一方は閉じる。

両方開くとヘッダーの下が渋滞し、アプリの一覧が画面の外へ押し出される。
Portal は「アプリを選ぶための画面」（§1）なので、
設定のために一覧が見えなくなる状態を作らない。

実装は `PANELS` 配列に `{ toggle, panel }` を並べ、
`setPanelOpen()` が開くときだけ他方を閉じる形にする。
パネルが3枚目に増えても、配列へ1行足すだけで排他が効く。

### §7-5 案内文（キーの取得手順）

パネル上部に3段で置く。**手順の話だけを書く。1段は1文にする。**

1. 保管の説明。「Gemini APIキーはお使いの端末（ブラウザ）にのみ保存され、当社サーバーには送信されません。」
2. 取得先。Google AI Studio への**リンクだけ**（v1.5）
3. 費用。「**Googleアカウントがあれば無料で発行できます。** Google Workspace などの有料契約は必要ありません。」

#### 遷移先は `/apikey` にする

| 項目 | 値 |
| --- | --- |
| リンクテキスト | 「Google AI Studio」 |
| `href` | `https://aistudio.google.com/apikey`（v1.5 以降、URL を文字では出さない） |

**トップURL（`https://aistudio.google.com/`）を使わない。**

実機で確認したところ、トップURLは Playground に着地する。
そこからキーを取るには、メニューを開いて鍵アイコンを探す必要があり、
「キーはここで取れます」と案内した先が取得画面でないことになる。
`/apikey` はキー管理画面へ直行する。

戻していないことをテストで固定している（§11）。
`aistudio.google.com` を含むかだけの検査では、`/apikey` が落ちても通る。

#### URL の再掲と「新しいタブで開きます」は落とした（v1.5）

v1.3〜v1.4 では、リンクの隣に**同じURLを文字としても置き**（`.auth-api-panel__url`）、
さらに「新しいタブで開きます。」を添えていた。**どちらも削除した。**

この1段だけで、同じ39文字のURLを2度読ませ、開き方の断りまで並べていた。
320px では3行になり、キーを入れに来た人の入力欄がそのぶん下がる。
Portal の改修の目的（画面から数えるものを減らす）と正面から反する。

**採らなかったこと（v1.3 の判断）は次のとおりで、承知のうえで捨てている。**
「押す前に行き先を確かめたい種類のリンクなので、触れない端末でも
確かめられるように文字でも置く」。行き先を事前に確かめる手段は
ホバーと長押しだけになった。リンクテキストが「Google AI Studio」で
遷移先が同名のサービスであること、`target="_blank"` で現在の画面が
そのまま残ることを、その代わりとする。

`.auth-api-panel__url` の CSS（`word-break: break-all`）は
`public/auth/auth.css` から**削除した**（v1.5.1）。
`auth.css` は認証系画面の共有スタイルなので、使い先が無いまま残しておくと
「どこかで使っているのだろう」と読む側に確認の手間を強いる。
再掲を戻すことになったら、そのとき書き直す。

#### 「有料契約は不要」を必ず添える

3段目は省略しない。同じパネルの末尾に Google Workspace の紹介（§7-6）があるため、
**「キーを取るには Workspace が要る」と読まれる余地を先に潰しておく。**

### §7-6 Google Workspace の紹介

パネルの**末尾**に、区切り線を持つ別ブロック（`aside.auth-api-panel__promo`）で置く。
**本文は `details` で畳む**（v1.5）。

| 項目 | 定め |
| --- | --- |
| リンク先 | `https://referworkspace.app.goo.gl/2KTq` |
| 要素 | `#portal-workspace-link`。`target="_blank"` ＋ `rel="noopener noreferrer"` |
| 見出し | 「Google Workspace のご案内（紹介リンク）」（`h3`。パネルの `h2` の下） |
| 開閉 | `details > summary`「くわしく見る」。**既定は閉**。状態は保存しない |
| 推奨文 | 独自ドメインのメールなど、ビジネス用途で Google を使うなら勧める趣旨 |

#### 畳む理由と、畳んだときに見えているもの

ここはAPIキーを設定しに来た人にとって本題ではない。
開いたままだと本文5行ぶんがパネルの末尾に積まれ、
「保存する」を押したあとの結果表示（`#portal-api-message`）より下に、
読まなくてよい文章が常に居座ることになる。

畳んだ状態で見えているのは**見出しの1行だけ**である。
そこに「（紹介リンク）」を必ず入れる。
`details` の中身は畳んでいるあいだ読み上げにも `innerText` にも出ないため、
見出しだけを見て「ただの案内リンク」と受け取られる形にしない。

#### 開いたときの表示から落としてはならない3点

1. **【紹介リンク】** — リンクと**同じ段落**に置く
2. **有料サービスである** — 「無料」と書かない。転送先は料金ページである
3. **キー取得には不要である** — 「Gemini APIキーの取得に Google Workspace は必要ありません。」

3点とも、抜けても画面は正常に見えてしまう。だからテストで固定する（§11）。

**リンクを押すには開くほかない**ので、この3点は必ずリンクと同時に目に入る。
加えて3の趣旨（有料契約は不要）は、§7-5 の3段目として畳まずに残してある。

#### 見出しは `details` の外に置く

`summary` の中へ `h3` を入れない。

`summary` は `display: list-item` であり、`h3`（block）を入れると
開閉の三角だけが1行を占め、見出しが次の行へ落ちる（Chrome 実機で確認）。
直すには CSS が要るが、`/portal/` にインラインCSSを置かない（§9）。
`h3` を `details` の前に置けば、追加のCSSなしで
「見出し1行 ＋ 『くわしく見る』1行」に収まる。

`aside` の名前は引き続き `aria-labelledby="portal-api-promo-title"` で
この `h3` から取る。

#### `summary` の押下領域は 44px 以上（v1.5.1）

UA 既定のままでは高さ約30pxで、この画面の他の操作子（トグル・ボタン）に
そろえた 44px に届いていなかった。`public/auth/auth.css` の
`.auth-api-panel__promo summary` に `min-height: 44px` と上下の余白を足して解消した。

規則の置き場所は `auth.css` である。`/portal/` にインラインCSSを置かない（§9）ため、
共有スタイル側へ足すほかない。セレクタは `.auth-api-panel__promo` 配下に限っており、
この class を持つのは `/portal/` だけなので、他の認証系画面には効かない。

**`display` は `list-item` のまま残す。** `flex` にすれば行の中央へ揃えられるが、
開閉の三角（`::marker`）が消え、押せば開くことが「くわしく見る」という
字面からしか分からなくなる。高さは余白で作り、手がかりは減らさない。
高さと `display` の両方をテストで固定している（§11）。

#### 置き場所は末尾にする

手順文の直後に挟まない。キーを入れに来た人の入力欄が下へ押し下げられる。
「手順文と区切る」ことと「手順文の直後に置く」ことは別である。

#### `/apps/` の実装を取り込まない

`public/apps/shared/external-links.js` に同じ紹介リンクの実装がある。
文言の方針（「無料」と書かない・紹介である旨・外部サイトである旨）は
そこを参考にしたが、**import はしない。**

`public/apps/` は TSAM AI のテスト環境であり、本番（`public/auth/` `public/portal/`）が
そこへ依存すると向きが逆になる。URLと文言は `public/portal/index.html` に直接置く。

**したがって、このURLはリポジトリ内に2か所ある。**
紹介プログラムのURLが変わったときは両方を直すこと。
片方だけ直しても画面は正常に見えるため、気づけない。

## §8 認証まわり（変更なし）

今回の改修で **`guardPage` / `verifySession` の挙動は1行も変えていない。**

- `#portal-content` は配信HTMLの時点で `hidden`
- `guardPage({ next: 'portal' })` がサーバーへ問い合わせる
- 有効と答えたときだけ描画する。ローカルの値を見た先読み描画はしない
- 無効なら `/login/?next=portal` へ送り、手元のトークンを消す

静的ホスティングでは HTML と JS の取得自体は防げない。
守れるのはサーバー側のデータであって、この画面のソースではない。
詳細は [SECURITY_NOTES.md](../../SECURITY_NOTES.md)。

## §10 設計判断の記録

### §10-1 「Portal」を `h1` のまま小さくした

見た目の階層と文書の階層は別物である。
帯の中で目立たせないのは視覚的な判断であり、
`div` や `p` に落とすと、見出しジャンプで移動する利用者が
この画面の主題を掴めなくなる。

### §10-2 カード全体をリンクにした

従来は「◯◯を開く」だけが当たり判定だった。
一覧から選ぶ画面で当たり判定が小さいのは、指で操作するほど不利になる。

### §10-3 バナーをフラグではなくパスで制御する

`enabled: false` のような真偽フラグにすると、
「フラグを立てたが画面はまだ無い」という組み合わせが作れてしまう。
遷移先そのものを条件にすれば、その状態は存在し得ない。

### §10-4 アカウント情報は項目名と値を縦に積む

改修の初版では1行に繋いだ（`user@example.com ／ ご利用中`）が、差し戻した。

区切り記号だけでは、どこまでがメールアドレスなのかが読み取れない。
アドレスは長さも形もまちまちで、`／` の前後が同じ大きさの地の文として続く。
項目名を添えて縦に積めば、読む側が区切りを探さずに済む。

カードの配置・枠線・角丸は変えていない。変えたのは中身の組み方だけである。

### §10-5 上端詰めは Portal だけに閉じる

`.auth-main` の `justify-content: center` を直接変えれば1行で済むが、
`/login/` `/password/*` `/payment/*` は縦センタリングのほうが収まりがよい。
共通クラスを直さず、修飾クラスを足す形にした。

「他の画面が中央寄せのままであること」もテストで固定している（§11）。
共通クラスを直した場合に落ちる。

### §10-6 ロールバッジは押せる範囲に含めない

改修の依頼は「見出し＋ロールバッジの並び一帯をトグルにする」だったが、
バッジはトグルの外に置いた。

`button` の内側に入れると、ボタンの読み上げ名が「Portal 管理者」になる。
このボタンが開くのはアカウント情報であって、管理者であることとは関係がない。
さらに `h1` がトグルを包む構造（§3-3）のため、`h1` の読み上げ名まで濁る。

`h1` を `button` の内側へ入れれば、バッジもまとめて1つのボタンにできる。
だがそれは `h1` を潰す（§3-3）。**見出しを残すことを優先した。**

押せる範囲は「Portal ＋ 逆三角」となり、`min-height: 44px` で指の当たる高さを取る。
バッジ（管理者のみ・幅40px程度）が押せないことによる不便は、
見出しを失うことと釣り合わない。

### §10-7 開閉状態を保存しない

`localStorage` へ書けば再訪時も開いたままにできるが、採らない。

保存する値が増えれば、消す責任も増える。
ログアウト時・セッション失効時・別の利用者がログインしたときに、
前の利用者の開閉状態が残っていてよい理由がない。

アカウント情報は毎回見るものではないため、
既定を閉にしておくほうが、アプリの一覧へ届くまでの距離が短い。

### §10-8 「見せておく」の既定を捨てた（v1.5）

v1.4 までの Portal は、まだ中身の無いものも形だけ見せていた。
0件でも「準備中」の枠を16個、ページ送りを2ページぶん、
使いようのない「初期状態に戻す」、押す前から全文が出ている紹介ブロック。

どれも1つずつは小さいが、**画面を開いた人が最初に見るもの**の量を決めていた。
Portal は「アプリを選ぶための画面」（§1）である。
選ぶ対象でないものは、必要になった時点で出す。

判断の順序をそろえておく。

1. いま押して意味のあるものか → 無ければ出さない（0件のグリッド・初期化ボタン）
2. 本題か → 違えば畳む（Google Workspace の紹介）
3. 同じことを2度言っていないか → 言っていれば1つ消す（URL の再掲・「新しいタブで開きます」）

**ただし「知らせるもの」は減らさない。**
取得失敗の通知と読み上げは、隠れる節の外へ移してある（apps-grid §2-3）。
畳んだ紹介の見出しには「（紹介リンク）」を残す（§7-6）。
短くしてよいのは、利用者の判断に要らない部分だけである。

### §11-1 v1.5 で揃っていなかった検査（v1.5.1 で解消）

何がどう落ちていたかを残す。

| 落ちていた検査 | 直した内容 |
| --- | --- |
| 「アプリ0件でも2ページぶんの枠が並ぶ」ほか、0件でグリッドが見えている前提のもの | 枠とドットは0件でも描かれている（隠すのは節だけ）ので DOM の検査はそのまま残し、「節ごと出さない」検査を足した |
| 「APIキーバナーはグリッドより上のまま」「パネルがアプリ一覧より上」 | お気に入りを1件入れてから測る形にした。入れるのは `renderAppsGrid(undefined, { stored })` で、`localStorage` は触らない（「配置データを書き込んでいない」検査を残すため） |
| ページ送りの Enter / Space | 同上。`hidden` の中の要素には `focus()` が入らず、キーを送っても何も起きない。**Space の検査は「1ページ目のまま」を見ていたため、効いていないのに通っていた**（偽陽性） |
| 「AI Studio の URL が文字としても見えている」 | `.auth-api-panel__url` ごと廃止したので検査も削除。行き先は `href` の検査で固定する |
| 「案内文と紹介ブロックが枠に収まる」 | 対象を案内文3段と紹介ブロックへ。**紹介は開いてから測る**（畳んだままでは `summary` の1行しか測らない） |
| 「有料サービス」「キー取得に Workspace は不要」を `innerText` で見るもの | `details.open = true` にしてから見る形にした |

**畳んだ `details` の中身は、座標では判定できない。**
`content-visibility: hidden` で描画だけを飛ばす作りのため、
中の要素の `getBoundingClientRect()` は0にならない（Chrome 実測で高さ15px）。
「畳まれている」ことは `innerText` に出ないことで見る。

`tests/unit/frontend.mjs` は v1.5 の変更後もそのまま通る（255/255 で確認済み）。
