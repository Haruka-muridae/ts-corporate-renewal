# Portal 画面仕様書 v1.1

対象範囲: `portal/index.html` / `portal/portal.js` / `auth/auth.css`（`.auth-portal-*` `.auth-app-card*` `.auth-account*`） / `auth/apps.js`

制定: 2026年7月31日／最終改訂: 2026年7月31日（v1.1）

改訂履歴は[末尾](#改訂履歴)にある。

---

## §1 位置づけ

Portal はログイン後の最初の画面であり、**アプリを選ぶための画面**である。

読み物ではないため、名乗り直し・導入文・説明文を置かない。
画面を開いた人がまず見るべきものはアプリの一覧であり、
それより上に置くものは少ないほどよい。

認証の扱いは [login-page-detailed-spec-v3.md](./login-page-detailed-spec-v3.md) に従う。
本仕様書はレイアウトと表示条件だけを定める。

```text
├──────────────────────────────────────────────────────┤

│ │ アカウント情報                                 │     │ §7 アカウント情報

│ │ ご利用中                                       │     │
│ │ パスワード                                     │     │

│ └──────────────────────────────────────────────┘     │
│                                                      │
│ 🔑 Gemini APIキーが未設定です。      APIキーを設定する    │ §5 バナー（既定は非表示）
│                                                      │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐               │
│ │   [録]   │ │   [ナ]   │ │   [名]   │               │ §6 アプリグリッド
│ │ アプリ名  │ │ アプリ名  │ │ アプリ名  │               │
│ │ 一言説明  │ │ 一言説明  │ │ 一言説明  │               │
│ └──────────┘ └──────────┘ └──────────┘               │
└──────────────────────────────────────────────────────┘

```

閉じているあいだ（既定）は、ヘッダーバーのすぐ下にアプリグリッドが来る。

`#portal-content` は配信されるHTMLの時点で `hidden` である。
`portal.js` がサーバーへ問い合わせ、**有効と答えたときだけ**外す（§8）。

### §2-1 上端から詰める

`<main>` に `.auth-main--top` を付け、**縦センタリングを外す**。

`auth/auth.css` の既定（`.auth-main`）は `justify-content: center` である。
入力欄が数個しかないログイン系の画面には合うが、
一覧が縦に伸びる Portal に当てると、内容が画面の高さに満たないあいだ
上に大きな空白ができ、ヘッダーバーが宙に浮く。

上余白は 0 にして、**帯そのものをビューポート上端へ接させる**。
文字の逃げは `.auth-portal-bar` の内側の余白（`padding-top: 14px`）で作る。

`.auth-main--top` は 768px 以上のメディアクエリでも上余白を 0 に戻す。
`.auth-main` 側が一括指定（`padding: 48px 24px 56px`）で上書きしてしまうため。

**この扱いは `/portal/` だけに適用する。** 他の画面の縦センタリングは変えない。

## §3 ヘッダーバー

`.auth-portal-bar`。1本の細い帯に、画面名・肩書き・ログアウトをまとめる。

| 位置 | 内容 | 要素 |
| --- | --- | --- |
| 左 | 「Portal」＋逆三角（アカウント情報の開閉トグル） | `h1.auth-portal-bar__title > button#portal-account-toggle` |
| 左 | ロールバッジ（管理者のみ） | `#portal-user-badge` |
| 右端 | ログアウト | `#portal-logout` |

- 見出しは `h1` のまま。見た目を小さくしても文書構造は変えない
- **メールアドレスは帯に出さない。** アカウント情報パネル（§7）へ移した
- 帯に押せる要素はトグルとログアウトの2つだけ
- 折り返しは `flex-wrap` に任せ、幅ごとの分岐を持たない

### §3-3 開閉トグルは見出しの内側に置く

```html
<h1 class="auth-portal-bar__title">
  <button id="portal-account-toggle" type="button"
          aria-expanded="false" aria-controls="portal-account-panel">
    Portal
    <svg class="auth-portal-bar__chevron" aria-hidden="true">…</svg>
  </button>
</h1>
<span id="portal-user-badge" hidden></span>
```

**`h1` を `button` の内側へ入れてはならない。** 順序はこの向きに固定する。

`button` の子孫は読み上げ上ひとかたまりに潰れる（presentational children）。
`h1` を内側に置くと見出しとして拾えなくなり、見出しジャンプで移動する利用者が
この画面の主題を掴めなくなる。§10-1 で `h1` を維持した判断がそこで無効になる。
包む向きなら「Portal（見出し）」と「Portal（ボタン・折りたたみ）」の両方が残る。

`button` の内容物は「Portal」と逆三角だけにする。
逆三角は `aria-hidden="true"` の装飾であり、読み上げでは状態を `aria-expanded` が伝える。
**ロールバッジをトグルの内側へ入れない。** ボタン名が「Portal 管理者」になり、
同時に `h1` の読み上げ名も濁る。バッジは押せる範囲の外に置く。

逆三角の回転は CSS が `aria-expanded` を見て決める
（`.auth-portal-bar__toggle[aria-expanded='true'] .auth-portal-bar__chevron`）。
JS が付け外しする専用クラスを持たないため、見た目と支援技術の状態がずれない。

### §3-1 ブランドブロックを置かない

`.auth-brand`（TSAM AI ／ TSアセットマネジメント合同会社）は **Portal には置かない**。

ログイン前の画面では「どこのサイトか」を示す必要があるが、
ログイン後は既に分かっている。社名はフッターに残す。

**この変更は `/portal/` だけに適用する。** `/login/` `/pricing/` `/password/*`
`/payment/*` `/legal/*` のブランドブロックはそのまま残す。

### §3-2 ロールバッジ

サーバーが返した `user.isAdmin === true` のときだけ出す。
**メールアドレスで判定しない。**

これは表示だけであり、権限そのものはサーバー側が持つ。
バッジを消しても管理者機能は使えるし、出しても権限は増えない。

## §4 削除した要素

| 要素 | 理由 |
| --- | --- |
| `.auth-brand` ブロック | §3-1 |
| 「ご利用になるアプリを選択してください。」 | グリッドを見れば分かる。1行ぶんアプリを下げる価値がない |
| カード内の「◯◯を開く」リンク | カード全体をリンクにしたため不要（§6-2） |
| ヘッダーバーのメールアドレス（`#portal-user-email`） | アカウント情報パネルへ移した（§7）。同じ値を2か所に出さない |
| 画面下部のアカウント情報カード | 同上。パネルへ移設した（§7-2） |

メールアドレスは `#portal-account-email` の1か所だけに出る。
`portal.js` の `render()` も1か所へ書くだけになった。

## §5 APIキー未設定バナー

`.auth-portal-banner` / `#portal-api-key-banner`。
鍵の図・本文「Gemini APIキーが未設定です。」・設定画面への導線を並べる。

### §5-1 今回は表示しない

**要素とスタイルは用意するが、常に非表示とする。**

キー管理画面が未実装であり、遷移先が無い。
「未設定です」と言いながら設定できない画面は、
利用者を行き止まりへ連れて行くだけである。

### §5-2 表示条件（将来有効化）

`portal.js` の `shouldShowApiKeyBanner(user)` が判定する。

```js
const API_KEY_SETTINGS_PATH = '';   // ← 遷移先が決まるまで空

export function shouldShowApiKeyBanner(user) {
  if (API_KEY_SETTINGS_PATH === '') {
    return false;                    // 行き先が無い間は必ず出さない
  }

  return user?.geminiApiKeyConfigured === false;
}
```

| 状態 | 表示 |
| --- | --- |
| `API_KEY_SETTINGS_PATH` が空 | **出さない**（今の状態） |
| `geminiApiKeyConfigured === false` | 出す |
| `geminiApiKeyConfigured === true` | 出さない |
| サーバーが答えていない（`undefined`） | 出さない |

サーバーが答えられない段階で「未設定」と決めつけない。
設定済みの利用者にも警告が出てしまう。

### §5-3 有効化の手順

1. キー管理画面を作り、そのパスを `API_KEY_SETTINGS_PATH` に入れる
   （サイトのルートからの相対パス。先頭に `/` を付けない）
2. `verifySession` の応答へ「キー設定済みか」を載せ、
   `portal.js` が `user.geminiApiKeyConfigured` として受け取れるようにする

**フラグを別に持たない。** パスが空なら必ず `false` を返すため、
「機能フラグを立てたが画面はまだ無い」という組み合わせが作れない。

有効化後の体裁（鍵の図・本文・導線がそろうこと、アプリ一覧より上に出ること、
320px で折り返して収まること）は、いまの時点でブラウザテストが確かめている。

## §6 アプリグリッド

### §6-1 データ

`auth/apps.js` の `PORTAL_APPS` から描画する。**この方式は変えない。**

| キー | 必須 | 内容 |
| --- | --- | --- |
| `id` | ○ | 識別子 |
| `name` | ○ | アプリ名 |
| `description` | | 一言説明 |
| `path` | ○ | サイトのルートからの相対パス。先頭に `/` を付けない |
| `icon` | | アイコンに出す1〜2文字（絵文字も可） |

`icon` を省略すると `name` の1文字目を使う。名前があればアイコンは必ず作れるため、
枠だけのカードが並ぶことはない。

`PORTAL_APPS` が空のあいだは、グリッドの代わりに
「ご利用可能なアプリは順次追加されます。」を出す（従来どおり）。

### §6-2 カード

`.auth-app-card` > `a.auth-app-card__link` > アイコン・名前・説明。

- **カード全体が1つのリンク**。名前・説明・アイコンのどこを押しても同じ場所へ行く
- 中央寄せ、角丸 12px
- アイコンは `aria-hidden="true"`。名前の1文字目を絵にしただけなので読み上げでは繰り返さない

角丸 12px はフォームのカード（`--radius-card: 6px`）より大きい。
押せる面であることを形でも示すため、意図的に変えている。

### §6-3 列数

| 画面幅 | 列 |
| --- | --- |
| 320px | 1 |
| 375px | 1 |
| 480px 以上 | 2 |
| 768px 以上 | **3（固定）** |

768px 以上を `auto-fit` にしない。幅次第で4列になり、カードが細くなる。

## §7 アカウント情報

`.auth-account` / `#portal-account-panel`。**ヘッダーバー直下の開閉パネル。**
枠線1px・角丸 `--radius-card`（6px）。

項目名と値を**縦に積む**（`dl`）。

| 項目名 | 値 |
| --- | --- |
| メールアドレス | `#portal-account-email` |
| ご契約の状態 | `#portal-account-subscription` |
| パスワード | 「パスワードを変更する」→ `../password/reset/` |

1行に繋ぐ形は採らない。長いメールアドレスと契約状態が地続きになり、
どこまでがアドレスなのか読み取れなくなる（§10-4）。

契約状態は内部値をそのまま出さず、日本語へ置き換える
（`active` → 「ご利用中」、`exempt` → 「決済不要（管理者）」など）。
`paymentExempt === true` の利用者は契約状態より優先して「決済不要（管理者）」を出す。

### §7-1 開閉

| 項目 | 定め |
| --- | --- |
| 初期状態 | **閉**。配信されるHTMLの時点で `hidden`、`aria-expanded="false"` |
| 開く操作 | §3-3 のトグル。クリック／Enter／Space |
| 開いた印 | `aria-expanded="true"`／`hidden` を外す／逆三角が180度回る |
| 状態の保存 | **しない。** 再読み込みで閉に戻る |
| 位置 | ヘッダーバーと APIキーバナー（§5）のあいだ |

状態を持つのは `aria-expanded` と `hidden` の2つだけとする。
見た目のための第3の状態（クラスなど）を増やさない。

`portal.js` は `click` だけを見る。`button` 要素なので Enter と Space は
既定動作で `click` になる。`keydown` を自前で拾うと二重に発火する。

**開閉状態を `localStorage` へ書かない。** アカウント情報は普段見るものではなく、
開いたままにしておく理由がない。保存する値が増えれば、
その値を消す責任（ログアウト時・失効時）も増える。

### §7-2 画面下部には置かない

v1 では一覧より下の小型カードだった。ヘッダーバー直下へ移した。

閉じているあいだは高さを持たないため、アプリの一覧を押し下げない。
下部に置いていたときは、アプリが増えるほどアカウント情報が遠ざかっていた。

## §8 認証まわり（変更なし）

今回の改修で **`guardPage` / `verifySession` の挙動は1行も変えていない。**

- `#portal-content` は配信HTMLの時点で `hidden`
- `guardPage({ next: 'portal' })` がサーバーへ問い合わせる
- 有効と答えたときだけ描画する。ローカルの値を見た先読み描画はしない
- 無効なら `/login/?next=portal` へ送り、手元のトークンを消す

静的ホスティングでは HTML と JS の取得自体は防げない。
守れるのはサーバー側のデータであって、この画面のソースではない。
詳細は [SECURITY_NOTES.md](../../SECURITY_NOTES.md)。

## §9 スタイルの制約

- 色は `css/style.css` のカスタムプロパティ（`--c-*` / `--color-*`）だけを使う。
  **`/portal/` 専用の色を新しく定義しない**
- 追加したクラスはすべて `auth/auth.css` に置く。`/portal/` にインラインCSSを持たない
- 320〜1440px で横スクロールを出さない

寸法（角丸 12px、アイコン 44px）はモックアップに合わせた値であり、
色ではないため個別に指定している。

## §10 設計判断の記録

### §10-1 「Portal」を `h1` のまま小さくした

見た目の階層と文書の階層は別物である。
帯の中で目立たせないのは視覚的な判断であり、
`div` や `p` に落とすと、見出しジャンプで移動する利用者が
この画面の主題を掴めなくなる。

### §10-2 カード全体をリンクにした

従来は「◯◯を開く」だけが当たり判定だった。
一覧から選ぶ画面で当たり判定が小さいのは、指で操作するほど不利になる。

### §10-3 バナーをフラグではなくパスで制御する

`enabled: false` のような真偽フラグにすると、
「フラグを立てたが画面はまだ無い」という組み合わせが作れてしまう。
遷移先そのものを条件にすれば、その状態は存在し得ない。

### §10-4 アカウント情報は項目名と値を縦に積む

改修の初版では1行に繋いだ（`user@example.com ／ ご利用中`）が、差し戻した。

区切り記号だけでは、どこまでがメールアドレスなのかが読み取れない。
アドレスは長さも形もまちまちで、`／` の前後が同じ大きさの地の文として続く。
項目名を添えて縦に積めば、読む側が区切りを探さずに済む。

カードの配置・枠線・角丸は変えていない。変えたのは中身の組み方だけである。

### §10-5 上端詰めは Portal だけに閉じる

`.auth-main` の `justify-content: center` を直接変えれば1行で済むが、
`/login/` `/password/*` `/payment/*` は縦センタリングのほうが収まりがよい。
共通クラスを直さず、修飾クラスを足す形にした。

「他の画面が中央寄せのままであること」もテストで固定している（§11）。
共通クラスを直した場合に落ちる。

### §10-6 ロールバッジは押せる範囲に含めない

改修の依頼は「見出し＋ロールバッジの並び一帯をトグルにする」だったが、
バッジはトグルの外に置いた。

`button` の内側に入れると、ボタンの読み上げ名が「Portal 管理者」になる。
このボタンが開くのはアカウント情報であって、管理者であることとは関係がない。
さらに `h1` がトグルを包む構造（§3-3）のため、`h1` の読み上げ名まで濁る。

`h1` を `button` の内側へ入れれば、バッジもまとめて1つのボタンにできる。
だがそれは `h1` を潰す（§3-3）。**見出しを残すことを優先した。**

押せる範囲は「Portal ＋ 逆三角」となり、`min-height: 44px` で指の当たる高さを取る。
バッジ（管理者のみ・幅40px程度）が押せないことによる不便は、
見出しを失うことと釣り合わない。

### §10-7 開閉状態を保存しない

`localStorage` へ書けば再訪時も開いたままにできるが、採らない。

保存する値が増えれば、消す責任も増える。
ログアウト時・セッション失効時・別の利用者がログインしたときに、
前の利用者の開閉状態が残っていてよい理由がない。

アカウント情報は毎回見るものではないため、
既定を閉にしておくほうが、アプリの一覧へ届くまでの距離が短い。

| **パネルの収まり（v1.1）** | 5幅で開いても横スクロールしない／開いたパネルが表示領域に収まる |
| ロールバッジ | 一般利用者では非表示、管理者では表示され左ブロックに入る |

上端詰めの検査はバーの座標を実測する。
縦センタリングを戻すと、320px で 38px、768px 以上で 123px、
内容の短い縦長画面（1024×1400）では 410px の空白が出て落ちる。

キーボードの検査は `Input.dispatchKeyEvent` で実際にキーを送る。
`click()` の呼び出しだけでは、`button` 以外の要素へ変えたときに気づけない。

ログイン後の画面は `verifySession` の**応答だけ**を差し替えて確かめる。
`guardPage` の手順は本物のまま動かすため、
「サーバーが答えるまで描画しない」という順序も同時に検証されている。
