## §1 3便の分担

この画面は3回に分けて作る。**便をまたいだ先取り実装をしない。**

| 便 | 内容 | 状態 |
| --- | --- | --- |
| **第1便** | 器（グリッド・ページ送り）と配置データの基盤 | **完了（v1）** |
| **第2便** | 並べ替え（ドラッグ）／グリップ／保存書き込み／「初期配置に戻す」 | **完了（v1.1）** |
| **第2.5便** | お気に入り＋カタログへの分割／仮アプリ3件／アイコンの画像対応 | **完了（v1.2）** |
| **第3便** | アプリ一覧の取得元をスプレッドシート（暫定DB）へ | **完了（v1.3）** |

第2便で書き込みが入った。保存するのは**並べ替えを確定したときだけ**で、
読み込み・ページ送り・ドラッグ中の途中経過では書かない（§11）。

アプリの定義は `public/auth/apps.js`（`PORTAL_APPS`）から
`public/portal/app-registry.js`（`APP_REGISTRY`）へ移した。形も
`{id, name, description, path, icon}` から `{id, name, icon, href}` へ変えている。

**`public/auth/apps.js` は削除済み。** 定義の置き場所は `public/portal/app-registry.js` の1か所だけとする。
残しておくと「足しても Portal に出ない定義」が2か所ある状態になり、
追加先を間違えても画面上は正常に見えるため気づけない。

復活していないことをテストで固定している（§9）。
中身が必要になったときは Git 履歴から取れる。

## §2 レイアウト

画面には**2つのグリッド**がある。

| | 中身 | 枠 | 埋め枠 | 並べ替え |
| --- | --- | --- | --- | --- |
| **お気に入り**（`.auth-apps`） | 利用者が選んだアプリだけ | 2列×4行＝8／ページ | あり（準備中） | できる |
| **カタログ**（`.auth-catalog`） | お気に入りに**入っていない**アプリ | 2列×最大10行＝20／ページ | **なし** | できない（定義の順） |

v1.1 までは、グリッドは1つで「全アプリの並び」だった。
v1.2 でお気に入りとカタログに分けた（§12）。

以下はお気に入り側の定めである。

**2列×4行＝8枠で1ページ。**

```
ページ数 = max(2, ceil(アプリ数 / 8))
```

| アプリ数 | ページ数 | 備考 |
| --- | --- | --- |
| 0 | （2） | **お気に入りの節ごと出さない**（§2-3）。枠とドットは作るが表示しない |
| 1 | 2 | 1枠がアプリ、15枠が「準備中」 |
| 8 | 2 | |
| 9 | 2 | `ceil(9/8) = 2` |
| 16 | 2 | |
| 17 | **3** | 3ページ目がここで自動発生する（§7-2） |

最低2ページとするのは、**1ページしかないとページ送りの存在自体が伝わらない**ため。
1件でも2ページぶんの枠を出しておき、増えたときに操作を覚え直さずに済ませる。

### §2-1 空き枠は「準備中」

アプリの入らない枠は、破線の枠 ＋ プラスアイコン ＋ 「準備中」の語で示す。

**リンクにしない。** 行き先が無いものを押せる形にすると、
押しても何も起きないという体験を作る。
`a` も `button` も置かず、押せる見た目（背景・カーソル）も与えない。

破線だけに頼らず「準備中」の語を必ず添える。
枠線の種類の違いが見えない人には、形だけでは空きだと分からない。

### §2-2 空状態のメッセージを置かない

「ご利用可能なアプリは順次追加されます。」（旧 `#portal-apps-empty`）は**廃止した。**

0件のときはお気に入りの節ごと消える（§2-3）。
無いものについて文で断る必要はない。

### §2-3 お気に入りが0件なら節ごと出さない（v1.4）

**お気に入りが1件も無いあいだは、`section.auth-apps` を `hidden` にする。**
1件目を追加した時点で出し、最後の1件を外した時点で消える。

v1.3 までは0件でも「準備中」の枠が16個とページ送りが並んでいた。
これは「まだ何も置いていない棚」を2ページぶん見せている状態で、
利用者は押せない枠を数えるだけになり、次にする操作は分からない。
0件のときに見るべきものは、下の「全アプリ一覧」（§12）である。

| 項目 | 定め |
| --- | --- |
| 隠す対象 | `section.auth-apps`（見出し・枠・ページ送り・初期化ボタンを含む） |
| 条件 | `favoriteApps.length === 0`。判断は `applyFavoritesVisibility()` の1か所だけ |
| 配信HTML | 既定で `hidden`。0件が既定（§4-d）なので、描く前に一瞬出さない |
| 枠とドット | **作る。** 隠すのは節だけで、中身は0件でも従来どおり描く |
| 「初期状態に戻す」 | 同じ条件で `#portal-apps-reset-block` も `hidden`（§11-2） |

枠を作らない形にはしない。0件専用の描き分けを増やすより、
「作ってから、出すかどうかだけを決める」ほうが状態が少ない。

#### 節の外へ出したもの

`#portal-apps-live`（読み上げ）と `#portal-apps-message`（保存失敗・取得失敗の通知）は
**節の外**（`section.auth-catalog` の見出し直後）へ移した。

節が隠れているあいだ、この2つは0件のときこそ要る。
「アプリ一覧を取得できませんでした」も、最後の1件を外したときの読み上げも、
`hidden` の中では伝わらない。`id` は据え置く（指しているのは
置き場所ではなく、お気に入りグリッドの状態である）。

## §3 幅と位置

グリッドの幅は **`min(360px, 100%)`**。全画面幅で**中央寄せ**にする。

**PCでもスマホと同じ見た目になり、左右に余白が出る。これは仕様である。**
広い画面で列数を増やさない。

画面幅ごとに列数を変えると、同じ人が同じアプリを別の位置で覚えることになる。
並べ替え（第2便）を入れる画面では、位置が幅で変わるほうが害が大きい。

`public/auth/auth.css` に**幅ごとの分岐を書かないこと**。
5幅すべてで2列であることをテストで固定している（§9）。

## §4 配置データ

| 項目 | 値 |
| --- | --- |
| 保存キー | `tsam-app-layout` |
| 形式 | `{"version":2,"order":["アプリID", …]}` |

**`order` は「お気に入りのID列（並び順込み）」である。**
ここに載っていないアプリは、お気に入りではない＝カタログに出る。

### 解決規則

定義（`APP_REGISTRY`）と保存データから、お気に入りとカタログを決める。

| | 規則 |
| --- | --- |
| **a** | 保存済み `order` にある ID は、**その順**でお気に入りに出す |
| **b** | `order` に無い既知アプリは**お気に入りに入れない**（カタログへ回る） |
| **c** | `order` にある**未知 ID**（定義に無い）は**無視**する |
| **d** | 保存が**読めない／形式不正／版違い**なら、**お気に入りは空**（全件カタログ） |

c と d は違う。未知 ID は1件だけ捨てて残りの並びは活かす（c）。
形式そのものが壊れているときだけ、全体を既定へ倒す（d）。

重複 ID は最初の1件だけを採る。
カタログの並びは**定義の順**。利用者が決めるものではない。

### §4-1 壊れていても画面を開く

保存データは利用者が開発者ツールから書き換えられる場所である。
**この層は例外を投げない。** 壊れた値で画面が開かなくなるより、
既定順へ戻って開くほうがよい。

`localStorage` の読み取りと `JSON.parse` の失敗処理は
`public/portal/app-layout.js` に閉じる。描画側はアプリの配列を受け取るだけにする。

### §4-2 版が違うものは読まない

`version !== 1` なら `null` を返し、既定順へ倒す（d）。

推測で解釈すると「並びが微妙に違う」という気づきにくい壊れ方をする。
読まないほうが安全側に倒れる。

---

### §4-3 v1 から v2 への移行

**v1 のデータは読まない。** `version !== 2` は `null` を返し、d へ倒す。

v1 の `order` は「表示順」で、全アプリが載っていた。
同じ形の配列だが**意味が違う**。v2 として読むと、
**過去に一度でも画面を開いた利用者の全アプリが、勝手にお気に入りへ入る。**

移行を書かずに版で弾くほうが安全である。
失われるのは「並び順」だけで、お気に入りは元々存在しなかった。

## §5 アプリ定義（レジストリ）

`public/portal/app-registry.js` の `APP_REGISTRY`。

| キー | 必須 | 内容 |
| --- | --- | --- |
| `id` | ○ | 一意。配置データ（`order`）の識別子 |
| `name` | ○ | カードに出す名前 |
| `icon` | | 1〜2文字（絵文字可）。省略時は `name` の1文字目 |
| `href` | ○ | サイトのルートからの相対パス。**先頭に `/` を付けない** |

**組み込みの一覧は、シートを取得できないときの受け皿である**（§15-4）。
制定時は空配列だったが、現在は本番で動くアプリだけが並んでいる（§14-3）。

### §5-1 `id` を後から変えない

`id` は利用者の端末に保存された `order` が指す先である。
変えると、その利用者が並べ替えた位置が失われ、そのアプリは末尾へ戻る（§4-b）。

名前や置き場所を変えるときも `id` は据え置く。

### §5-2 テストから定義を注入できる

`portal.js` は `renderAppsGrid(registry, { stored })` を公開する。
画面からは引数なしで呼び（既定は本物のレジストリと保存済み配置）、
テストからは定義を渡して描き直す。

DOM を手で組むテストにしない。実装が変わっても気づけなくなる。

## §6 ページ送り

グリッド下部に**ドット ＋ 左右矢印**を置く。

| 項目 | 定め |
| --- | --- |
| 初期表示 | 1ページ目 |
| 表示中の印 | ドットの色 ＋ **`aria-current="true"`** |
| 要素 | ドット・矢印とも `button`。`aria-label` 付き |
| キーボード | Tab で到達し、Enter / Space で作動（`button` の既定動作） |
| 端の扱い | 1ページ目で「前へ」、最終ページで「次へ」を**無効化** |
| 表示ページの保存 | **しない。** 再読み込みで1ページ目へ戻る |

### §6-1 端で巻き戻さない

最後→最初へ巻き戻る動きにしない。
押した結果からいま何ページ目なのかが読み取れなくなる。

### §6-2 押せる面は44px

ドットの見た目は8pxだが、押せる面は44px確保する（透明な余白で稼ぐ）。
指で操作する画面で、8pxの的を狙わせない。

**いま実装しない。** 下の条件が起きたときに、この節を読んで着手する。

### §7-1 第2便（並べ替え）— **完了（v1.1）**

実装内容は §10・§11 にある。着手時に決めた条件は次のとおり果たした。

### §7-2 アプリが8個を超えたとき

**何もしなくてよい。** 17件目で3ページ目が自動的に増える（§2）。

このとき初めてドットが3つになる。
ドットの数がページ数と一致することはテストで固定している（§9）。

### §7-3 1ページの枠数を変えたくなったとき

`PAGE_SIZE` は `public/portal/app-layout.js` の定数。
変えると**既存利用者の並びのページまたぎが変わる**（`order` 自体は保たれる）。

2列×4行という形は §3 の「幅で変えない」判断と対になっている。
枠数だけを変えると縦に伸びるため、先に §3 を読み直すこと。

前置を忘れると、片方の変更でもう片方の検査が通ってしまう。

| `tests/unit/frontend.mjs` | **未着手。** `localhost` を指すのは既知の仮データ3件だけ（`PROVISIONAL_IDS`）を見ている。仮データが無くなったので、「`localhost` を指すエントリが1件も無い」へ狭める |

**この2つは複数の画面・アプリで共有しているスイートである。**
書き換えは Portal 単独の判断で行わず、まとめて更新すること。

お気に入りを入れる手段は `renderAppsGrid(undefined, { stored: { version: 2, order: [...] } })`。
`localStorage` を直接書かないのは、「配置データを書き込んでいない」という
別の検査（第2便まで読むだけ、を固定するもの）を潰さないため。

## §10 並べ替え（第2便）

### §10-1 グリップからしか始めない

移動の始点は**グリップ（`⠿`）だけ**とする。カード本体（`a`）からは始めない。

| | |
| --- | --- |
| 位置 | カードの**右上**に常時表示（現れたり消えたりしない） |
| 対象 | **実アプリの枠だけ。** 「準備中」の枠には付けない |
| 要素 | `button.auth-app-card__grip`。`aria-label` は「〈アプリ名〉 を移動」 |
| CSS | **`touch-action: none`**（後述） |

本体から始められるようにすると、開こうとしただけの指のわずかな動きで
移動が始まる。押し間違いの結果が「並びが変わった」という**気づきにくい形**で残る。

グリップは `a` の内側に入れられない（対話要素は入れ子にできない）。
カードは `li > [a, button]` の兄弟構成にし、グリップを右上へ重ねる。

### §10-2 挿入位置の見せ方 — ライブ押しのけ

挿入先が変わるたびに**並びを組み替えて描き直す**。まわりのカードが実際に寄る／空く。

- 掴んだカードの位置には**穴**（破線・淡色）が開く
- カード本体は**半透明のゴースト**としてポインターに追従する
- 落とすと、そのとき見えている並びがそのまま確定する

線（インジケーター）を引く方式は採らない。
線は「どの隙間か」しか示せないが、押しのけなら
**落としたあとの並びそのもの**が見える。

ゴーストには **`pointer-events: none` が必須**。
これが無いと指の下にあるのが常にゴーストになり、挿入先の枠を拾えない
（自分自身の上にしか落とせなくなる）。

### §10-3 挿入の意味論は「押しのけ」

`moveItem(list, from, to)`（`app-layout.js`）。
元の位置から抜き、目的の位置へ挿し込む。あいだの要素は1つずつずれる。

```
moveItem(['a','b','c','d'], 3, 0) → ['d','a','b','c']
moveItem(['a','b','c','d'], 0, 2) → ['b','c','a','d']
```

**入れ替え（swap）ではない。** 2件だけが入れ替わると、
掴んだものが遠くへ飛んだように見える。

`to` が範囲外なら端へ丸める。
**準備中の枠（アプリ数より後ろ）へ落とすと末尾扱い**になるのは、この丸め込みによる。

読み取り規則 a〜d（§4）は変えていない。純関数層への追加は挿入操作だけ。

### §10-4 Pointer Events で統一する

マウスとタッチを別々に書かない。Pointer Events 一本にする。

タッチでスクロールと競合させないために、**2つとも要る**。

1. グリップの **`touch-action: none`**（CSS）
2. `pointerdown` / `pointermove` での **`preventDefault()`**（JS）

片方だけでは、指を動かした瞬間にブラウザがスクロールを始め、
`pointermove` がこちらへ来なくなる。

### §10-5 ページまたぎ

ドラッグ中に**ページドットへ重ねる**と、そのページへ切り替わり、
掴んだまま続けて落とせる。

**ドットが見えていることが前提**である。画面が低くてドットが表示領域の外にあると
重ねられない（`elementFromPoint` は表示領域の外を拾えない）。
これは制限であって不具合ではない。

### §10-6 Esc で取り消す

ドラッグ中の Esc で、掴む前の並びへ戻す。**保存もしない。**

Esc は画面のどこにいても効かせる。ドラッグ中は特定の要素に焦点が無いため、
`document` で拾う。

### §10-7 キーボードでの移動

グリップは `button` なので、Enter と Space は既定動作で `click` になる。

| 操作 | 結果 |
| --- | --- |
| Enter / Space（1回目） | 移動モードに入る |
| ←→ | 1つ前 / 1つ後ろへ |
| ↑↓ | 2つぶん（**1行＝2列**のため） |
| Enter / Space（2回目） | 確定して保存 |
| Esc | 取り消して元へ戻す |

移動モード中のカードには枠を出し、どれを動かしているかを示す。
移動先が別ページなら、そのページへ自動で送る。

描き直すとグリップの要素は作り直されるため、**移動のたびに焦点を戻す**。
戻さないと、1回動かした時点でキーボード操作が続かなくなる。

#### 読み上げ

`#portal-apps-live`（`role="status"` / `aria-live="polite"`）へ短く出す。

- 移動モードに入ったとき … 「〈n〉番目。矢印キーで移動し、Enterで確定、Escで取消します。」
- 動かすたび … 「〈n〉番目に移動」
- 確定 … 「〈n〉番目に確定しました。」／取消 … 「移動を取り消しました。」

画面では位置が見えるが、キーボードだけで操作している人には見えない。

## §11 保存

| いつ | 何を |
| --- | --- |
| ドロップで確定したとき | `tsam-app-layout` へ現在の並びを書く |
| キーボードで確定したとき | 同上 |
| **それ以外** | **書かない**（読み込み・ページ送り・ドラッグ中の途中経過・Esc） |

形式は第1便のまま `{"version":1,"order":[…]}`（§4）。
書き込みも `app-layout.js` に閉じる（`writeStoredLayout` / `clearStoredLayout`）。
描画側から `localStorage` を触らない。

### §11-1 保存に失敗しても並びは戻さない

容量超過などで書けなかったときも、**画面上の並びはそのまま保つ。**
控えめに「保存できなかった」とだけ伝え、操作は続けさせる。

せっかく並べたものが操作のたびに巻き戻るほうが困る。
書けなかった事実は次に開いたときに分かる（既定順で出る）。

### §11-2 初期配置に戻す

グリッド下部に置く。**確認を1枚挟む。**

確定したら**保存キーごと削除**する。空の `order` を書かない。
消えたあとは「保存が無い」状態＝お気に入り空（§4-d）へ戻る。

**お気に入りが0件のときは出さない**（v1.4）。
空のものを空へ戻すボタンに、押して意味のある状態が無い。
節ごと隠れる（§2-3）ため二重ではあるが、判断は
`applyFavoritesVisibility()` の1か所で行い、`#portal-apps-reset-block` にも
`hidden` を立てる。節の見せ方を変えたときに、この決めごとが黙って消えないようにする。

戻したあとは**焦点を「全アプリ一覧」の見出しへ移す**。
押したボタンごと画面から消えるため、行き先を指定しないと焦点が `body` へ落ち、
キーボードだけで操作している人が画面のどこにいるか分からなくなる。

## §12 カタログ（全アプリ一覧）

`.auth-catalog` / `#portal-catalog`。お気に入りグリッドの**下**に置く。
見出しは「全アプリ一覧」。

| 項目 | 定め |
| --- | --- |
| 中身 | レジストリのうち、**お気に入りに入っていないもの**だけ |
| 並び | **定義の順**。利用者が決めるものではない |
| レイアウト | 2列。枠の体裁はお気に入りに準拠（角丸アイコン＋名前） |
| 1ページ | 2列×10行＝**20件**。超えたらお気に入りと同型のドット式ページ送り |
| 埋め枠 | **置かない** |
| グリップ | **付けない** |
| 0件のとき | 枠を並べず「すべてのアプリをお気に入りに追加済みです。」の一文だけ |
| 幅 | お気に入りと同じ `min(360px, 100%)` で中央寄せ |

### §12-1 埋め枠を置かない

カタログは「まだ選んでいないものの一覧」であって、
枠を並べて見せるものではない。0件なら一文で足りる。

お気に入り側に埋め枠があるのは、**そこが持ち物を置く棚**だからである。
空の棚は「ここへ置ける」ことを示すが、空の一覧は何も示さない。

### §12-2 ページ送りは1ページなら出さない

お気に入りは0件でも2ページ出す（§2）が、カタログは違う。
1ページに収まるならページ送り自体を隠す。

お気に入りの2ページは「まだ置ける場所がある」ことを伝えるためのもので、
カタログにその意味は無い。

## §13 追加と解除（対称の操作）

| 操作 | 場所 | 押下領域 | 確認 |
| --- | --- | --- | --- |
| お気に入りに追加 | カタログの枠の下「お気に入りに追加」 | 44px | **なし** |
| お気に入りから外す | お気に入りの枠の**左上**「×」 | 44px | **なし** |

追加はお気に入りの**末尾**へ足す。既存の並びの途中へ割り込ませない。
解除するとカタログの**定義順の位置**へ戻る。

どちらも確定した時点で保存する（§11）。

### §13-1 確認を挟まない

押し間違えても、**同じ1タップで元へ戻せる**。
対称に戻せる操作へ確認を挟むと、日常の操作が重くなるだけになる。

「初期配置に戻す」（§11-2）に確認があるのは、あれが**まとめて全部**を
消す操作で、1タップでは戻せないからである。

### §13-2 「外す」はグリップと対称の位置へ

グリップが右上なら、外すは左上。**大きさも 44px でそろえる。**
左右で的の大きさが違うと、指で押し分けにくい。

### §13-3 初期化の意味

「**お気に入りを初期状態に戻す**」＝ お気に入りを空にする。
保存キーごと削除し、全アプリがカタログへ戻る。

v1.1 では「並び順を既定へ戻す」だった。文言も挙動も新しい意味へ更新した。

## §14 アプリ定義（v1.2 で増えたこと）

### §14-1 `href` はサイト外も取れる

`https://` `http://` で始まる絶対URLはサイト外として扱い、
**別タブ（`target="_blank"`）＋ `rel="noopener noreferrer"`** を付ける。

それ以外はサイトのルートからの相対パスとして解決する（従来どおり）。

### §14-2 `icon` は画像URLも取れる

`http(s)://` で始まるか、画像の拡張子（`.svg` `.png` …）で終われば画像として扱う。

**読み込みに失敗したら、名前の1文字目を色付きの角丸で出す。**
枠の中には先に文字を置き、画像が読めたときだけ文字を隠す
（`.auth-app-card__icon--image-ready`）。読めなければ文字が残る。

読み込み中に空の枠を見せないための順序である。
「壊れた画像アイコン」を出さないことも兼ねる。

### §14-3 仮データは全部消した（v1.4）

v1.2 で入れた仮データ3件は、すべて画面から無くなった。

| id | 名前 | 顛末 |
| --- | --- | --- |
| `202607No01` | 音声録音・MP3変換アプリ | 実物（`production-app/voice-recorder/`）へ差し替え（2026-08-05） |
| `202607No02` | 領収書・収支管理システム | **削除**（2026-08-19） |
| `202607No03` | 電子契約書作成アプリ | **削除**（2026-08-19） |

後の2件は、遷移先が GitHub 上のソースファイルと個人の GitHub Pages で、
アイコンが `http://localhost:8000/...` のままだった。
本番の利用者から見ると、当社のアプリの一覧に、押した先が当社のものではない枠が
2つ並んでいることになる。アイコンも必ず読み込みに失敗して頭文字へ落ちる。
「動くアプリだけを載せる」ほうを採った。

**`id` は再利用しない。** 利用者の端末の `order` にこの2つが残っていても、
定義に無い ID は未知 ID として無視される（§4-c）ので、お気に入りから静かに外れる。
同じ番号を別のアプリへ振り直すと、外れたはずの位置に別のアプリが現れる。

これで `APP_REGISTRY` に `localhost` を指すものは1件も無い。
組み込みの `icon` はすべて文字1字であり、画像アイコン（§14-2）を通るのは
スプレッドシート（§15）のアイコンURL列だけになった。

### §14-4 DB化の発動条件 — **実施済み（v1.3）**

**次のどれかが起きたら**、レジストリをファイルからデータベース
（またはスプレッドシート）へ移す。

1. 本番アプリを登録する（第3便）。仮データを1件でも本物へ差し替えるとき
2. アプリの追加・削除を、コードを触らずに行いたくなったとき
3. 利用者やプランごとに見せるアプリを変える必要が出たとき

移すときも `id` は据え置く（§5-1）。
利用者の端末に保存された `order` が指す先であり、変えるとお気に入りが失われる。

## §15 データソース（第3便）

アプリ一覧は **Googleスプレッドシート（暫定DB）** から取る。
取得層は `public/portal/app-source.js`。

| 項目 | 値 |
| --- | --- |
| シート | 「アプリ一覧」（`gid=0`） |
| 列 | A:アプリID / B:アプリ名 / C:アプリURL / D:アイコンURL |
| 取得 | Google の CSV 出力（gviz）へ**ブラウザから直接** fetch |
| シートID | `public/portal/app-source.js` の `SHEET_ID` |

**シートIDはこの仕様書に書かない。**
`docs/specs/README.md` の「秘密情報（…スプレッドシートID…）を仕様書へ書かない」に従う。
差し替えるときはコード側の1か所だけを直す。

サーバーを1つも挟まない。キーも中継も要らないため、
壊れる箇所も、秘密にすべき値も増えない。

### §15-1 共有設定が前提

**シートが「リンクを知っている全員が閲覧可」であることが前提。**

未設定のあいだ、Google は 401 とログイン画面の HTML を返す。
そのときは取得失敗として扱い、§15-3 の段構えで表示を続ける。
画面は開くが、シートの内容は反映されない。

この値は配信される JS に含まれるため、閲覧者から見える。
共有設定と同じ強さしかないので、**秘密にすべき情報をこのシートへ置かないこと。**

### §15-2 シートの中身を信用しない

シートは画面の外で編集される。列がずれる、URL欄に `javascript:` が書かれる、
名前欄にタグが書かれる、といったことが起こりうる。

取得層を通ったあとの値は次を満たす。

| 検査 | 落とすもの |
| --- | --- |
| `id` | 空・重複（先に出たほうを採る） |
| `name` | 空 |
| `href` | `http://` `https://` 以外（`javascript:` `data:` など） |
| `icon` | 不正なら**行は残して `icon` だけ空**にする（頭文字へ落ちる） |

**1行が壊れていても、その行だけを捨てて残りは活かす。**
シートの1か所の打ち間違いで一覧全体が消えるほうが困る。

1行目は、見出し語（「アプリID」等）か、URL列がURLでないことで
ヘッダーと判定して読み飛ばす。ヘッダーが無いシートでも1行目を落とさない。

CSV の解析は引用符・カンマ・改行・`""` に対応する。
`split(',')` では、名前にカンマが入った時点で崩れる。

**描画側は `textContent` と `href` への代入だけを行う。**
`innerHTML` へ流さない。ここで弾いていても、流す口があれば別の経路から入る。

### §15-3 表示を止めない三段構え

取得を待ってから描くと、通信の分だけ画面が白くなる。

| | すること |
| --- | --- |
| **1. まず描く** | キャッシュ（`tsam-app-registry-cache`）があればそれ、無ければ組み込みの一覧 |
| **2. あとで直す** | 取得できたら差し替え、キャッシュも更新する |
| **3. だめなら** | 1 のまま残し、控えめに知らせる |

失敗時の文言は、いま何が出ているのかが分かるよう言い分ける。

- キャッシュで描いた … 「アプリ一覧を更新できませんでした。前回取得した内容を表示しています。」
- 既定で描いた … 「アプリ一覧を取得できませんでした。既定の一覧を表示しています。」

**0件は失敗として扱う。** 共有設定が未了だと Google はログイン画面の HTML を返すため、
素直に解析すると「0件のシート」と区別がつかない。
空の一覧を出すより、前回の内容を残すほうがよい。

キャッシュから読み戻した値にも、取得直後と同じ検査（§15-2）を通す。
`localStorage` は利用者が書き換えられる。

### §15-4 組み込みの一覧は残す

`public/portal/app-registry.js` の配列は**消さない**。
取得もキャッシュも無いときの最後の受け皿になる。

**ただし、受け皿に置いてよいのは実際に動くアプリだけである**（v1.4）。
ここに書いたものは、シートが読めないあいだ、そのまま利用者の画面に出る。
仮の遷移先を置いておくと、取得できない日にだけ壊れた枠が現れることになる。
`localhost` や当社の管理外のURLを指すエントリを足さないことを、
引き続きテストで固定する（§14-3）。

### §15-5 シートから消えた ID

**何もしなくてよい。** 定義に無い ID は「未知 ID」になり、
お気に入りの解決規則 c（§4）で自動的に外れる。

保存されている `order` は書き換えない。シートへ戻せば、お気に入りも戻る。

### §15-6 入れ替えの発動条件

スプレッドシートは**暫定**である。次のどれかが起きたら、本来のDBへ移す。

1. 利用者やプランごとに見せるアプリを変える必要が出たとき
   （シートは全員へ同じ内容しか配れない）
2. 公開できない情報を一覧へ持たせる必要が出たとき（§15-1）
3. 更新の頻度や件数が増え、CSV の取得と解析が重くなったとき

移すときも `id` は据え置く（§5-1）。
利用者の端末に保存された `order` が指す先であり、変えるとお気に入りが失われる。

**実ネットワークへは出ない。** `window.fetch` を包み、
CSV出力のURLだけをテスト側で差し替える。

差し替える内容は `localStorage` 経由で渡す。
`Page.addScriptToEvaluateOnNewDocument` は新しい文書ごとに実行されるため、
`window` に置くと画面を開き直すたびに初期値へ戻る。

取得に失敗したときの通知（`#portal-apps-message`）は、
**お気に入り0件のときにも見えていること**を確かめる（§2-3）。
節の中に置いたままだと、0件＝既定の状態で通知だけが消える。
