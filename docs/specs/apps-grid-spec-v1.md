## §1 3便の分担

この画面は3回に分けて作る。**便をまたいだ先取り実装をしない。**

| 便 | 内容 | 状態 |
| --- | --- | --- |
| **第1便** | 器（グリッド・ページ送り）と配置データの基盤 | **完了（v1）** |
| **第2便** | 並べ替え（ドラッグ）／グリップ／保存書き込み／「初期配置に戻す」 | **完了（v1.1）** |
| 第3便 | 最初のアプリ搭載 | 未着手 |

第2便で書き込みが入った。保存するのは**並べ替えを確定したときだけ**で、
読み込み・ページ送り・ドラッグ中の途中経過では書かない（§11）。

アプリの定義は `public/auth/apps.js`（`PORTAL_APPS`）から
`public/portal/app-registry.js`（`APP_REGISTRY`）へ移した。形も
`{id, name, description, path, icon}` から `{id, name, icon, href}` へ変えている。

**`public/auth/apps.js` は削除済み。** 定義の置き場所は `public/portal/app-registry.js` の1か所だけとする。
残しておくと「足しても Portal に出ない定義」が2か所ある状態になり、
追加先を間違えても画面上は正常に見えるため気づけない。

復活していないことをテストで固定している（§9）。
中身が必要になったときは Git 履歴から取れる。

## §2 レイアウト

**2列×4行＝8枠で1ページ。**

```
ページ数 = max(2, ceil(アプリ数 / 8))
```

| アプリ数 | ページ数 | 備考 |
| --- | --- | --- |
| 0 | 2 | 現在の状態。16枠すべてが「準備中」 |
| 8 | 2 | |
| 9 | 2 | `ceil(9/8) = 2` |
| 16 | 2 | |
| 17 | **3** | 3ページ目がここで自動発生する（§7-2） |

最低2ページとするのは、**1ページしかないとページ送りの存在自体が伝わらない**ため。
0件でも送れる形にしておき、アプリが増えたときに操作を覚え直さずに済ませる。

### §2-1 空き枠は「準備中」

アプリの入らない枠は、破線の枠 ＋ プラスアイコン ＋ 「準備中」の語で示す。

**リンクにしない。** 行き先が無いものを押せる形にすると、
押しても何も起きないという体験を作る。
`a` も `button` も置かず、押せる見た目（背景・カーソル）も与えない。

破線だけに頼らず「準備中」の語を必ず添える。
枠線の種類の違いが見えない人には、形だけでは空きだと分からない。

### §2-2 空状態のメッセージを置かない

「ご利用可能なアプリは順次追加されます。」（旧 `#portal-apps-empty`）は**廃止した。**

準備中の枠が16個並んでいれば、まだ何も入っていないことは見れば分かる。
同じことを文でも言うと、画面の情報量だけが増える。

## §3 幅と位置

グリッドの幅は **`min(360px, 100%)`**。全画面幅で**中央寄せ**にする。

**PCでもスマホと同じ見た目になり、左右に余白が出る。これは仕様である。**
広い画面で列数を増やさない。

画面幅ごとに列数を変えると、同じ人が同じアプリを別の位置で覚えることになる。
並べ替え（第2便）を入れる画面では、位置が幅で変わるほうが害が大きい。

`public/auth/auth.css` に**幅ごとの分岐を書かないこと**。
5幅すべてで2列であることをテストで固定している（§9）。

## §4 配置データ

| 項目 | 値 |
| --- | --- |
| 保存キー | `tsam-app-layout` |
| 形式 | `{"version":1,"order":["アプリID", …]}` |

`order` はアプリの `id` の並び。`version` は形が変わったときに上げる。

### 解決規則

定義（`APP_REGISTRY`）と保存データから、実際に並べる順序を決める。

| | 規則 |
| --- | --- |
| **a** | 保存済み `order` にある ID は、**その順**で先に出す |
| **b** | `order` に無い既知アプリは、**定義の順で末尾**へ足す |
| **c** | `order` にある**未知 ID**（定義に無い）は**無視**する |
| **d** | 保存が**読めない／形式不正／版違い**なら、**既定順**（定義の順）へ倒す |

c と d は違う。未知 ID は1件だけ捨てて残りの並びは活かす（c）。
形式そのものが壊れているときだけ、全体を既定順へ倒す（d）。

重複 ID は最初の1件だけを採る。

### §4-1 壊れていても画面を開く

保存データは利用者が開発者ツールから書き換えられる場所である。
**この層は例外を投げない。** 壊れた値で画面が開かなくなるより、
既定順へ戻って開くほうがよい。

`localStorage` の読み取りと `JSON.parse` の失敗処理は
`public/portal/app-layout.js` に閉じる。描画側はアプリの配列を受け取るだけにする。

### §4-2 版が違うものは読まない

`version !== 1` なら `null` を返し、既定順へ倒す（d）。

推測で解釈すると「並びが微妙に違う」という気づきにくい壊れ方をする。
読まないほうが安全側に倒れる。

## §5 アプリ定義（レジストリ）

`public/portal/app-registry.js` の `APP_REGISTRY`。

| キー | 必須 | 内容 |
| --- | --- | --- |
| `id` | ○ | 一意。配置データ（`order`）の識別子 |
| `name` | ○ | カードに出す名前 |
| `icon` | | 1〜2文字（絵文字可）。省略時は `name` の1文字目 |
| `href` | ○ | サイトのルートからの相対パス。**先頭に `/` を付けない** |

現在は**空配列**。本番で動くアプリがまだ無い。

### §5-1 `id` を後から変えない

`id` は利用者の端末に保存された `order` が指す先である。
変えると、その利用者が並べ替えた位置が失われ、そのアプリは末尾へ戻る（§4-b）。

名前や置き場所を変えるときも `id` は据え置く。

### §5-2 テストから定義を注入できる

`portal.js` は `renderAppsGrid(registry, { stored })` を公開する。
画面からは引数なしで呼び（既定は本物のレジストリと保存済み配置）、
テストからは定義を渡して描き直す。

DOM を手で組むテストにしない。実装が変わっても気づけなくなる。

## §6 ページ送り

グリッド下部に**ドット ＋ 左右矢印**を置く。

| 項目 | 定め |
| --- | --- |
| 初期表示 | 1ページ目 |
| 表示中の印 | ドットの色 ＋ **`aria-current="true"`** |
| 要素 | ドット・矢印とも `button`。`aria-label` 付き |
| キーボード | Tab で到達し、Enter / Space で作動（`button` の既定動作） |
| 端の扱い | 1ページ目で「前へ」、最終ページで「次へ」を**無効化** |
| 表示ページの保存 | **しない。** 再読み込みで1ページ目へ戻る |

### §6-1 端で巻き戻さない

最後→最初へ巻き戻る動きにしない。
押した結果からいま何ページ目なのかが読み取れなくなる。

### §6-2 押せる面は44px

ドットの見た目は8pxだが、押せる面は44px確保する（透明な余白で稼ぐ）。
指で操作する画面で、8pxの的を狙わせない。

## §10 並べ替え（第2便）

### §10-1 グリップからしか始めない

移動の始点は**グリップ（`⠿`）だけ**とする。カード本体（`a`）からは始めない。

| | |
| --- | --- |
| 位置 | カードの**右上**に常時表示（現れたり消えたりしない） |
| 対象 | **実アプリの枠だけ。** 「準備中」の枠には付けない |
| 要素 | `button.auth-app-card__grip`。`aria-label` は「〈アプリ名〉 を移動」 |
| CSS | **`touch-action: none`**（後述） |

本体から始められるようにすると、開こうとしただけの指のわずかな動きで
移動が始まる。押し間違いの結果が「並びが変わった」という**気づきにくい形**で残る。

グリップは `a` の内側に入れられない（対話要素は入れ子にできない）。
カードは `li > [a, button]` の兄弟構成にし、グリップを右上へ重ねる。

### §10-2 挿入位置の見せ方 — ライブ押しのけ

挿入先が変わるたびに**並びを組み替えて描き直す**。まわりのカードが実際に寄る／空く。

- 掴んだカードの位置には**穴**（破線・淡色）が開く
- カード本体は**半透明のゴースト**としてポインターに追従する
- 落とすと、そのとき見えている並びがそのまま確定する

線（インジケーター）を引く方式は採らない。
線は「どの隙間か」しか示せないが、押しのけなら
**落としたあとの並びそのもの**が見える。

ゴーストには **`pointer-events: none` が必須**。
これが無いと指の下にあるのが常にゴーストになり、挿入先の枠を拾えない
（自分自身の上にしか落とせなくなる）。

### §10-3 挿入の意味論は「押しのけ」

`moveItem(list, from, to)`（`app-layout.js`）。
元の位置から抜き、目的の位置へ挿し込む。あいだの要素は1つずつずれる。

```
moveItem(['a','b','c','d'], 3, 0) → ['d','a','b','c']
moveItem(['a','b','c','d'], 0, 2) → ['b','c','a','d']
```

**入れ替え（swap）ではない。** 2件だけが入れ替わると、
掴んだものが遠くへ飛んだように見える。

`to` が範囲外なら端へ丸める。
**準備中の枠（アプリ数より後ろ）へ落とすと末尾扱い**になるのは、この丸め込みによる。

読み取り規則 a〜d（§4）は変えていない。純関数層への追加は挿入操作だけ。

### §10-4 Pointer Events で統一する

マウスとタッチを別々に書かない。Pointer Events 一本にする。

タッチでスクロールと競合させないために、**2つとも要る**。

1. グリップの **`touch-action: none`**（CSS）
2. `pointerdown` / `pointermove` での **`preventDefault()`**（JS）

片方だけでは、指を動かした瞬間にブラウザがスクロールを始め、
`pointermove` がこちらへ来なくなる。

### §10-5 ページまたぎ

ドラッグ中に**ページドットへ重ねる**と、そのページへ切り替わり、
掴んだまま続けて落とせる。

**ドットが見えていることが前提**である。画面が低くてドットが表示領域の外にあると
重ねられない（`elementFromPoint` は表示領域の外を拾えない）。
これは制限であって不具合ではない。

### §10-6 Esc で取り消す

ドラッグ中の Esc で、掴む前の並びへ戻す。**保存もしない。**

Esc は画面のどこにいても効かせる。ドラッグ中は特定の要素に焦点が無いため、
`document` で拾う。

### §10-7 キーボードでの移動

グリップは `button` なので、Enter と Space は既定動作で `click` になる。

| 操作 | 結果 |
| --- | --- |
| Enter / Space（1回目） | 移動モードに入る |
| ←→ | 1つ前 / 1つ後ろへ |
| ↑↓ | 2つぶん（**1行＝2列**のため） |
| Enter / Space（2回目） | 確定して保存 |
| Esc | 取り消して元へ戻す |

移動モード中のカードには枠を出し、どれを動かしているかを示す。
移動先が別ページなら、そのページへ自動で送る。

描き直すとグリップの要素は作り直されるため、**移動のたびに焦点を戻す**。
戻さないと、1回動かした時点でキーボード操作が続かなくなる。

#### 読み上げ

`#portal-apps-live`（`role="status"` / `aria-live="polite"`）へ短く出す。

- 移動モードに入ったとき … 「〈n〉番目。矢印キーで移動し、Enterで確定、Escで取消します。」
- 動かすたび … 「〈n〉番目に移動」
- 確定 … 「〈n〉番目に確定しました。」／取消 … 「移動を取り消しました。」

画面では位置が見えるが、キーボードだけで操作している人には見えない。

## §11 保存

| いつ | 何を |
| --- | --- |
| ドロップで確定したとき | `tsam-app-layout` へ現在の並びを書く |
| キーボードで確定したとき | 同上 |
| **それ以外** | **書かない**（読み込み・ページ送り・ドラッグ中の途中経過・Esc） |

形式は第1便のまま `{"version":1,"order":[…]}`（§4）。
書き込みも `app-layout.js` に閉じる（`writeStoredLayout` / `clearStoredLayout`）。
描画側から `localStorage` を触らない。

### §11-1 保存に失敗しても並びは戻さない

容量超過などで書けなかったときも、**画面上の並びはそのまま保つ。**
控えめに「保存できなかった」とだけ伝え、操作は続けさせる。

せっかく並べたものが操作のたびに巻き戻るほうが困る。
書けなかった事実は次に開いたときに分かる（既定順で出る）。

### §11-2 初期配置に戻す

グリッド下部に置く。**確認を1枚挟む。**

確定したら**保存キーごと削除**する。空の `order` を書かない。
消えたあとは「保存が無い」状態＝定義の順（§4-d）へ戻る。
