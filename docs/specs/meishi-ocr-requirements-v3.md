### 1.0 v3.1 の変更点 — 両面名刺をMVP対象へ格上げ

**v3.0 で「MVP対象外」としていた両面統合を、MVPに含める。**
表面1枚での登録は引き続き可能で、裏面は任意である。

| 区分 | v3.0 | v3.1 |
| --- | --- | --- |
| 対象 | 表面1枚を1件として処理。両面統合はMVP対象外（§6 の6、§7.2） | **表面（必須）＋裏面（任意）の2枚で1件**を構成できる |
| OCR | 1回 | **面ごとに実行**（最大2回）。並列に投げる（FR-08） |
| Gemini | 1回 | **1回のまま。** 表裏のテキストを面のラベル付きで結合して送る（FR-11） |
| 統合 | 無し | **表面優先・裏面で補完。競合は自動上書きしない**（FR-15） |
| 保存 | 画像1枚 | 画像2枚（`_front` / `_back`）。列も面ごとに持つ（FR-07、§11.2） |
| 所要時間 | 中央値45秒以内 | 表面のみ45秒 / **両面60秒**（別建ては確定。数値はフェーズ2で実測確定。§13.1） |

**この改訂の根拠**: テスト環境の `public/apps/card-scanner/` が、
表面（必須）＋裏面（任意）の構成と `mergeParsed()` による統合を
すでに実装しており、**成立することが分かっている**。
本アプリは同アプリを import しないが（§3）、設計判断の根拠としては使える。
以下の各条で「card-scanner の実績」として参照する。

**進行中のフェーズ0の50枚測定は、表面のみの精度測定として有効なまま**とする。
両面統合の精度検証をどこで行うかは §18 に定めた。

### 1.1 v2.0からの主な変更点(v3.0)

v3.0は、本システムの位置づけを「社内の名刺管理ツール」から「**TSAM AI 利用者へ提供する Portal アプリ**」へ変更する改訂である。

| 区分 | 変更内容 |
| --- | --- |
| 位置づけ | TSAM AI の一機能として利用者に公開する。Portal にアプリアイコンを掲載し、ログイン(`/login/`)→ Portal → 本アプリの導線とする |
| データ保存先 | 会社共有ドライブ・会社スプレッドシートを**廃止**。名刺データ・保存画像は**利用者本人のマイドライブ**(`マイドライブ/TSAM AI/名刺データ/`)に保存する |
| バックエンド | GAS APIを**全廃**。重複照会・保存を含む全処理を、利用者のOAuthトークンによるブラウザからの Google API 直接呼び出しへ変更(サーバーコードゼロ) |
| データの帰属 | 名刺データは利用者本人のGoogleアカウント内にのみ存在し、**当社はデータを保持・閲覧しない**。利用者のドライブの状態(容量・整理・削除)は当社は関知しない |
| Geminiキー | **無料枠キーでも利用可能**とする。無料枠のデータ取り扱い(プロダクト改善への利用可能性)を画面上で開示し、区分の選択は利用者の判断に委ねる |
| 権限分離 | 「全ユーザーが全データを閲覧できる」制約が消滅。**各利用者は自分のデータのみ**を扱う(構造上、他者のデータへ到達できない) |
| 管理者運用 | 管理者によるデータ修正・削除運用(旧FR-22)を廃止。利用者が自身のスプレッドシートを直接編集する |

> **v3.0の設計原則**: 利用者の資格情報(Geminiキー・OAuthトークン)も、利用者のデータ(名刺画像・名刺情報)も、**当社サーバーへ一切送信しない**。当社が提供するのは「道具(静的アプリ)」であり、データの器はすべて利用者自身のGoogleアカウントである。

## 2. システムの目的

本システムは、TSAM AI の利用者が、スマートフォンまたはPCから名刺画像をアップロードし、文字情報を抽出・構造化したうえで、**利用者自身のGoogleドライブ内のスプレッドシート**へ保存できるようにすることを目的とする。

以下を重点目標とする。優先順位はこの順とする。

1. 名刺情報の手入力作業を削減する。「1件あたりの登録所要時間(確認・修正含む)が手入力より短いこと」を効果測定の基準とする。
2. OCRやAIの誤認識を、登録前に人が確認・修正できるようにする。
3. 名刺画像と構造化データを関連付けて、利用者自身のドライブ内に保存する。
4. **利用者の資格情報とデータを利用者の管理下から出さない**(当社サーバーへの送信ゼロ)。
5. サーバーを持たず、静的配信のみで完結させる。
6. スマートフォンから簡単に利用できる軽量なWebアプリとする。

## 3. 背景と課題

手入力による名刺管理の課題(入力時間、転記ミス、原本との対応、重複登録、表記の不統一)はv1.1から変わらない。

v3.0では、これに加えて以下を前提とする。

* TSAM AI Portal には、利用者が自身のGemini APIキーを保存・管理する KeyStore が存在する。本アプリはその最初の消費アプリとなる。
* 本アプリは TSAM AI の提供価値の一部として利用者に公開する。当社が利用者の名刺データ(第三者の個人情報)を預かる構成は、当社側の管理負担と法的責任を増大させるため、**データを利用者自身のGoogleアカウント内で完結させる**構成を採用する。
* テスト環境 `/apps/` には名刺スキャナの実験実装(`public/apps/card-scanner/`。Drive OCRのみ使用、Geminiキー不要)が存在するが、**本アプリはこれとは別物の本番実装である**。本番アプリからテスト環境のコードを import してはならず(リポジトリの既存方針)、流用したいロジックは本番側へ複製する。また本アプリはGemini分類を行うため**Geminiキーが必須**であり、キー不要のテスト環境版とは利用条件が異なる。
* 利用者のドライブの容量・整理状態・データの取り扱いは利用者自身の責任範囲とし、当社は関知しない。

## 4. システム概要

### 4.1 テキスト抽出方式

方式B(Drive OCR + テキスト送信)とする。実行主体はすべて利用者本人である。

* OCR: 利用者のOAuthトークンで、ブラウザから Drive API を直接呼び出す。一時ドキュメントは利用者のマイドライブに作成し、即時完全削除する。
* AI分類: 利用者のGeminiキーで、ブラウザから Gemini API を直接呼び出す。送信するのは正規化後の**テキストのみ**とし、画像は送信しない。
* Drive OCRのレイアウト起因の行順崩れ対策(文脈から項目を抽出させるプロンプト)はv1.1から継続する。

### 4.2 全体構成

```text
利用者のブラウザ(tsam-ai.com 配下の静的ページ)
        │
   [導線] https://tsam-ai.com/login/ → Portal → 名刺OCRアイコン
        │
        ├─ [認証1] TSAM AI ログイン確認(tsam-auth-session)
        ├─ [認証2] Google OAuth(初回のみ同意、drive.file スコープ)
        ├─ [キー]  KeyStore.get('gemini')(未設定なら Portal のキー設定へ誘導)
        │
        ├─ [初期化] 利用者のマイドライブに保存構造を用意(なければ作成)
        │     マイドライブ/TSAM AI/名刺データ/
        │       ├─ 名刺管理スプレッドシート(名刺データ・変更履歴シート)
        │       └─ images/YYYY/MM/(保存画像)
        │
        ├─ ブラウザ側で画像縮小・圧縮
        ├─ Drive API: 画像→Googleドキュメント変換(OCR)→テキスト取得→完全削除
        ├─ ブラウザ側でテキスト正規化・正規表現抽出
        ├─ Gemini API: テキスト送信→構造化JSON取得(利用者キー)
        ├─ 結果統合 → 確認・修正画面
        │
        ├─ Sheets API: 利用者自身のスプレッドシートから重複候補を照会
        └─ 確定保存
             ├─ Drive API: 保存画像を images/ へ格納
             └─ Sheets API: 名刺データシートへ1行追加(または更新+変更履歴記録)
```

**当社側に存在するもの**: 静的ファイル(HTML/CSS/JS)、Portal のアイコン、KeyStore、TSAM AI 認証系、GoogleのOAuthクライアント設定のみ。**サーバーコード・データベース・利用者データの保管場所は存在しない。**

### 4.3 使用サービス

| 区分 | 使用技術・サービス | 用途 |
| -------- | ------------------------------- | ---------------- |
| フロントエンド | HTML、CSS、Vanilla JavaScript(ESモジュール、ビルドなし) | 全処理(撮影〜保存) |
| 配信 | ts-corporate-renewal リポジトリ(tsam-ai.com) | 静的ページとして配信 |
| 導線 | TSAM AI Portal(`public/portal/`) | アプリアイコン掲載 |
| アプリ認証 | TSAM AI 本番認証系(`auth/`、`tsam-auth-session`) | ログイン確認 |
| Google認証 | Google Identity Services(トークンモデル) | Drive / Sheets API 用トークン取得 |
| OCR | Google Drive API v3(ブラウザから直接) | 画像から文字情報を抽出 |
| APIキー管理 | Portal KeyStore(`public/auth/keystore.js`) | 利用者のGeminiキーの取得(読み取りのみ) |
| AI分類 | Gemini API(利用者キー、ブラウザから直接) | 名刺項目への分類・構造化 |
| 画像保存 | 利用者のマイドライブ(`TSAM AI/名刺データ/images/`) | 名刺保存画像の格納 |
| データ保存 | 利用者のスプレッドシート(Sheets API) | 構造化データ・変更履歴の管理 |
| 設定情報 | 静的設定ファイル(tsam-ai.com 配信のJSON) | モデル名等のアプリ設定 |

LockService・Script Properties・時間主導型トリガー・処理ログの中央保管は廃止する(サーバーが存在しないため)。

## 5. 対象ユーザー

### 5.1 対象

TSAM AI のアカウントを保有する利用者。**社内限定ではなく、TSAM AI の一般利用者へ公開し、MVPでは全プランに開放する。** 将来的にスコープ(対象プラン)を限定する可能性があるため、Portal の表示とアプリ側の利用可否判定にプラン条件を後付けできる構成とする(実装上はログイン確認処理の一箇所にプラン判定を差し込める形とし、MVPでは常に許可を返す)。

### 5.2 利用条件

* TSAM AI のアカウントでログインできること。
* Googleアカウントを保有し、本アプリへのDriveアクセス(drive.file)を許可できること。
* 自身のGemini APIキーを保有し、Portal のキー設定画面で保存済みであること(**無料枠キーでも利用可**)。
* スマートフォンまたはPCのブラウザを利用でき、インターネットへ接続できること。

### 5.3 利用上の明示事項

以下を利用規約・利用者向けヘルプおよび初回利用時の案内画面に明記する。

* 名刺データ・保存画像は**利用者本人のGoogleドライブにのみ**保存される。当社は利用者の名刺データを受信・保管・閲覧しない。
* データの管理(バックアップ、整理、削除、共有設定、ドライブ容量)は利用者自身の責任で行う。**当社は利用者のドライブの状態を関知せず、データの復旧義務を負わない。**
* Gemini APIの利用費(有料キーの場合)は利用者本人に課金される。
* **無料枠のGeminiキーでは、送信したテキストがGoogleのプロダクト改善に利用される場合がある。** 名刺は第三者の個人情報であるため、業務利用では有料区分キーの使用を推奨する。区分の選択と結果への責任は利用者に帰属する。
* 名刺情報(第三者の個人情報)の取り扱いに関する法令遵守(利用目的、保管、削除等)は、データを保有する利用者自身の責任で行う。
* 利用者が保存フォルダやスプレッドシートを削除・移動・改変した場合、本アプリは次回起動時に新しい保存構造を作成する。過去データとの連続性は保証しない。

## 6. 前提条件

1. フロントエンドは ts-corporate-renewal リポジトリの **`public/production-app/card-ocr/`** に配置し、`https://tsam-ai.com/production-app/card-ocr/` として配信する(アプリID: `card-ocr`)。**Portal と同一オリジンであることが KeyStore 参照の必須条件である。** なお `APP_REGISTRY`(`public/portal/app-registry.js`)へ登録する `href` に `apps/` を含めてはならず、先頭に `/` を付けてもならない(自動テスト `tests/unit/frontend.mjs` が禁止している)。
2. アプリ認証は TSAM AI 本番認証系(`tsam-auth-session`)を使用する。
3. Google Cloud プロジェクトを用意し、OAuthクライアントID(Webアプリケーション種別)を発行、承認済みJavaScript生成元に `https://tsam-ai.com` を登録し、**Google Drive API と Google Sheets API** を有効化する。
4. OAuth同意画面はユーザータイプ「外部」・公開ステータス「本番」とする(TSAM AI 利用者は当社Workspace外の一般Googleアカウントであるため)。要求スコープは `https://www.googleapis.com/auth/drive.file` のみとし、テストユーザー数上限・未確認アプリ警告が発生しない状態で公開する。必要な審査・確認手続きはフェーズ0で洗い出す。
5. Cloud プロジェクト側の Drive / Sheets API クォータ(プロジェクト単位の上限)は全利用者で共有されるため、利用者数の見込みに対する上限をフェーズ0で確認する。
6. MVPでは日本語および英語が記載された一般的な名刺を対象とする。画像はJPEGまたはPNGを基本とする。**1件は「表面1枚（必須）＋裏面1枚（任意）」で構成する**（v3.1）。裏面を撮らずに表面だけで登録することも、引き続き通常の使い方とする。3枚以上、および複数名刺の一括撮影はMVP対象外とする。

## 7. スコープ

### 7.1 MVPに含める機能

* Portal へのアプリアイコン掲載と、ログイン → Portal → 本アプリの導線
* TSAM AI ログイン確認と未ログイン時の `/login/` への誘導
* Google OAuth 連携(初回同意、トークン再取得)
* KeyStore からのGeminiキー取得と、未設定時の Portal への誘導
* 初回起動時の保存構造の自動作成(フォルダ・スプレッドシート)と、以降の再発見
* スマートフォンカメラからの名刺撮影、端末内画像の選択
* **裏面の撮影（任意）と、裏面なしでの登録**（v3.1）
* ブラウザ側での画像縮小・JPEG圧縮（面ごと）
* ブラウザからの Drive OCR 実行と一時ドキュメントの即時完全削除・孤児回収
* テキスト正規化・正規表現抽出(ブラウザ側)
* Gemini APIによる項目分類(利用者キー、テキストのみ)
* **表面と裏面の結果の統合、および競合の提示**（v3.1）
* AI解析結果の表示、登録前の確認・修正
* 利用者自身のスプレッドシートに対する重複候補検出と差分確認
* 確定保存: 利用者のドライブへの画像格納、スプレッドシートへの1行保存、更新時の変更履歴記録
* 処理エラーの表示、抽出失敗時の手入力による登録

### 7.2 MVPに含めない機能

v1.1の対象外一覧(自動切り抜き、台形補正、一括撮影、QR解析、CRM/Contacts連携、一覧・検索・登録後修正UI、オフライン、一括インポート、独自DB、AI評価、第三者向けAPI)に加え、以下を対象外とする。

> **v3.1 で「両面統合」をこの一覧から外した。** MVPに含める（§1.0）。
> ただし**3枚以上の登録と、既に登録した件へあとから裏面を足すこと**は
> 引き続き対象外とする（§20 で要判断）。

* 当社サーバーによるデータの受信・保管・バックアップ・ログ集中管理
* 会社キーによるGemini呼び出し(フォールバック含む)
* Geminiキーの本アプリ内での登録・変更UI(Portal に一元化)
* 利用者間のデータ共有・チーム共有機能(各自のドライブ内で完結)
* 利用者のドライブ容量・データ整理状態の監視や代行管理

## 8. 業務フロー

### 8.1 基本フロー

全処理が利用者のブラウザと利用者のGoogleアカウントの間で完結する。

```text
[ステージ0] 起動時チェック(ブラウザ)
  1. TSAM AI セッションを確認する。未ログインなら /login/ へ誘導する。
  2. KeyStore.has('gemini') を確認する。未設定なら Portal のキー設定画面へ誘導する。
  3. Google OAuth トークンの有無を確認する(なければ「Googleと連携する」から同意フロー)。
  4. 保存構造を確認する。
     - 本アプリが作成した「TSAM AI/名刺データ」フォルダとスプレッドシートを検索する。
     - 見つからなければ新規作成する(初回、または利用者が削除した場合)。
     - スプレッドシートIDをブラウザにキャッシュし、次回以降の検索を省略する
       (キャッシュが無効になった場合は再検索・再作成する)。
  5. 過去の孤児一時ドキュメントを検索し、あれば完全削除する。

[ステージ1] 画像準備(ブラウザ) ※v3.1で両面に対応
  6. 表面を「撮影する」または「画像を選択する」。**表面は必須**。
  7. ブラウザ側で画像の向き、サイズ、容量を調整し、プレビューを表示する。
  8. 「裏面も読み取りますか?」を出す。
     - 「裏面を撮る」 → 6〜7を裏面について繰り返す
     - 「裏面なしで進む」 → そのまま次へ（**既定の導線はこちら**）
  9. ユーザーが「読み取る」を押す。

[ステージ2] 抽出(ブラウザ → Google API) ※v3.1で両面に対応
  10. Drive API で**面ごとに**画像をGoogleドキュメントへ変換する(ocrLanguage: ja)。
      裏面がある場合、表面と**並列**に投げる。
  11. 面ごとに本文テキストを取得し、一時ドキュメントを完全削除する。
      **裏面のOCRが失敗しても、表面の結果だけで先へ進む**（裏面は補助）。
  12. 面ごとにテキストを正規化し、正規表現抽出を行う。
  13. 表裏のテキストを**面のラベルを付けて結合**し、Gemini API へ1回で送る。
  14. 正規表現抽出結果とGemini結果を統合する（FR-15）。

[ステージ3] 確認(ブラウザ ⇄ 利用者のスプレッドシート)
  14. Sheets API で名刺データシートの重複判定キー列を取得し、ブラウザ内で照合する。
  15. 確認・修正画面を表示する。重複候補があれば差分確認画面を表示する。

[ステージ4] 確定保存(ブラウザ → 利用者のドライブ)
  16. ユーザーが内容を確認・修正し、「登録する」を押す。
  17. 保存画像を images/YYYY/MM/ へアップロードし、ファイル名を確定する。
  18. 名刺データシートへ1行追加する(更新の場合は対象行を record_id で特定して
      上書きし、変更前値を変更履歴シートへ記録する)。
  19. 登録完了画面を表示する。ブラウザ上の画像データと抽出結果を破棄する。
```

キャンセル・離脱時は、一時ドキュメントの削除(未了なら次回起動時の孤児回収)以外の後始末を必要としない。登録に至らなかった画像はどこにも保存されない。

### 8.2 画像仕様

v1.1と同一とする: JPEG/PNG、1.5MB以下、推奨長辺1,600〜2,000ピクセル、JPEG品質0.80〜0.85(0.75未満へは下げない)、正しい画像方向、名刺全体が画像内に収まっていること。Drive OCRの推奨(2MB以下等)を満たす。

## 9. 機能要件

### FR-01 Webアプリ表示

システムは、tsam-ai.com 配下のアプリURLへアクセスした利用者に、名刺登録画面を表示すること。画面には最低限、アプリ名、撮影ボタン、画像選択ボタン、画像プレビュー、読み取り開始ボタン、処理状況、エラーメッセージを表示する。Portal・ログイン画面と共通の見た目(`auth/` 配下の共通資産)を再利用する。

---

### FR-02 アクセス制御(v3.0改訂)

システムは、次の3層で利用可否を判定すること。

1. **TSAM AI 認証**: 画面表示時に `tsam-auth-session` のセッションを確認し、未ログインなら `/login/` へ誘導する。確認は共通実装(`public/auth/` の `guardPage()`)を使用し、独自実装しない。**Portal の一覧に掲載する・しないにかかわらず、アプリ自身にこのガードを必ず入れる**(URLを直接知っている未ログイン者への対策)。保護すべき当社側データは存在しないため、サーバー側の検証APIは設けない。ログイン確認は「TSAM AI 契約者向け機能」であることの担保として行う。
2. **Google OAuth**: スコープは `drive.file` のみ。利用者のドライブ全体を読むスコープを要求してはならない。トークンはメモリ上でのみ保持する。
3. **Geminiキー**: KeyStore.get('gemini') で取得する。取得できない場合は抽出を開始せず、Portal のキー設定画面へ誘導する。

利用者のデータの実質的な保護は、利用者自身のGoogleアカウント認証(OAuth)によって担保される。本アプリは他利用者のデータへ到達する経路を構造上持たない。

---

### FR-03 名刺画像取得(v3.1改訂: 両面)

v1.1と同一とする(`<input type="file" accept="image/jpeg,image/png" capture="environment">`、iOS Safari・Android Chrome実機必須、HEIC選択時の案内とカメラ撮影誘導)。加えて次のとおりとする。

* **表面と裏面は、別々の入力として順に取得する。** 1画面に2つの入力欄を並べない
* **表面は必須、裏面は任意。** 表面を取得したあとに「裏面も読み取りますか?」を出し、
  「裏面なしで進む」を**既定の導線**として並べる
* 裏面を撮ったあとで「裏面を取り消す」ができること

> **推奨と理由（設計論点1: 撮影フローのUI）**
>
> **順に取得する案を推奨する。** 1画面に2枠を並べる案と比べて、
> スマートフォンで片手で扱うときに「いま何を撮ればよいか」が一意に決まる。
> 名刺の多くは裏面が空白か英語表記の複製であり、**裏面なしが多数派**である。
> 多数派の操作を最短にし、裏面は明示的に選んだ人だけが通る形にする。
>
> card-scanner も「表面（必須）＋裏面（任意）」の構成を採っており、
> **成立することが分かっている**（同アプリ README「1件につき表面（必須）と
> 裏面（任意）の2枚を登録できる」）。

### FR-04 画像プレビュー(v3.1改訂: 両面)

v1.1と同一とする(確認、取り直し、別画像選択、読み取り開始、処理前キャンセル、手動回転)。加えて、**面ごとにプレビューと取り消しを行えること**。読み取り開始前は、表面・裏面のどちらも差し替えられる。

### FR-05 画像前処理

v1.1と同一とする(Canvas縮小・JPEG変換・品質圧縮・1.5MB確認・方向補正、EXIF二重補正の実機確認、超過時の段階的圧縮と撮り直し案内)。

---

### FR-06 画像ハッシュ生成(v3.1改訂: 面ごと)

システムは、ブラウザ側で圧縮後画像のSHA-256ハッシュを生成すること(Web Crypto API)。位置づけはv1.1と同一: 検出できるのは同一ファイルの再送のみであり、同一名刺の再登録検出はFR-17の属性ベース判定を主力とする。

**v3.1: ハッシュは面ごとに生成し、面ごとの列へ保存する**（§11.2）。裏面が無ければ空。

重複判定では、**表裏の取り違えも拾う**。候補の表面ハッシュが既存行の裏面ハッシュと一致する場合（およびその逆）も、同一名刺の再登録として警告する。撮る順番を間違えるのはよくあることで、それを別件として登録させない。card-scanner が同じ扱いをしている。

---

### FR-07 保存構造と保存画像の格納(v3.0改訂)

システムは、利用者のマイドライブに以下の保存構造を維持し、確定保存時に保存画像を格納すること。

```text
マイドライブ
└─ TSAM AI
   └─ 名刺データ
      ├─ 名刺管理(Googleスプレッドシート)
      └─ images
         └─ YYYY
            └─ MM
```

* **初期化**: 起動時に上記構造を確認し、存在しなければ作成する(8.1 ステージ0)。フォルダ・スプレッドシートの発見は、drive.file スコープで参照できる「本アプリが作成したファイル」の検索により行う。
* **再作成**: 利用者がフォルダやスプレッドシートを削除・改変していた場合は、警告なく新規作成して以降の登録先とする。旧データの取り込み・救済は行わない(5.3の明示事項)。
* **ファイル名**(v3.1改訂): `YYYYMMDD_HHMMSS_会社名_氏名_front.jpg` / `..._back.jpg`(取得不能時は `YYYYMMDD_HHMMSS_UNCLASSIFIED_一意ID_front.jpg`)。使用できない記号は除去する。**面の接尾辞は表面にも必ず付ける。** 裏面が無い件でも付けることで、ファイル名の形が1つに定まり、あとから裏面を足す余地も残る。
* **共有設定**: 本アプリはフォルダ・ファイルに共有設定を付与しない。利用者が自ら共有した場合の結果は利用者の責任とする。
* **保持期間**: 定めない。データは利用者の資産であり、削除・保管は利用者の判断による。

### FR-08 テキスト抽出(ブラウザからのDrive OCR)

v2.0と同一とする。

1. `files.create`(multipart)で画像をアップロードし、`mimeType: application/vnd.google-apps.document`、`ocrLanguage: 'ja'` でGoogleドキュメントへ変換する。作成先は「TSAM AI/名刺データ」配下の一時領域とする。
2. `files.export`(text/plain)で本文テキストを取得する。
3. テキストが空の場合は一時ドキュメントを削除のうえ変換からやり直す(最大3回)。
4. 成否にかかわらず一時ドキュメントを `files.delete` で完全削除する(try-finally相当の構造で必ず実行)。
5. OCR言語ヒントは `ja` を初期値とし、英語名刺を含む実データでフェーズ0に精度検証する。

**v3.1: 面ごとに1〜4を実行する。**

6. 裏面がある場合、**表面と裏面のOCRを並列に投げる**。
7. **裏面のOCRが失敗しても、全体を失敗にしない。** 表面の結果だけで先へ進み、
   画面に「裏面は読み取れませんでした」と出す。裏面は補助である。
8. 401 を受けた場合だけは例外で、再認可のうえ**両面をやり直す**。
   片面だけ新しいトークンで通すと、どちらが失敗したのか分からなくなる。
9. 一時ドキュメントは面ごとに作られる。**両方とも消えたことを確認する**（AC-07）。
10. **片面のテキストが空でも、もう片面にテキストがあれば先へ進む**（v3.1）。
    3 の再試行（最大3回）は面ごとに行い、**再試行を尽くしても空だった面は
    「その面にテキストが無かった」として扱う**。両面とも空のときだけ OCR-002 とする。

> **10 は v3.0 になかった扱いである。** v3.0 は表面1枚だけを扱っていたため、
> 「テキストが空 = 読み取り失敗」で正しかった。
>
> 両面になると、これが成り立たなくなる。**表面がロゴだけの名刺**
> （§16.1 の評価セットに4枚含まれる）は、表面のOCRが正当に空を返す。
> ここで全体を失敗にすると、**裏面に氏名も連絡先も揃っているのに登録できない。**
>
> 空を「失敗」ではなく「その面には文字が無かった」と読み替えることで、
> FR-15 の統合規則2（表面が空の項目だけ裏面で補完）がそのまま働く。

> **推奨と理由（設計論点3-a: OCRを並列にするか）**
>
> **並列を推奨する。** 直列にすると所要時間がほぼ倍になり、§13.1 の
> 中央値45秒という目標を単独で壊す。Drive のクォータは利用者あたり
> 12,000/分（フェーズ0実測）で、1件あたり6回に増えても影響は無い。
>
> card-scanner は表面→裏面の**直列**である。並列にしなかった理由は
> 同アプリの README からは読み取れないが、401時に両面をやり直す設計と
> 相性がよいためと考えられる。本アプリは 8 で同じ復旧方針を採るため、
> 並列でも扱いは同じになる。
>
> **並列で確定した（§20、2026年8月3日）。** 直列で45秒に収まるかどうかに
> かかわらず並列で実装する。実装の単純さより、目標値に余裕を残すことを取る。

v1.1と同一とする(NFKC、空白・改行・記号の統一、制御文字除去、重複行除去、Gemini送信2,000文字以内、切り捨て時は抽出済み項目を含む行を優先)。実行場所はブラウザ。

### FR-11 Gemini API利用(v3.0改訂)

v2.0の内容を基本とし、キー区分の扱いのみ変更する。

* 利用者キーを `x-goog-api-key` ヘッダーに載せ、正規化テキストのみを送信する。画像は送信しない。
* 初期設定モデル: **主 `gemini-2.5-flash-lite` / フォールバック `gemini-3.5-flash-lite`**(静的設定ファイルで変更可能。v3.2 で確定)。主モデル404時はフォールバックモデルで1回再試行する。会社キーへのフォールバックは行わない。
  * フェーズ0で `gemini-3.5-flash-lite` に 503(混雑)が続き、主モデルを `gemini-2.5-flash-lite` へ入れ替えたところ同じキー・同じリクエストで6/6成功した(計画 §7-5-2)。**実測で通ったほうを主に置く。**
  * 両モデルとも実在することは確認済み。したがって**フォールバックが働く場面は「主モデルが廃止されたとき」**であり、混雑時の退避ではない(退避の是非は §20 の要判断)。
* `thinking_level` 最小相当、履歴なし、1名刺1リクエスト、出力上限初期値400トークン。
* **無料枠キーの利用を許容する。** 401/403時はキー確認の案内(KEY-002)、429時は利用者自身のクォータである旨の案内(AI-002)を表示する。無料枠の利用上限に達した場合の待機・有料化の案内をヘルプに用意する。

**v3.1: 両面でも Gemini の呼び出しは1名刺あたり1回のまま。**

* 表裏のテキストを**面のラベルを付けて結合**して送る。

  ```text
  【表面】
  (表面の正規化テキスト)

  【裏面】
  (裏面の正規化テキスト)
  ```

* 裏面が無い場合は `【表面】` のブロックだけを送る。
* 入力上限（2,000文字）は**結合後の全体**に対して適用する。超える場合の
  切り捨ては FR-09 の方針（抽出済み項目を含む行を優先）を面ごとに適用し、
  **表面を先に確保してから裏面を詰める**。
* 出力に `fromBackFields`（裏面から採った項目名の配列）と
  `conflicts`（表裏で値が食い違った項目名の配列）を加える（FR-12）。

> **推奨と理由（設計論点3-b: Gemini を1回にするか2回にするか）**
>
> **結合して1回を推奨する。** 理由は3つある。
>
> 1. **クォータ。** FR-14 が「無料枠キー利用者のクォータ消費を抑える」ことを
>    求めている。2回にすると、無料枠のレート上限に当たる頻度が倍になる。
>    フェーズ0で 429 の挙動を確かめている最中でもあり、呼び出し回数を
>    増やす方向の変更は避けたい。
> 2. **矛盾の解消。** 表面が日本語、裏面が英語という名刺は多い。
>    別々に分類すると「株式会社サンプル商事」と「Sample Trading Co., Ltd.」が
>    別の値として競合する。**1回で両方を見せれば、同じ会社の別表記だと
>    モデル側で判断できる。**
> 3. 所要時間。Gemini の往復が1回で済む。
>
> **代償は、値の由来が機械的には分からなくなること。** 面ごとに呼べば
> 「この値は裏面から来た」と確実に言えるが、1回にすると分からない。
> そこで `fromBackFields` と `conflicts` をモデルに報告させる。
> **これはモデルの自己申告であり、機械的な照合より弱い。**
>
> **この構造ごと確定した（§20、2026年8月3日）。** まず1回で実装し、
> フェーズ2の両面精度検証（§18）で `fromBackFields` の一致率を見る。
> 当てにならないと分かれば、面ごとに2回呼ぶ案（card-scanner の
> `mergeParsed()` と同じ構造）へ切り替える。
> **「切り替える条件と切替先」まで含めて決定事項である。**

### FR-15 結果統合(v3.1改訂: 表裏の統合)

v1.1と同一とする(ユーザー修正値 > 項目特性別の機械抽出値/Gemini値 > 未設定)。

**v3.1: 表面と裏面の統合を次の順序で行う。**

1. **表面を優先する。** 表面に値がある項目は、裏面の値で上書きしない
2. **表面が空の項目だけ、裏面で補完する**
3. **両面に値があって内容が違う場合、自動で上書きしない。** 表面の値を採ったうえで
   競合として記録し、確認画面に**両方を並べて**「裏面の値を使う」を選べるようにする
4. **メールアドレスは競合させず、和集合にする。** 単一値ではないため、
   表と裏で違っても「どちらが正しいか」の問題にならない。
   裏面にしか無いアドレスがあった場合は、追加した旨だけを案内する
5. **裏面から補完した項目は、確認画面で「要確認」を出す**

> **推奨と理由（設計論点2: 統合ロジックと競合時の優先順位）**
>
> **表面優先を推奨する。** 名刺の裏面は、英語表記の複製・事業内容の説明・
> 地図であることが多く、**表面が正**である場合がほとんどである。
> 裏面を優先すると、英語表記が日本語表記を潰す事故が起きる。
>
> **競合を自動解決しない**のは、要件定義書 FR-13 の「推測しない」と同じ理由である。
> どちらが正しいかはアプリには決められない。決められないものを黙って決めると、
> **間違ったほうが選ばれたことに誰も気づけない。** 両方見せて人に選ばせる。
>
> **裏面由来を「要確認」にする**のは、確認画面に「どちらの面から来たか」を
> 出さないためである。出しても利用者の判断材料にならず、画面が混むだけだが、
> 根拠が弱いことは伝える必要がある。
>
> この5点は card-scanner の `mergeParsed()` がすでに採っている規則であり、
> **実運用で成立することが分かっている**（同アプリ README「表面と裏面の統合」）。

**「裏面にしか情報が無い名刺」に特別な規則は要らない。**

表面がロゴだけの名刺は、表面から取れる項目が0件になる。このとき規則2
（表面が空の項目だけ裏面で補完）が全項目に働き、結果として裏面の内容が
そのまま採用される。規則5により全項目が「要確認」になる。**これで正しい。**

必要だったのは統合側の特別扱いではなく、**そこへ到達できること**である。
FR-08 の10 がそれを担う。空のOCRを失敗として扱う限り、統合規則は呼ばれない。

> 全項目が「要確認」になると、印としての情報量は下がる。ただし
> **記録全体が裏面由来という異例の状態**なので、全部を確認してもらうのが
> 正しい。画面には「表面から項目を読み取れませんでした」を別に出し、
> 何が起きたのかが分かるようにする。

v1.1と同一とする(全項目修正、複数候補からの主項目選択、uncertainFields強調、名刺交換日・場所・担当者・タグのセッション既定値、手入力導線)。

### FR-17 重複候補検出(v3.0改訂: 利用者のシート内で完結)

システムは、登録前に**利用者自身の名刺データシート**との重複を確認すること。

* Sheets API で重複判定キー列(duplicate_key、正規化メール、正規化電話)のみを取得し、ブラウザ内で照合する。全列の全件取得を行わない。
* 判定優先順位・正規化ルール(NFKC、法人格辞書、記号除去、国番号正規化)はv1.1と同一とする。画像SHA-256一致は補助判定とする。
* 重複候補がある場合の選択肢(新規登録・既存更新・キャンセル)、更新時の差分確認必須・無確認自動上書き禁止・変更前値の変更履歴記録・record_idによる行特定はv1.1と同一とする。
* 検索対象は利用者本人のシートのみである。他利用者のデータとの重複は概念として存在しない。

---

### FR-18 スプレッドシート保存(v3.0改訂: Sheets API)

システムは、確認後の情報を利用者の名刺データシートへ1件1行で保存すること。

* 追加は `spreadsheets.values.append`、更新は record_id で行を特定して `values.update` で行う。
* **入力値サニタイズ**: `=` `+` `-` `@` で始まる値は保存前に強制的にテキスト化する(利用者自身のシートを数式インジェクションから守るため。RAW入力オプションの使用と併せてフェーズ0で方式を確定する)。
* **競合**: サーバー側ロックは存在しない。同一利用者が複数タブ・複数端末で同時登録した場合、まれに重複行が生じ得る。これは許容し、FR-17の重複検出が次回以降に候補として提示することをもって緩和策とする(ヘルプに明記)。
* 保存後、シートの並び・書式は操作しない(利用者が自由に編集してよい領域とする。ただしヘッダー行と record_id 列の改変は動作保証外である旨をヘルプに明記する)。

### FR-20 エラー処理

ログの中央保管は行わない。エラー詳細はブラウザコンソールへ出力し、問い合わせ時に利用者が画面のエラーコードを伝えられる表示とする。

## 11. データ要件

### 11.1 スプレッドシート構成(利用者ごと)

利用者のマイドライブ内スプレッドシート「名刺管理」に、以下の2シートを用意する。

| シート名 | 用途 |
| ----- | ------------------ |
| 名刺データ | 確定した名刺情報 |
| 変更履歴 | 既存データ更新時の変更前値の記録 |

処理ジョブ・処理ログ・設定シートは廃止する。アプリ設定(モデル名等)は tsam-ai.com 配信の静的設定ファイルで管理する。

### 11.2 名刺データシート

v1.1の列構成を基本とし、以下を変更する。

* 削除: `registered_by`(利用者本人のシートであり自明)、`extraction_method` / `gemini_model` / `prompt_version` → `app_version` と `prompt_version` の2列に整理
* `record_id` `image_hash` はブラウザで生成する(UUID / Web Crypto)。サーバーが存在しないため「サーバー側で確定」の概念は消滅するが、これらの列を利用者が手編集した場合の動作は保証外とする(FR-18)。
* `drive_file_id` `drive_file_url` は利用者自身のドライブ上の保存画像を指す。

**v3.1: 面ごとの列に分ける。**

| 変更 | 列 |
| --- | --- |
| 分割 | `drive_file_id` → `front_file_id` / `back_file_id` |
| 分割 | `drive_file_url` → `front_file_url` / `back_file_url` |
| 分割 | `image_hash` → `front_image_hash` / `back_image_hash` |
| 追加 | `has_back`（裏面の有無。`TRUE` / 空） |
| 追加 | `back_filled_fields`（裏面から補完した項目名。空白区切り） |

* **裏面が無い件では、`back_*` の列は空にする。** 列自体は常に置く。
  行ごとに列数が変わると、利用者が表計算ソフトで扱いにくくなる。
* `back_filled_fields` を残すのは、あとから「この値はどこから来たのか」を
  たどれるようにするためである。確認画面の「要確認」（FR-15 の5）と対応する。
* 画像URLは `=HYPERLINK()` でクリックできるようにし、表示文言を
  `表面画像を見る` / `裏面画像を見る` とする。**この値も数式であるため、
  FR-18 のサニタイズの対象外として明示的に組み立てる**（利用者入力ではない）。

> **推奨と理由（設計論点4: データ構造）**
>
> **面ごとに列を分ける案を推奨する。** 1つの列にJSONを詰める案は、
> 利用者が表計算ソフトで直接編集する前提（FR-22）と両立しない。
> 列が増えても、**人が読める形のまま**にしておくほうがこの設計に合う。
>
> OCR本文を面ごとに残すかは**要判断**とした（§20）。card-scanner は
> 表面OCR / 裏面OCR / 統合OCR の3列を持つが、名刺1枚ぶんの全文が
> 3列に入ることになり、利用者のシートが重くなる。

### 11.3 変更履歴シート

v1.1と同一の列構成とする(history_id、changed_at、record_id、field_name、old_value、new_value)。changed_by は削除する(本人のみのため)。

## 13. 非機能要件

### 13.1 性能

| 項目 | 目標 |
| ---------- | -------------- |
| 初期画面表示 | 中央値3秒以内(初回の保存構造作成時を除く) |
| 初回セットアップ(保存構造作成) | 30秒以内 |
| 画像圧縮 | 中央値5秒以内 |
| 1件全体・**表面のみ**(読み取り開始〜確認画面表示) | 中央値45秒以内 / 95パーセンタイル90秒以内 / 最大許容180秒 |
| 1件全体・**両面**(v3.1新設) | **中央値60秒以内 / 95パーセンタイル120秒以内 / 最大許容240秒**（暫定値。フェーズ2の実測で確定） |
| 確定保存 | 中央値10秒以内 |
| 重複照会 | 3秒以内(1万行時点。超過時はDB移行ではなく取得方式の見直しを検討) |

> **推奨と理由（設計論点3-c: 所要時間目標への影響）**
>
> **両面の目標を別に立てることを推奨する。** 表面のみの45秒に両面を
> 押し込もうとすると、OCRの並列化が必須要件になり、失敗時の扱い（FR-08 の8）が
> 複雑になる。**別の数字を置けば、直列でも収まるかを実測で確かめられる。**
>
> 暫定値の根拠は、OCRを並列にすれば増えるのは画像圧縮とアップロードのぶんだけ
> という見込みである。**実測していない。** フェーズ0の両面検証（§18）で
> 確定させる。直列にした場合はほぼ倍（90秒前後）になる見込みで、
> そのときは目標値を見直すか並列化を必須にするかを決める。
>
> **1件あたりのDrive呼び出しは3回から6回に増える。** プロジェクト単位の
> クォータ（Drive 12,000/分）から見れば無視できる。

**クォータに関する留意**:

* OCR・Sheets操作のユーザー単位クォータは利用者ごとに分散する。
* **Cloud プロジェクト単位の Drive / Sheets API クォータは全利用者で共有される。** 公開アプリとして利用者数が伸びた場合の律速要因となるため、フェーズ0で上限値を確認し、必要に応じて引き上げ申請の手順を整理する。
* Gemini APIのレート・課金は利用者キーごとに独立する。無料枠キーはレート上限が低いため、429時の案内(FR-11)を丁寧に行う。

### 13.2 容量

当社側の容量計画は不要である(データを保持しないため)。利用者のドライブ容量は利用者の責任範囲とし、保存画像が1件最大1.5MBである旨をヘルプに記載する。

### 13.3 可用性

* Google各サービスとTSAM AI認証系の稼働状況に依存する。
* Drive OCR・Gemini・Sheetsのいずれの障害時も再試行できること。Gemini障害時は手入力登録で業務を継続できること。
* 当社サーバー起因の障害点は静的配信と認証系のみである。

### 13.4 保守性

* モデル名(主・フォールバック)、出力上限、プロンプト(バージョン付き)、JSON Schema、正規表現・法人格辞書を静的設定・ESモジュールとして一元管理する。
* ts-corporate-renewal リポジトリの規約に従い、本アプリの仕様書を docs/specs/ に置く。Portal 改修(FR-25)も同規約に従う。
* テストは本番系のスイート(`tests/`)に追加し、`tests/run.mjs` の SUITES へ登録する。テストでは fetch をスタブし、実際の Google / Gemini API へ通信しない(KeyStore仕様書§7の方針に従う)。テスト環境 `public/apps/tests/` には追加しない。
* エラーコードを定義する。OAuthクライアントは開発用・本番用を分離する。

### 13.5 拡張性

将来的に以下を追加できる構成とする。

* 名刺一覧・検索UI(利用者自身のシートの読み取り)、CSV出力(サニタイズ必須)

* チーム共有(利用者が自身のスプレッドシートを自ら共有する運用の案内から着手)

## 14. セキュリティ要件

### 14.1 APIキー

v2.0と同一とする(利用者所有・KeyStoreが唯一の管理場所、当社側に一切保存しない、送信先はGemini APIのみ、localStorage平文保存ゆえXSS対策を最重要視、API制限設定の推奨案内、ローテーションはPortalに委ねる)。

### 14.2 認証・認可

* アプリ利用は TSAM AI ログインを前提とする(FR-02)。当社側に保護対象データが存在しないため、認可の実体は利用者自身のGoogle OAuthである。
* OAuthトークン・Geminiキーは当社で預からない。

### 14.3 入力値の取り扱い

* 抽出テキスト・AI出力・ユーザー入力は信頼できない入力として扱い、画面表示に `innerHTML` を使用しない。
* シート保存前の数式インジェクション対策(FR-18)を行う。守る対象は利用者自身のスプレッドシートである。
* 外部スクリプトは Google Identity Services 等の必要最小限とし、第三者CDNを使用しない。CSPの適用可否をフェーズ0で検証する。**XSSはGeminiキー窃取に直結するため、クライアント側対策を最重要要件とする。**

### 14.4 データアクセス

* 名刺データ・保存画像は利用者のGoogleアカウント内にのみ存在する。当社従業員を含む第三者は、利用者が自ら共有しない限りアクセスできない。
* 本アプリはフォルダ・ファイル・スプレッドシートに共有設定を付与しない。
* OCR一時ドキュメントは共有設定を行わず、即時削除する。

### 14.5 個人情報(v3.0改訂)

* 名刺情報は第三者の個人情報であるが、**当社はこれを取得・保管・閲覧しない**。個人情報の取扱事業者としての義務(利用目的、保管、削除、開示対応等)は、データを保有する利用者に帰属することを利用規約に明記する。
* 当社の対応事項を以下に限定し、本番リリース前に完了する。
  1. 利用規約・ヘルプへの責任分界の明記(5.3)と、初回利用時の案内表示。
  2. 無料枠キーのデータ取り扱い(14.6)の開示文言の確定。
  3. 当社が名刺データを受信しない構成であることの通信レベルでの検証(19章 完了条件)。
* 上記の整理(特に「当社はツール提供者であり個人情報取扱事業者に当たらない」という整理の妥当性)は法務確認を経て確定する。

### 14.6 Gemini APIの利用区分(v3.0改訂: 無料枠を許容)

* **無料枠キーでの利用を許容する。**
* ただし、無料区分では送信テキストがGoogleのプロダクト改善に利用され得る。名刺は第三者の個人情報であるため、以下を実施する。
  1. 初回利用時の案内画面とヘルプに、無料枠のデータ取り扱いと有料区分の推奨を明記する。
  2. キー区分の選択と、それに伴う第三者個人情報の取り扱い責任は利用者に帰属することを利用規約に明記する。
* 当社がキー区分を検証・保証しないことは v2.0 から継続する(検証手段が存在しない)。

| 利用形態 | キー | 当社の対応 |
| ---- | ----------- | --------- |
| お試し・個人利用 | 無料枠キー可 | データ取り扱いの開示 |
| 業務利用(実在名刺) | **有料区分キーを推奨** | 推奨の明示。強制はしない |

## 16. 受入基準

### 16.1 評価用サンプルセット(v3.1改訂)

v1.1と同一とする(確定サンプル50枚: 日本語横書き20、縦書き8、日英併記8、英語のみ5、ロゴ表記のみ4、低品質5)。

**v3.1: この50枚は「表面のみ」の測定に使う。取り直さない。**

両面統合の検証には、**別に「裏面に情報がある名刺」15枚**を用意する。
内訳は次のとおり。50枚のうち裏面がある名刺を流用してよい。

| 種別 | 枚数 | 何を見るか |
| --- | --- | --- |
| 裏面が英語表記の複製 | 6 | 表面優先が効いて、日本語が英語で潰されないこと |
| 裏面に追加情報がある（携帯・部署・別メール） | 5 | 補完が効くこと。`back_filled_fields` に載ること |
| ↑のうち**表面がロゴだけ**のもの | （5枚のうち2枚） | **表面のOCRが空でも先へ進み**（FR-08 の10）、裏面だけで1件が成立すること |
| 裏面が地図・事業内容など、項目を含まない | 4 | **余計な項目を作らないこと**（FR-13） |

> **推奨と理由（設計論点5-a: 既存サンプルへの波及）**
>
> **50枚を取り直さないことを推奨する。** 表面のみの精度は、両面対応を
> 入れても変わらない（表面のOCRと分類の経路は同じ）。
> **測り直す費用に見合う情報が得られない。**
>
> 一方、両面の統合は「新しく増えた振る舞い」なので、それだけを狙った
> 小さなサンプルで測る。15枚としたのは、上の3種別それぞれで傾向が
> 見える最小限だからである。**統計的な精度ではなく、統合規則が
> 意図どおり効くかを見る**ための枚数である。

### 16.2 定量基準(v3.2改訂: 判定はフェーズ2)

v1.1と同一とする(主要5項目正解率85%以上、メール正規化一致率95%以上、処理完了率95%以上、登録所要時間が手入力より短いこと、推測追加0件)。

**v3.2: 判定の時期をフェーズ0からフェーズ2へ移した。**

v1.1 と v3.0 では「フェーズ0実測で確定」としていたが、
両面対応（v3.1）でプロンプトが変わるため、フェーズ0で測っても
**実装後に測り直しになる**。フェーズ2の完了条件で判定する（§18）。

**母数は50枚のまま**（§16.1）。フェーズ0の6枚は予行であり、判定に使わない。

**v3.1: 両面についての基準を別に置く。**

| 指標 | 基準 |
| --- | --- |
| 表面優先が守られる率 | **100%**（表面に値がある項目が裏面で上書きされないこと） |
| 裏面にしか無い項目の取得率 | **80%以上** |
| 競合の検出漏れ | **0件**（表裏で値が違うのに競合として出ない、が無いこと） |
| 項目を含まない裏面での誤検出 | **0件**（地図・事業内容から項目を作らないこと） |

**「表面優先が守られる率100%」と「競合の検出漏れ0件」を厳しく置く**のは、
どちらも**間違いに気づけない**種類の失敗だからである。取得率が低いのは
「取れなかった」と分かるが、上書きされた値は正しそうな顔で残る。

### 16.3 機能別受入基準

### フェーズ0: 方式検証PoC(必須)

* ブラウザからの Drive OCR(multipart + ocrLanguage + export + delete)の疎通と精度検証(サンプル30枚以上)
* drive.file スコープのみでの保存構造作成・再発見・Sheets操作の成立性検証
* KeyStore 経由のキー取得と Gemini 呼び出しの疎通(Portal と同一オリジン)

* Cloud プロジェクト単位クォータの確認と引き上げ手順の整理
* 数式サニタイズとRAW入力の方式確定、CSP適用可否の検証
* 行順崩れ対策プロンプトの検証、定量受入基準の目標値の確定

**v3.1: フェーズ0では両面統合を検証しない。**

理由は、フェーズ0の目的が「**方式が成立するか**」の確認であり、
両面統合は方式の問題ではなく**統合規則が正しいかの問題**だからである。
表面1枚で OCR → Gemini → 項目が成立すれば、面が2つになっても方式は変わらない。

**v3.2（2026年8月4日改訂）: 精度・所要時間の本判定もフェーズ0では行わない。**

フェーズ0は「**方式の成立性の実証**」をもって完了とする。
上の項目のうち「精度検証（サンプル30枚以上）」と「定量受入基準の目標値の確定」は
**フェーズ2へ移す**（§16.2、フェーズ2の完了条件）。

移す理由は3つある。

1. **成立性は全経路で実証済み。** OAuth・KeyStore・Gemini・Drive OCR・
   保存構造の作成と再発見・一時ドキュメントの完全削除まで、
   すべて実機で通っている（計画 §4-0-1）
2. **6枚の予行で、方式が破綻しないことは分かった。**
   完了率100%、所要時間の中央値17.9秒（基準45秒の半分以下）（計画 §7-5-1）
3. **両面対応でプロンプトが変わる。** いま測っても、フェーズ2の実装後に
   測り直しになる。**同じ作業を二度行う理由がない**

> **フェーズ0で「精度が基準に届く」ことは確かめていない。**
> 確かめたのは「**経路が通り、破綻しない**」ことである。
> この区別を曖昧にしないこと。基準への合否はフェーズ2で判定する。

| **両面の所要時間目標**（§13.1） | **確定: 別建てとし、暫定値は中央値60秒 / 95%tile 120秒 / 最大240秒。** 実測していないため、**フェーズ2の実測で数値を確定**させる。別建てにすること自体は確定 |
| **裏面のみに氏名・会社名がある名刺の扱い** | **解消。特別な規則を設けない。** FR-15 の統合規則2（表面が空の項目だけ裏面で補完）の自然な帰結として扱う。ただし**手前の FR-08 に手当てが要る**ことが分かったため、FR-08 に 10 を新設した（片面が空でも、もう片面にテキストがあれば先へ進む）。§16.1 の両面サンプルに「表面がロゴだけ」を2枚含める |

**未確定（引き続き要判断）**

| 項目 | 仮設定・確定時期 |
| ----------------- | --------------------- |
| **OCR本文を面ごとにシートへ残すか**（§11.2） | **仮: 残さない。** card-scanner は表面/裏面/統合の3列を持つが、利用者のシートが重くなる。デバッグに要るかを実装時に判断 |
| **既に登録した件へあとから裏面を足せるようにするか** | **仮: 対象外。** FR-22 のとおり登録後の編集は利用者がシートを直接触る方針であり、画像の追加だけアプリが担うのは筋が悪い。要望が出たら再検討 |
| 裏面付き評価サンプルの枚数（§16.1） | **仮: 15枚。** 統計ではなく統合規則の確認が目的。不足と分かれば増やす |
| **503（混雑）のときに別モデルへ退避するか**（FR-11） | **仮: 退避しない。** FR-11 の切り替え条件は現在 404 のみ。フェーズ0で `gemini-3.5-flash-lite` の 503 を観測し、**モデル単位の混雑であることを実証した**（計画 §7-5-2）ため、退避すれば通る場面はある。ただし**退避先のモデルでは精度が変わる**ため、同じ名刺でも結果が日によって違うことになる。「登録できないより、精度が違っても登録できるほうがよい」と考えるなら入れる。**MVPの利用者体験をどう置くかの判断**であり、フェーズ2で決める |
| **表面のOCRが空で、かつ裏面も無い場合の案内**（FR-08 の10） | **仮: OCR-002。** 「裏面も撮ってみてください」を案内に足すかは、両面検証の結果を見て決める |

当社側に置かないもの

## 付録A: v3.0で廃止・変更した論点

| 論点 | 扱い |
| --- | --- |
| 会社共有ドライブ・会社スプレッドシートへの保存 | 廃止。利用者自身のドライブ内で完結する構成へ変更 |
| GAS API(重複照会・確定保存・セッション検証) | 全廃。Sheets/Drive APIのブラウザ直接呼び出しへ変更。サーバーコードゼロ |
| 運用専用アカウントによるデータ所有 | 廃止(所有すべきデータが当社側に存在しない)。OAuthクライアント等のCloud資産の管理者としてのみ残る |
| LockService による排他制御 | 廃止。同一利用者の同時登録による重複行は許容し、重複検出で緩和 |
| 処理ログの中央保管 | 廃止。エラーコード表示とブラウザコンソールで代替 |
| 許可ユーザー一覧による認可 | 廃止。TSAM AI ログイン(+対象プラン判定)へ変更 |
| 管理者によるデータ修正・削除運用(旧FR-22) | 廃止。利用者自身の直接編集へ変更 |
| 「全ユーザーが全データを閲覧できる」制約の明示 | 廃止(構造上、各自のデータのみとなったため) |
| 有料区分キーの使用義務(同意・規約による担保) | 変更。無料枠を許容し、データ取り扱いの開示と有料推奨へ緩和。責任は利用者に帰属 |
| 保存画像の保持期間(3年)・容量計画・定期クリーンアップ | 廃止。データは利用者の資産であり当社は関知しない |
| 個人情報保護法対応(当社が取扱事業者となる前提の整理) | 変更。当社はツール提供者としての責任分界の明記へ(法務確認は継続) |

## 付録A-2: v3.1 で撤回した論点

| 論点 | 扱い |
| --- | --- |
| 「両面統合はMVP対象外」(v3.0 §6 の6、§7.2) | **撤回。** MVPに含める。表面（必須）＋裏面（任意）で1件を構成する |

## 付録B: v1.1・v2.0から引き継いだ不採用論点

Gemini呼び出しスキップ機能、LockService固定保持上限前提、confidence表示、GDPR個別対応、撮影時原本の二重保存(以上v1.1)、方式A(画像直接送信)、会社キーによるフォールバック(以上v2.0)は、引き続き不採用とする。
