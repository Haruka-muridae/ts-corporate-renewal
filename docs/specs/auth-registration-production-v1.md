## 2. 目的

現在 **Stripe テストモード（サンドボックス）** で構成されている初回登録フローを、
**Stripe 本番（ライブ）モード**へ切り替え、実際の顧客が実カードで申し込み、
アカウントを取得してログインできる状態にする。

重点は次の順とする。

1. **テスト設定と本番設定の混在を作らない。** キー・Price ID・Webhook 合言葉は
   モード間で互換性がなく、片方だけ切り替えると「決済は成立するのに
   アカウントが作られない」という最悪の形で壊れる。
2. **切替は検証可能な手順で行い、実決済1件の通し確認で完了とする。**
3. **切り戻し手段を先に決めてから切り替える。**

---

## 3. 現状（As-Is）

| 構成要素 | 現状 |
| --- | --- |
| 稼働状態 | **テストモードで初回登録フローは動作確認済み**（2026-08-11 時点、事業者確認）。本切替は動作している構成のモード切替のみを行う |
| Stripe キー | Script Properties の `STRIPE_SECRET_KEY` にテスト用キーを設定 |
| 商品・料金 | テストモードで作成した Price を `plans` シートの `stripe_price_id` に登録 |
| Webhook | テストモードのエンドポイント（構成A: Apps Script の `/exec?path=stripe-webhook&k=…` へ直接送信） |
| 処理イベント | `checkout.session.completed` ほか5種（[STRIPE_SETUP.md](../../STRIPE_SETUP.md)「処理しているイベント」） |
| 決済導線の表示 | `publicConfig` の `checkoutAvailable`（Stripe 設定済み かつ 有効プランあり）で自動判定。フラグの手動操作は無い |
| 利用者データ | 認証スプレッドシートの `users` ほか。テストで作成した行が残っている可能性がある |

初回登録の成立条件は「Stripe から Webhook が届き、`checkout.session.completed` の
イベント照会（`GET /v1/events/{id}`）が成功すること」。本文は信用せず照会結果のみを
使うため、**Webhook がライブモードで正しく登録されていなければ登録は一切成立しない。**

## 4. スコープ

### 4.1 対象（To-Be）

1. **ライブモードで商品と料金（Price）を作成する。** テストの Price ID は
   ライブでは使えない。金額・請求間隔はテストと同一にする。
2. **`plans` シートの `stripe_price_id` をライブの値へ更新する。**
   D列（表示用金額）と Stripe 側の Price の金額が一致していることを同時に確認する。
3. **`STRIPE_SECRET_KEY` をライブのシークレットキーへ更新する**
   （Script Properties。設定シートには書かない — `SECRET_KEYS` は
   設定シートから読まない設計）。
4. **ライブモードで Webhook エンドポイントを作り直す。**
   - 構成A（現行）の場合、URL の合言葉 `k=` は既存の `STRIPE_WEBHOOK_URL_KEY` を
     継続使用してよい（Apps Script 側の値は変わらないため）。
   - 送信イベントはテストと同じ5種のみ。
5. **`checkAuthSetup()` を実行し、設定の整合を確認する。**
6. **実カードで1件、初回登録を通しで確認する**（§7 受入条件）。確認後に返金する。
7. **切替の実施記録を残す**（実施日・確認結果。§8 の様式）。

### 4.2 対象外（変更しない）

- `gas-auth/` のコード変更。**本切替はコード変更を伴わない設定作業である。**
  コードを触る必要が生じた場合は、それは本書の範囲外の不具合として別途扱う。
- `public/auth/config.js` の `apiUrl`。Apps Script の再デプロイは行わないため
  `/exec` URL は変わらない（**新規デプロイを作らないこと** — URL が変わると
  Stripe Webhook と `config.js` の両方の修正が必要になる。既存デプロイの
  バージョン更新もそもそも不要）。
- 交流会申込アプリ（`app/event/`）の Stripe 設定。**同じダッシュボード上の
  別系統であり、本切替で触らない。**
- 料金・プラン構成そのものの変更。
- メール文面（`MailTemplates.gs`）。

## 5. 前提・制約

1. **Stripe ダッシュボードには複数アカウント・複数サンドボックスがある。**
   交流会アプリの切替時（[docs/production-cutover.md](../production-cutover.md)）に
   確認済みの実在リスク。**Stripe を操作する前に毎回、画面左上のアカウントが
   認証系で使う正しいアカウントであることを確認する。** 別アカウントに
   Webhook やキーを作ると「決済は通るのに登録されない」「決済画面で認証失敗」
   という切り分けにくい故障になる。
2. テストモードとライブモードは、キー・Price ID・Webhook がすべて別。
   **部分的な切替状態を作らない**ため、§6 の手順は一気に実施する
   （途中で日をまたがない）。
3. 切替作業中も既存利用者のログイン・セッションは影響を受けない
   （変更するのは決済系の設定のみで、`users` `sessions` は触らない）。
4. 決済導線の表示（`checkoutAvailable`）は自動判定のため、
   「受付開始」の明示操作は無い。**ライブキーと有効プランが揃った時点で
   料金ページに申込ボタンが出る**ことを理解した上で作業順を組む
   （通し確認が済むまで告知はしない）。

## 6. 切替手順（要件としての手順骨子）

詳細な操作は [STRIPE_SETUP.md](../../STRIPE_SETUP.md) §6 に従う。順序を要件として定める。

1. ライブモードで商品・Price を作成する。
2. `plans` シートの `stripe_price_id` を更新する。
3. `STRIPE_SECRET_KEY` をライブキーへ更新する。
4. ライブモードで Webhook エンドポイントを登録する（イベント5種）。
5. `checkAuthSetup()` を実行し、問題なしを確認する。
6. 実カードで1件申し込み、§7 の受入条件を全て確認する。
7. Stripe ダッシュボードからその1件を返金し、Webhook 経由で
   `subscription` の状態が追従することを確認する（解約時の挙動確認を兼ねる）。
8. テスト決済で作られた利用者行の扱いを決めて記録する
   （残す場合はテストと分かる注記。交流会の前例では「記録として残す」を採った）。

---

## 7. 受入条件

すべてライブモードでの実決済1件により確認する。

| # | 条件 |
| --- | --- |
| 1 | 料金ページにプランが表示され、申込ボタンが出る（`checkoutAvailable` が真） |
| 2 | 同意チェックを経て Stripe の決済画面（ライブ）へ遷移する |
| 3 | 実カードで決済が成立する |
| 4 | Webhook が受信され、`stripe_events` に `processed` で記録される |
| 5 | `users` に利用者が作成され、`subscription_status` が `active` になる |
| 6 | 初期設定メールが届き、リンクからパスワードを設定できる |
| 7 | 設定したパスワードでログインでき、ポータルが表示される |
| 8 | 返金・解約後、該当 Webhook イベントで `subscription_status` が追従し、ログインできなくなる |
| 9 | 不正な合言葉（`k=` 改変）の POST が `INVALID_REQUEST` で拒否される |
| 10 | `checkAuthSetup()` が警告なしで通る |

---

## 8. 切り戻し

| 事象 | 戻し方 |
| --- | --- |
| 通し確認で失敗し、原因調査に時間がかかる | `STRIPE_SECRET_KEY` をテストキーへ戻し、`plans` の `stripe_price_id` をテスト値へ戻す。これで `checkoutAvailable` はテスト構成に戻る（誤って実決済される状態を残さない） |
| 申込を一時停止したい | `plans` シートの `enabled` を全行 `FALSE` にする。プランが0件になり `checkoutAvailable` が偽になって申込ボタンが消える（即時・コード変更不要） |
| ライブ Webhook の誤設定 | Stripe 側でエンドポイントを無効化／削除して作り直す。Apps Script 側の変更は不要 |

切替の実施記録（実施日、各手順の結果、テスト決済の受付・返金記録、
テストデータの扱いの判断）は本書の末尾か
[docs/production-cutover.md](../production-cutover.md) と同様の記録文書に残す。

---

## 9. リスクと対策

| リスク | 対策 |
| --- | --- |
| 別 Stripe アカウント／交流会側への誤設定 | §5-1。全 Stripe 操作の前にアカウント名を確認。交流会の Webhook・キーには触れない |
| 片側だけの切替（キーのみ／Price のみ） | §6 を一連の作業として実施し、`checkAuthSetup()` と実決済で確認するまで完了としない |
| 通し確認前に顧客が申し込む | ライブキー設定から通し確認完了までの間は告知を行わない。必要なら `plans.enabled=FALSE` で導線を閉じたまま作業する |
| テストデータの混入 | §6-8 で扱いを明示的に決めて記録する |
| 初期設定メールの不達 | 通し確認で実際の着信を確認する。Gmail 送信元の制約は既存構成のままで変更しない |

## 10. 採用しなかった提案とその理由

1. **テスト用と本番用の Apps Script プロジェクトを分けて並行運用する** —
   利用者データの正は1つのスプレッドシートであり、二重管理は
   登録先の取り違えという新しい事故を生む。切り戻しはキーと Price の
   差し戻しで足りる（§8）。
2. **決済導線の表示に手動フラグを追加する（コード変更）** —
   `plans.enabled` の全行 `FALSE` で同じ効果が得られ、
   コード変更なしという本切替の性格（§4.2）を保てる。
3. **構成B（署名検証つき中継）への同時移行** — 真正性の本質は
   イベント照会（`GET /v1/events/{id}`）であり、切替と同時に構成を
   変えると障害時の切り分けができなくなる。必要なら別作業とする。
