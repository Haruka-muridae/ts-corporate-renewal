本指示書とあわせて、仕様書ファイルを渡しています。

- `login-page-detailed-spec-v3.md`(ログインページ詳細定義書 v3)

この仕様書を **正** とします。
本作業は新機能の追加ではありません。仕様書と実装を完全一致させるための整合作業です。

以下を厳守してください。

- 指示された範囲外のリファクタリング・機能追加・挙動変更を禁止します
- 既存テスト571件+ブラウザスイートをすべて緑のまま維持してください
- アカウント列挙耐性に関わる挙動(AUTH_FAILED への集約 / ダミー照合 / SESSION_INVALID 単一化 / 再設定の常時成功応答)は **1文字も変更禁止** です
- 判断に迷う点があれば、実装せずに質問として報告してください

## 作業0: 仕様書のリポジトリ配置(最初に行うこと)

仕様書を今後の作業の恒久的な参照先としてリポジトリへ配置します。

1. `docs/specs/` ディレクトリを作成してください(既に docs/ がある場合はその配下に specs/ を作成)
2. 渡された仕様書を `docs/specs/login-page-detailed-spec-v3.md` として配置してください(内容の変更・整形は禁止。そのまま置くこと)
3. 本指示書も `docs/instructions/2026-07-29-login-v3-alignment.md` として配置してください
4. `docs/specs/README.md` を新規作成し、以下の内容を記載してください
   - このディレクトリの仕様書が実装の正であること
   - 現在の有効版の一覧(login-page-detailed-spec-v3.md)
   - 仕様書と実装が食い違う場合は、黙って乖離させず、どちらを直すか判断して両方を同期させるルール
5. ここまでを **単独のコミット** にしてください(コード変更と混ぜないこと)

配置場所の制約:

- `docs/` はリポジトリルート直下とします
- GitHub Pages がルートを配信しているため、docs/ 配下も公開されます。**仕様書に秘密情報(鍵・ID・内部URL等)が含まれていないことを配置前に確認してください**(v3には含まれていないはずですが、機械的に確認すること)
- 公開を避けたい判断になった場合は、配置せずにその旨を報告し、指示を待ってください

以降の作業では、仕様書への参照はすべて `docs/specs/login-page-detailed-spec-v3.md` のセクション番号(§n)で行います。

## 作業1: 仕様書と実装の突き合わせ検証

仕様書の以下のセクションについて、実装が記述と一致しているかをコードを根拠に検証してください。

- §2 レイアウト定義(要素・属性・順序)
- §5 API契約(action / フィールド名 / レスポンス形状 / エラーコード / フォールバック)
- §6 リダイレクト仕様(ALLOWED_NEXT / safeNextName / guardPage の挙動)
- §7 セッション(保存キー / 保存内容 / Session fixation 対策の実在確認)
- §8 サーバー側判定(判定順序 / 設定値 / ロック挙動)
- §9 エラー文言の管理場所

出力形式:

```
一致       : <セクション番号> — 根拠(ファイル名:関数名)
不一致     : <セクション番号> — 仕様の記述 / 実装の実態 / 修正提案(仕様修正 or 実装修正のどちらが妥当か)
確認不能   : <セクション番号> — 理由
```

**不一致を発見しても、この段階では修正しないでください。** 報告のみ行い、修正判断は人間側で行います。

## 作業2: Session fixation / 全失効のテスト確認・追加

仕様書 §12 の以下2項目について、対応するテストが既存スイートに存在するか確認してください。

1. ログイン成功時に、直前まで有効だったトークンとは異なる新規トークンが発行されること
   (同一トークンの再利用・継続使用が起きないこと)
2. パスワード変更後、変更前に発行された全セッションの verifySession が SESSION_INVALID を返すこと

- 存在する場合: テスト名とファイルを報告し、追加不要と結論してください
- 存在しない場合: 既存のテストハーネス(tests/helpers/gas-harness.mjs)と既存スイートの書式に従って追加してください
  - 追加先は既存の分類に従うこと(セッション関連なら tokens-sessions スイート等)
  - 新しいテスト基盤・ライブラリの導入は禁止

## 作業3: 既知の課題2件の解消(仕様書 §13)

### 3-1. 文言の二重定義の統一

- ui.js の MESSAGES.notConfigured は未参照であり、実際に表示されるのは api.js の NOT_CONFIGURED_MESSAGE です
- **api.js 側の文言を正とし**、ui.js の未使用定義を削除してください
- 削除後、grep で notConfigured への参照が残っていないことを確認してください

### 3-2. ストレージ利用不可文言の移動

- login.js に直書きされているストレージ利用不可の文言を、ui.js の MESSAGES へ移動してください
- login.js は MESSAGES 経由で参照する形に変更してください
- 表示される文言そのものは変更しないでください

いずれも挙動(表示される文字列・タイミング)を変えない純粋な整理です。ブラウザテストの文言検証が既にある場合、テスト側の参照も追従させてください。

作業3完了後、仕様書の §13 を「解消済み」へ更新し、§3・§9 の該当記述(login.js 直書きの注記)も同期させてください。**仕様書の変更はこの同期のみ許可します。**

## 作業4: 実装コメントへの設計意図の反映(任意・軽量)

仕様書 §14 で却下された提案のうち、コードを読んだ将来の実装者が「直したくなる」可能性が高い以下2箇所に、短いコメントが既にあるか確認し、無ければ1〜2行で追加してください。

1. remember の `=== true` 厳密判定(Main.gs)
   例: `// Boolean()正規化は不可。Boolean("false")===true となり30日セッションが誤発行される(docs/specs §14)`
2. userAgent のクライアント送信(api.js)
   例: `// GASのdoPost(e)はHTTPヘッダーを受け取れないため、サーバー側でUA取得は不可能(docs/specs §14)`

既に同趣旨のコメントがあれば追加不要です。
