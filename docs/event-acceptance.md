```
checkout.session.completed  → 支払済みに更新（受付番号 TSAM-0001）／メール送信済み
charge.refunded             → 返金済み（例外対応）に更新しました
```

### テスト申込のデータについて

本番DBに残した申込2件は、**記録として意図的に残している**（事業者判断、2026-08-01）。

| 受付番号 | 状態 | 備考 |
| --- | --- | --- |
| （未発行） | `awaiting` | 決済へ進んだが完了しなかったもの。支払は発生していない |
| `TSAM-0001` | `refunded` | 実決済テスト。決済3,300円 → 全額返金済み |

**次の申込者の受付番号は `TSAM-0002` から始まる。** 受付番号はイベント内の連番で、
支払済みになった時点で採番される。テスト分を消さない限り `TSAM-0001` は
再利用されない。当日の受付でこの2件を参加者と取り違えないよう、
名札印刷用CSVの出力時は `refunded` が含まれないことを確認すること
（名札用CSVは `paid` のみを対象にしているため、返金済みは自動的に外れる）。

## 条件6の経緯（テストモードでは確認できなかった）

**テスト環境（サンドボックス）では、領収書メールの送信を確認できない。**

* 領収書メールの設定（Customer emails → Successful payments）は
  サンドボックスでグレーアウトしており、**変更できない**（事業者確認済み）
* 決済詳細からの手動送信も効かない。請求の `receipt_email` を再設定して
  送信を促しても `receipt_number` は採番されなかった
* 返金済みの請求が原因ではないことも確かめた。**未返金の請求**
  （`pi_3TzJKDCL3niUmYGZ0Vg5w0zl`、7,700円、`succeeded`）を新たに作って
  同じく確認したが、30秒待っても `receipt_number` は採番されなかった
  （確認後に返金済み）

Stripe は領収書を送信した時点で `receipt_number` を採番するため、
未採番であることが未送信の確かな手掛かりになる。

### テストモードで確認できていたこと（実装側の準備）

* Checkout Session に `customer_email`（申込者のメールアドレス）を渡している
* 決済後の請求に `receipt_email` が正しく設定される
* 領収書のURL（`receipt_url`）も発行される

コードの変更は不要で、本番で設定を入れれば送信される状態だった。

### どこで合格にしたか

本番の設定（<https://dashboard.stripe.com/settings/emails> の
「Successful payments」）を有効にしたうえで、本番の実決済で**領収書メールの
受信を確認**した。着信までに遅延があったが届いた。これをもって条件6を合格とする。

### 次に同じ確認をするときの注意

テスト環境の設定画面（<https://dashboard.stripe.com/test/settings/emails>）は
グレーアウトしていて変更できない。**領収書メールの動作確認は本番でしか行えない**。
テストモードで「領収書が届かない」と見えても、それは実装の不具合ではない。
