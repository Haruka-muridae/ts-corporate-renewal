# カレンダー通知の設計ノート

制定: 2026年8月10日（V2）

**このファイルは「なぜそうなっているか」を置く場所である。**

配布物（`gas-notifier/` のテンプレート）は、利用者のスプレッドシートへコピーされて
配られる。つまり**コードは読まれる前提**である。V1 では設計判断の理由をコード
コメントとして書いていたが、それは同時に「どう作ってあるか」を丸ごと渡すことでもあった。

V2 では、コードには**作りが分かる程度**の説明だけを残し、判断の理由はここへ移した。
配布物には含まれない。

> 秘密（鍵・トークン・スプレッドシートID）はここにも書かない。
> リポジトリは GitHub にあり、この文書も公開されうる。

## 1. 判定を運営側（Workers）へ移した

V1 は利用者の Apps Script が鍵生成・判定・署名・送信の全部を持っていた。
コピーした人は解約後も通知を受け取り続けられ、**サブスクリプションとして
成立していなかった。**

V2 では次の2つを運営の Workers（`notifier-gate`）へ移した。

| 移したもの | なぜそこでなければならないか |
| --- | --- |
| 判定（何を通知するか） | 製品の頭脳。利用者のシートにあると読めるし変えられる |
| VAPID JWT の発行 | 署名が無ければ Push を送れない。判定だけ止めても、テンプレートを改造すれば自前の判定で送れてしまう |

**「コピー・改変では迂回できない位置」に置くことが目的**であって、
利用者を疑っているわけではない。判定を手元に残したまま「使わないでください」と
書く形では、対価と機能の対応が保てない。

移していないもの（利用者の手元に残るもの）:

- Google カレンダーの読み取り
- 予定名・説明・参加者（利用者自身のスプレッドシートのみ）
- Push の送信そのもの（購読を持っているのは利用者側）

## 2. シートの持ち方

### 2-1. 時刻はエポックミリ秒の数値で持つ

ISO 8601 の文字列をセルへ書くと、Google スプレッドシートが日時として解釈し、
読み戻したときに Date オブジェクトや別書式の文字列になる。そうなると
`sentAt >= now - 10分` のような比較が**静かに壊れる**。

表示用の整形は API の応答を作る時点（`Api.gs`）で行う。

### 2-2. 設定は読むたびに丸める

画面は保存前に検証するが、シートは利用者が直接編集できる。丸めておかないと、
`timing` に文字列が入っただけで通知が一切出なくなる。

文字列 `'false'` を `Boolean()` に渡すと `true` になる。同じ誤りが本番認証系で
30日セッションの誤発行を起こしている。`toBool_` が文字列を明示的に見ているのは
そのため。

### 2-3. 列は末尾へ足す

`HEADERS` の順序がそのまま列順である。途中へ挿入すると既存データがずれる。

## 3. 匿名化（eid）

運営の Workers が受け取ってよいのは、次の骨格だけである。

```
eid / feature / startAt / status / allDay / cancelled
```

**予定名・説明・参加者・メールアドレス・カレンダーIDは渡さない。**
これは要件 DR-03/04（運営はデータを預からない）の実装であり、
同時に「運営サーバーが侵害されても予定の中身は出ない」という設計でもある。

予定IDそのものも渡さない。セットアップ時に生成した端末ごとの秘密鍵
（`EID_HMAC_KEY`）で HMAC-SHA256 にかけた値（`eid`）を渡す。

- 鍵は利用者のスクリプトプロパティにしか無い。運営は元の予定IDへ戻せない
- 利用者ごとに鍵が違うので、**別の利用者の同じ予定でも別の eid になる**
  （運営側で「同じ会議に出ている2人」を突き合わせられない）
- `eid` → 実際の予定の対応表は `notify_queue` / `sent_log`（利用者のシート）だけが持つ

守り方を「送らないよう気をつける」に頼っていない。Workers 側の
`validateEvents` が、許可した項目以外を含む要求を**受け取らずに拒否する**。

`EID_HMAC_KEY` を作り直すと、送信済みの記録（`sent_log` の `eid`）と
突き合わなくなり、同じ通知がもう一度出る。だから `ensureEidHmacKey_` は
既にあれば触らない。

## 4. リスケされたときの再通知（宿題 B-05）

V1 は重複判定キーが `eventId + timing` で、**開始時刻を含まなかった。**
そのため「10:00 の会議の通知を受け取ったあと、会議が 14:00 へ動いた」場合に
通知が出なかった。

V2 はキーへ開始時刻を含める。ただしそのままだと、主催者が1〜2分ずらすたびに
別キーになって通知が連発する。そこで

> **開始時刻の差が5分未満なら「送信済み」を引き継ぎ、再通知しない。**

とした。比較の相手は常に**送信時点の開始時刻**で、前回の同期で見た値ではない。
毎回の値と比べると、4分ずらしを繰り返すことで無限に先送りできてしまう。
送信時点と比べれば、4分ずらしを2回した時点で元から8分動いており再通知される。

この判定に必要な「いつ・どの予定を・何分前設定で送ったか」は利用者のシートにある。
だから `buildSentDigest_` がそれを Workers へ渡す。**Workers 側は無状態**で、
送信の記録を持たない（持てば、それは利用者の予定の履歴を運営が持つことになる）。

## 5. 取得済みは購読（端末）単位（宿題 B-04）

V1 は `sent_log` の1行に `fetchedAt` を1つ持つだけだった。2台以上の端末を
登録していると、**最初に取りに来た端末がその行を取得済みにしてしまい**、
2台目の Service Worker は空の配列を受け取る。`userVisibleOnly` の約束を守るため、
そこで汎用のフォールバック通知（「通知の内容を取得できませんでした」）が出る。
2026-08-09 の本番検証で実際に踏んだ。

V2 では

- `subscriptions` に `subId`（購読ごとの短い識別子）を持たせる
- `sent_log` の `fetchedBy` に、取りに来た `subId` を並べる
- `pending` は**呼び出し元の endpoint を必須にし**、その購読についてだけ取得済みにする

`pending` で endpoint を省略できるようにしなかったのは、省略を許すと
「最初に来た端末が全部さらう」V1 の挙動へ静かに戻るからである。

## 6. Push の送り方

### 6-1. 本文を送らない

Web Push の本文は、購読ごとの鍵（p256dh / auth）から ECDH + HKDF で導いた鍵で
AES128GCM 暗号化する決まりになっている。Apps Script には ECDH も HKDF も無い。

本文なしの Push（tickle）なら、必要なのは VAPID の署名だけで済む。
通知の中身は Service Worker が `pending` で取りに来る（要件 FR-15/16）。

1回の tick につき1購読あたり Push は最大1通にしている。件数分送ると、
2通目以降の push イベントでは pending が空になり、フォールバック通知が
誤って表示される。

### 6-2. TTL を5分にしている

Push サービスは、ブラウザが受け取れない間（電源断・スリープ）通知を預かる。
その時間を5分に切っているのは意図的である。

**「10:55 に知らせてほしい」通知が 12:00 に届いても、会議はもう始まっている。**
役に立たないどころか混乱のもとになる。遅れて届くくらいなら届かないほうがよい。

この挙動は利用者から見えるため、`docs/calendar-notifier-setup.md` に同じ説明がある。

### 6-3. V2 では署名を自前で行わない

V1 は jsrsasign（約500KB）を利用者に手で貼らせて ES256 署名を作っていた。
これがセットアップの最大の障害で、貼り忘れ・順序違い・途中で切れた、の
いずれも「通知が届かない」という同じ症状になり、原因が見えなかった。

V2 では JWT を Workers が発行する。Workers には WebCrypto があり、
`crypto.subtle.sign` の ECDSA/P-256 は JWS がそのまま要求する `r||s` の
64バイトを返す。**利用者側から貼り付け工程が消え、同時にライセンスの
効きどころにもなった。**

## 7. Web アプリを接続キーで守る

ウェブアプリのURLは「リンクを知っている全員」に開かれている
（Service Worker から匿名で叩くため、この設定でなければ動かない）。
URLだけで予定名が読めてしまわないよう、`health` 以外の全 action で接続キーを検証する。

`health` を素通しにしているのは、「URLが正しいか」と「接続キーが正しいか」を
利用者が切り分けられるようにするため。だから `health` には予定の情報を入れない。

接続キーを誤って共有してしまった場合の失効手段が `regenerateConnectKey` である。
**現在のキーを知っている相手だけが呼べる。**

---

## 8. ライセンスキーは録音アプリから GAS へ渡す

引き継ぎの向きは2つ考えられた。

| 向き | 経路 | 判定 |
| --- | --- | --- |
| 録音アプリ → テンプレート | コピーリンクの `#lk=` に載せる | **不成立** |
| 録音アプリ → GAS | 接続確立後に `saveLicense` で渡す | **採用** |

前者が成立しないのは、**Google スプレッドシートのコピーURLはフラグメントを
引き継がない**からである。コピー後に開かれるのは新しいドキュメントのURLで、
`#lk=` は消える。加えてサイドバーは Sheets の iframe の中にあり、
親ページのURLを読めない。

したがって順序を逆にした。

1. 利用者がテンプレートをコピーし、ウィザードで［セットアップ］→［公開］
2. ウィザードが引き継ぎリンク（`#setup=` に execUrl と接続キー）を出す
3. 録音アプリがそれを受け取って保存し、**すでに確立した接続越しに**
   ライセンスキーを `saveLicense` で送る

この形なら**利用者がキーを貼る欄は要らない**（要件どおり）。
さらに、ライセンスキーが第三者ページのURLやクリップボードを経由しない。

## 9. ワンボタン公開

V1 は「デプロイ」→「新しいデプロイ」→ 種類の選択 →
アクセス設定、という Google 側の画面を利用者に踏ませていた。
選択肢が多く、1つ違えると動かない。

V2 は Apps Script API（`projects.versions.create` / `deployments.*`）を
スクリプト自身から呼んで公開する。`ScriptApp.getOAuthToken()` の
アクセストークンは**サーバー側関数の中だけで使い、クライアントへ渡さない。**

### 冪等にする

既存のウェブアプリ用デプロイがあれば、新しいバージョンを作って
そのデプロイを `update` する。`create` し直すと `/exec` URL が変わり、
録音アプリ側の設定が黙って無効になる。

`@HEAD` のデプロイ（`versionNumber` を持たない）は `update` できないため、
探索から外す。ここを外さないと、2回目の公開が必ず失敗する。

### 9-2. 部分失敗でバージョンを増やさない

公開は「バージョンを作る」→「デプロイへ結びつける」の2段階で、
**前半だけ成功する**ことがある。そのまま作り直すと、使われないバージョンが
残る。ウィザードは API の許可待ちで5秒ごとに公開を試すため、
デプロイ側の失敗が続くあいだバージョンが増え続ける。

そこで、作ったバージョン番号を `PENDING_VERSION` へ控え、
**デプロイが通るまで同じ番号を使い回す。** 通った時点で控えを消す。

再試行の間にコードが変わることはない（利用者はエディタを開かない）ので、
使い回して困る場面が無い。控えたバージョンが実は公開済みだった場合も、
同じ内容を再デプロイするだけで害が無い。

待ち続ける側にも上限を置いた（5秒 × 60 = 5分）。放置されたまま
呼び続けないためで、上限に達したら公開ボタンの画面へ戻す。

### 行き止まりを作らない

Apps Script API は既定でオフで、初回は 403 が返る。ウィザードはこれを
`API_DISABLED` として検出し、設定ページへ誘導したうえで、数秒ごとに
公開を試して自動で次へ進む。

それ以外の失敗（権限・通信・想定外）では、**手動でデプロイする手順を
折りたたみで開く。** 自動化が失敗したときに何もできなくなる状態を作らない。

## 10. レート制限は「失敗したときの振る舞い」とセットで決める

ゲートの `/v1/vapid` は1キーあたり**1時間20回**に制限してある
（[constants.mjs](../workers/notifier-gate/src/constants.mjs) の `RATE_LIMITS`）。
この数字より大事なのは、**上限に当たったあとどうするか**である。

### 10-1. 上限だけを決めて事故になった

当初は1時間4回だった。JWT は12時間キャッシュされるので、
定常状態なら1日1〜2回で足りる、という見積もりである。

実機で破綻した（2026-08-11）。見落としていたのは2つ。

1. **セットアップ中はキャッシュが空**である。「12時間に1回」が効くのは
   1回成功したあとの話にすぎない
2. **失敗するほど呼び出しが増える。** 鍵が取れない → 保存されない →
   次の操作でまた取りに行く

2 の増幅が具体的にどう起きたか。

| 起きたこと | `/v1/vapid` の消費 |
| --- | --- |
| `saveLicense` が鍵の先取りに失敗し、**action ごと失敗を返した** | 1 |
| 録音アプリは「引き渡せなかった」と解釈し、ライセンスキーを消さない | — |
| 続く `publicKey` が鍵を取りに行く | 1 |
| 利用者がもう一度［接続テスト］を押す（画面には × しか出ていない） | 2 |

正規の操作2回で使い切り、以後すべて `RATE_LIMITED`。
**成功しないと呼び出しが減らないのに、呼べないから成功しない。**
上限そのものが罠になっていた。

### 10-2. 直した3か所

**上限を上げるだけでは同じ罠が残る。** 呼び出しが増える経路を塞ぐほうが本体である。

| どこ | 何を変えたか |
| --- | --- |
| [Api.gs](../gas-notifier/Api.gs) `handleSaveLicense_` | 鍵が取れなくても**成功**を返す。この action の仕事はキーを預かることで、それは終わっている。取れなかった事実は `gateError` で添える |
| [Gate.gs](../gas-notifier/Gate.gs) `gateVapid_` | 失敗したら次に試してよい時刻を控え、**その間は呼ばない**。何度押しても呼び出しは増えない |
| [ratelimit.mjs](../workers/notifier-gate/src/ratelimit.mjs) | 断るときに**窓が明けるまでの秒数**を返す。これが無いと呼び出し側は当てずっぽうで再試行し、その再試行がまた断られる |

待つ長さは事情で変える。上限に当たったときはゲートが告げた秒数に従い、
一時的な不調（5xx・通信断）は1分だけ空ける。**ライセンス未設定では待たせない**
（ゲートを呼んでもいないので待つ理由が無く、待たせるとキーが届いた直後に
取りに行けなくなる）。

### 10-3. 上限を決めるときの見方

`RATE_LIMITS` を触るときは、次の2つを**両方**満たす値にすること。
テスト（[notifier-gate.mjs](../tests/unit/notifier-gate.mjs)）が意味のまま縛っている。

- 利用者が［接続テスト］を10回押しても使い切らない（1回につき最大1呼び出し）
- 毎分の暴走（1時間60回）は止まる

### 10-4. 失敗の記録は、その相手が直ったときだけ消す

`LAST_GATE_ERROR` は「最後の失敗」を1つだけ持つ（[Gate.gs](../gas-notifier/Gate.gs)
`clearGateError_`）。以前は**どれか成功したら空にしていた**が、実機では
evaluate が1分ごとに成功し vapid だけが失敗し続けたため、記録が出たり消えたりして
原因が読めなかった。消すのは、その失敗を出した相手が成功したときに限る。

キャッシュで足りていて呼んでいない場合も消す。呼ばないことを理由に古い記録が
残ると、直っているのに画面には「失敗しています」と出たままになる。
