# Phase 0 技術検証計画書 v0.1

**対象プロダクト**: コンテンツ自動展開・投稿アプリ(要件定義書 v0.1 準拠)
**作成日**: 2026年8月7日
**目的**: MVP開発(Phase 1〜3)着手前に、外部依存の成立可否・コスト・制約を実機で確認し、Go/No-Go とフォールバック方針を確定する。

---

## 1. 検証のゴール

Phase 0 完了時点で、次の6つの問いに証拠付きで答えられる状態にする。

1. Threads へ API 経由で実投稿できるか。審査・権限・制限は何か。
2. X へ API 経由で実投稿できるか。1投稿あたりのコストはいくらか。
3. YouTube へ API 経由で動画をアップロードし「公開」状態にできるか(監査の壁を越えられるか)。
4. note は公式連携が可能か。不可の場合のフォールバック体験は成立するか。
5. TTS + FFmpeg で「見られる品質」のテンプレート動画を、許容時間・コスト内でレンダリングできるか。
6. OAuth トークン管理・ジョブキュー・冪等性の基盤構成は要件(14章)を満たせるか。

各トラックの結論は「Go / 条件付きGo(フォールバック採用) / No-Go」の3値で記録する。

## 2. 事前調査サマリー(2026年8月時点)

実装前に把握しておくべき前提。**すべて Phase 0 で公式ドキュメント・実機により再確認すること。**

| 媒体 | 現時点の把握 | 要再確認 |
| --- | --- | --- |
| Threads | 公式APIあり・無償。Meta for Developers でアプリ作成し App Review を通す。投稿系スコープは threads_basic / threads_content_publish。API経由の投稿は 24時間 250件 の上限。1投稿の文字数上限は500字(拡大済み)。 | 審査所要期間、開発モードで検証可能な範囲、コンテナ作成→公開の2段階仕様 |
| X | Free プランは廃止済み。2026年に従量課金(Pay-Per-Use)へ移行し、投稿作成は1件ごとの単価課金。旧 Basic/Pro はレガシー扱い。 | console.x.com 上の最新単価(特にURL付き投稿)、支出上限設定、OAuth 2.0 のスコープ |
| YouTube | Data API v3 の videos.insert でアップロード可能。**未監査のAPIプロジェクト(2020/7/28以降作成)からのアップロードは強制的に非公開になる**ため、公開自動化には監査(コンプライアンス審査)通過が必須。日次クォータは既定10,000ユニット。 | videos.insert の消費ユニット数と1日の実質アップロード可能本数、監査申請の要件と所要期間、OAuth 同意画面の検証要件 |
| note | **公式APIは提供されていない**(2026年時点)。内部APIを流用する非公式手段は存在するが、Cookie認証依存・規約/仕様変更リスクがあり製品には不採用とする。 | 公式連携・パートナーAPIの動向、下書きエディタへの遷移URL仕様 |

> **note の方針(先行確定)**: 要件定義書 FR-065 / 19章のとおり、note は「アプリ内下書き + 本文コピー + note下書きエディタへの遷移導線」を MVP の正式仕様とする。Phase 0 では非公式APIの検証は行わず、フォールバック体験の UX 検証に時間を充てる。

> ### 【限定解除・2026-08-08】非公式API（Draft Bridge）について
>
> **上の「製品には不採用」という判断は維持する。第2段（ポータル会員向け提供）での
> 不採用は変わらない。**
>
> そのうえで、次の範囲に限って使用を認める。
>
> > **発注者個人の利用であり、かつ既存の Note Draft Helper 経由である場合に限り、
> > Cookie + 内部API による下書き作成（Draft Bridge）を使用してよい。**
>
> **限定の理由**: 不採用の根拠は「規約リスク」と「仕様変更で壊れるリスク」だった。
> 前者は第三者へ提供することで拡大し、後者は利用者が増えるほど影響が広がる。
> **利用者が発注者1名であれば、どちらも発注者自身が引き受けられる範囲に収まる。**
>
> **第1段の一想は Draft Bridge を実装しない。** note 投稿は Helper へバトンを渡し、
> Helper の実証済み導線を再利用する（[roadmap.md](./roadmap.md) §2）。
> したがって Draft Bridge が存在するのは **Helper 側の1か所だけ**である。
>
> リスク管理の原則は v1.0-personal の設計原則として明文化する
> （原本は必ず Sheets／低頻度で使う／失敗時はコピー＆ペーストへフォールバック／
> 最悪ケースはアカウント停止と割り切る）。

## 3. 検証トラック

### T1: Threads API

**目的**: OAuth 連携〜テキスト投稿〜結果取得の一連を実アカウントで通す。

| # | 確認項目 | 合格基準 |
| --- | --- | --- |
| T1-1 | Meta アプリ作成、Threads ユースケース追加、開発モードでのテスト投稿 | 自アカウントへ投稿成功 |
| T1-2 | コンテナ作成 → 公開の2段階フローとエラーパターン | 状態遷移を PublishJob の状態(11章)へマッピングできる |
| T1-3 | App Review 申請(threads_basic / threads_content_publish) | 審査要件・所要日数を記録。通過まではアプリ内下書きで代替 |
| T1-4 | レート制限(threads_publishing_limit の取得含む) | 24h 250件上限を投稿キュー設計に反映 |
| T1-5 | 文字数・改行・URL の扱い | 500字上限とプレビュー表示仕様を確定 |

**リスク/フォールバック**: 審査が長期化した場合、MVP初期は「アプリ内下書き + コピー」で出荷可能とする(FR-065)。

### T2: X API

**目的**: 従量課金モデル下で、投稿1件あたりの実コストと運用方法を確定する。

| # | 確認項目 | 合格基準 |
| --- | --- | --- |
| T2-1 | console.x.com でのプロジェクト作成、従量課金の有効化、支出上限設定 | 上限到達時に課金でなく停止となることを確認 |
| T2-2 | OAuth 2.0 (PKCE) でのユーザー認証とトークンリフレッシュ | リフレッシュ失敗時の再認証導線を設計に反映 |
| T2-3 | テキスト投稿(URL付き/なし)の単価実測 | 1投稿あたりコストを記録し、ユーザー課金プラン設計(19章コスト)の入力にする |
| T2-4 | 投稿削除・エラー応答・レート制限ヘッダ | FAILED→再試行の実装方針を確定 |

**リスク/フォールバック**: 単価が想定より高い場合、X は「ユーザー自身のAPIキー持ち込み」または「コピー投稿」をオプション化する判断材料とする。

### T3: YouTube Data API

**目的**: 「台本→動画→公開」の最終区間である公開アップロードの成立条件を確定する。**Phase 0 で最も期間を要する可能性が高いトラック。初週に着手する。**

| # | 確認項目 | 合格基準 |
| --- | --- | --- |
| T3-1 | GCP プロジェクト作成、OAuth 同意画面(テスト)、youtube.upload スコープでの認証 | テストユーザーで認証成功 |
| T3-2 | videos.insert(Resumable Upload)でのテスト動画アップロード | 非公開動画としてアップロード成功。中断・再開の挙動確認 |
| T3-3 | クォータ実測 | videos.insert の消費ユニットを実測し、既定10,000ユニット/日での1日アップロード可能本数を算出 |
| T3-4 | **API プロジェクト監査(コンプライアンス審査)の申請** | 未監査だと公開設定でも非公開に強制される制約の解除。申請要件・所要期間を記録 |
| T3-5 | OAuth 同意画面の本番公開(検証)要件 | センシティブスコープ審査のプロセスと必要物(プライバシーポリシー等)を整理 |
| T3-6 | タイトル・概要・サムネイル設定のAPI反映 | FR-044 の生成物をそのまま反映できる |

**リスク/フォールバック**: 監査通過まで、MVPは「非公開アップロード + ユーザーが手動で公開」を正式フローとして許容する(承認モードと整合的)。

### T4: note フォールバック体験

**目的**: 公式API不在を前提に、「アプリ内下書き→note公開」の摩擦を最小化する。

| # | 確認項目 | 合格基準 |
| --- | --- | --- |
| T4-1 | 見出し・装飾を保った本文コピー(Markdown/リッチテキスト)の検証 | note エディタへ貼り付けた際の再現度が実用水準 |
| T4-2 | note 新規下書き画面への遷移URL・モバイル挙動 | ワンタップで貼り付け直前まで到達できる |
| T4-3 | 公開URLの手動登録フロー | PublishedPost へURLを記録し履歴管理(FR-060系)が成立 |

**リスク**: 非公式API採用の誘惑はあるが、規約・安定性リスクから製品では不採用。判断を検証レポートに明記し再燃を防ぐ。

### T5: TTS・動画レンダリング

**目的**: テンプレート型動画の品質・時間・コストの実数を得る。

| # | 確認項目 | 合格基準 |
| --- | --- | --- |
| T5-1 | 日本語TTS 2〜3サービスの比較(自然さ、読み誤り、SSML/読み調整、単価) | 主採用+予備を決定 |
| T5-2 | シーンJSON→FFmpeg合成(背景+テロップ+音声)のPoC | 5分動画をエラーなくレンダリング |
| T5-3 | 字幕とナレーションの同期方式(TTSのタイムスタンプ or 強制アライメント) | ずれが視聴上気にならない水準 |
| T5-4 | レンダリング時間・マシンスペック・1本あたりコスト実測 | 非同期ジョブのタイムアウト設計とコスト見積りに反映 |
| T5-5 | BGM・画像素材の権利条件確認 | rights_meta(10章 MediaAsset)に保持すべき項目を確定 |

### T6: 共通基盤

**目的**: 14章の非機能要件を満たす最小構成を確定する。

| # | 確認項目 | 合格基準 |
| --- | --- | --- |
| T6-1 | OAuthトークンの暗号化保管(Secret管理 or DB暗号化)方式の選定 | クライアントへトークン非露出の構成図を確定 |
| T6-2 | ジョブキュー(予約投稿・レンダリング)の候補比較と冪等性検証 | 同一ジョブ二重実行で二重投稿しないことをテストで確認 |
| T6-3 | 指数バックオフ再試行と最終失敗の通知経路 | FAILED理由がユーザーに表示される |

## 5. Go/No-Go 判断基準

- **Phase 1 着手条件**: 外部審査の結果を待たずに着手可(文章パイプラインは外部API非依存)。
- **Phase 2 着手条件**: Threads または X のいずれか1媒体で、開発モードでも実投稿が成功していること(AC-04 の目処)。
- **Phase 3 着手条件**: T5-2(レンダリングPoC)成功、かつ T3-2(非公開アップロード)成功。YouTube監査は Phase 3 と並走可(非公開アップロード+手動公開で受入条件AC-07を暫定充足)。
- **フォールバック確定条件**: 審査不通過・コスト超過・API仕様上の不成立が確認された媒体は、FR-065 のアプリ内下書き+コピー/遷移へ切り替え、要件定義書 v0.2 に反映する。
