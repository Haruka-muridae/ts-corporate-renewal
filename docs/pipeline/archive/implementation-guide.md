## 2. データ非保持アーキテクチャ(v0.4 の核)

### 2-1. 原則

1. **利用者のコンテンツ(着想・生成物・下書き)、SNSアクセストークン、公開履歴を、運営側のいかなる永続ストアにも保存しない**
2. サーバーは「認証確認」「秘密鍵を要する処理の**無状態中継**」「利用量の計数」のみを行う。中継時も本文・トークンをログ・エラーレポート・分析に書き出さない(ログには利用者ID・媒体・結果コードのみ)
3. 運営側が保持してよいデータは次の3種に限定: **利用量カウンタ**(利用者ID・媒体・回数・月)、**上限・許可リスト設定**、**匿名化された運用メトリクス**(成功率等)。保存先は既存スプレッドシート運用(Apps Script)か最小の Supabase テーブルかを Phase 0 T6 で比較選定
4. 要件定義書14章の監査性は「操作メタデータのみのサーバーログ + 利用者ローカルの操作履歴」で読み替える

### 2-2. データの置き場所

| データ | 置き場所 | 備考 |
| --- | --- | --- |
| テーマ・各媒体の生成物・下書き・派生関係(ContentVersion 相当) | **利用者ブラウザの IndexedDB** | 要件10章のスキーマをローカルスキーマとして実装。エクスポート/インポート(JSONファイル)を**Must**とする |
| SNSトークン | 利用者ブラウザ内のみ | サーバーはOAuthコード交換後にトークンを返却し、破棄する |
| 公開URL・投稿履歴 | 利用者ローカル | サーバーには結果コードの計数のみ |
| ~~生成動画・音声~~ | **§8 拡張フェーズへ移動(v0.5)** | 動画化は MVP 対象外 |

**明示すべきUX上の制約**: データはブラウザ単位の保存となるため、PC/スマホ間で自動同期されず、ブラウザデータ削除で消える。初回起動時にこの旨とエクスポート機能を案内する画面を必須とする。

### 2-3. 媒体別の接続方式

**MVP の対象は Threads / X / note の3媒体。**

| 媒体 | 方式 |
| --- | --- |
| Threads | 発注者名義の Meta アプリを共有。OAuthはサーバーでコード交換→トークンを利用者ブラウザへ返却(非保存)。投稿はブラウザ→無状態中継API→Threads API(直接CORS呼び出しの可否を Phase 0 T1 で検証し、可能なら中継も外す) |
| X | **利用者自身のAPIキー登録(BYOキー)方式を第一候補とする**。従量課金が投稿ごとに発生するため、発注者名義キーの共有は利用者数に比例した青天井の費用と負担者のねじれを生む。利用者のキー・トークンはブラウザ内保存、投稿は無状態中継(X APIはブラウザ直接呼び出し不可のため)。BYOキーの登録手順ガイドをアプリ内に用意する。**認証は公開クライアント + PKCE を第一候補として検証する(v0.5 決定。T2-2)** |
| note | 従来どおり整形コピー + note下書きエディタ遷移(公式API不在)。履歴はローカル保存 |
| LLM生成 | **Gemini(Google AI)。利用者自身のAPIキー(BYO)**。キーは利用者ブラウザ内のみに保存し、サーバーは保持しない。**ブラウザから Gemini API を直接呼ぶ(§3-2 で実証済み)。中継APIは実装しない。** 費用は利用者負担のため運営側の生成回数上限は設けない(v0.6) |
| ~~YouTube~~ | **§8 拡張フェーズへ移動(v0.5)。** 台本の生成(テキスト)は Phase 1 に残るが、アップロード連携は行わない |
| ~~TTS~~ | **§8 拡張フェーズへ移動(v0.5)** |

### 2-4. 予約投稿の仕様変更(重要)

サーバーがトークンを保持しない以上、**利用者が不在の時刻にサーバーが代理投稿する方式(要件 FR-063)は成立しない**。以下に読み替える:

- **標準: 予約リマインダー方式** — 利用者が予約日時を設定(ローカル保存)すると、指定時刻に通知(Web Push。許諾UIを実装)。利用者が開くとワンタップで投稿実行。AC-05 は「リマインダーが指定時刻に発火し、ワンタップ投稿の成功/失敗が記録できる」と読み替える
- タブが開いている間のみ有効な「このブラウザで自動実行」オプションは実装してよいが、確実性がない旨を明示する
- 真のサーバー予約投稿を将来提供する場合は「利用者が予約ごとに明示同意し、実行時刻までトークンを暗号化保管、実行後即削除」というオプトイン設計とし、**本MVPスコープ外**とする(発注者の将来判断事項)

> **v0.5 注記**: YouTube が MVP から外れても、この方式は Threads / X のリマインダーとして**引き続き必要**。Phase 0 T6-5(Web Push)は凍結せず継続する。

### 3-1. 認証の実装方式(確定: 案A — Authorization ヘッダ)

tsam-auth-session は localStorage 保存でありリクエストに自動では乗らないため、次の方式とする。

- **API保護**: クライアントは `/pipeline/api/*` の全呼び出しに `Authorization: Bearer <tsam-auth-session値>` を付与。ルートハンドラは既存の Apps Script 検証経路でセッションの妥当性と利用者IDを確認してから処理する。検証結果は短時間のメモリキャッシュのみ可(永続保存・ログ出力は不可)
- **画面ガード**: /portal と同様のクライアント側チェック+リダイレクトとする。データ非保持構成によりサーバーが利用者データをレンダリングする画面は存在しないため、サーバーコンポーネントでの入口ガードが無いことは許容する(案Aの弱点が実害にならない設計上の対)
- **OAuthコールバック**(SNSからのトップレベルGET。ヘッダを付与できない): 利用者セッションを要求しない設計とする。CSRF対策はクライアント発行の state と `path=/pipeline/` 限定・短命の非セッションCookieの突合で行い、ハンドラはコード交換後にトークンをクライアントへ引き渡して(URLフラグメント等。サーバー非保存)終了する。利用者との紐づけはクライアント側で行う(サーバーに保存する物が無いため、コールバック時点のサーバー側利用者特定は不要)
- **禁止事項**: 案B(public/auth/session.js への Cookie 書き込み追加)は本番認証系の変更にあたるため行わない。案C(独立Cookieセッション)は将来サーバー側ガードが必要になった場合の留保選択肢

> **v0.5 注記**: 機密クライアント／公開クライアント+PKCE の選択は、YouTube(Google)が対象外になったため **X のみの論点**になった。X は公開クライアント + PKCE を第一候補とする(§2-3)。PKCE が成立すれば `client_secret` をサーバーに置かずに済み、非保持の主張がさらに強くなる。

### 3-2. ブラウザ→Gemini 直接呼び出しは**社内で実証済み**(v0.6)

「CORS が成立するかを最優先で検証」という指示だが、**検証は既に終わっている。**
同じリポジトリの本番アプリが、まさにこの方式で稼働している。

| アプリ | 状態 | 根拠 |
| --- | --- | --- |
| `public/production-app/card-ocr/` | **本番稼働** | `gemini.js` が `x-goog-api-key` ヘッダ付きでブラウザから `generativelanguage.googleapis.com` を直接呼ぶ |
| `public/production-app/receipt-ocr/` | **本番稼働** | 同上。`ai-complete.js` が `responseSchema` を使用 |
| `public/apps/audio-transcriber/` | テスト環境 | 同上。CSP の `connect-src` に Gemini ホストを許可済み |

**`x-goog-api-key` はカスタムヘッダなのでプリフライトが飛ぶ。それでも通っている**
＝ Gemini API 側が CORS プリフライトに応答している、ということが本番で確認済み。

したがって **`/pipeline/api/llm/` 中継は実装しない。**

> **Phase 1 のサーバー処理はゼロになる。** 画面もデータもキーも生成も、すべて利用者の
> ブラウザ内で完結する。**非保持の主張は「記録しない」ではなく「そもそも通らない」**になり、
> これ以上ないほど強くなる。

#### 既存実装から引き継ぐべき知見(**再発見のコストを払わない**)

| 知見 | 出どころ |
| --- | --- |
| **`responseSchema` の `type` は大文字。** 小文字だと 400 で弾かれる(proto の列挙型のため) | `card-ocr/prompt.js` 冒頭。フェーズ0で SYS-999 の原因になった実績 |
| **APIキーは `x-goog-api-key` ヘッダに載せる。URLのクエリに置かない** | `card-ocr/gemini.js` 冒頭。履歴や拡張機能から拾える場所を増やさないため |
| **モデルの 503(混雑)は実際に起きる。** フォールバック先を持つ | `card-ocr/config.js`。主モデルを入れ替えて 6/6 成功した記録 |
| **`fetchImpl` を差し替え可能にしてテストで実APIを叩かない** | `card-ocr/gemini.js` / keystore-spec-v1.md §7 |
| **キーは localStorage に1件だけ。プロバイダーごとにキーを分けない**(消し忘れ防止) | `public/auth/keystore.js` |

> **コードは複製する。import しない。** [repository-structure.md](../repository-structure.md) §4-1 / §5-3
> のとおり、本番アプリ間で共通層を作らない。複製元のパスと複製日を冒頭コメントに書く。
> （`app/pipeline/` は Next.js のビルド対象で、`public/` 配下から import できないという
> 技術的な理由もある。）

### 3-3. カウンタの再評価(v0.6)

BYOキー方式により**費用が利用者負担になった**ため、原価防衛のための上限は不要になった。
ただし**カウンタ自体が不要になったわけではない。**

| 対象 | カウンタの要否 | 理由 |
| --- | --- | --- |
| LLM(Gemini) | **不要。撤廃** | 利用者のキー・利用者の課金。運営は費用も枠も負担しない |
| X | **不要** | 同上(BYOキー) |
| note | **不要** | API を使わない |
| **Threads** | **必要。残す** | **発注者名義の Meta アプリを全利用者で共有**しており、**24時間250件の上限がアプリ単位で効く**(T1-4)。1人が使い切ると**他の利用者が投稿できなくなる** |

**カウンタの対象は Threads だけになる。** T6-4(保存先の選定)は廃止せず、
**規模を下げて継続**する(必要な列が「利用者ID・月・Threads投稿回数」だけになる)。

> **これは原価防衛ではなく、利用者間の公平性の問題。** 費用の話が消えても
> 共有資源の枯渇は残る。**撤廃してはいけない唯一のカウンタ**である。

### 3-4. 乱用防止として残すもの(v0.6・再提案)

指示により再検討した結果、**残すべきは2つだけ**。

| 施策 | 残す/やめる | 理由 |
| --- | --- | --- |
| **Threads の利用者別・全体の日次上限** | **残す** | §3-3 のとおり共有資源の保護。**全体上限も要る**(利用者を分散しても総量は同じ) |
| **段階公開の許可リスト** | **残す** | 利用者数そのものを絞るのが最も確実。Meta の審査通過前は特に |
| LLM の月次生成回数上限 | **やめる** | 費用も枠も利用者負担。制限する根拠が無い |
| X の月次投稿数上限 | **やめる** | 同上。利用者自身が X の支出上限で制御する |
| サーバー側のレート制限 | **不要** | Phase 1 にサーバー処理が無い。Phase 2 で Threads 中継を作る時点で再検討 |

> **「利用者が自分のキーで自分の枠を使い切る」ことは乱用ではない。** 止める理由がない。
> 止めるべきは**他人の枠を奪う行為**だけで、それに当たるのは Threads のみ。

## 4. 実装順序(v0.5 で縮小)

**MVP = Phase 0(縮小) + Phase 1 + Phase 2。** 各フェーズ完了時に AC(§2-4 の読み替え込み)を検証し `docs/pipeline/acceptance/` に記録。

1. **Phase 0(縮小)**: 検証トラック **T1・T2・T4・T6** を実施。**T3(YouTube)と T5(TTS・レンダリング)は §8 送りにつき凍結**(削除はせず、再開できるよう凍結理由を記録する)。T6 のうち T6-2(レンダリングジョブの冪等性)も対象が消えるため凍結、**T6-5(Web Push)は Threads / X のリマインダーに必要なため継続**。審査申請物の準備は初日に完了し、発注者作業のタスクリストを提出
2. **Phase 1**: 文章パイプライン(FR-001〜044)を**完全ローカル動作**で実装。**v0.6 により、サーバー処理は1つも無い**(LLM は利用者のBYOキーでブラウザから Gemini を直接呼ぶ。§3-2)。IndexedDB スキーマ、エクスポート/インポート、データ保存場所の説明画面。**YouTube 台本の生成はテキスト成果物として残す**(FR-040〜044)。→ AC-01/02/03
3. **Phase 2**: OAuth 連携(トークン非保存)、即時投稿(中継/直接)、予約リマインダー + ワンタップ投稿、失敗時再試行(ローカルキュー)、note フォールバック、利用者別・全体の利用量上限制御。**対象媒体は Threads / X / note。** → AC-04/08、AC-05(読み替え版)
4. ~~**Phase 3**: 動画 MVP~~ → **§8 拡張フェーズへ移動(v0.5)**

### 4-1. 受入条件の MVP 対象範囲

| ID | 受入条件 | MVP |
| --- | --- | --- |
| AC-01 | 1つのテーマからThreads、X、note、YouTube台本を順番に生成できる | **対象**(台本はテキストまで) |
| AC-02 | 各段階でユーザーが編集した内容が次段の生成元として使用される | **対象** |
| AC-03 | 生成物は媒体ごとにアプリ内下書きとして保存され、再編集できる | **対象** |
| AC-04 | 少なくとも1つのSNSでOAuth連携した実投稿が成功する | **対象** |
| AC-05 | 予約投稿ジョブが指定時刻に実行され、成功／失敗状態を確認できる | **対象**(§2-4 の読み替え版) |
| AC-06 | noteからYouTube台本を生成し、シーン分割された動画をレンダリングできる | **対象外(v0.5)** |
| AC-07 | 生成動画をYouTubeへアップロードする一連のフローを実行できる | **対象外(v0.5)** |
| AC-08 | 外部APIエラー時にFAILEDとなり、ユーザーが再試行できる | **対象** |
| **AC-09** | **note記事からYouTube台本を生成でき、台本が複数のシーンに分割され、各シーンがナレーションと映像指示を持つ** | **対象(v0.5 で新設)** |

### AC-09 を新設した理由

AC-06 は「台本を生成し**、かつ**シーン分割された動画をレンダリングできる」という
複合条件だった。台本生成の部分は AC-01 がカバーするが、**シーン分割(FR-043・Must)を
確認する受入条件は AC-06 だけ**であり、AC-06 を対象外にすると FR-043 が
Phase 1 に残りながら受入条件を持たない状態になる。

**発注者判断により、FR-043 は Phase 1 に残し、受入条件を新設する。** 根拠:

> YouTube 台本を MVP に残した根拠は「利用者が手動で動画化する使い方が残る」ことであり、
> 手動制作者にとっての台本の価値は**シーン構造(ナレーションと映像指示の対)そのもの**にある。

したがって AC-09 は**シーン構造の有無**を見る。動画化しない以上、尺・映像の品質は問わない。

| AC-09 が見るもの | AC-09 が見ないもの |
| --- | --- |
| 台本が複数シーンに分割されていること | シーン数の妥当性・尺(FR-042 の目標尺) |
| 各シーンがナレーションを持つこと | ナレーションの読み上げ品質(TTS は §8) |
| 各シーンが映像指示を持つこと | 映像指示どおりに映像が作れるか(レンダリングは §8) |

> **AC-06 との関係**: AC-09 は AC-06 の前半を引き継いだものではない(前半は AC-01 が持つ)。
> **AC-06 のうち「シーン分割」だけを切り出して MVP へ残したもの**である。
> 拡張フェーズで AC-06 を復活させるときは、AC-09 と重複する部分を差し引くこと
> (詳細は [requirements-v0_2-changes.md](./requirements-v0_2-changes.md))。

漏洩面が広がるだけで得るものがない。拡張フェーズの着手時に登録する。
