# 1. 文書の目的

本書は、短い着想からSNS投稿、長文記事、YouTube動画までを生成・管理・投稿するアプリケーションの初期要件を定義する。開発チームがMVPのスコープ、主要画面、データ構造、外部連携、非機能要件、および将来拡張の方向性を共通認識として持てる状態を目的とする。

| **前提  **媒体固有のAPI仕様・審査・投稿権限・下書き保存可否は変更され得る。実装時は公式APIを優先し、非対応の場合は「アプリ内下書き」「コピー／遷移」「手動公開」をフォールバックとして採用する。 |
| --- |

# 2. 背景と解決したい課題

現在、1つの考えを複数媒体へ展開するには、媒体ごとの文章量・文体・構成に合わせた書き換え、下書き管理、投稿作業、動画化などが個別に発生する。本プロダクトは、それらを「同じテーマを媒体ごとに深めていく一連の制作フロー」として統合する。

媒体ごとに文章を書き直す手間が大きい。

短文・長文・動画が別々に管理され、同じテーマの派生コンテンツとして追跡しにくい。

投稿先ごとの認証、予約、失敗時の再投稿などの運用負荷がある。

noteからYouTubeへ移行する際、「読む文章」を「話す文章」に再構成する必要がある。

動画制作では台本、シーン分割、音声、字幕、素材、レンダリング、アップロードが分断されている。

# 3. プロダクトビジョン

| **着想** 1〜3行 | **Threads** 最短文 | **X** 補足 | **note** 長文化 | **台本** 話し言葉 | **動画** 自動生成 | **YouTube** 公開 |
| --- | --- | --- | --- | --- | --- | --- |

ユーザーは「今日考えたこと」「伝えたいテーマ」「元記事」などを1つ入力する。AIはその核を維持したまま、媒体ごとに最適な情報量と表現へ段階的に変換する。重要なのは、同一原稿を単純に転載するのではなく、Threadsでは最小単位の気づき、Xでは補足を含む短文、noteでは背景と考察、YouTubeでは視聴に適した話し言葉と映像へ育てることである。

# 4. 対象ユーザー

| **区分** | **想定ユーザー** | **主要ニーズ** |
| --- | --- | --- |
| 主対象 | 個人発信者・専門家・経営者・クリエイター | 少ない入力から複数媒体へ継続的に発信したい |
| 副対象 | 企業の広報・採用・マーケティング担当 | 1テーマを複数チャネルへ効率よく展開したい |
| 将来対象 | 制作代行・SNS運用支援者 | 複数アカウント・複数ブランドを承認フロー付きで管理したい |

# 5. 対象媒体と役割

| **順序** | **媒体** | **役割** | **初期の生成目安** | **公開方式** |
| --- | --- | --- | --- | --- |
| 1 | Threads | 最も短い。気づき・主張の核だけを提示 | 50〜150字を基準に調整 | API直投稿またはアプリ内下書き |
| 2 | X | Threadsの主張に理由・補足・具体性を追加 | 150〜300字を基準に調整 | API直投稿またはアプリ内下書き |
| 3 | note | 背景・経験・考察・読者への示唆まで長文化 | 1,500〜3,000字を基準に調整 | 下書き／手動公開を基本。公式連携可否を技術検証 |
| 4 | YouTube | noteの内容を話し言葉・視聴構成へ変換 | 5〜10分程度の本編を初期想定 | 動画生成後にAPIアップロードを想定 |

| **設計原則  **「Threadsが最短」という運用ルールを本プロダクトのデフォルトとして採用する。一般的な媒体平均ではなく、ユーザーの制作戦略を優先する。 |

# 8. 標準ユーザーフロー

ユーザーがテーマまたは短いメモを入力する。

AIがThreads案を生成する。ユーザーは採用・編集・再生成を行う。

採用したThreads案を起点にX案を生成する。

X案を起点にnote記事へ展開する。

note記事を起点にYouTube台本へ変換する。

台本をシーン分割し、音声・字幕・映像素材を生成して動画化する。

ユーザーが各媒体の内容と動画を確認する。

媒体ごとに「下書き保存」「今すぐ投稿」「予約投稿」を選択する。

投稿結果、公開URL、エラーをアプリ側で記録する。

# 11. 投稿ステータス定義

| **状態** | **意味** | **主な遷移** |
| --- | --- | --- |
| DRAFT | AI生成済み／編集中 | → READY |
| READY | 内容確認済み | → SCHEDULED / PUBLISHING |
| SCHEDULED | 予約待ち | → PUBLISHING |
| PUBLISHING | 外部APIへの投稿処理中 | → PUBLISHED / FAILED |
| PUBLISHED | 公開完了 | 終了 |
| FAILED | 投稿失敗 | → PUBLISHING（再試行）/ DRAFT |

# 14. 非機能要件

| **分類** | **要件** |
| --- | --- |
| セキュリティ | OAuthトークンは暗号化またはSecret管理基盤に保存し、クライアントへ直接露出させない。 |
| 可用性 | 投稿ジョブは冪等性を持ち、同一ジョブの重複実行で二重投稿しない。 |
| 信頼性 | 外部API失敗時は指数バックオフ等で再試行し、最終失敗理由をユーザーに表示する。 |
| 性能 | 文章生成は対話的待ち時間を意識し、動画生成は非同期ジョブとして扱う。 |
| 監査性 | 生成、編集、投稿、失敗、再試行の操作履歴を記録する。 |
| 権利管理 | 動画に使用する画像・音源・素材の出所や利用条件を保持できる設計とする。 |
| 可観測性 | SNS APIエラー率、投稿成功率、動画レンダリング失敗率等を監視できる。 |
| 拡張性 | 新しい媒体を追加できるよう、Platform Adapter方式で投稿処理を抽象化する。 |

# 15. AI生成ルール

Threads → X → note → YouTubeの順で、前段の採用版を次段の主要入力として扱う。

媒体間で中心主張を保持しつつ、文章量・構成・語り口のみを最適化する。

事実として入力されていない数字、固有名詞、具体エピソードを勝手に創作しない。

YouTube台本はnoteの朗読ではなく、視聴者に話しかける構造へ再編集する。

ユーザーが修正した表現を次段の生成に反映し、AI原案よりユーザー編集を優先する。

将来は投稿実績を基に個人ごとの表現傾向を学習するが、MVPでは明示的な設定値と履歴参照を中心とする。

# 16. 投稿自動化レベル

| **モード** | **動作** | **MVP** |
| --- | --- | --- |
| 承認モード | AI生成 → ユーザー確認 → 手動で投稿実行 | 必須 |
| 予約モード | AI生成 → ユーザー確認 → 指定時刻に自動投稿 | 必須 |
| 半自動モード | 事前設定した条件を満たす場合に予約キューへ自動投入 | 将来 |
| 完全自動モード | テーマ取得 → 生成 → 投稿まで人手を介さず実行 | 将来 |

| **初期方針  **MVPのデフォルトは承認モードとし、完全自動投稿は初期設定で無効にする。誤投稿、生成誤り、API事故のリスクを抑えながら価値検証を進める。 |

# 19. リスク・要検証事項

| **項目** | **リスク** | **対応方針** |
| --- | --- | --- |
| SNS API | 投稿権限・料金・レート制限・審査条件が媒体ごとに異なる | Phase 0で公式仕様を確認し、媒体別Adapterとフォールバックを設計 |
| note連携 | 公式の投稿／下書きAPIが利用できない可能性 | アプリ内下書き＋コピー／ブラウザ遷移を必須フォールバックとする |
| 動画品質 | 完全自動では単調な動画になりやすい | テンプレート型から開始し、シーン編集とプレビューを必須化 |
| 生成誤り | AIが事実を補完・誤生成する可能性 | ユーザー承認をMVPの標準とし、事実捏造禁止ルールを設定 |
| コスト | 長文生成・TTS・動画生成・ストレージで変動費が増える | 利用量メトリクスを計測し、プランごとの上限を将来設定 |
| 著作権 | BGM・画像・映像素材の利用条件が不明確になり得る | 権利情報をMediaAssetに保持し、許諾済み素材を優先 |

# 20. 初期KPI候補

| **KPI** | **定義** |

# 21. 現時点で確定しているプロダクト判断

コンテンツの基本順序は「Threads → X → note → YouTube」とする。

Threadsを最も短い文章として扱う。

XはThreadsより情報量を増やし、noteでさらに長文化する。

YouTubeはnoteの単純朗読ではなく、台本へ再構成してから動画化する。

YouTubeでは最終的に台本生成、動画生成、公開まで自動化する。

SNS側の下書きAPIに依存せず、アプリ内下書き／投稿キューを中核とする。

MVPは人間の確認を挟む承認・予約フローを基本とし、完全自動化は後段で解放する。
