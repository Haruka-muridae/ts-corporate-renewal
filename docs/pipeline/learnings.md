# 第1段の運用で得る学び

**作成**: 2026年8月8日
**目的**: 個人ツール（第1段）の実運用で得た事実を記録し、**第2段（ポータル会員向け提供）の
判断材料にする**（[roadmap.md](./roadmap.md) §3）

---

## この文書の使い方

- **記録するのは事実と実数。** 「良かった」ではなく「3案のうち2案がそのまま使えた」と書く
- **第2段の設計は既にある**（[archive/](./archive/)）。ここで確かめるのは
  **「作れるか」ではなく「会員に出せるか」**
- **書けなかった観点も記録する。** 「測っていない」と「測ったが差が無かった」は別物
- 個人の感想も価値があるが、**事実と分けて書く**（「所感」として明示）

> **1テーマ終えるごとに追記する。** まとめて後から書くと、うまくいかなかった回が
> 記憶から落ちる。**うまくいかなかった回のほうが判断材料になる。**

## 1. プロンプト品質

**問い**: 段階別プロンプトは、会員に渡せる水準で安定しているか。

| 記録する項目 | 書き方の例 |
| --- | --- |
| 段階ごとの**採用率** | Threads 3案中そのまま採用 / 手直しして採用 / 全案破棄 の回数 |
| **手直しの量** | ほぼそのまま / 一部書き換え / ほぼ書き直し の3段階で |
| **手直しの中身の傾向** | 「毎回、語尾を直している」「毎回、冒頭を削っている」— **傾向はプロンプトで直せる** |
| **FR-033 違反**（入力に無い数字・固有名詞・エピソードの創作） | **発生したら必ず記録。** 会員に出すうえで最も危険 |
| 段階間の**主張のぶれ** | Threads と note で言っていることが変わったか（要件15章） |
| **台本のシーン構造**（AC-09） | シーン数・ナレーションと映像指示が両方埋まった割合・再生成した回数 |
| プロンプトを**直した履歴** | いつ・どの段階を・なぜ直したか。**単一ソース（roadmap §1 要件1）を直した記録** |

> **「毎回同じ手直しをしている」はプロンプトのバグ。** 気づいたら定義側を直す。
> 手で直し続けると、第2段の会員が同じ手直しをすることになる。

## 2. 採用UX

**問い**: 段階採用のUXは、会員が迷わず使える形になっているか。

| 記録する項目 | |
| --- | --- |
| **どの段階で詰まるか** | 「note が長すぎて読む気にならない」「台本まで行かずに終わる」 |
| **複数案は3案でよいか** | 使っているのは何案目か。2案で足りるか、5案欲しいか（FR-013） |
| **再生成の回数** | 段階ごとに平均何回。**多い段階＝プロンプトが弱い段階** |
| **前段が未採用だと次段へ進めない**制約 | 邪魔になっていないか（[phase1-design](./archive/phase1-design.md) §2-3 の設計） |
| **派生の追跡を実際に使うか** | 「どの Threads 案から派生したか」を遡って見ることがあるか。**要件10章が「体験の中核」としているが、実際に使うかは未検証** |
| **途中でやめたテーマ** | 何本着手して何本公開まで行ったか（要件20章の「テーマ→公開到達率」） |

> **派生追跡は要件10章が「本プロダクトの中核データ」としている。**
> 第1段で一度も遡らなかったなら、**第2段でその前提を見直す材料になる。**

## 3. Threads の 24時間 250件上限

**問い**: 共有アプリの上限は、会員向けで現実的か。

| 記録する項目 | |
| --- | --- |
| **1日の実投稿数** | 発注者1人で何件使うか |
| 上限に**当たったか** | 当たった日付と状況 |
| `threads_publishing_limit` の**実測値** | 残数の見え方（旧 T1-4 の項目） |
| **開発モードのまま投稿できたか** | **第1段の最初の検証項目。** できなければ第1段の Threads 連携が成立しない |

> **1人あたりの実数が、第2段の会員数の上限を決める。**
> 例えば1人が1日5件使うなら、250 ÷ 5 = 50人が理論上の天井になる。
> **v0.6 §3-3 のカウンタ設計は、この実数が無いと初期値を決められない。**

## 4. note 内部APIの安定性（Draft Bridge）

**問い**: Cookie＋内部APIの方式は、どれだけ持つか。

> **前提**: 検証計画 §2 は「Cookie認証依存・規約/仕様変更リスクがあり**製品には不採用**」と
> 決着させている。第1段で採るのは**個人利用だからであり、第2段では整形コピー方式へ戻す**
> （[roadmap.md](./roadmap.md) §2）。**ここで記録するのは「第2段で採用すべきか」ではなく
> 「第1段でどれだけ手間がかかったか」。**

| 記録する項目 | |
| --- | --- |
| **壊れた回数と日付** | 仕様変更で動かなくなった回数 |
| **復旧にかかった時間** | 1回あたり何分・何時間 |
| **Cookie の有効期間** | 何日で入れ直しが要るか |
| **フォールバックの発動率** | コピー＆ペーストへ落ちた割合 |
| コピー方式との**実際の差** | Bridge が動いたときと、コピーしたとき。**体感で何分違うか** |

> **「差が小さい」なら、第2段でコピー方式に戻すことの損失も小さい。**
> 逆に「差が大きい」なら、第2段の体験が第1段より悪くなることを意味する。**そこは設計で埋める必要がある。**

## 4-2. X の課金（第1段は発注者の実費）

**問い**: 投稿1件あたりの実費はいくらで、会員向けに耐えるか。

> **第1段では発注者に直接課金される**（[setup-v1_0-personal.md](./setup-v1_0-personal.md) §E）。
> **第2段では、この実費が会員1人あたりの原価そのものになる。**
> 月額550円（A-13）に含められるかは、ここの実数で決まる。

| 記録する項目 | |
| --- | --- |
| **そもそも無料で投稿できたか** | **2026年時点で Free プラン廃止という情報がある。** 実際にコンソールで見た結果を書く（[setup-v1_0-personal.md](./setup-v1_0-personal.md) §E-0 の【記録】） |
| **投稿1件あたりの実費** | **単価と課金単位**（投稿ごとか、リクエストごとか）。**基本料の有無も** |
| **月次の実支出** | 月ごとに。**0円だった月も記録する** |
| 支出上限に**当たったか** | X 側（既定 10 USD）と、一想側の `x.monthlyPostLimit`（既定 60件/月）の**どちらで止まったか** |
| 投稿の**失敗率** | 失敗も課金対象かどうかを含めて |
| 初期値の**妥当性** | 60件/月・10 USD が過大か過小か。**変えたなら、いつ何に変えたか** |

> **料金体系そのものが変わる。** 「いくらだったか」だけでなく
> **「いつ時点の話か」を必ず書く。** 第2段の価格を決めるときに、
> 古い単価で計算すると原価を読み違える。

> **「投稿1件あたり」が分からないと、第2段の価格が決められない。**
> 会員が1人あたり月10件投稿するなら、原価は単価×10。**550円を超えるなら、
> BYOキー方式（会員自身の X アカウントで課金）へ戻す判断材料になる。**

## 5. 1テーマあたりの所要時間

**問い**: 実作業時間は短縮されているか（要件20章「制作時間削減」）。

| 記録する項目 | |
| --- | --- |
| **着想の入力から note 公開まで**の実時間 | 分単位。中断を含む実経過ではなく**実作業時間** |
| 段階ごとの内訳 | 生成待ち / 読む / 手直し / 投稿操作 |
| **一想を使う前**の所要時間 | 比較の基準。**思い出せるうちに書く** |
| 生成の**待ち時間** | Flow の実行にどれくらいかかるか |

> **比較の基準が無いと「短縮された」と言えない。** 使い始める前に、
> 直近で書いた記事の所要時間を思い出して書いておくこと。

## 6. 第1段の運用そのものについて

**問い**: この構成（Studio + GAS + Sheets）は、道具として使えているか。

| 記録する項目 | |
| --- | --- |
| **Studio 上の手作業**の量 | Flow を手で実行しているか、貼り直しの頻度 |
| **Sheets を直接触った回数** | 画面で足りず、シートを手で直した回数 → **画面の不足を示す** |
| **壊れた・詰まった箇所** | GAS の実行時間上限、Sheets の行数、権限まわり |
| **使わなかった機能** | 作ったが一度も使わなかったもの → **第2段で作らない候補** |

> **「使わなかった機能」は、第2段の設計を軽くする最良の材料。**
> 会員版で作らずに済むものが分かる。
