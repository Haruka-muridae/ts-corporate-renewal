# リポジトリ構成

制定: 2026年7月31日

このリポジトリには、**TSAM AI と無関係な別プロジェクトが同居する。**
独立したドメインのコストを当面かけないための判断であり、
プロジェクト同士に関係があるからではない。

同居する以上、事故はルールでしか防げない。以下を構成の宣言とする。

---

## 前提

- **Vercel** が配信している（2026-08-01 に GitHub Pages から移行。`CNAME` は削除済み）
- 静的ファイルの配信ルートは **`public/`**。リポジトリのルートではない
- **`main` へマージしたものは、そのまま本番として公開される。** 別途の公開操作は無い
- `main` 以外への push はプレビューへ出る（Vercel SSO で保護され、ログインしないと見えない）
- したがって `main` へ入れる判断は、置き場所がどこであっても公開の判断と同じ重さを持つ

## 2. `/labs/` のルール

### 2-1. TSAM AI の共通資産を参照・変更しない

`public/auth/` `public/css/` `public/js/` `public/assets/` `gas-auth/` `docs/specs/` などを、
`labs/` 配下から**読まないし、書き換えない。**

同居は経費の都合であって、設計の都合ではない。
いつでも別リポジトリ・別ドメインへ切り出せる状態を保つ。
共通資産へ1本でも線が伸びると、切り出すときにその線をすべて解く必要が出る。

必要なものは `labs/<プロジェクト名>/` の中に自前で持つ。
コピーが重複しても構わない。**重複より結合のほうが高くつく。**

### 2-2. `main` へのマージは TSAM AI と同じ型を通す

作業ブランチを切り、**`main` へマージする前に確認を取る。**
`main` は本番配信物であり、置き場所によって基準を変えない。

### 2-3. `main` へ入れたものは公開されうる

置き場所で決まる。

| 置き場所 | 公開 |
| --- | --- |
| `public/labs/<プロジェクト名>/` | **`https://tsam-ai.com/labs/<プロジェクト名>/` で誰でも見られる** |
| `labs/<プロジェクト名>/`（`public/` の外） | Web からは届かない。ただし**リポジトリは公開**されており、GitHub 上では誰でも読める |

Vercel は `public/` を静的ルートとして配る。Pages 時代と違い、
リポジトリのルート全体が配信されるわけではない。

**どちらに置いても「関係者しか読めない」状態にはならない。**
非公開のまま育てたいものは、`main` へマージせずブランチに留める。
秘密情報（鍵・トークン・個人情報）を置かないことは、本体と同じく必須。

Web で公開したいかどうかで置き場所を決め、決めた側を
`labs/<プロジェクト名>/README.md` に書き残すこと。

## 3. 指示書のスコープ

| 指示 | 既定のスコープ |
| --- | --- |
| TSAM AI の実装指示書 | **`labs/` はスコープ外。** 明示がない限り触れない |
| `labs/` 側の作業 | **TSAM AI 本体のファイルを変更しない** |

「リポジトリ全体を整理して」「全ファイルに適用して」といった指示を受けたときも、
上の境界は既定で維持する。またぐ必要があると判断したら、
**実行せずに確認を取る。**

## 4. 本番アプリ領域のルール

### 4-1. アプリ間で共通層を作らない

`public/production-app/` の下に `shared/` `common/` `lib/` の類を**置かない。**
アプリどうしで直接 import し合うこともしない。

同じロジックが要るときは**複製する。** 複製元のパスと複製日を、
複製先ファイルの冒頭コメントに書く。

**この判断は 2026年8月4日に、`receipt-ocr` と `card-ocr` の全ファイルを
突き合わせたうえで下したものである。** 理由は4つ。

1. **本当に同一になる範囲が狭い。** 8つの対応するモジュールを比べて、
   引数と定数の差だけで同一化できたのは4断片・約200行（全体の3%）だけだった。
   multipart 本文の組み立て、Drive クエリのエスケープ、一時ドキュメント OCR の
   中核、数式エスケープ。残りは「似ているが方針が違う」ものである
2. **方針の食い違いが13点あった。** エラーコード体系、同名フォルダが重複した
   ときにどちらを採るか、`valueInputOption`、テストの差し替え口、モデル名など。
   共通化するとは、これを13回決着させることを意味する
3. **共有層は作業ラインの同期点になる。** 2つのアプリは別々に開発が進む。
   片方の都合で共有層を変えると、もう片方のテストが壊れる
4. **3本目が来たときに困る。** 2本では、共通部分が「たまたま同じ」なのか
   「本質的に同じ」なのか判別できない。いま抽象を決めると、2本の都合だけで
   決めたものを3本目へ押し付けることになる

**`labs/` に対する 2-1 と同じ考え方である。「重複より結合のほうが高くつく」。**
ただし理由は違う。`labs/` は切り出せる状態を保つためだが、
ここは**別々に進む開発を互いに止めないため**である。

> **純粋関数だけなら共有してよい、とはしない。** 上の4断片は fetch も状態も
> 持たないが、それでも方針が乗っている。数式エスケープは対象文字が違い、
> multipart の boundary 生成は品質差そのもの、OCR の中核はリトライ回数と
> 孤児回収の有無が違う。「純粋だから安全」に見えて、書くには先に
> 13点の一部を決着させる必要がある。

### 4-2. 再検討する条件

**3本目の本番アプリが入るとき、この判断をやり直す。**

3つを見比べれば、共通部分が本質的なものかどうかを判別できる。
そのときに共通層を作るなら、3つすべてを見たうえで抽象を決める。

複製 → 集約は安全だが、共有層 → 離脱は難しい。だから**先に複製しておく**、
という順序をとっている。

### 4-3. 複製元の欠陥を持ち込まない

複製は「動いているコードをそのまま写す」ことではない。
**複製元に既知の不具合があれば、写す前に直す。**

`receipt-ocr` については、`card-ocr` のフェーズ0で直した内容が未反映の箇所が
7件ある（[receipt-ocr-findings-20260804.md](./receipt-ocr-findings-20260804.md)）。
`card-ocr` へ複製するときは、直したうえで写す。

逆方向（`receipt-ocr` にあって `card-ocr` に無い配慮）も同じで、
複製するときに取り込む。

## 迷ったときの判断

| 状況 | 判断 |
| --- | --- |
| `labs/` の作業で本体の共通資産を直したくなった | 直さない。`labs/` 側に持つ（2-1） |
| 本体の変更が `labs/` を壊しそう | 壊れてよい。`labs/` は本体に依存していないはず（2-1） |
| 本番アプリで、別の本番アプリと同じロジックが要る | 共通層を作らず複製する。複製元と複製日を書く（4-1） |
| 複製元に不具合がありそう | 写す前に直す。複製元は別ラインなので勝手に直さず、指摘として残す（4-3） |
| どちらの領域か判断できない | 実装せず、確認を取る |
