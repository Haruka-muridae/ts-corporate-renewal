| 項目 | 内容 |

| 実装 | `public/production-app/card-mail/` |

| 作成日 | 2026年8月18日 |

**このアプリは `card-ocr` が作った台帳を「読むだけ」である。**
作らない・書かないという制約が、実装のあちこちに現れている（§4-1）。

---

## §1 責務と境界

### 1-1. 引き受けること

- `card-ocr` の台帳「名刺管理」からメールアドレス列を読む
- 宛先を検証・重複排除し、**不正なものを一覧で見せる**
- 100件ずつに分けて、**利用者自身の Gmail** から BCC で送る
- 途中で失敗したとき、どこまで送れたかを返して再開できるようにする

### 1-2. 引き受けないこと

- **台帳の作成・書き込み**（§4-1）
- 当社サーバーを通した送信。送信は利用者の Gmail アカウントから行われる
- 配信停止の管理・購読者リストの管理
- 法令遵守そのもの。**表示義務の確認を促すのは画面だが、責任は利用者にある**

### 1-3. 隣との関係

| 相手 | 関係 |
| --- | --- |
| `card-ocr` | 台帳の**正本を持つ側**。**同じクライアントIDを意図的に共用**する（`drive.file` の可視範囲がクライアントIDごとに分かれるため、共用しないと台帳が読めない） |
| KeyStore | 使わない（Gemini を呼ばない） |

## §4 主要フロー

### 4-1. 台帳の解決（`ledger.js`）— 「作らない」の実装

`card-ocr` の `drive-storage.js` の3段階から、**「作成」を抜いた形**になっている。

```
段階1 … キャッシュのIDを検証する（404/403 系ならキャッシュを捨てて段階2へ）
段階2 … 名前・親・種別・未削除で検索する
（段階3の「作成」は無い。見つからなければ LEDGER_NOT_FOUND）
```

**なぜ作らないのか。** 保存構造の正本は `card-ocr` が持つ。こちらが「無ければ作る」を
すると、**空の台帳がもう1つでき、`card-ocr` がどちらを正本と見るかが運任せになる**
（同名検索は古いほうを採るため、先に作った側が勝つ）。
台帳が無い＝まだ名刺を登録していない、なので案内して終わる。

### 4-2. メール列の読み取り

**列は見出し行から探す**（`findEmailColumnIndex()`）。
`card-ocr` の列構成は版によって増える（右端に追加される決まり）ため、
**「何列目」を決め打ちすると、古い版・新しい版のどちらかで別の列を読む。**

`columnLetter()` / `quoteTabTitle()` が A1 記法を組み立てる。

### 4-3. 宛先の整理（`recipients.js`）

- `isValidEmail()` … **RFC 5322 を完全には検査しない。**
  quoted-string まで許すとヘッダーインジェクションの検査が複雑になるため、
  名刺に載る実在のアドレスで使われる形だけを通す
- `normalizeRecipients()` … 正規化と重複排除
- `chunkRecipients()` … `BCC_BATCH_SIZE`（100）ごとに分割

**不正な宛先を黙って除いて送らない。** 台帳のメール列には OCR の読み取りミスが残る。
黙って除くと**送られなかった相手がいることに利用者が気づけない。**
一覧で見せたうえで「残りに送る」を利用者が選ぶ。

### 4-4. メッセージの組み立て（`mail.js`）

- **外部ライブラリを使わない。** `TextEncoder` と `btoa` だけで組み立てる
  （Node 22 にも両方あるため、テストがそのまま動く）
- **宛先はすべて BCC。To を付けない。**
  受信者に他の宛先を見せないためと、To を付けないことで
  「1通100宛先」という無償 Gmail の上限に BCC 100件がちょうど収まるため
- **From も付けない。** Gmail API が送信アカウント本人のアドレスを自動で入れる。
  こちらで書くと、本人のエイリアス設定と食い違ったときに差し戻される
- **ヘッダーインジェクションを送信前に止める。** 値に改行・空白があれば送らない
- 件名は `encodeHeaderWord()` で MIME エンコードする

### 4-5. 送信と再開（`sendAllBatches()`）

```
for chunk of chunks:
    進捗を通知（例外は握りつぶす）
    sendBatch()
      失敗 → Error('send_failed_midway') に sentCount / batchesDone を付けて投げる
    成功 → カウンタを進める
```

**進捗表示の失敗を送信計画に巻き込ませない。** `onProgress` の例外を握りつぶさないと、
表示側の不具合で「どこまで送れたか」の情報が付かない例外が飛び、
**再送時に全件二重送信**につながる。

### 4-6. 法令表示の確認

画面（`index.html`）に、広告・宣伝を含むメールでは特定電子メール法により
**送信者の氏名・名称と受信拒否の連絡先の表示が義務付けられている**旨を出し、
確認のチェックを求める。**判断と責任は利用者にある。**

## §5 外部インターフェース

| 系統 | エンドポイント | スコープ |
| --- | --- | --- |
| Drive | `DRIVE_FILES_ENDPOINT` | `drive.file` |
| Sheets | `SHEETS_ENDPOINT` | 同上 |
| Gmail | `GMAIL_SEND_ENDPOINT`（`users/me/messages/send`） | `gmail.send` |

**2つのスコープを両方とも検証する。** 同意画面で利用者が片方のチェックを外しても
トークンは発行されるため、検証しないと**読み込みは成功するのに送信で 403 になる。**
一度スコープ不足を見たら、次は同意画面を強制して付け直させる。

## §6 エラー設計

| 型 | 範囲 |
| --- | --- |
| `LedgerError` / `LedgerErrorCode`（`LEDGER_NOT_FOUND` ほか） | 台帳の解決・読み取り |
| `DriveError` / `DriveErrorCode` | Drive・Sheets・Gmail の HTTP |
| `send_failed_midway`（プレーンな `Error` ＋ `sentCount` / `batchesDone`） | 送信の中断 |

送信の中断だけ専用クラスを持たないのは、**再開に必要なのは位置情報だけ**だからである。

## §7 移植（他プロダクトへの組み込み）

### 7-1. 移植単位

| 単位 | ファイル | 依存 | 単独で持ち出せるか |
| --- | --- | --- | --- |
| **BCC 一斉送信** | `mail.js` ＋ `recipients.js` | `config.js` の4定数 | **可。外部ライブラリ無しの RFC 5322 組み立てとヘッダーインジェクション対策を含む** |
| 途中再開つきバッチ送信 | `mail.js` の `sendAllBatches()` | 上記 | 可（送信関数を差し替えれば他の一括処理にも使える） |
| 台帳の「読むだけ」解決 | `ledger.js` | `drive-api.js` | 可（正本を別アプリが持つ構成でそのまま効く） |
| 認可（2スコープ検証） | `drive-auth.js` ＋ `gis-loader.js` | `config.js` | 可 |

### 7-2. 置換点

1. **`GOOGLE_CLIENT_ID`。** **`card-ocr` と共用している事実がこのアプリの前提**である。
   移植先で別々にするなら、台帳を読む方法から作り直す
2. `ROOT_FOLDER_NAME` / `APP_FOLDER_NAME` / `SPREADSHEET_NAME` / `DATA_TAB_NAME` /
   `EMAIL_COLUMN_HEADER`
3. `BCC_BATCH_SIZE`（100）。**Gmail の上限に合わせた値**なので、
   別のメール基盤へ移すなら再検討する
4. `MAX_SUBJECT_LENGTH`（250）／`MAX_BODY_LENGTH`（100000）
5. `STORAGE_KEYS`
6. 法令表示の文面（`index.html`）。**移植先の国・用途で要件が変わる**

### 7-3. 前提

- 利用者の Google アカウントが Gmail を使えること
- **`gmail.send` スコープが Google Cloud 側で有効化され、審査を通っていること**
  （上位文書 §6）
- 台帳が既に存在すること（このアプリは作らない）

### 7-4. 持ち出してはいけないもの

- **不正な宛先を黙って除く改変**（§4-3 の理由）
- **`onProgress` の例外を素通しする改変**（§4-5。二重送信につながる）
- **To を付ける改変**（受信者に全宛先が見える）
- 「無ければ作る」を足した `ledger.js`（§4-1）

## §10 既知の制約・未解決

1. **クライアントID の共用が機能の前提。** 分けると台帳が見えなくなる（§1-3）
2. **送信の成否は Gmail の応答までしか分からない。** 実際に届いたか、
   迷惑メールに入ったかは観測できない
3. **配信停止の管理を持たない。** 受信拒否の連絡先は本文に利用者が書く（§4-6）
4. **`BCC_BATCH_SIZE` は無償 Gmail 前提。** Workspace では上限が異なる
5. **台帳の重複行はそのまま宛先の重複になる**（正規化で吸収するが、
   表記が違えば別アドレスとして残る）

## §11 設計判断の記録

| 判断 | 採らなかった案 | 理由 |
| --- | --- | --- |
| 台帳を作らない | 無ければ作る（`card-ocr` と同じ形） | 空の台帳が2つでき、正本が運任せになる |
| 列を見出しで探す | 列位置を決め打ち | `card-ocr` の列は版で増える |
| 不正な宛先を見せる | 黙って除く／全体を中止する | 送られなかった相手に気づけない／1件の誤りで全部止まる |
| RFC 5322 を完全検査しない | 厳密なパーサを持つ | インジェクション検査が複雑になる。実在の形だけ通せば足りる |
| 外部ライブラリを使わない | メール組み立てライブラリ | 依存追加には事前確認が要る（[../../AGENTS.md](../../AGENTS.md)）。標準 API で足りる |
| To を付けない | To に自分を入れる | 上限100件に収まらなくなる。エイリアス設定と食い違う |
| 進捗の例外を握りつぶす | そのまま投げる | 位置情報が失われ、再送で全件二重送信になる |
| 再開情報を例外に付ける | 戻り値で返す | 失敗はスローで扱う設計を保ちつつ、位置だけは必ず渡せる |
