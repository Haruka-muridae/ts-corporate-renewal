**11本すべての本番アプリがここに乗っている。**
移植するとき、各アプリの設計書 §7 が「まず外す」と書いているのがこの層である。
本書はその**外し方**（§5）まで含めて記述する。

**この層は複製の対象ではない。** アプリ間で共通層を作らない方針
（[../repository-structure.md](../repository-structure.md) §4-1）は
`public/production-app/` の下の話であり、`public/auth/` は
**本番認証系という1つの系の内部**として共有されている。

## §2 `session.js` — 何が「ログイン済み」の根拠か

**根拠はサーバー（`sessions` シート）にある行だけである。**

ブラウザが持つのは推測困難なランダム文字列だけで、
有効期限も利用者IDもロールも、この文字列からは読み取れない。
`localStorage` を書き換えても、サーバーに存在しないトークンは検証で必ず落ちる。

したがってこのモジュールは次を守る。

- **ローカルの値だけで「ログイン済み」と判断しない**
- **保護対象の内容は、サーバー確認が終わるまで描画しない**
- **ロールは毎回サーバーから受け取ったものを使う**

### 2-1. `guardPage()` の契約

```js
const user = await guardPage();
if (!user) return;   // すでにログイン画面へ遷移している
render(user);        // ここで初めて内容を描画する
```

**戻り値が利用者オブジェクトになるまで、保護対象の内容を描画しない。**
11本のアプリすべてがこの形を守っている。

### 2-2. 失敗時の分岐（設計上いちばん細かい部分）

| 状況 | トークン | 画面 |
| --- | --- | --- |
| トークンが無い | — | ログインへ |
| サーバーが利用者を返さない | **捨てる** | ログインへ |
| 期限切れ・失効・改ざん（`ApiError` かつ `code !== 'NETWORK'`） | **捨てる** | ログインへ |
| 通信エラー | **残す**（オフラインで消してしまわない） | ログインへ |

**「オフラインなら通す」という妥協はしない。** 確認できていない状態を
「ログイン済み」と扱わないためである。

トークンを捨てるのは `clearSessionTokenIfUnchanged()`、つまり
**「いま検証した当のトークン」がまだ入っているときだけ。**
待っているあいだに別タブでログインし直された場合に、
その新しいトークンを巻き添えにしないため。

### 2-3. `next` の許可リスト

ログイン後に元の画面へ戻す仕組みは、**2つの許可リスト**で守られている。

| 場所 | 役割 |
| --- | --- |
| `config.js` の `SCREENS` | 画面名 → 相対パス |
| `session.js` の `ALLOWED_NEXT` | **`next` に使ってよい画面名** |

**`SCREENS` に書いただけでは `next` には使えない。**
アプリを足すときは両方へ足す。

引き継ぐパラメータも `safeNextParams()` の許可リストを通る。
元 URL をそのまま引き継ぐわけではない（`voice-recorder` の `?eventId=` が唯一の実例）。

### 2-4. 相対パスの解決

各画面が読み込み時に `setScreenDepth(n)` を1度だけ呼び、
`rootPath()` が `'../'.repeat(n)` を返す。
`/login/` は 1、`/production-app/<app>/` は 2。

**`basePath` を使わない配信構成**（[../../CLAUDE.md](../../CLAUDE.md)）と対になっている。

## §3 `api.js` — Apps Script との通信

### 3-1. POST を `text/plain` で送る

`Content-Type: application/json` にすると、ブラウザが事前に OPTIONS
（プリフライト）を送る。**Apps Script の Web アプリは OPTIONS に応答しない**ため、
本体のリクエストが届かない。

`text/plain` は「単純リクエスト」に該当し、プリフライトが発生しない。
本文は JSON 文字列のまま送り、サーバー側で `JSON.parse` する。

**移植時に最も引っかかる箇所である。** Apps Script 以外のバックエンドへ移すなら、
この回避は不要になる（むしろ `application/json` に戻すべき）。

### 3-2. エラーは分類だけ

`ApiError` と `ApiErrorCode` を返し、**文言はここで作らない。**
画面ごとに出し方が違うためである。

`NETWORK` かどうかが `session.js` の分岐（§2-2）に効いている。

## §4 `keystore.js` — APIキーの保管

**当社サーバーへ送らない。預からない。** 保管場所はその端末の `localStorage` だけ。

| 項目 | 値 |
| --- | --- |
| キー | `tsam-api-keys`（`KEYSTORE_STORAGE_KEY`） |
| プロバイダー | `PROVIDERS.gemini`（現在1つ） |
| API | `KeyStore.get / set / remove / has` の**4つだけ** |

### 4-1. 入口を1つに閉じる

**このファイルの外に `localStorage` を直接触る箇所を作らない。**
触る場所が増えるほど「どこかで GAS へ送っていないか」を確かめる手間が増える。
入口をここ1つに閉じておけば、**「KeyStore の外にキーは出ない」を読むだけで確かめられる。**

キーを `console` へ出す・ログへ残す・URL へ載せるコードも書かない。

### 4-2. 空文字で消させない

`set()` は空文字を受け付けない。削除は `remove()` を使う。
「空文字で上書き＝削除」を許すと、**入力欄の初期化ミスで気づかないうちにキーが消える。**

### 4-3. 使えない環境

プライベートモード等で `localStorage` が使えなくても**画面を壊さない**
（`isKeyStoreAvailable()` で判定し、アプリ側が案内を出す）。

## §5 移植（この層をどう外すか）

**各アプリの設計書 §7 が「まず外す」と書いているのがこの層である。**
移植先には当社の認証系が無いので、次の3つを差し替える。

### 5-1. `guardPage()`

| 移植先の状況 | 置き換え |
| --- | --- |
| 認証が要らない | `async () => ({})` を返すスタブにする。**戻り値が真であることだけが契約**（§2-1） |
| 別の認証基盤がある | その基盤の「現在の利用者を返す」関数へ差し替える。**確認できないときは偽を返し、画面を描画させない**という性質を保つ |
| セッションを自前で持つ | `session.js` ごと持ち出す。ただし `api.js` の通信先（§3-1）を作り直す |

**「オフラインなら通す」に緩めないこと**（§2-2）。

### 5-2. `KeyStore`

| 移植先の状況 | 置き換え |
| --- | --- |
| 利用者が自分のキーを入れる（BYOK） | `keystore.js` をそのまま持ち出す。**`KEYSTORE_STORAGE_KEY` は変える** |
| 自社のキーを使う | **キーをクライアントへ置けない。** サーバー側の中継を作り、各アプリの `gemini.js` が `fetchImpl` で中継先を叩く形にする |

各アプリは `KeyStore.get(PROVIDERS.gemini)` を**都度呼んで引数として渡す**だけなので、
供給源の差し替えは1行で済む。**キーをモジュール変数に保持しない設計**が効いている。

### 5-3. `setScreenDepth()` / `screenPath()`

移植先の URL 構成に合わせる。ルーティングを持つフレームワーク上なら、
**そのルータへ委ねてこの層を落とす**のが素直である。

### 5-4. `ui.js` / `password-form.js`

認証画面そのものの部品なので、**アプリだけを移植するなら不要。**

## §7 設定値と環境依存

`config.js` の `AUTH_CONFIG`。**`apiUrl`（Apps Script の `/exec` URL）は秘密ではない**
（静的サイトのフロントから呼ぶ公開エンドポイント）。

**絶対に入れてはならないもの**が明記されている。

- Stripe シークレットキー / Webhook シークレット
- セッション署名用シークレット / トークン用シークレット
- **Stripe Price ID**（フロントには持たせない）

## §8 既知の制約・未解決

1. **クライアント側ガードは主たる防御ではない。** 静的配信のため HTML と JS の取得は
   防げない（[../../SECURITY_NOTES.md](../../SECURITY_NOTES.md)）。
   守っているのはサーバー側の検証と、各アプリでは OAuth である
2. **`SCREENS` と `ALLOWED_NEXT` の二重管理**（§2-3）。片方だけ足すと黙って効かない
3. **`text/plain` での POST は Apps Script の制約への回避**（§3-1）。
   バックエンドを変えるなら不要になる
4. `gas-auth/*.gs` は**エディタで保存しただけでは公開中の Web アプリに反映されない**
   （デプロイの更新が要る。[../../CLAUDE.md](../../CLAUDE.md)）

## §9 設計判断の記録

| 判断 | 採らなかった案 | 理由 |
| --- | --- | --- |
| 検証をサーバーに置く | JWT を渡して自己検証させる | 失効を即座に効かせられる。ロールを毎回サーバーから取れる |
| 通信できないときも入れない | オフラインなら通す | 確認できていない状態を「ログイン済み」と扱わない |
| 通信エラーではトークンを残す | いつでも捨てる | オフラインで手元のトークンを失わせない |
| 検証したトークンと同じときだけ捨てる | 無条件に捨てる | 別タブの新しいログインを巻き添えにしない |
| `next` を許可リストにする | 元 URL をそのまま戻す | オープンリダイレクトを作らない |
| `text/plain` で POST | `application/json` | Apps Script が OPTIONS に応答しない |
| エラー文言を `api.js` で作らない | 共通の文言を持つ | 画面ごとに出し方が違う |
| KeyStore の入口を1つにする | 各画面が `localStorage` を触る | 「キーが外へ出ない」を読むだけで確かめられる |
| 空文字を受け付けない | 空で上書き＝削除 | 初期化ミスでキーが消える |
