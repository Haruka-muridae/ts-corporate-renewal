## §1 責務と境界

### 1-1. 引き受けること

- 領収書の画像を受け取り、OCR で文字列を得る
- **2つの独立した方法**（ルール抽出と Gemini 補完）で項目を読み、突き合わせる
- 妥当性を検証し、信頼度を**コード側で**判定する
- 保存前に人が確認する画面を出す
- 利用者のドライブへ保存構造を作り、原本画像と台帳1行を保存する

### 1-2. 引き受けないこと

- **当社サーバーでの処理・保管**（v2.0 の設計原則）
- 会計ソフトへの連携・電子帳簿保存法への適合宣言
- 自動確定（**保存前確認を飛ばす経路を作らない**。§4-5）

### 1-3. 隣との関係

| 相手 | 関係 |
| --- | --- |
| `card-ocr` | 複製先。手順・列の組み立て方・ハッシュ・無害化の系譜がここから伸びている |
| `voice-recorder` | **同じ OAuth クライアントID**を使う |
| KeyStore | Gemini キーの取得元 |

### 2-1. `gateway.js` の位置づけ

`provisioning.js` は**判断だけ**を持ち、Drive / Sheets の呼び出しは
`gateway` という形の object 越しに行う。テストは同じ形の偽物を渡す。

**§9.3（壊れた状態への対応）の6行と §9.4 は「どう判断するか」の仕様であって
「どう通信するか」の仕様ではない。** 切り離しておけば、壊れた状態のテストを
実通信なしで全行ぶん書ける。

**`gateway.js` に判断を書かない。** 分岐が要るなら `provisioning.js` 側へ置く。

## §3 状態とデータ構造

### 3-1. 保存構造

利用者のドライブに `DRIVE_NAMES` の構造を作る。原本画像は
**`YYYY/MM` の月別フォルダ**へ入る（`datetime.js` が Asia/Tokyo で切る）。

### 3-2. `localStorage`

**`store.js` だけが直接触ってよい。** キーは `tsam-receipt-ocr-locations`。

- 入れてよいのは Drive のファイルID（秘密情報ではない）だけ
- **Gemini APIキーは KeyStore、OAuth トークンはメモリのみ**
- ここは**正本ではなくキャッシュ**であり、実在しなければ解決し直す

### 3-3. ステータス（3軸）

v1.3 は4軸だったが、v2.0 では `processingStatus` を持たない。

サーバーが無く、処理はすべてブラウザ内で完結してから1行が書かれる。
**書かれた行は必ず「処理済み」**であり、`PROCESSING` の行が残ることがない。
持っても常に同じ値になる列を増やすだけなので、列ごと落とした。

## §4 主要フロー

### 4-1. OCR（`ocr.js` が差し替え口）

`config.js` の `OCR_ENGINE` **1か所**で案A／案Cを切り替える。
どちらのエンジンも同じ形（`recognize` / `requiresApiKey`）を持つ。

| 案 | 実装 | 特徴 |
| --- | --- | --- |
| **A（現行 `'drive'`）** | `ocr-drive.js` | 画像を Google ドキュメントへ変換する過程で OCR が走る。**追加コスト無し・`drive.file` だけで足りる。** 代償はレイアウトを失った一続きのテキスト（座標が無い） |
| C | `ocr-gemini.js` | Gemini へ画像を直接投入。**キーが必須**になり、未設定の利用者は使えない |

比較のたびに呼び出し側を書き換えるのでは条件を揃えた比較にならない、という理由で
この差し替え口が作られている。

**エンジンが返すのは「読み取った文字列」まで。** 項目への振り分けはルール抽出の仕事。

### 4-2. ルール抽出（`extract.js`）

プレーンテキスト化された OCR 結果では**行順序・左右の対応が崩れる。**
「近くの金額」という判定には限界がある。したがって、ここが返すのは**候補**であって確定ではない。

金額は `amount.js` で正規化する。**変換に失敗したら `null`。0 にしない。**
0 を返すと「0円の領収書」として通り、「合計金額が0円より大きい」検証もすり抜ける。
**読めなかったことは、読めなかったまま上へ伝える。**

### 4-3. Gemini 補完（`completion-policy.js` → `ai-complete.js`）

要否の条件は v1.3 §11 のまま。**判定を実行する場所がサーバーからブラウザへ移っただけ。**

**OCR が短いときは補完せず「要確認」にする。**
OCR が情報を失っている場合、テキストだけを受け取る Gemini は誤補完（推測）しかできない。

実行時の制約が2つある。

1. **独立抽出。** ルール抽出が出した候補を Gemini へ見せない。
   見せると、ルール側の誤読をそのまま追認する答えが返り、
   **「2つの方法で読んで突き合わせる」という仕掛けが意味を失う。**
   `buildPrompt()` は OCR 原文しか受け取らない。**候補を引数に足さないこと**
2. **`confidence` を使わず `evidence` を必須にする**（§4-4）

### 4-4. 検証と信頼度

- `validate.js` … **ルール由来でも Gemini 由来でも必ず通す。**
  不合格なら、ルールで値が取れていても確定しない（安全側に倒す）
- `confidence.js` … **コード側で算出する。Gemini の自己申告値は使わない。**
  LLM の自己申告確率は校正されておらず、自動確定の根拠にできない

### 4-5. 保存前確認（`review.js`）

**ここを飛ばして保存できる経路を作らない。**
上位文書 §15.1 が「誤った値を信頼度が高いとして提示した件数0件」を求めており、
**機械が確信していても、人が見る機会は残す。**

`review.js` は画面に出す「形」を作るだけで DOM を触らない。
描画は `app.js` が `textContent` で行う（**`innerHTML` を使わない**）。

### 4-6. 保存（`provisioning.js` ＋ `record.js` ＋ `sheets.js`）

保存先の解決・作成・健全性確認は `provisioning.js` の判断による。

**推測して書き込まない。** 列がずれているシートに対し、
「たぶんこの列だろう」と判断して書くことはしない（§9.3 の「列の改変」行）。

Sheets の `valueInputOption` は **`RAW`**。数式が評価されないため、
アポストロフィの付加と合わせて**防御が2枚**になっている
（`card-ocr` は `USER_ENTERED` で1枚。[component-catalog.md](./component-catalog.md) §3-4）。

## §7 移植（他プロダクトへの組み込み）

### 7-1. 移植単位

| 単位 | ファイル | 依存 | 単独で持ち出せるか |
| --- | --- | --- | --- |
| **判断と通信の分離パターン** | `provisioning.js` ＋ `gateway.js` | なし | **可。これは実装というより設計の型で、他アプリへ写す価値が最も高い** |
| ルール抽出 | `extract.js` ＋ `amount.js` ＋ `datetime.js` | なし（純粋関数） | 可（**日本の領収書に特化**している） |
| 検証・信頼度 | `validate.js` ＋ `confidence.js` | 抽出の出力形 | 可 |
| 独立2経路の突き合わせ | `completion-policy.js` ＋ `ai-complete.js` | Gemini | **可。LLM とルールを併用する設計の雛形になる** |
| OCR エンジンの差し替え口 | `ocr.js` ＋ `ocr-drive.js` ＋ `ocr-gemini.js` | 認可 | 可 |
| 重複判定 | `duplicate.js` | なし | 可 |
| 保存前確認の形 | `review.js` | `schema.js` | 可 |

### 7-2. 置換点

1. `config.js`（`OAUTH.clientId`、`OCR_ENGINE`、`DRIVE_NAMES`、`GEMINI`、
   `IMAGE_MAX_EDGE_PX`、`ACCEPTED_IMAGE_TYPES`、`TIME_ZONE`）
2. `schema.js` の列と `status.js` の軸
3. `extract.js` の正規表現一式（**日本の商習慣に強く依存する**）
4. `store.js` のキー
5. **`RAW` と無害化の組。** `card-ocr` 側の `USER_ENTERED` と混ぜない
6. `public/auth/` への依存、CSP、DOM id

### 7-3. 前提

- セキュアコンテキスト（`crypto.subtle`）
- Drive・Sheets の API 有効化と承認済みオリジン
- 案C を選ぶなら利用者の Gemini キーが必須

### 7-4. 持ち出してはいけないもの

- **保存前確認を飛ばす経路**（§4-5）
- **ルール候補を Gemini のプロンプトへ入れた版**（§4-3。突き合わせが無意味になる）
- **Gemini の `confidence` を信頼度として使う版**（§4-4）
- 金額の変換失敗を 0 にする版（§4-2）
- **既知の未反映7件を直さずに写すこと**（[../receipt-ocr-findings-20260804.md](../receipt-ocr-findings-20260804.md)。
  [../repository-structure.md](../repository-structure.md) §4-3）

## §10 既知の制約・未解決

1. **`card-ocr` のフェーズ0で直した内容が未反映の箇所が7件ある**
   （[../receipt-ocr-findings-20260804.md](../receipt-ocr-findings-20260804.md)）。
   とくに `oauth.js` は**失敗した Promise をキャッシュし続ける**形になっており、
   一度失敗すると連携が再試行で直らない（#1）。
   **複製する前に直すこと**が [../repository-structure.md](../repository-structure.md) §4-3 の要求
2. **OCR がレイアウトを失う。** 案A の構造上の代償で、
   「近くの金額」の判定に限界がある（§4-2）
3. **上位文書が2本立て。** v1.3 のどの章が現役かを毎回確認する必要がある
4. **v2.0 は「ドラフト」のまま**（[../specs/README.md](../specs/README.md) の一覧）
5. 電子帳簿保存法への対応方針は上位文書 §0.3 のとおり**宣言していない**

## §11 設計判断の記録

| 判断 | 採らなかった案 | 理由 |
| --- | --- | --- |
| サーバーを持たない（v2.0） | v1.3 のサーバー構成 | 利用者のドライブに閉じる。当社が預からない |
| OCR エンジンを差し替え可能にする | 1方式に決め打ち | フェーズ0で条件を揃えた比較を行うため |
| ルールと Gemini を**独立**に読ませる | ルール候補を渡して補完させる | 追認が返り、突き合わせが無意味になる |
| 信頼度をコードで算出 | Gemini の自己申告 | LLM の確率は校正されていない |
| `evidence` を必須にする | `confidence` を要求する | 根拠のほうが検証できる |
| 金額の失敗を `null` に | 0 にする | 0円の領収書として検証をすり抜ける |
| 保存前確認を必須にする | 高信頼度なら自動確定 | §15.1 の「誤りを高信頼度として提示 0件」を満たすため |
| `RAW` で書く | `USER_ENTERED` | 数式が評価されない。防御が1枚増える |
| 判断と通信を分ける | まとめて書く | 壊れた状態のテストを実通信なしで書ける |
| `processingStatus` を落とす | v1.3 の4軸を維持 | サーバーが無く、常に同じ値になる |
| 日付を Asia/Tokyo 固定 | 端末の時間帯 | 同じ領収書が端末によって別の月へ入る |
