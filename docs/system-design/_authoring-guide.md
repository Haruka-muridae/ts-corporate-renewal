# system-design 執筆規約（要件定義〜詳細設計書）

制定: 2026年8月18日

`docs/system-design/` は、このリポジトリに同居する各アプリを**他のプロダクトへ組み込める状態で文書化する**ためのディレクトリである。読者は「このリポジトリを知らないが、アプリを自分のプロダクトへ移植したい開発者」を想定する。

## ディレクトリ構成

```text
docs/system-design/
├── README.md                 # 索引（全アプリ一覧と文書へのリンク）
├── _authoring-guide.md       # 本書
└── <アプリID>/
    ├── 01_requirements.md    # 要件定義書
    ├── 02_basic-design.md    # 基本設計書
    ├── 03_detailed-design.md # 詳細設計書
    └── 04_integration-guide.md # 他プロダクトへの組み込みガイド
```

## 全文書共通のルール

- **日本語で書く。** コマンド名・ファイルパス・設定キー名・コード識別子は原文のまま。
- **実装とdocs/specs/の既存仕様書が正。** 本文書群は既存仕様書を置き換えない。矛盾させず、詳細は既存仕様書へ §番号で参照を張る。執筆中に仕様と実装の乖離を見つけた場合、文書に推測で書かず、乖離として報告する。
- **秘密情報を書かない。** 鍵・トークン・スプレッドシートID・フォルダID・クライアントID・デプロイ済みURL（`/exec` URL 等）・実在するメールアドレス・内部URLは記載禁止。環境変数・設定値は**名前と役割のみ**を書き、値は書かない。
- **推測で埋めない。** コードから読み取れない運用値・未確定事項は「未確定」と明記する。
- 図は mermaid コードブロックで書く（構成図は `graph`/`flowchart`、処理フローは `sequenceDiagram`）。
- 参照はセクション番号（§n）とファイルパスで行い、行番号は使わない。
- 「何をしているか」より「なぜそうしたか（と、採らなかった選択肢）」を残す。既存コード・仕様書のコメントから理由が読み取れるものは必ず拾う。
- 要件には `FR-nn`（機能要件）/ `NFR-nn`（非機能要件）の形式で通し番号を付け、後続文書から参照できるようにする。

## 各文書の章立て

### 01_requirements.md（要件定義書）

1. 目的・背景
2. 用語定義
3. スコープ（対象外を明記する）
4. 利用者とロール
5. 機能要件（FR-nn。表＋必要な補足）
6. 非機能要件（NFR-nn。セキュリティ / 性能 / 可用性 / 運用 / アクセシビリティ）
7. 制約条件（技術選定上の制約、リポジトリ運用上の制約）
8. 外部依存（外部サービス・API・OAuth スコープ）
9. 前提条件・未確定事項

### 02_basic-design.md（基本設計書）

1. システム構成（mermaid 構成図）
2. コンポーネント一覧と責務
3. 外部インターフェース一覧（連携先サービスと通信方式）
4. データ設計概要（保存先と主要エンティティ）
5. 画面一覧と画面遷移
6. 認証・認可方式
7. エラー処理方針
8. 運用・デプロイ構成
9. 主要な設計判断と採らなかった選択肢

### 03_detailed-design.md（詳細設計書）

1. ファイル・モジュール構成（パスと責務の表）
2. 主要処理フロー（mermaid sequenceDiagram。正常系＋主要な異常系）
3. データモデル詳細（テーブル / シート / ストレージのスキーマ）
4. インターフェース仕様（API エンドポイント・主要関数の入出力・エラーコード）
5. 状態管理・セッション設計
6. エラーハンドリング詳細
7. 設定値・環境変数一覧（名前・役割・置き場所。値は書かない）
8. テスト構成（既存テストスイートとの対応）

### 04_integration-guide.md（組み込みガイド）

1. 移植の前提条件
2. 依存関係マップ（このアプリが何に結合しているか）
3. 切り離しポイント（他プロダクトへ持ち出すときに差し替える箇所）
4. 必要な外部サービスと設定作業の概要
5. 複製時の注意（`docs/repository-structure.md` §4 の複製方針に従う。複製元の既知の不具合を持ち込まない）
6. 最小組み込み手順

## 分量の目安

水増ししない。アプリの規模に応じて各文書 100〜400 行程度。実装に存在しない機能・将来構想は書かない（書く場合は「未実装」と明記して分離する）。
