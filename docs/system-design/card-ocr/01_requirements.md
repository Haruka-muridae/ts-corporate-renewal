# 名刺OCR・データ登録アプリ（card-ocr）要件定義書

## 1. 目的・背景

TSAM AI の利用者が、スマートフォンまたはPCから名刺画像をアップロードし、文字情報を抽出・構造化したうえで、**利用者自身のGoogleドライブ内のスプレッドシート**へ保存できるようにする。手入力による名刺管理の課題（入力時間、転記ミス、重複登録、表記の不統一）を、OCRとAIによる項目分類で軽減する。

本アプリは**サーバーコードを持たない**（静的フロントエンドのみ）。利用者の資格情報（Gemini APIキー・Google OAuthトークン）も、利用者のデータ（名刺画像・名刺情報）も、当社サーバーへは一切送信しない。当社が提供するのは「道具（静的アプリ）」であり、データの器はすべて利用者自身のGoogleアカウントである。この設計原則は、同じ台帳を読み取る姉妹アプリ「名刺メール配信アプリ（`card-mail`）」にも引き継がれている。

実装済みの詳細は既存仕様書 [docs/specs/meishi-ocr-requirements-v3.md](../../specs/meishi-ocr-requirements-v3.md)（以下「既存仕様書」）を正とする。本書は既存仕様書とコード（`public/production-app/card-ocr/`）を要件定義〜詳細設計の章立てへ再構成したものであり、内容を置き換えない。既存仕様書は両面（表面・裏面）対応や統合ロジックの設計論点を詳細に記録しており、背景を知りたい場合はそちらを参照する。

## 2. 用語定義

| 用語 | 意味 |
| --- | --- |
| 台帳 / 名刺管理 | 本アプリが利用者のGoogleドライブに作るスプレッドシート（マイドライブ／TSAM AI／名刺データ／名刺管理）。「名刺データ」「変更履歴」の2タブを持つ |
| 面（表面・裏面） | 名刺の1件は表面（必須）＋裏面（任意）の最大2枚の画像で構成する |
| drive.file | 「そのクライアントIDのアプリが作成した、または利用者が明示的に選んだファイルだけ」に見える範囲を絞ったGoogle Driveの権限スコープ |
| KeyStore | Portal が提供する、利用者のAPIキーをブラウザの `localStorage` に保存する共通の仕組み（`public/auth/keystore.js`） |
| guardPage | `public/auth/session.js` が提供する、TSAM AIログインセッションを検証してから画面を描画する共通の入口関数 |
| GIS | Google Identity Services。トークンモデルの OAuth 2.0 をブラウザから直接扱うための Google 公式スクリプト |
| 一時ドキュメント | OCRのために画像を変換して作る一時的なGoogleドキュメント。テキスト取得後に完全削除する |
| 孤児回収 | 削除に失敗して残った一時ドキュメントを、起動時に検索して回収する処理 |
| 測定モード（`measure/`） | フェーズ2の精度・所要時間測定のために本番モジュールを直接importして使う開発者向け画面。エンドユーザー向け機能ではなく、測定終了後に撤去予定（詳細は §3） |

## 3. スコープ

### 3.1 含む

- Portal（`public/portal/`）からの起動と、TSAM AI ログイン確認（`guardPage()`）
- Google OAuth連携（`drive.file` スコープのみ、GISトークンモデル）
- KeyStore からの Gemini APIキー取得（未設定時は Portal のキー設定へ誘導）
- 保存構造（フォルダ・台帳）の自動作成・再発見・既存台帳の健全性検査
- 表面（必須）＋裏面（任意）の撮影・選択、面ごとのプレビュー・回転・取り消し
- ブラウザ側の画像圧縮（段階的な品質・寸法調整で1.5MB以内に収める）
- ブラウザからの Drive OCR（面ごと、並列実行、一時ドキュメントの即時完全削除・孤児回収）
- テキスト正規化・正規表現による事前抽出
- Gemini API による項目分類（1名刺1回、表裏テキストを結合して送信）
- 正規表現抽出結果とGemini結果の突き合わせ、表面優先の表裏統合
- 読み取り結果の確認・修正（全項目編集可能）画面
- 台帳内での重複候補検出（画像ハッシュ・会社名＋氏名）と、検出時の選択肢（新規登録・既存更新・キャンセル）
- 確定保存（画像アップロード、台帳への1行追記）
- 登録済み行の更新（`record_id` で行を特定して `values.update`）と、差分確認・変更前値の「変更履歴」シートへの記録（2026-08-18 実装）
- エラーコード（既存仕様書 §15）に基づくエラー表示と手入力導線
- ヘルプ画面（`help/`。データの扱い・削除方法・連携解除の案内）

## 4. 利用者とロール

- TSAM AI のアカウントを保有し、ログインできる利用者全員。ロールによる機能差はない。MVPでは全プランに開放し、プラン判定は行わない（既存仕様書 §5.1。コード上もプラン判定は実装していない）。
- Google アカウントを保有し、本アプリへの `drive.file` アクセスを許可できること。
- 自身の Gemini APIキーを保有し、Portal のキー設定画面（KeyStore）で保存済みであること（無料枠キーでも利用可）。
- 名刺データ・保存画像は利用者本人のGoogleドライブにのみ保存され、当社は受信・保管・閲覧をしない。データの管理責任は利用者自身にある。

## 7. 制約条件

- **本番アプリ間で共通層を作らない。** `public/production-app/` 配下に `shared/`・`common/`・`lib/` の類を置かず、アプリ間でのimportも行わない（[docs/repository-structure.md](../../repository-structure.md) §4）。姉妹アプリ `receipt-ocr`・`card-mail` と重複するロジック（Drive APIのエラー分類、GIS読み込み、multipart組み立て等）はすべて複製しており、複製元パスと複製日をファイル冒頭コメントに記す。
- テスト環境 `public/apps/`（`card-scanner` 等）からは import しない。動作の実績としては参照するが、コードは複製する。
- **card-mail とはOAuthクライアントIDを意図的に共用する。** `drive.file` はクライアントIDごとに見える範囲が分かれるため、`card-mail` が本アプリの作成した台帳を読むには同じIDが要る（ルート `CLAUDE.md`「名刺メール配信アプリ」節）。一方でテスト環境 `/apps/` や `receipt-ocr` とはクライアントIDを分離している（`config.js`）。
- 静的フロントエンドのみで実装する。サーバーコード・APIエンドポイントを持たない。
- 配信は `public/` 配下の静的ファイルとして行い、ビルド工程を持たない。デプロイは手動（`npm run deploy`）で、`main` へのマージだけでは公開されない。
- OCR一時ドキュメントの名前接頭辞（`card-ocr-temp-`）は他アプリ・検証ページと重複させない（孤児回収が誤って他方の処理中ファイルを消すのを防ぐため）。

## 9. 前提条件・未確定事項

### 前提条件

1. Google Cloud プロジェクト側で、Drive API・Sheets API が有効化され、`card-ocr`（`card-mail` と共用）用のOAuthクライアントIDが発行されていること。承認済みJavaScript生成元に本番オリジンが登録されていること。
2. OAuth同意画面の公開ステータスが「本番」であること。フェーズ0では「テスト」のまま検証しており、「本番」への切り替えと審査手続きの要否確認はフェーズ5の作業として計画されていた（既存仕様書 §18）。**本書執筆時点で切り替え済みかどうかはコードから判定できない（未確定）。**
3. デプロイは手動（`npm run deploy`）で行う。

### 未確定事項（本書執筆時点でコード・既存仕様書から読み取れないもの）

- OAuth同意画面の公開ステータス（「テスト」のままか「本番」へ切り替え済みか）と、審査の要否・完了状況。
- Portal（`public/portal/app-registry.js`）への掲載時期。本書執筆時点でレジストリに `card-ocr` のエントリは存在しない（§5 FR-25、末尾の乖離報告を参照）。
- 既存仕様書 §16.2 の定量受入基準（主要5項目正解率85%以上等）の実測・判定。既存仕様書はフェーズ2のミニ検収も含めて「未実施」のままMVP完了条件から除外すると記録している（既存仕様書 §19 条件9）。
- 名刺交換日・場所・担当者・タグの入力（FR-16 相当）の実装時期。**「実装しない」という決定はどこにも無い。** 既存仕様書 §18 のフェーズ3に含まれ、§17.1 は「セッション既定値の連続登録」を正常系テスト項目として挙げている。台帳へ4列を足す変更を伴うため、既存利用者のシートの見出し判定と併せて計画する必要がある。
- 利用規約への追加条項の正式化、法務確認の実施時期（既存仕様書 §14.5・§19 条件13の注記）。
- 「変更履歴」タブの見出しを利用者が書き換えた場合の扱い。現在は**検査していない**（台帳＝名刺データタブのみ `verifyHeader` で検査する）。改変されたタブへ追記すると、利用者の記録が読みにくくなる可能性はあるが、名刺データ側と違って**個人情報が別の列へ入る危険は無い**ため、起動時の読み取りを1回増やすことと引き換えにしていない（[03_detailed-design.md](./03_detailed-design.md) §4.3）。
