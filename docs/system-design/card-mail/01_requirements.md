# 名刺メール配信アプリ（card-mail）要件定義書

## 1. 目的・背景

TSAM AI の利用者が、名刺OCRアプリ（`card-ocr`）で蓄積した名刺の宛先へ、**利用者自身のGmail**から、宛先を互いに見せずに（BCC）宣伝・案内メールを一括送信できるようにする。

名刺OCRにより、名刺のメールアドレスは利用者ごとのGoogleスプレッドシート「名刺管理」に貯まる。次の課題は「集めた宛先への一斉連絡」である。メールソフトでの手動BCC送信は、(1) To/CcとBCCの取り違えによる宛先の相互漏えい、(2) 無償Gmailの1通あたり宛先数上限（100件）を超えたときの手分割、(3) OCR由来の壊れたアドレスへの気づきにくさ、という事故を生む。台帳はこちらのシステムが作っているため、宛先の読み取りまで自動化する。

本アプリは**サーバーコードを持たない**（静的フロントエンドのみ）。名刺データも宛先も本文も、当社サーバーへは一切送信しない。これは名刺OCRの設計原則（本人のGoogleドライブから出さない）を引き継いだものである。

実装済みの詳細は既存仕様書 [docs/specs/card-mail-requirements-v1.md](../../specs/card-mail-requirements-v1.md)（以下「既存仕様書」）を正とする。本書は既存仕様書を要件定義〜詳細設計の章立てへ再構成したものであり、内容を置き換えない。

## 2. 用語定義

| 用語 | 意味 |
| --- | --- |
| 台帳 / 名刺管理 | 名刺OCRアプリが利用者のGoogleドライブに作るスプレッドシート。宛先の正本。パス: マイドライブ／TSAM AI／名刺データ／名刺管理 |
| BCC | 受信者に他の宛先を見せずに同じメールを届ける宛先欄。本アプリは全宛先をここに入れ、To・Ccを使わない |
| 束（バッチ） | BCC宛先を100件ずつに区切った1通分の単位 |
| drive.file | 「そのクライアントIDのアプリが作成したファイルだけ」に見える範囲を絞ったGoogle Driveの権限スコープ |
| gmail.send | Gmailの**送信のみ**を許す権限スコープ。受信箱の閲覧はできない。Googleの制限付きスコープで、一般公開には審査が必要 |
| トークンモデル | リフレッシュトークンを持たず、短命のアクセストークンだけで動くOAuthの形。静的サイト向け |
| guardPage | `public/auth/session.js` が提供する、TSAM AIログインセッションを検証してから画面を描画する共通の入口関数 |
| Portal | TSAM AIのアプリ一覧画面（`public/portal/`）。本番アプリはここから起動する |

## 3. スコープ

### 3.1 含む

- Google連携（drive.file + gmail.send、トークンはメモリ上のみ）
- 台帳の解決（検索のみ・作らない）とメールアドレス列の読み取り
- 宛先の検証・重複排除・不正宛先の一覧表示
- 件名・本文（テキストメール）の入力
- 特定電子メール法の表示義務に関する利用者の確認（チェックボックス）
- 100件ずつのBCC分割・直列送信、進捗表示
- 途中失敗時の送信済み件数表示と、残りからの再開

詳細は既存仕様書 §7.1。

### 3.2 含まない（現時点の判断）

| 機能 | 含めない理由（要約） |
| --- | --- |
| Portalへの掲載 | Google審査（後述 §8, §9）の完了が先 |
| 宛先の選別（会社・タグ等） | まず全件送信で成立させる |
| 宛名の差し込み | 宛先ごとに1通になり送信上限に触れやすい |
| HTMLメール | テキストで足りる |
| 送信履歴のアプリ内保存 | 利用者のGmail「送信済み」が記録を兼ねる |
| 受信拒否の自動管理 | 台帳側の運用で対応。列追加が要るため次版で検討 |

理由の詳細は既存仕様書 §7.2。

## 4. 利用者とロール

- TSAM AIのログインユーザー全員（`guardPage()` を通過した利用者）。ロールによる機能差はない。
- 送信元は利用者自身のGmailアカウントであり、会社名義での代理送信ではない。認証を利用者ごとに配れることが、お客様全員への開放と両立する前提になっている（既存仕様書 §12）。
- 前提として、名刺OCRアプリで名刺を登録済みで台帳が存在することを要する（§9）。

## 5. 機能要件

既存仕様書 §9 の番号をそのまま踏襲する。

| ID | 要件 | 補足 |
| --- | --- | --- |
| FR-01 | 画面ガード | `guardPage()` を通過するまで内容を描画しない（`card-ocr` と同じ方式） |
| FR-02 | Google連携 | スコープは `drive.file` と `gmail.send` の2つのみ。両方の付与を検証し、欠けていれば案内して進まない。トークンはメモリ上のみ保持し、Storage・URL・console・当社サーバーへ出さない |
| FR-03 | 台帳の解決（読むだけ・作らない） | キャッシュ検証→名前・親・種別・未削除での検索、の順で解決する。見つからなくても作らない（空の台帳を作ると `card-ocr` の正本と競合する）。localStorageに入れるのは台帳の場所（ファイルID）だけ |
| FR-04 | 宛先の読み取り | 「名刺データ」タブの見出し行から「メールアドレス」列を**位置ではなく見出しで**探し、その列だけを読む。他の列（氏名・住所・電話等）は取得しない |
| FR-05 | 宛先の検証・重複排除 | メールアドレスの形式でない値は送信対象から外し一覧で見せる（黙って除かない）。大文字小文字だけ違う宛先は1件にまとめる |
| FR-06 | BCC送信と分割 | 宛先は上から順に100件ずつの束にし、1束＝1通としてBCCで送る。To・Fromヘッダーは付けない。1通ずつ直列に送る |
| FR-07 | 途中失敗と再開 | 失敗したら残りを打ち切り、送信済みの件数・通数を表示する。再開時は送信済みの束を飛ばし、残りの束だけを送る |
| FR-08 | 法令表示の確認 | 「本文に送信者の氏名・名称と受信拒否の連絡先を記載した」チェックを入れない限り送信ボタンを有効にしない。本文の中身自体はアプリが検査できないため、確認は利用者の宣言による |

各要件の背景・理由は既存仕様書 §9 を参照。

## 6. 非機能要件

| ID | 分類 | 要件 |
| --- | --- | --- |
| NFR-01 | セキュリティ | OAuthアクセストークンはメモリ上にのみ保持し、localStorage・sessionStorage・Cookie・URL・console・例外メッセージ・当社サーバーのいずれにも出さない（既存仕様書 §11） |
| NFR-02 | セキュリティ | 通信先はCSP（`index.html` の `<meta>`）で Google 3系統（Drive・Sheets・Gmail）とTSAM AI認証系（`script.google.com` / `script.googleusercontent.com`）に固定する。他のホストを足さない |
| NFR-03 | セキュリティ | メールヘッダーインジェクション対策として、宛先・件名の改行・制御文字・カンマ・セミコロンを送信前に検査し、検出したら例外で止める（宛先の形式検査と、メッセージ組み立て側の二重の関門） |
| NFR-04 | セキュリティ | 台帳からはメールアドレス列だけを取得し、氏名・住所・電話番号等の他の個人情報は読まない（個人情報の過剰取得の回避） |
| NFR-05 | 性能 | メール送信は1通ずつ直列に行う（並列化しない）。理由は、失敗位置を確定できることと、Gmailのレート制限へ配慮するため |
| NFR-06 | 可用性 | 当社サーバーを経由しないため、当社サーバーの障害の影響を受けない。一方、Google API（Drive/Sheets/Gmail/GIS）が不調の間は利用できない。Gmailの1日あたり送信上限（無償アカウントは目安500宛先程度）に達すると、Googleにより一時的に送信が止められることがある。アプリはこの上限を検知できないため、上限エラー時は「日を改める」案内に留める |
| NFR-07 | 運用 | デプロイは手動（`npm run deploy`）。`main` へのマージだけでは公開されない。公開時はPortalのアプリ一覧（`public/portal/app-registry.js`）へ登録する（本書執筆時点で未登録。§9） |
| NFR-08 | アクセシビリティ | セマンティックHTMLとネイティブ要素（`<details>` `<summary>` `checkbox` 等）を優先し、スキップリンクと `aria-live` を用いる。操作要素は44px以上を確保する（`style.css`）。アニメーションの低減は共通CSS（`public/auth/auth.css`）の `prefers-reduced-motion` 対応に従う |

## 7. 制約条件

- **`card-ocr` と同じOAuthクライアントIDを意図的に共用する。** `drive.file` はクライアントIDごとに見える範囲が分かれるため、`card-ocr` が作成した台帳を読むには同じIDが要る（既存仕様書 §4.2、§12）。アプリごとにIDを分けるのが本来の方針（`card-ocr` の `config.js`）だが、本アプリは例外として扱う。
- **本番アプリ間で共通層を作らない。** `public/production-app/` 配下に `shared/`・`common/`・`lib/` の類を置かず、アプリ間でのimportも行わない（[docs/repository-structure.md](../../repository-structure.md) §4-1）。`card-ocr` と共通するロジック（Drive APIのエラー分類、GIS読み込み等）は複製し、複製元パスと複製日をファイル冒頭コメントに記す。
- 静的フロントエンドのみで実装する。サーバーコード・APIエンドポイントを持たない。
- 配信は `public/` 配下の静的ファイルとして行い、ビルド工程を持たない。
- テストはNode実行のユニットテスト（`tests/unit/card-mail.mjs`）と、実ブラウザでの結線確認（`tests/browser/card-mail.mjs`）で行い、いずれも本物のGoogle API・TSAM AI認証系へは通信しない（スタブで代替する）。

## 8. 外部依存

| 依存先 | 用途 | 認証・スコープ |
| --- | --- | --- |
| Google Identity Services（GIS） | OAuth 2.0 トークンモデルでの認可 | 公式配信URL（`accounts.google.com/gsi/client`）のみを承認済みの読み込み先とする |
| Google Drive API v3 | 台帳（フォルダ・スプレッドシート）の検索・検証 | `drive.file` スコープ。書き込み系エンドポイントは呼ばない |
| Google Sheets API v4 | 「名刺データ」タブのメールアドレス列の読み取り | Drive連携と同じアクセストークンを使用（Sheets固有のスコープは要求しない） |
| Gmail API v1 | 利用者自身のアカウントからのメール送信（`messages.send`） | `gmail.send` スコープ。送信のみで受信箱は読めない |
| TSAM AI 認証系（`script.google.com` / `script.googleusercontent.com`） | ログインセッションの検証（`guardPage()` 経由） | 本番認証系の既存の仕組みをそのまま利用（本書のスコープ外。詳細は認証系の設計文書を参照） |

要求するOAuthスコープは `drive.file` と `gmail.send` の2つのみで、増やさない方針（既存仕様書 §12、`config.js` のコメント）。

## 9. 前提条件・未確定事項

### 前提条件

1. 利用者が名刺OCRアプリで名刺を登録済みで、台帳「マイドライブ／TSAM AI／名刺データ／名刺管理」が存在すること。無い場合、本アプリは台帳を作らず「先に名刺OCRで登録」と案内する。
2. Google Cloud側で、`card-ocr` と共用するクライアントのOAuth同意画面に `gmail.send` スコープが追加され、公開に必要な審査（制限付きスコープのため）が完了していること。審査完了までは「確認されていないアプリ」の警告が出る（テストユーザー登録で回避可能）。この作業はコードには現れない（既存仕様書 §6-2）。
3. デプロイは手動（`npm run deploy`）で行う。

### 未確定事項（本書執筆時点でコード・既存仕様書から読み取れないもの）

- Google Cloud側での `gmail.send` スコープ追加・審査の進捗状況（完了済みかどうか）。
- Portal（`public/portal/app-registry.js`）への掲載時期。本書執筆時点でレジストリに `card-mail` のエントリは存在しない（§10「執筆中に見つけた乖離」参照）。
- Gmailの日次送信上限に抵触した場合の運用手順（利用者への案内以上の対応があるか）。
- 受信拒否（オプトアウト）管理を台帳側でどう運用するかの具体的な手順（既存仕様書は「台帳側の運用」とのみ言及し、手順は定めていない）。
