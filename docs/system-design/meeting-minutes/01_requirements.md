# AI議事録アプリ（meeting-minutes）要件定義書

## 1. 目的・背景

TSAM AIの利用者が、会議・面談・打ち合わせの文字起こしをGeminiで整理し、確認・編集可能な議事録へ
仕上げられるようにする。文字起こし結果を読み直して要点・決定事項・担当タスクを手作業で整理する
負担を軽減することが目的だが、AIの出力を確定情報として扱わず、利用者が原文と照合して完成させる
ことを前提とする（プロンプトインジェクション対策と根拠のクライアント側照合により、この前提を
仕組みとしても支える）。

本アプリはPortal内で次の系列の**最終段**に位置する。

1. `voice-recorder`（ブラウザ録音）で音声を作成する
2. `audio-transcriber`（音声文字起こし）で音声をテキスト化する
3. `meeting-minutes`（本アプリ）で文字起こしを議事録へ整理する

本アプリは録音機能・音声認識機能を再実装しない。

実装済みの詳細は既存仕様書
[docs/specs/meeting-minutes-requirements-v1.md](../../specs/meeting-minutes-requirements-v1.md)
（以下「既存仕様書」。現行版はv1.3）を正とする。本書は既存仕様書を要件定義〜詳細設計の章立てへ
再構成したものであり、内容を置き換えない。FR番号は本書独自の通し番号で、既存仕様書の章番号
（§4-nのnと同じ）に対応させてある。

## 2. 用語定義

| 用語 | 意味 |
| --- | --- |
| drive.file | 「そのクライアントIDのアプリが作成したファイルだけ」に絞ったGoogle Driveの権限スコープ |
| トークンモデル | リフレッシュトークンを持たず、短命のアクセストークンだけで動くOAuthの形。静的サイト向け |
| KeyStore | Gemini APIキーを端末内`localStorage`にのみ保管する共通機構（`public/auth/keystore.js`）。ポータルの「API設定」から利用者が登録する |
| guardPage | `public/auth/session.js`が提供する、TSAM AIログインセッションを検証してから画面を描画する共通の入口関数 |
| Portal | TSAM AIのアプリ一覧画面（`public/portal/`）。本番アプリはここから起動する |
| 引継ぎ（handoff） | `audio-transcriber`が`sessionStorage`へ書き、本アプリが読み取る文字起こしデータの受け渡し |
| evidence（根拠） | 決定事項・タスクに紐づく、原文中の該当箇所の短い引用。AIが生成した文字列をクライアント側で原文に対して照合する |
| ドラフト | 入力原文・会議情報・テンプレート・生成結果・編集内容を端末内（IndexedDB）へ保存したもの |
| テンプレート | 議事録の構成（出力するセクションと見出し）を決める固定プリセット。標準／要点重視／詳細／1on1・面談の4種 |

## 3. スコープ

### 3.1 含む（既存仕様書 §2-1）

- 文字起こしテキストの貼り付け・.txt/.mdファイルの読込み・`audio-transcriber`からの引継ぎ
- 会議情報の任意入力、議事録テンプレートの選択
- Geminiによる議事録生成（構造化JSON出力）
- 原文と生成結果の並列確認、evidenceのクライアント側照合
- 生成結果の編集、セクション別再生成
- Markdownのコピー・ダウンロード
- Googleドライブへの明示的な保存（利用者操作による。v1.2で追加）
- 端末内ドラフトの自動保存・復元・消去

### 3.2 含まない（既存仕様書 §2-2）

| 機能 | 含めない理由（要約） |
| --- | --- |
| ブラウザ録音・音声からの文字起こし | `voice-recorder`/`audio-transcriber`の役割。重複実装しない |
| リアルタイム議事録生成、発言者の音声識別 | 録音済み文字起こしの整理という範囲を超える |
| Zoom/Google Meet/Teams等との直接連携 | 外部サービス連携はMVP範囲外 |
| 複数人での同時編集、議事録の承認ワークフロー | 単独利用のブラウザ完結アプリという設計を超える |
| 当社管理サーバーへの議事録保存、利用者間の議事録共有 | 「当社サーバーへ保存しない」という本アプリの原則に反する |
| Word/PDFへの直接出力、Google Driveへの自動保存 | 明示操作を要件とするため、自動化は採らない |
| 会議予定・参加者情報の自動取得 | 外部カレンダー等との連携を持たない |

将来拡張候補（Google Docsへの書き出し、テンプレートの利用者定義、生成履歴のIndexedDB保存等）は
既存仕様書 §2-3を参照。MVPの受入条件には含めない。

## 4. 利用者とロール

- TSAM AIのログインユーザー全員（`guardPage()`を通過した利用者）。ロールによる機能差はない。
- Gemini生成を使う場合、利用者がポータル「API設定」（KeyStore）で自分のGemini APIキーを
  登録済みであること。本アプリにキーの入力欄は無い。
- Googleドライブへの保存を使う場合、利用者が保存操作の時点でOAuth認可を行うこと（アプリを
  開いただけでは認可を求めない）。
- `audio-transcriber`からの引継ぎを使う場合、利用者が直前にそのアプリで文字起こしを完了させ、
  「AI議事録を作成」等の導線から遷移してきていること。

## 5. 機能要件

既存仕様書 §4のn番目の項目を`FR-0n`として対応させる。

| ID | 要件 | 補足 |
| --- | --- | --- |
| FR-01 | 認証・画面ガード | `setScreenDepth(2)`＋`guardPage()`。有効な利用者と確認できるまで`#mm-content`を描画しない。無効時はローカルセッションを消去して`/login/?next=portal`へ（既存仕様書 §4-1） |
| FR-02 | 入力方式 | テキスト貼り付け／.txt・.mdファイル読込み（File API、当社サーバー非送信）／`audio-transcriber`からの引継ぎ、の3方式（既存仕様書 §4-2） |
| FR-03 | 入力検証 | 空・空白のみ・対応外拡張子・読込み失敗・バイナリ疑い・文字コード不正・上限超過（60,000字。`config.js`の`TRANSCRIPT_MAX_CHARS`）をそれぞれ判定し案内する（既存仕様書 §4-3） |
| FR-04 | 会議情報 | 会議名・開催日・開始/終了時刻・参加者・目的・補足事項を任意入力とする。未入力をAIに推測させない（既存仕様書 §4-4） |
| FR-05 | 議事録テンプレート | 標準／要点重視／詳細／1on1・面談の4プリセット固定。編集はMVPに含めない（既存仕様書 §4-5） |
| FR-06 | Gemini APIキー | KeyStoreから取得。未設定なら生成を開始せず設定導線を表示。`x-goog-api-key`ヘッダーで送信し、URL・ログ・画面へ露出しない。無効時もKeyStoreから自動削除しない（既存仕様書 §4-6） |
| FR-07 | AIへの送信前確認 | 生成前に送信先・送信内容・機密情報注意・AI出力確認責任を表示し、明示操作でのみ送信する（既存仕様書 §4-7） |
| FR-08 | 議事録生成 | Geminiへ直接リクエスト。事実補完の禁止・不明表示・発言者関連付け・雑談除外・決定/検討の区別・タスク根拠必須・日本語出力・原文準拠をAIへ指示する（既存仕様書 §4-8） |
| FR-09 | 構造化出力 | `meeting/summary/topics/decisions/actionItems/openIssues/notes`を持つJSON Schemaで応答を制約。不正JSONは1回だけ安全な再解析・再生成を試みる（既存仕様書 §4-9） |
| FR-10 | 根拠確認 | 決定事項・タスクのevidenceを原文へ対してクライアント側で照合し、実在しない引用は「根拠を確認できません」とする。原文にタイムスタンプがあれば直前のものを付与し、無ければ擬似時刻を作らない（既存仕様書 §4-10） |
| FR-11 | 編集 | 生成結果の全項目を編集可能。プレーンテキストとして扱う。項目の追加・削除・並べ替え。未保存編集がある状態での離脱に警告する（既存仕様書 §4-11） |
| FR-12 | 再生成 | 全体／要約のみ／決定事項のみ／タスクのみの4択。対象外セクションは編集中の内容を保持する（既存仕様書 §4-12） |
| FR-13 | コピー・ダウンロード | 完成Markdownをクリップボードへコピー、またはUTF-8の.mdとしてダウンロード。既定ファイル名は`YYYY-MM-DD_会議名_議事録.md`（会議名が無ければ`YYYY-MM-DD_議事録.md`）（既存仕様書 §4-13） |
| FR-14 | ドラフト | 入力原文・会議情報・テンプレート・生成結果・編集内容をIndexedDBへ自動保存。「端末内の作業データを削除」で本アプリのデータのみ消去する。APIキー・認証セッションは対象に含めない（既存仕様書 §4-14） |
| FR-15 | Googleドライブへの保存 | 出力画面の明示操作でのみ実行。保存先は利用者自身のドライブ「マイドライブ ＞ TSAM AI ＞ 議事録データ」（名前解決・無ければ作成）。毎回新規ファイルとして作成し、上書きしない。スコープは`drive.file`のみ（既存仕様書 §4-15） |
| FR-16 | アプリ間引継ぎ | `audio-transcriber`が`sessionStorage`（キー`tsam-meeting-minutes-handoff-v1`）へ書いた引継ぎデータを、信頼できない入力として検証（メジャーバージョン一致・送信元一致・TTL30分以内）してから取り込む。正常取込み後・キャンセル後のいずれも消去する（既存仕様書 §5） |

各要件の背景・理由は既存仕様書 §4・§5を参照。

| NFR-03 | セキュリティ | 文字起こしは処理対象データとして扱い、命令として実行しない。システム指示と本文を別partに分離し、応答形式をJSON Schemaで制約する。外部URL取得・ツール実行・追加API呼び出しをモデルへ許可しない（既存仕様書 §8-3） |

| NFR-06 | 運用（依存関係） | 新しい外部ライブラリを原則追加しない。Gemini API・Drive APIともSDKを使わずfetchで直接呼ぶ。Google Identity Services以外の外部スクリプト・第三者CDNを追加しない（既存仕様書 §10-2） |
| NFR-07 | 可用性（対応ブラウザ） | Portal本体の対応ブラウザ方針に準拠し、最新安定版Chrome系でゴールデンパスを確認する。File API・Clipboard API・IndexedDBが使えない場合は代替手段または説明を提示する（既存仕様書 §10-3） |
| NFR-08 | アクセシビリティ | ネイティブ要素を使用し、全入力に可視ラベルを付ける。Tab/Enter/Spaceで主要操作へ到達できる。生成完了・失敗は適切なライブリージョンで通知し、色だけでエラーを伝えない。ライトテーマ固定（背景は常に純白）でコントラストを確認する（既存仕様書 §6-7・§6-8。v1.3でダークテーマを廃止） |
| NFR-09 | セキュリティ・データ最小化 | 認証情報・APIキー・Portal利用者IDをプロンプトへ含めない。ファイル名は会議名として利用者が明示的に採用しない限り送信しない。`console.log`にAPIキー・文字起こし・会議情報・生成結果を出力しない（既存仕様書 §7-3・§7-4） |
| NFR-10 | 運用 | デプロイは手動実行（`npm run deploy`）。`main`へのマージのみでは公開されない。Portal（`public/portal/app-registry.js`）から起動する（既存仕様書 §12、`CLAUDE.md`配信構成の項） |

## 7. 制約条件

- **本番アプリ間で共通層を作らない。** `public/production-app/`配下に`shared/`・`common/`・`lib/`の類を
  置かず、アプリ間でimportもしない（[docs/repository-structure.md](../../repository-structure.md) §4-1）。
  `oauth.js`・`drive-client.js`は`audio-transcriber`からの複製・適合であり、フォルダ解決の対象を
  「保存先のみ」に絞るなど本アプリ用に縮小してある。
- **OAuthクライアントIDを`voice-recorder`・`audio-transcriber`と意図的に共用する。** `drive.file`は
  クライアントIDごとに見える範囲が分かれるため、同じIDでないと同系統アプリが作成したフォルダを
  共有できない。一致は自動テストで検知する。
- npmビルドを持たない素のESモジュール構成。Gemini SDK（`@google/genai`）・Drive SDKは導入せず、
  公式REST（`fetch`）を直接使う。
- 静的配信のみで、サーバーコード（API・キュー・変換処理）を持たない。
- ダークテーマは持たない。背景は常に純白（#FFFFFF）とし、`prefers-color-scheme`で配色を変えない
  （v1.3の決定。既存仕様書 §14-1）。

## 8. 外部依存

| 依存先 | 用途 | 認証・スコープ |
| --- | --- | --- |
| Gemini API（`generativelanguage.googleapis.com`） | 議事録の生成（`generateContent`、構造化JSON出力） | 利用者自身のAPIキー（`x-goog-api-key`ヘッダー） |
| Google Identity Services（GIS） | Drive保存のためのOAuth 2.0トークンモデル認可 | 公式配信URL（`accounts.google.com/gsi/client`）のみを読み込み先とする |
| Google Drive API v3 | 保存先フォルダの解決（無ければ作成）、議事録Markdownのアップロード | `drive.file`スコープ。APIキー・client secretは使わない |
| TSAM AI認証系（`script.google.com`/`script.googleusercontent.com`、`auth-verify.potenitas-lp.workers.dev`） | ログインセッションの検証（`guardPage()`経由） | 本番認証系の既存の仕組みをそのまま利用（本書のスコープ外） |
| `audio-transcriber`（同一オリジン） | `sessionStorage`経由の文字起こし引継ぎ | 直接のAPI呼び出しは無く、共有キー名（`tsam-meeting-minutes-handoff-v1`）による受け渡しのみ |

要求するOAuthスコープは`drive.file`の1つのみで、増やさない方針（既存仕様書 §4-15、`config.js`のコメント）。

## 9. 前提条件・未確定事項

### 前提条件

1. Gemini生成を使う場合、利用者がポータル「API設定」で自分のGemini APIキーを登録済みであること。
2. Drive保存を使う場合、Google Cloud側で共用OAuthクライアントの「承認済みのJavaScript生成元」に
   本番オリジンが登録されていること。この作業はコードには現れない。
3. `audio-transcriber`からの引継ぎを使う場合、送信元アプリ側が引継ぎキー・データ形式・TTLの定めを
   守って`sessionStorage`へ書き込んでいること（既存仕様書 §5-4）。
4. デプロイは手動（`npm run deploy`）で行う。`main`へのマージのみでは公開されない。

### 未確定事項（本書執筆時点でコード・既存仕様書から読み取れないもの）

- 実Gemini APIキーでの疎通確認（構造化出力の生成、モデルのフォールバック挙動を含む）が本番オリジン
  で完了しているか。
- 本番オリジンでの実アカウントによるDrive連携（認可、フォルダ作成、ファイル保存）の確認が
  完了しているか。
- OAuth同意画面が「本番公開」へ切り替わっているか、または「テスト」状態のまま利用者を個別追加
  しているかは`audio-transcriber`側と共通の設定であり、本書の対象からは確認できない。
- `audio-transcriber`側の「AI議事録を作成」導線（`minutes-handoff.js`、同一タブ遷移）は実装済みで
  引継ぎキー・データ形式が本アプリ側と一致していることをコードから確認できたが、本番オリジンでの
  実際の遷移・引継ぎ確認（実機での一連の操作確認）が完了しているかは本書からは確認できない。
