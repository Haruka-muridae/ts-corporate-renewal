# receipt-ocr 要件定義書

対象アプリ：領収書スキャナ（アプリID `receipt-ocr`）
配置：`public/production-app/receipt-ocr/`
実装の正：[docs/specs/receipt-ocr-v2.md](../../specs/receipt-ocr-v2.md)（現行）／[docs/specs/receipt-ocr-v1.3.md](../../specs/receipt-ocr-v1.3.md)（抽出・検証ロジックの詳細。v2.0はv1.3を「サーバーを持たない構成」へ転換した改訂版で、抽出・検証・信頼度の章はv1.3を継承する）

本書はこの2文書と実装コードから読み取れる内容を要約したものであり、詳細はそれぞれの§番号を参照する。矛盾を見つけた場合は本書に推測で書かず、乖離として別途報告する。

---

## 1. 目的・背景

領収書・レシート画像から利用日・支払先・合計金額などを人手で転記する作業には時間と入力ミスが伴う。本アプリはOCRとルール処理でこれらの項目を抽出し、不足時のみAI（Gemini）で補うことで、経理データ化の負担を減らす。

会計証憑を扱うため、**「誤った値を自信を持って自動確定すること」を最大のリスク**と位置づけ、抽出できないことよりも誤った自動確定を防ぐことを設計上優先する（v1.3 §1）。

v2.0で「利用者本人のGoogleドライブを器にする」モデルへ一本化した。当社サーバー・データベースは存在せず、利用者の資格情報（Geminiキー・OAuthトークン）もデータ（領収書画像・抽出結果）も当社へ一切送信しない。当社が提供するのは静的な「道具」のみであり、データの保管・閲覧・バックアップの責任は利用者に帰属する（v2 §0.1・§0.5）。

## 2. 用語定義

| 用語 | 意味 |
| --- | --- |
| BYOK | Bring Your Own Key。利用者が自分のGemini APIキーをPortalのKeyStoreに保存し、それを使う方式 |
| `drive.file`スコープ | Google OAuthのスコープの一種。「このアプリが作成した、または利用者が明示的に開いたファイル」だけにアクセスできる。ドライブ全体は見えない |
| 案A / 案C | OCR方式の選択肢。案A＝Drive OCR（画像をGoogleドキュメントへ変換して文字を得る）、案C＝Gemini画像直接投入。v1.3の案Bは会社サーバー時代のCloud Vision案でv2.0では除外済み |
| evidence | Geminiが返す、抽出値の根拠となったOCR原文の一部。原文中に実在するかをコード側で照合し、幻覚検出に使う |
| confirmed | ルール抽出が単独で確定してよいと判断したか（候補が複数ある場合や近接ラベルが無い場合はfalse） |
| extractionMethod | 値がどの経路で確定したかを示す区分。`RULE` / `GEMINI` / `HYBRID` / `MANUAL`の4値 |
| reviewStatus | 確認状態。`NOT_REQUIRED` / `REQUIRED` / `REVIEWED`の3値 |
| duplicateStatus | 重複判定の結果。`NONE` / `CANDIDATE` / `EXACT`の3値 |
| KeyStore | Portal共通のAPIキー保管庫（`public/auth/keystore.js`）。localStorageへの直接アクセスを1か所に閉じる |
| guardPage() | TSAM AI認証の共通ガード（`public/auth/session.js`）。サーバー確認が終わるまで画面を描画しない |
| プロビジョニング | 利用者のドライブに保存先フォルダ・スプレッドシートが無い場合、アプリが自動作成する処理（v2 §9） |

## 3. スコープ

### 3.1 対象（MVP。v2 §3.1）

* 領収書画像の取得（ファイル選択・カメラ撮影、JPEG/PNG）
* 保存先（フォルダ・スプレッドシート）の自動プロビジョニング
* 原本画像の利用者ドライブへの保存
* OCR（実装は案Aと案Cの両方を備え、設定ファイル1か所で切替可能。既定は案A）
* ルール抽出（v1.3 §10の全項目：利用日・支払先・合計金額の必須3項目＋消費税内訳・支払方法・レシートNo.・電話番号・登録番号・勘定科目候補・宛名・但し書き）
* 金額正規化・妥当性検証・信頼度算出
* 必要時のみのGemini補完（利用者キー・ブラウザから直接・独立抽出）
* SHA-256による重複確認（自分のシートとの照合。完全一致・類似の2段階）
* 「要確認」の管理（利用者自身のシート上。フィルタビューを自動作成）
* 保存前確認・修正画面（保存前に人が確認・修正できる）

### 3.2 対象外

* サーバーコード（GAS等）、会社側でのデータ保管・閲覧
* 会社シートへの集約・管理者によるデータ修正運用
* 電子帳簿保存法のスキャナ保存対応（紙原本は廃棄しない。v2 §0.3）
* PDF・複数枚一括処理・商品明細のデータ化・会計ソフト連携
* 会社キーによるGemini呼び出し・フォールバック
* 消費税内訳の行またぎ形式（「税率10%」と金額が別行にある形）の抽出（v2 §7.1。フェーズ0の出現率次第で今後判断）
* HEIC画像のブラウザ内JPEG変換（**未実装**。仕様書v2 §3.1は「変換できる場合のみ受付」としているが、`ACCEPTED_IMAGE_TYPES`はJPEG/PNGのみで、変換処理はコード上に存在しない。2026-08-18以降、HEICは`image.js`の`isHeic()`で見分け、「iPhoneのフォーマット設定を変えて撮り直す」案内を出すが、**変換はしない**）

## 4. 利用者とロール

* 想定利用者はTSAM AI Portalにログインできる社内利用者。ロールによる機能差はない
* 各利用者は自分のGoogleドライブ・スプレッドシートのみを扱い、構造上（`drive.file`スコープ・各自のシートへの書き込みのみ）他者のデータへ到達する経路が無い
* 経理担当による確認・集約は行わない。要確認データの確認・修正は利用者本人が自分のシート上で行う（v2 §11）

## 5. 機能要件

| ID | 要件 | 参照 |
| --- | --- | --- |
| FR-01 | 3層ガード（①TSAM AI認証 `guardPage()`、②Google OAuth `drive.file`、③Geminiキーの有無確認）を起動時に行う。①は未ログインなら`/login/`へ、③は未設定でも案Aでは処理を止めず案内のみ出す | v2 §4 |
| FR-02 | 起動のたびに保存先（フォルダ階層・スプレッドシート）を検出し、無ければ自動作成する。既存IDの有効性確認→名前検索での再発見→新規作成の順を守る | v2 §9.2 |
| FR-03 | 既存スプレッドシートのヘッダー行・タブ構成を検証し、改変を検出したら書き込みを停止する（列位置を推測して書かない） | v2 §9.3・§9.4 |
| FR-04 | 選択された画像のSHA-256をブラウザ内（Web Crypto API）で計算する | v2 §5-②・§10 |
| FR-05 | 原本画像をDrive API v3で利用者ドライブの月別フォルダへアップロードする | v2 §5-④ |
| FR-06 | 自シートのハッシュ列のみを取得し、完全一致（保存不可）・類似＝同日同店舗同金額（警告のみ）を判定する | v2 §10 |
| FR-07 | OCRで画像から文字列を取得する。方式は差し替え可能な形にし、設定ファイル1か所で切り替える | v2 §0.2・§6 |
| FR-08 | OCR文字列からルールで項目を抽出する（利用日・支払先・合計金額・消費税内訳・支払方法・レシートNo.・電話番号・登録番号・勘定科目候補）。ラベル近接必須の項目は近接なしで確定しない | v1.3 §10 |
| FR-09 | 抽出した金額・日付をコード側で検証する（金額の桁妥当性・税額逆算による加点・未来日/1年超過去の除外） | v1.3 §13 |
| FR-10 | 検証結果からコード側で信頼度スコアを算出し、高・中・低へ分類する（Geminiの自己申告値は使わない） | v1.3 §14 |
| FR-11 | ルール抽出で確定できない・検証に不合格などの条件でのみGemini補完を要求する。OCR文字数が基準未満なら補完せず要確認とする | v1.3 §11 |
| FR-12 | Gemini補完はOCR原文のみから独立抽出させ（ルール候補を見せない）、evidence必須のStructured Outputで受け取る | v1.3 §12.2〜12.5 |
| FR-13 | Geminiのevidenceが保存済みOCR原文に実在するかを照合し、実在しない値は不採用とする | v1.3 §13.3 |
| FR-14 | ルール抽出値とGemini値を突合し、一致→加点、片方のみ→採用、不一致→要確認（自動で一方を選ばない） | v1.3 §12.2 |
| FR-15 | 保存前に抽出結果と原本画像を並べた確認画面を表示し、利用者が値を修正できる。低信頼度・要確認・食い違い項目は強調表示する | v2 §8 |
| FR-16 | 利用者が修正した値は抽出値より優先し、打ち直しは`extractionMethod=MANUAL`、AI値の採用は`HYBRID`として区別する | v2 §8・v1.3 §18.1-4 |
| FR-17 | 「要確認のまま保存」を選べる | v2 §8 |
| FR-18 | 保存はデータタブへの1行追加とOCR原文タブへの1行追加の2回に分け、データ行を先に書く | v1.3 §16.1・§16.2 |
| FR-19 | 保存する文字列は数式インジェクション対策（先頭が`=+-@`等ならクォート付与）を経てから書き込む | v1.3 §16.1・v2 §13 |
| FR-20 | 保存ボタンは処理中に無効化し、多重押下による二重登録を防ぐ | v2 §10 |
| FR-21 | プロビジョニング時に「要確認一覧」フィルタビューとヘッダー行の保護を作成する | v2 §9.1・§11 |
| FR-22 | 初回利用時に、データ帰属・削除時の復元不可・電帳法非対応・無料枠キーの取り扱いの案内を表示する | v2 §9.2末尾・§0.3〜0.5 |
| FR-23 | エラー表示は「どこまで完了しているか」（原本未保存／原本保存済み／シート保存済み）を必ず添える | v2 §12 |
| FR-24 | 画面を離れる（`pagehide`）ときにOAuthトークンとプレビューURLを破棄する | 実装（`app.js`） |

## 7. 制約条件

* `public/production-app/receipt-ocr/`にPortalと同一オリジンで配置する（KeyStore参照の必須条件）。Portalへの登録は`public/portal/app-registry.js`の`APP_REGISTRY`へ1件追加する形で行い、`href`に`apps/`を含めない・先頭に`/`を付けない（自動テストが検査する）。`id`はアプリIDと同一の`receipt-ocr`で固定し、あとから変えない（配置データがこれを参照するため）
* 本番アプリ同士（`receipt-ocr` / `card-ocr` 等）で共通層（`shared/` `common/` `lib/`）を作らない。同じロジックが要る場合は複製し、複製元と複製日をコメントへ書く（[docs/repository-structure.md](../../repository-structure.md) §4-1）
* テスト環境`public/apps/`のコードをimportしない。流用するロジックは本番側へ複製する
* サーバーコードを持たない（Apps Script・Cloud Functions等を新設しない）。すべての処理はブラウザ内で完結する
* Google Identity Services（`accounts.google.com`）以外の第三者スクリプトを読み込まない。CSPを`index.html`のmeta要素で宣言する

## 9. 前提条件・未確定事項

以下は実装からは読み取れない、または方針が未確定のまま実装が先行している事項である。推測で埋めず、ここに未確定として明記する。

1. **OCR方式のフェーズ0確定状況。** 仕様書（v2 §0.2・§16フェーズ0）は「案A（Drive OCR）と案C（Gemini画像直接）を実物領収書で実測比較したうえで主経路を決める」としているが、実装は両エンジンを備えたうえで`config.js`の`OCR_ENGINE = 'drive'`を既定値としている。実測比較・経理税理士確認（v2 §0.6）が完了した結果としての確定なのか、暫定の既定値なのかはコードから判断できない
2. **消費税内訳の行またぎ形式への対応要否。** v2 §7.1は出現率の実測後に判断するとしており、判断が下った記録は見当たらない
3. **勘定科目の初期店舗マスタ。** `INITIAL_STORE_MASTER`は空配列で作成される。経理担当による初期値の定義（v2 §0.6-2）は未確定のまま
4. **信頼度スコアのしきい値。** `DEFAULT_THRESHOLDS`（高120点・中60点）はコードコメントで「暫定値」と明記されており、フェーズ0・受入テストでの校正（v1.3 §14）は未実施と推測される
5. **経理・税理士・法務確認（v2 §0.6）の完了状況。** 電帳法の位置づけ、要確認データの確認手順、責任分界・キー費用の規約明記、社内経理運用の承認は、いずれもコードからは確認できない
6. **利用者向け簡易統計（NFR-07）の実装計画。** 仕様書には記載があるが実装は無い。着手予定かどうかは未確定（画像の事前縮小〈NFR-05〉は2026-08-18に実装済み）
7. **HEIC画像対応の実装計画。** 仕様書は変換対応を前提にした書きぶりだが、実装・テストのいずれにも変換処理が存在しない（2026-08-18に判別と案内だけを入れた）
8. **信頼度しきい値の校正値。** 設定タブ→実行時の配線は2026-08-18に済んだが、初期値（高120・中60）が暫定である点は変わらない（上の4と同じ）
