# X 投稿アプリ（x-post）要件定義書

## 1. 目的・背景

TSAM AI の利用者が、X（旧 Twitter）への投稿文を「書く／貼る／AIで作る」→ 下書きとして残す → 本文入りの X 投稿画面を開いて投稿する、を1画面で行えるようにする。

本アプリは Threads 投稿アプリ（`threads-post`）の基底仕様を X 向けに差分実装したものである。基底仕様（[docs/specs/threads-mvp-requirements-v1.md](../../specs/threads-mvp-requirements-v1.md)、以下「基底仕様」）が定める重点方針をそのまま引き継ぐ。

1. **最後の「投稿」は必ず人が押す。** intent リンク方式（本文入りの投稿画面を開くだけ）を採り、X の API・トークンは使わない。誤投稿・二重投稿が構造的に起きない。
2. **投稿文・下書き・履歴を利用者の管理下から出さない。** 保存は端末内（localStorage）のみで、当社サーバーへの送信はゼロ。名刺OCR・領収書スキャナと同じ設計原則を引き継ぐ。
3. **AI 生成は補助にとどめる。** 生成しただけでは何も起きず、保存・投稿は人の操作。

実装済みの詳細は既存仕様書 [docs/specs/x-post-requirements-v1.md](../../specs/x-post-requirements-v1.md)（差分仕様、以下「既存仕様書」）と基底仕様を正とする。本書は既存仕様書・基底仕様を要件定義〜詳細設計の章立てへ再構成したものであり、内容を置き換えない。

### 1.1 姉妹アプリとの関係

`x-post` は、Threads 投稿アプリ（`threads-post`）を土台に、note 下書きアプリ（`note-post`）と並ぶ3本目の「投稿補助アプリ」である。3本とも認証・端末内保存・Gemini 生成の骨格を共有するが、**共通層（`shared/`）は作らず、アプリごとにファイルを複製する**方針（[docs/repository-structure.md](../../repository-structure.md) §4-1）を採る。詳細は §7、04_integration-guide.md §2 を参照。

| アプリ | 投稿先 | 投稿方式 | 差分の要点 |
| --- | --- | --- | --- |
| `threads-post`（基底） | Threads | intent リンク（`threads.net/intent/post`） | 500字（コードポイント基準） |
| `x-post`（本書） | X（旧 Twitter） | intent リンク（`x.com/intent/post`） | 280「ウェイト」（全角=2） |
| `note-post` | note | コピー＋作成画面（intent 相当が無い） | タイトル／本文の別枠、記事向け生成 |

## 2. 用語定義

| 用語 | 意味 |
| --- | --- |
| intent リンク | `https://x.com/intent/post?text=…` の形式で、本文入りの投稿画面を別タブで開く X 公式の仕組み。API・トークンなしで使える |
| ウェイト | X が文字数制限に用いる独自の重み。半角系のコードポイントを1、それ以外（日本語・絵文字を含む）を2として数える。上限280 |
| KeyStore | `public/auth/keystore.js` が提供する、利用者自身の外部AI（Gemini）APIキーの端末内保管庫。当社サーバーへは送らない |
| guardPage | `public/auth/session.js` が提供する、TSAM AI ログインセッションを検証してから画面を描画する共通の入口関数 |
| Portal | TSAM AI のアプリ一覧画面（`public/portal/`）。本番アプリはここから起動する |
| 下書き | 「下書き保存」で端末内（localStorage）に保存した投稿文。呼び出す・削除ができる |
| 履歴 | 「X で投稿」を押して投稿画面を開いた事実を、日時・本文つきで端末内に記録したもの。実際に X 側で投稿されたかは観測できない |
| 書き方の調整プロンプト | 文体・トーン等の指示を常設欄に書き、以後の Gemini 生成すべてに自動で差し込む端末内保存の設定 |

## 3. スコープ

### 3.1 含む

- 投稿文の入力・280ウェイトでの検証・カウント表示
- X intent リンクによる投稿画面表示（最後の投稿は利用者が押す）
- 下書きの保存・一覧・呼び出し・削除（端末内）
- 履歴の記録・一覧（端末内。「投稿画面を開いた」事実のみ）
- Gemini によるテーマ・指示からの投稿文生成（1本・テキストエリアへ入れるのみ）
- 書き方の調整プロンプトの端末内自動保存と、生成への自動適用
- Portal 掲載・`guardPage()` による画面ガード

### 3.2 含まない（対象外）

| 機能 | 対象外とする理由 |
| --- | --- |
| X API・アクセストークンを用いた自動投稿 | 「最後の投稿は人が押す」という基底方針（誤投稿・二重投稿の構造的排除）に反する |
| 予約投稿 | 静的配信にはサーバーもトリガーも無く、閉じたブラウザからは何も送れない（基底仕様 §9・別機能として検討中） |
| 複数媒体への同時投稿・分析・画像投稿 | 基底仕様のスコープ外（基底仕様 §2） |
| 投稿の成否確認（X 側での実投稿確認） | intent 方式では観測不能。履歴は「こちらで起きたこと」までに限定する |
| 端末をまたいだ下書き・履歴の同期（Drive/Sheets 保存） | 端末内保存なら当社サーバー送信ゼロのまま審査不要。必要が生じた時点で再検討（基底仕様 §9） |
| キー入力欄をこのアプリに置くこと | KeyStore（Portal）での一元管理に反する |

## 4. 利用者とロール

- TSAM AI のログインユーザー全員（`guardPage()` を通過した利用者）。ロールによる機能差はない。
- Gemini 生成を使う場合のみ、利用者自身が Portal で Gemini APIキーを設定している必要がある（未設定でも生成以外の機能は全部動く）。

## 5. 機能要件

| ID | 要件 | 補足 |
| --- | --- | --- |
| FR-01 | 画面ガード・Portal掲載 | Portal（`public/portal/app-registry.js`）にアプリID `x-post` で掲載する（`id` は後から変えない）。ページ自身も `setScreenDepth(2)` + `guardPage()` を行い、利用者が返るまで中身を描画しない |
| FR-02 | 投稿文の入力と検証 | テキストエリアで書く／貼り付ける。280「ウェイト」でのカウント（全角=2）を常時表示し、超過は赤く示す。検証（空・280ウェイト超）は intent リンクを開く前に行い、不合格なら開かない |
| FR-03 | 投稿（intent リンク） | 「X で投稿」で、本文入りの投稿画面（`https://x.com/intent/post?text=…`）を別タブ（`noopener,noreferrer`）で開く。最後の「ポスト」は人が押す。X へ fetch はしない（CSP の `connect-src` にも `x.com` を入れない） |
| FR-04 | 下書き（端末内） | 「下書き保存」で localStorage（`tsam-x-post-v1`）へ追記。一覧から「呼び出す」「削除」（削除は確認あり）ができる。保存領域が使えない環境では、その旨を画面に出したうえで書く・生成する・投稿画面を開くだけは動かす。壊れた保存データは読み捨て、次の保存で作り直す |
| FR-05 | 履歴（端末内） | 「投稿画面を開いた」を日時・本文つきで記録し、新しい順に表示する。X 側で本当に投稿されたかは観測できないため、記録は「こちらで起きたこと」までである旨を画面にも明記する。保持は直近100件（超えた分は古い順に捨てる） |
| FR-06 | 投稿文の生成（Gemini） | 「テーマ・指示」（上限100字）から投稿文を1本生成し、テキストエリアに入れるだけ（下書き・履歴へは自動で書かない）。入力中の本文がある場合は置き換え前に確認する。キー未設定時は Portal での設定を促す案内を出す（キー入力欄はこのアプリに作らない） |
| FR-07 | 書き方の調整プロンプト | 生成セクションに常設のテキストエリアを置き、文体・トーン等の指示を書ける。入力は端末内へ自動保存され（下書き・履歴の操作で消えない）、ページを開くと復元される。空でなければ、以後の生成のたびにプロンプトへ「# 書き方の調整（利用者設定）」として差し込む（先頭2000字で頭打ち） |

各要件の背景・理由は既存仕様書 §2、基底仕様 §3 を参照。

## 6. 非機能要件

| ID | 分類 | 要件 |
| --- | --- | --- |
| NFR-01 | セキュリティ | 当社サーバーは投稿文・下書き・履歴を受け取らない。通信先は Gemini・TSAM AI 認証確認のみで、`index.html` の CSP（`<meta http-equiv="Content-Security-Policy">`）で固定する |
| NFR-02 | セキュリティ | Gemini APIキーは利用者自身のもので、KeyStore（端末内 localStorage）だけが扱う。このモジュール（`app.js`）はキーを都度読むだけで保持しない。例外・console にキーを出さない |
| NFR-03 | セキュリティ | アクセス制御はクライアント側ガード（`guardPage()`）が主。静的配信のため HTML/JS の取得自体は防げない（[SECURITY_NOTES.md](../../../SECURITY_NOTES.md)）。守るべきデータが端末内にしか無いため、これで足りる |
| NFR-04 | 性能・費用 | Gemini 呼び出しは主モデルが 404（廃止）のときだけフォールバックモデルへ1回切り替える。401/403/429/503 では再試行しない（無料枠のクォータを削るだけで結果が変わらないため） |
| NFR-05 | 可用性 | 当社サーバーを経由しないため当社サーバー障害の影響を受けない。一方、Gemini API または TSAM AI 認証確認（`auth-verify.potenitas-lp.workers.dev`）が不調の間は、生成またはログイン確認ができない |
| NFR-06 | 運用 | 配信は本リポジトリの `main` へのコミット＋手動デプロイ（`npm run deploy`）のみ。`main` へのマージだけでは公開されない |
| NFR-07 | アクセシビリティ | セマンティックHTML・スキップリンク・`aria-live`（`#xp-message`）を用いる。操作要素の押下領域は共通CSS（`public/auth/auth.css`）の44px基準に従う。アニメーションは `prefers-reduced-motion` に対応する（`style.css`） |

## 7. 制約条件

- **本番アプリ間で共通層を作らない。** `public/production-app/` 配下に `shared/`・`common/`・`lib/` の類を置かず、アプリ間で import し合わない（[docs/repository-structure.md](../../repository-structure.md) §4-1）。`threads-post` と重なるロジック（検証・intent・端末内保存の骨格、Gemini エラー分類）は複製する。
- 静的フロントエンドのみで実装する。サーバーコード・APIエンドポイントを持たない。
- 配信は `public/` 配下の静的ファイルとして行い、ビルド工程を持たない。
- テストは Node 実行のユニットテスト（`tests/unit/x-post.mjs`）のみで行い、実際の X・Gemini・TSAM AI 認証系へは通信しない（`fetchImpl` の差し替えによるスタブ化）。`threads-post`／`note-post` と異なり、実ブラウザでの結線確認スイート（`tests/browser/*`）は本書執筆時点で用意されていない（§9）。

## 8. 外部依存

| 依存先 | 用途 | 認証・スコープ |
| --- | --- | --- |
| Gemini API（`generativelanguage.googleapis.com`） | テーマ・指示からの投稿文生成 | 利用者自身の APIキー（`x-goog-api-key` ヘッダー）。OAuth スコープは使わない |
| X（`x.com`） | intent リンクによる投稿画面の表示のみ | API・トークンは使わない。fetch もしない（別タブでの画面遷移のみ） |
| TSAM AI 認証系（`script.google.com` / `script.googleusercontent.com`、および `auth-verify.potenitas-lp.workers.dev` 経由のセッション検証） | ログインセッションの確認（`guardPage()` 経由） | 本番認証系の既存の仕組みをそのまま利用（本書のスコープ外） |

Google OAuth（GIS）は使わないため、Google Cloud 側の作業は無い（既存仕様書が引き継ぐ基底仕様の判断）。

## 9. 前提条件・未確定事項

### 前提条件

1. Gemini 生成を使う利用者は、Portal で Gemini APIキーを事前に設定していること（未設定でも生成以外は動く）。
2. デプロイは手動（`npm run deploy`）で行う。

### 未確定事項（本書執筆時点でコード・既存仕様書から読み取れないもの）

- `tests/browser/x-post.mjs` 相当の実ブラウザ結線確認スイートを用意するかどうか（`card-mail` にはあるが `x-post`／`threads-post`／`note-post` には無い。理由・方針は既存仕様書・基底仕様のどちらにも記載がない）。
- X 側の intent リンクの仕様変更（URL パラメータの上限・挙動）を継続的に確認する運用手順の有無。
- 予約リマインダー等の関連機能（基底仕様 §9 で「別機能として実装」とされたもの）の着手時期。
