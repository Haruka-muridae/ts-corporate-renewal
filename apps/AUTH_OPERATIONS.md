# TSAM AI 認証の運用手順

利用者対応と管理者作業をまとめる。
設定手順は `SUPABASE_SETUP.md`、実装は `apps/shared/auth.js` を参照。

---

## 1. 二段階認証（TOTP）を失った場合

認証アプリを入れた端末を紛失・初期化した、アプリを消した、
機種変更で移行し忘れた——いずれもコードを出せなくなる。

### まず確認すること

| 質問 | はい | いいえ |
|---|---|---|
| 別の端末に同じ認証アプリが同期されているか | そこでコードを出す。対応終了 | 次へ |
| 二段階認証を**複数登録**しているか | 生きているほうでログイン → `apps/account/` から古い要素を解除 | 次へ |
| いま、どこかのブラウザでログインしたままか | **下の「自力での解除」へ** | 「管理者による解除」へ |

### 自力での解除（AAL2 のセッションが生きている場合）

二段階認証の解除は **AAL2（そのログインでコードを入力済み）** を要求する。
ログインしたままのブラウザがあっても、そのセッションが AAL1 なら解除できない。

1. コードを入力してログインした状態のブラウザを開く
2. `apps/account/` を開く
3. 「二段階認証を解除する」が**押せる**なら、そのまま解除する
4. 押せない（グレーアウト）場合は AAL1。自力では解除できない → 管理者対応へ

**この制限は意図的なもの。** パスワードだけを知っている人に
二段階認証を外させないためにある。緩めないこと。

### 管理者による解除

**独自の「解除用画面」は実装していない。作らないこと。**
そうした画面は、作った瞬間に二段階認証を迂回する裏口になる。

手順は次のいずれか。

#### A. Supabase ダッシュボードから（推奨）

1. Supabase → **Authentication → Users** で対象の利用者を開く
2. MFA / Factors の欄から、登録済みの要素を削除する
3. 利用者へ「解除した。ログイン後すぐ再登録してほしい」と伝える

#### B. Management API から

ダッシュボードに該当操作が無い版では、管理APIを使う。

```
DELETE /auth/v1/admin/users/{user_id}/factors/{factor_id}
```

**この呼び出しには service_role キーが必要。**

> ### service_role キーの扱い（厳守）
>
> - **ブラウザで使わない。** 開発者ツールのコンソールへ貼るのも不可。
>   そのタブの拡張機能・履歴・キャッシュに残りうる。
> - **リポジトリへ置かない。**
> - 管理者の端末から、サーバー側（curl / スクリプト）でのみ使う。
> - 使ったあと、漏れた可能性が少しでもあれば **rotate する**。
>
> このキーは RLS を無視して全データを読み書きできる。
> 「一度だけだから」で例外を作らないこと。

### 本人確認（誰が、どうやって）

**技術ではなく運用で守る部分。** ここを決めずに解除対応を始めない。

最低限、次を満たすこと。

- 依頼を**メールの返信だけで受け付けない**（メールが乗っ取られている前提を捨てない）
- 依頼者と管理者が**既知の関係**であること（社内の別経路で確認できる）
- 電話・対面・社内チャットなど、**登録メール以外の経路**で本人確認する
- 対応した日時・担当者・確認方法を記録する

二段階認証は「パスワードが漏れても守る」ための仕組みである。
解除依頼をメールだけで受けると、その前提が崩れる。

### バックアップコードについて

**Supabase の TOTP にはバックアップコードの機能が無い（2026-07 時点）。**
したがって利用者へは次を案内する。

> 認証アプリは、機種変更しても引き継げるもの
> （1Password、Authy、iCloudキーチェーン等）を使うか、
> **2台目の端末にも登録**しておいてください。
> どちらも無い状態で端末を失うと、管理者による解除が必要になります。

複数登録は `apps/account/` から可能（登録操作を2回行う）。
ログイン時は、登録済みのどれか1つのコードで通る。

### 復旧できない場合

管理者にも連絡が取れない、本人確認ができない——という場合、
そのアカウントは復旧しない。

新しいアカウントを作り直す（招待し直す）。
旧アカウントは Supabase → Authentication → Users から削除するか、
Ban 設定で無効化する。

## 2. パスワードを忘れた場合

1. 利用者が `apps/login/` →「パスワードを忘れた方」
2. メールアドレスを入力して送信
3. 届いたメールのリンクを**要求したのと同じブラウザで**開く
4. 新しいパスワードを設定
5. 自動でログイン画面へ戻るので、新しいパスワードでログイン

### 注意点

- 登録の有無にかかわらず「送信しました」と表示する。
  どのアドレスが登録済みかを外部へ漏らさないため（アカウント列挙の防止）。
  **「送ったのに届かない」＝そのアドレスは未登録**の可能性がある。
- リンクは**1回だけ**有効。メールクライアントのプレビュー機能が
  先にリンクを開いてしまい、利用者がクリックすると期限切れになることがある。
- 別ブラウザで開くと失敗する（PKCE。`SUPABASE_SETUP.md` 第3節）。
- **二段階認証は解除されない。** パスワードを変えても、
  次のログインでコードは必要。これは意図した動作。

---

## 3. メールが届かない場合

| 確認 | 対処 |
|---|---|
| 迷惑メールフォルダ | 送信元ドメインを許可リストへ |
| Supabase の送信制限 | 既定の送信元は1時間あたり数通。SMTP を設定する（`SUPABASE_SETUP.md` 第6節） |
| アドレスの打ち間違い | Authentication → Users で実際の登録値を確認 |
| そもそも未登録 | 招待から始める |

---

## 4. 利用者を追加する

1. Supabase → **Authentication → Users → Invite user**
2. メールアドレスを入力して送信
3. 利用者が届いたリンクを開き、パスワードを設定
4. ログイン後、`apps/account/` から二段階認証を登録してもらう

**公開サインアップは無効にしておくこと**（`SUPABASE_SETUP.md` 第4-2節）。
有効なままだと、URLを知った誰でもアカウントを作れる。

---

## 5. 利用者を停止する

退職・端末紛失など。

1. Supabase → **Authentication → Users** → 対象を開く
2. **Ban user**（一時停止）または **Delete user**（完全削除）

Ban だけでは、**発行済みのアクセストークンは期限まで有効**。
即座に締め出したい場合は、続けてセッションを失効させる。

- 対象ユーザーの Sessions を取り消す、または
- パスワードを管理者側で変更する（他端末のセッションが切れる）

---

## 6. この構成で守れないこと

運用判断のため、限界を明記する。

| 項目 | 状態 |
|---|---|
| Supabase 上のデータ | **守れる**。トークンとRLSで守られる |
| `/apps/` 配下の静的ファイル | **守れない**。URLを知れば誰でも取得できる |
| ログイン画面のJS | 誰でも読める（秘密を書かない前提） |
| 画面表示用の写し（`tsam-ai-session`） | 偽装できる。**保護の根拠にしない** |
| XSS が起きた場合のトークン | 静的サイトには HttpOnly Cookie を設定するサーバーが無い。localStorage のトークンは盗まれうる |

したがって:

- **秘密にしたいデータは Supabase 側（RLS付きのテーブル）へ置く。**
  HTMLやJSへ直接書かない。
- 外部スクリプトを増やさない。特にログイン画面と `auth-callback`。
- 画面へ値を出すときは必ず `textContent` を使う（`innerHTML` を使わない）。

---

## 7. 定期的に確認すること

| 頻度 | 項目 |
|---|---|
| 認証ライブラリの更新時 | `apps/vendor/NOTICE-supabase-auth-js.md` の手順で再生成し、SHA-256 を更新 |
| 月次 | Authentication → Users に身に覚えのないアカウントが無いか |
| 月次 | Rate limit に張り付いていないか（総当たりの兆候） |
| テーブル追加時 | **RLS を有効にしたか** |
| 随時 | service_role キーを使った作業の記録 |

### 認証ライブラリの更新について

`@supabase/auth-js` は自己ホストしているため、
**Dependabot などの自動追跡が効かない**（`package.json` に載っていない）。

更新の有無は手動で確認する。

```sh
curl -s https://registry.npmjs.org/@supabase/auth-js/latest \
  | node -e "let d='';process.stdin.on('data',c=>d+=c).on('end',()=>console.log(JSON.parse(d).version))"
```

同梱版（現在 2.110.8）と違いがあれば、
`apps/vendor/NOTICE-supabase-auth-js.md` の再生成手順に従って更新する。
更新後は認証まわりのテストを再実行すること。
